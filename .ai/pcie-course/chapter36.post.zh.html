交易排序要先確認TC（Traffic Class，流量類別）、要求種類與屬性，再讀允許超越的規則。RO（Relaxed Ordering，放寬排序）與IDO（ID-Based Ordering，依身分放寬排序）都可能影響先後，但不能取代軟體原本需要的資料依賴。

Table 2-42 的 Yes，為什麼容易讀反？

先固定觀察方向：Column是先發送的交易，Row是後發送的交易，表格問的是後者能否超越前者。接著到pp.223–224讀格子的條件，尤其a／b兩種情況；只看一個No或Yes會漏掉屬性例外。

作者案例：同一要求者、同TC，一般Posted資料寫入之後接Posted通知寫入，沒有適用放寬條件。按A2a，後者不得超越前者。這只說明該排序關係；資料是否已持久保存，或CPU需要何種記憶體屏障，仍要按相應裝置與平台規則處理。

兩筆交易相遇時，怎麼查排序表？

教學假設：以下每列都是獨立情境；兩筆交易使用同一個 Traffic Class（TC，流量類別），並在同一個轉送位置比較。先把較早發出的交易放在 Table 2-42 的欄，再把較晚發出的交易放在列，最後讀表格下方的對應條文。

手機閱讀時，可左右滑動表格查看完整內容。

想開 IDO 提升效能，要先看哪種案例？

先用Figure E-1放回拓樸，再看Appendix E的單一對象與多對象通訊。只與一個對象直接通訊，和同時透過主記憶體及P2P協作，風險不同。E.4.1示範兩個裝置都更新同一記憶體位置時，放寬後可能改變最後結果。

Appendix D則從資源依賴切入，描述收到一種交易卻必須等另一種交易送出時，如何形成等待關係。它沒有替所有平台訂完跨TC依賴規則，系統仍須在配置TC／VC時理解自身限制。

不同 Requester 的交易可以超越，就一定安全嗎？

教學情境，依 Appendix E.4.1：Device Y 先對主記憶體寫入資料，接著以 Peer-to-Peer（P2P，裝置對裝置）寫入通知 Device Z；Z 收到通知後，向同一記憶體位置寫入自己的資料。

依 Figure E-1 先找 Y、Z、Switch 與 Root Complex，再把三筆交易依觀察位置排好。假設 Y 和 Z 寫入使用同一 TC，並在 Root Complex 的共同處理位置比較。前兩筆來自 Y；Z 後來的寫入則有另一個 Requester ID。若 Z 的 Posted Write 設置 IDO，且 Table 2-42 A2b 的其他適用條件成立，Root Complex 可能讓它超越仍在等待的 Y 寫入，最後的記憶體內容便可能改變。

這個案例說明：用 Requester ID 區分交易流，無法單獨描述跨裝置的資料依賴。是否可以啟用 IDO，要先理解哪些裝置和記憶體共同參與，再依各 TLP、路徑與同步方式判斷。附錄提出同步的可能方向，具體協定仍由裝置與平台定義。

Appendix D 處理另一種問題：不同 TC 的封包若在有限緩衝資源之間形成循環等待，可能造成死結。它討論的是資源依賴；不要把不同 TC 缺少一般排序要求，理解成系統永遠不會產生依賴。

要改 Bus Number，先清 Bus Master Enable 就夠嗎？

§6.4把停止流程分成多項責任：阻止裝置新要求、阻止軟體新存取、確認裝置服務中的要求完成、確認已發出的Non-Posted要求完成，以及確認Posted要求已到目的地。Transactions Pending只涵蓋其中一部分。

因此，先與驅動協調停止使用，再按要求種類確認在途工作。更改身分時仍有Request／Completion在途，可能讓原有識別失效；不能把一個控制位已清零當成所有交易都已排空。

準備改 Bus Number 時，要確認哪些工作已停下來？

教學情境：驅動程式準備重新配置一個 Endpoint。先依 §6.4 與驅動協調，阻止裝置產生新 Request，也停止軟體送往裝置的新 Request，並確認裝置正在服務的要求已完成。

接著看 Device Status 的 Transactions Pending：它用於判斷該 Function 已發出的 Non-Posted Request 是否完成；這個欄位本身不代表先前的 Posted Write 都已到達。仍須依交易使用的 TC、排序屬性與裝置同步機制，確認 Posted Request 的目的地已收到相應工作。

§6.4 說明裝置對系統記憶體使用 TC0 的 Write，可由 Host 讀取裝置來完成相應 flush；對其他 TC 需要適用的同步機制。這是特定條件下的路徑，不能忽略 RO、IDO 或平台記憶體規則。若裝置間有 P2P 互動，即使使用 TC0，也需要參與裝置之間明確的同步協定。

想查 Message Code，應先看附錄 F 還是封包圖？

先用Table F-1以用途找到Message Code、路由與Msg／MsgD，再沿它指向的正式章節讀完整格式與規則。例如頁面要求、失效通知與LTR都能從這個入口接回前章。Table F-1也提醒其他規格可能新增Message，版本較新的定義不一定收錄在這份Base 6.0清單。

查到一個代碼後，怎麼找到完整格式？

教學情境：要找 Invalidate Request，先在 Appendix F 的 Table F-1 找到這一列：Message Code 0000 0001b、Routing 010b、類型 MsgD。再沿同一列的參照讀 §10.3.1，才能確認該功能的封包欄位與處理條件。

若要找 Function Readiness Status（FRS，Function 就緒狀態），改查 Table F-2 的 PCI-SIG-Defined VDM Subtype：0000 1001b。它是子類型，不能當成 Table F-1 的一般 Message Code。接著讀 §2.2.8.6.3，並結合 Chapter 34 的就緒事件與佇列流程。
