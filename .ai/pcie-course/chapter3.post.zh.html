先看本章的角色與路徑

枚舉是由已知根部向下發現 Function 的過程。本章沿用前兩章的拓樸，先替橋接路徑建立可轉送的 Bus 範圍，再探查下游，最後記錄已找到的功能。

前情提要：Chapter 1 教你辨認 Port 與 Function；Chapter 2 教你在已知 Function 的設定空間中找欄位。現在要建立那些已知位置。

規格路線：Figures 7-1／7-2 的階層 → Figure 7-14 的橋接 Bus 欄位 → Figures 7-7／7-8 的身分與標頭。

枚舉要先建立可走的設定路徑，才能找到下游 Function。讀到某個值時，也必須分清有效身分、暫時未就緒，以及存取失敗。本章把 Bridge 的 Bus Number 配置與這些結果放在同一個流程中。

版本與教學前提

欄位與交易依 Base 6.0；平台與交接依 PCI Firmware 3.3，後者並非 Base 6.0 的同版配套。以下為作者推演，不是實機操作。採傳統 BDF，不用 ARI、SR-IOV 或 FPB。平台提供 Segment 0000、Bus 00–3F，Root Port 00:01.0 已可存取，連線與等待條件已滿足；軟體獨占這段配置，沒有其他階層競爭 Bus Number。文件頁與 PDF 頁序相同。

平台提供起點，Function 讀值提供下一步證據

系統先從平台取得 Host／Root Bridge 的 Segment、Bus 範圍與設定存取介面，不是任意掃描實體記憶體。Root Bridge 的平台介面與 Root Port 的對外 Link 角色不同。Firmware 3.3 要求韌體配置所有 Host Bridge，讓 OS 能處理其下游裝置。

探查 Function 時，Vendor ID 是規格建議的存在性線索，FFFFh 表示沒有 Function。但軟體可見資料不等於 Completion payload：對依賴全 1 回覆的軟體，Root Complex 會把 Configuration Request 的 UR 結果合成全 1。讀取失敗或路徑尚未建立，則不能只憑任意 buffer 值判定實體卡不存在。

來源

Firmware 3.3 §3.1.1，p.32；§3.5，pp.34–35。Base 6.0 Vendor ID：§7.5.1.1.1，p.917；未實作目標與 UR：§7.3.1，p.911；全 1 資料合成：§2.3.2，p.221。

0xFFFF0001 不是一般的 Vendor／Device ID

RRS（Request Retry Status）是 Base 6.0 用來表示指定情況下暫時不能處理要求的狀態。它只在適用的 Reset／Readiness 條件下合法，不能當作任何時刻通用的忙碌回覆。

另一個尚未就緒的情境

假設目標剛經過允許回 RRS 的 Reset，尚未成功完成後續設定要求，也沒有 Configuration-Ready、Immediate Readiness 或其他禁止條件。Root Port 以自身控制位管理可見性，PCIe Capability 起點已查得為 0x70。這個情境獨立於下節的正常枚舉。

先開放可能的下游範圍，再回填實際結果

本例採先走完一個分支再返回的搜尋策略，暫以平台授予的 3F 作 Subordinate 上限，完成後縮回實際範圍。這是教學策略，不是所有平台唯一的程序。

Bus Number 配置的教學順序
順序動作
1Root Port 00:01.0 設 Secondary=01、Subordinate=3F。
2找到 01:00.0 的 Switch Upstream Port，設 Secondary=02、Subordinate=3F。
3找到 02:01.0 的 Downstream A，設 Secondary=03、Subordinate=3F。
4確認 03:00.0 與 03:00.1；本分支完成後，A 的 Subordinate 改為 03。
5回到 Bus 02，替 02:02.0 的 Downstream B 設 Secondary=04、Subordinate=3F。
6確認 04:00.0；B 的 Subordinate 改為 04，最後 Upstream Port 與 Root Port 也改為 04。

03:00.0 的 Header Type=80h 只允許探查其他 Function；Function 1 存在是另一筆有效結果。04:00.0 的 Header Type=00h，且無其他機制指示，因此不得一律掃描 Function 1–7。本例的普通 Link 對端用 Device 0，Switch 內部 Downstream Port 則可出現在其他 Device Number。

讀 Figure 7-14 找 Secondary／Subordinate 的 0x19／0x1A，各讀寫 8 bits，再依 p.937 的定義使用。設定寫入必須完成，才能使用新路徑；本例不以 Primary Bus Number 推導 Bridge 自身 BDF。平台若有保留需求，也不一定要把最後的上限縮到 04。

Header 的 Type 與要求封包的 Type，必須分開

Configuration Header Type 1 描述 Bridge 的標頭格式；Configuration Request Type 1 則用於向更深層路由。對目標 03:00.1，Root Port 的下一層 Bus 是 01，因此仍以 Type 1 往 Switch 送；Switch 判定 Bus 03 正是 Downstream A 的下一層，再轉為 Type 0 送到 Endpoint。對 Bridge 自身設定空間的有效 Type 0 Request，同樣可以由 Bridge 處理。

本例描述對外路由結果，不假設 Switch 的內部邏輯 Bus 是另一條實體 PCIe Link。若目標不在有效範圍，則依 UR 規則處理。（Base 6.0 §7.3.2–§7.3.3，pp.912–913。）

找到 BDF 後，仍未完成資源與工作設定

枚舉結果提供 Function 清單、橋接路徑與身分線索，不能直接證明 MMIO 或 DMA 已可用。Firmware 3.3 §3.5（pp.34–35）要求開機／主控台路徑及所有 Host Bridge 完成指定配置，其他裝置可留給 OS；不能只因任意 Endpoint 尚未配置就宣告韌體違規。

讀到 0xFFFF0001，就以 Device ID FFFFh 選擇驅動程式，可以嗎？

在本例 RRS 條件下不可以。這是暫時未就緒的合成值，尚未取得真正身分；應處理重試與就緒，而非當成未知產品繼續初始化。（§2.3.2，p.220。）

最後 Subordinate 比 04 大，一定是枚舉錯誤嗎？

不一定。要核對平台授予範圍、分支一致性與保留政策；04 是本例採用的最終範圍，不是通用常數。
