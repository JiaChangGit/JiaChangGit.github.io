Connect descriptors, DMA data and completion flags

DMA (Direct Memory Access) allows a device to initiate memory transactions. A working cycle also needs buffer ownership transfer and platform synchronization. This chapter connects descriptor publication, device writes and host consumption.

Specification route: DMA mapping and addresses → descriptor publication → transaction ordering in Table 2-42 → packet attributes and host ownership.

A valid PCIe write alone does not establish that the CPU can safely use its result. DMA also requires valid addresses, mappings, ownership transfer, and memory synchronization. A data-write followed by a completion flag separates these guarantees.

Version and scope

PCIe follows Base 6.0 in Non-Flit Mode; platform background uses official Linux 6.12 documentation. Examples use ordinary Endpoint 03:00.0 without ATS, PASID, SR-IOV, peer-to-peer, or IDE. Unless varied, traffic uses the same Function, direction, and TC0, with RO, IDO, and No Snoop clear. Mappings, descriptors, OWN, and completion flags are author-created, not common PCIe interfaces.

DMA needs addresses reachable by the device

The device reads host memory with MRd and receives CplD, or writes results with ordinary MWr without an ordinary Write Completion. BME permits relevant Request generation/forwarding; it does not create buffers or DMA mappings.

Linux 6.12 distinguishes CPU virtual, CPU physical, and DMA addresses. The authored example maps CPU pointer p to physical 0x90001000–0x90001FFF and device DMA range 0x40001000–0x40001FFF. Thus DMA 0x40001080 reaches physical 0x90001080. These numbers define no universal conversion. BAR0 at 0x80004000–0x80007FFF is a separate resource.

Sources

Base 6.0 §2.1.1.1 (p.116), §2.2.7.1 (pp.162–164), Table 7-4 (p.919); necessary platform background: Linux 6.12 DMA addresses. No particular IOMMU page-table format is taught here.

Coherence and access ordering need separate treatment

Assume a descriptor contains DMA address 0x40001000, length 256 bytes, and OWN. The device interface permits reading the other fields after acquiring OWN. The CPU must publish the fields before ownership, then notify the device through appropriate MMIO access. It must also follow platform rules when reclaiming data after the device releases ownership.

Base 6.0 §2.4.2 does not make a single MRd an atomic snapshot of changing data. Linux 6.12 coherent memory can still need barriers; dma_* barriers do not order MMIO. Streaming mappings require their DMA API synchronization. PCIe ordering cannot replace these responsibilities.

Sources and limits

Base 6.0 §2.4.2 (p.228); Linux 6.12 DMA mapping Guide; Linux 6.12 memory barriers. This is a responsibility map, not a universal driver sequence.

Does an interrupt mean the CPU can already use the data?

Keep data write D from the preceding section and replace the later action with an MSI-X (Message Signaled Interrupts Extended) transaction. First inspect PCIe ordering, then check how the platform makes the result available to the CPU. Each step needs its own evidence.

Simulated data: one Function writes data and signals an interrupt

Assume Endpoint 03:00.0 first sends an ordinary Memory Write of 64-byte D to 0x40001000, then sends an MSI-X Memory Write to indicate completion of this work. The platform has configured the MSI-X address and data. Both are Posted Requests with RO=0 and IDO=0; the MSI-X has No Snoop=0. The DMA mapping and BME are enabled, and Flow-Through IDE is excluded.

A control bit grants permission; it does not describe every packet

With PCIe Capability at 0x70, Device Control is at 0x78. An assumed value of 0x2810 enables conditional use of RO and No Snoop through bits 4 and 11; bits 14:12=010b set MRRS to 512 bytes. It does not assert RO or No Snoop in every TLP.

Inspect the actual packet's Attr[1] for RO, Attr[0] for No Snoop, and Attr[2] for IDO; these bits are not all adjacent in a Non-Flit header. No Snoop does not change ordering and is not a cache-flush command. Its use still requires a guarantee that the target address is not cached anywhere in the system. IDO has separate enable and identity conditions and stays clear here. MSI/MSI-X specifically require RO and No Snoop clear.

Check the scope of the conclusion

Does reading the descriptor in one transaction guarantee a snapshot?

No. Changing data requires additional interface and synchronization guarantees; §2.4.2 (p.228) does not supply that atomicity.

Does one test without RO reordering prove it never happens?

No. Permitting reordering does not require every transaction to reorder. An observation does not turn permission into prohibition.
