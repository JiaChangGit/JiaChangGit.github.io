【模擬資料】本章位址、設定與裝置 Register 為教學用途建立，不代表特定硬體或平台。

先看本章的角色與路徑

BAR（Base Address Register，基底位址暫存器）提供裝置資源的型別與配置入口。軟體先取得需求，再分配對齊的位址，讓沿途 Bridge Window 涵蓋它，最後開啟適用的解碼。

前情提要：Chapter 3 已找到這個 Function。現在處理它的資源，尚未開始驅動程式的工作流程。

規格路線：Figures 7-10–7-12／Table 7-9 → Figure 7-14 與 Bridge Window 條文 → Figure 7-5／Table 7-4 的 Command 控制。

找到 Function 後，還要建立資源位址與沿途轉送範圍。BAR 描述 Endpoint 自己需要的空間；Bridge Window 決定要求能否走到下游；Command 的控制位則決定目前允許哪些存取。這三件事必須一起成立。

版本與前提

欄位依 Base 6.0；位址視角與交接依 PCI Firmware 3.3，兩者不是同版配套。案例是一般 Type 0 PCI Express Endpoint，非 VF，不用 Enhanced Allocation 或 Resizable BAR。所有資料為作者設計，不操作實機。探測時驅動尚未使用裝置，沒有進行中的交易，MSE、BME 均為 0；軟體保存 BAR 原值並確認設定寫入完成。文件頁與 PDF 頁序相同。

先認格式，再談大小

BAR 位於 Configuration Header，不是工作資料緩衝區。Type 0 Header 提供六個 DWORD 位置；64-bit BAR 佔兩個連續位置。Bridge 的 Type 1 Header 則只有兩個 BAR 位置，與下游 Memory Window 分開。

Memory BAR 的 bit 0 為 0，bits 2:1 的 00b／10b 分別表示 32／64-bit，bit 3 為 Prefetchable；I/O BAR 的 bit 0 為 1，位址從 bit 2 起，不能套用 Memory BAR 的低四位遮罩。本例不用 I/O BAR：一般 PCIe Endpoint 不得依賴 OS 配置 I/O 資源，也不得發 I/O Requests。

Prefetchable 表示資源容許規格列出的無讀取副作用與寫入合併等行為，不是 CPU 快取狀態。對本例的一般 Endpoint，Prefetchable BAR 須支援 64-bit；非 Prefetchable 可以是 32-bit。

探測值必須按 32 或 64 bits 計算

規格的探測方法先停用相應解碼、保存原 BAR，再寫全 1、讀回並遮掉類型 bits。取反加一時，必須限制運算寬度；最後還原原值，或在重新啟用前完成一致的新配置。BME 清零不代表先前交易自動消失，本例另以沒有進行中交易為前提。

沿途每一層 Window 都要涵蓋目標

到 03:00.0 的路徑經 Root Port 00:01.0、Switch Upstream Port 01:00.0、Downstream A 02:01.0。本例三者皆支援並配置下列窗口，平台已保留相應範圍，其他分支不佔用它們。

MSE 與 BME 不是同一個開關

Command 位於 0x04，寬度 16 bits。bit 0 控制 I/O Space，bit 1 的 MSE 控制收到的 Memory 存取，bit 2 的 BME 控制 Function 發起 Memory／I/O Requests；Type 1 Port 的 BME 還控制向上游轉送相關要求，不阻擋 Completion。

在資源、窗口、平台映射與裝置介面均已就緒的前提下，本例 Endpoint 與三個 Bridge 的 Command=0x0002，允許 CPU 讀取已配置的 MMIO，但 Endpoint 尚不能發起 DMA Memory Request；讀取回覆的 Completion 不被 BME 阻擋。BME=0 也禁止 MSI／MSI-X，因為它們是帶內 Memory Write。

把 Endpoint 改為 0x0006，只增加發起相關要求的許可，仍要準備緩衝區、裝置工作、平台轉譯與上游 Port 的 BME。修改 Command 時也不能任意連同 0x06 的 Status 一起原樣回寫，因為 Status 含 RW1C 位元。

設定空間可讀，為什麼 Memory Read 還會失敗？

設定存取用 BDF 與 Register offset 選擇 Function 和欄位；Memory Read 則使用記憶體位址選擇目標。沿用本章案例，先把 0x80004120 放回 BAR0 與每一層 Window，再檢查接收方向上的 Memory Space Enable（MSE，記憶體空間解碼控制）。

假設 03:00.0 的設定空間可讀，BAR0 及三個 Bridge Window 都如前節配置；Root Port、Switch Upstream Port 與 Endpoint 的 MSE 均為 1，Downstream A 的 MSE 為 0。CPU 使用本章假設的相同映射，對有效的 BAR0 + 0x120 發出 4-byte Memory Read；假設該 Request 合法，並已到達 Downstream A 的 Primary Side（橋接器面向上游的一側）。

Memory Read 的 PCI 位址是 0x80004120位址落在 BAR0 的 0x80004000–0x80007FFF，也落在假設配置的各個 Memory Window 中。範圍符合後，還要看接收端和各 Bridge 的 MSE。
Downstream A 的 MSE=0本例的 Memory Read 已到達其 Primary Side。依 Table 7-4，該存取按 Unsupported Request（UR，不支援的要求）處理。此 Port 以 UR 處理該讀取，不再將它轉送至 Endpoint。Memory Read 需要 Completion，依規則產生 UR Completion；還要確認回程是否成功送達。

假設其他條件不變，再將 Downstream A 的 MSE 設為 1，只是讓它得以進行位址解碼與後續處理。還要觀察 Request 是否到達 Endpoint、Completion 是否返回，以及裝置介面是否已準備好，才能判斷整筆讀取的結果。CPU 最終如何看到錯誤，取決於平台的呈現方式；PCIe Completion Status 與 CPU 讀值不能直接畫上等號。

只要位址落在 BAR 內，每個 byte 都可以讀嗎？

BAR 的大小定義資源位址範圍；實際有哪些可用的裝置 Register，要查裝置介面文件。本例只假設 +0x120 是可讀 Register，並未定義 +0x3000 的用途，雖然它也在 BAR0 範圍內。Base 6.0 §7.5.1.2.1（p.930）允許 Function 對程式模型從不存取的未使用位置回 UR。要判定某次存取的結果，還需要該裝置介面及實際交易證據。

配置與交接的結論要分清

Firmware 3.3 §3.5（pp.34–35）以 I/O／Memory Enable 及 ROM Enable 判斷相應資源配置，不使用 BME 判定 BAR 是否有效。已啟用的資源必須由韌體正確配置，但驅動仍須依裝置介面準備工作。

16 KiB BAR 改放 0x80005000，可以嗎？

不行。低 14 bits 不是全 0，未達自然對齊；本例正確的基底 0x80004000 才符合。（§7.5.1.2.1，p.930。）

窗口正確，Endpoint MSE=0，是否仍可成功讀 MMIO？

不能期待成功。MSE=0 時，Endpoint 收到的 Memory Space 存取按 UR 處理；路徑可轉送不能代替終點啟用。（Table 7-4，p.918。）
