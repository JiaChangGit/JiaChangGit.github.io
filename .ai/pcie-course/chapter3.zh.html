版本與範圍

欄位與交易規則依 PCI Express Base Specification Revision 6.0；韌體交接依 PCI Firmware Specification Revision 3.3。採傳統 BDF，不使用 ARI、SR-IOV 或 FPB。以下是教學推演，不執行實機掃描或寫入；本文的 offset 均以 byte 為單位。

1. 完全不知道裝置位置時，第一筆查詢從哪裡開始？

枚舉（enumeration）不是從任意記憶體位址開始猜。系統軟體先取得平台提供的 Host／Root Bridge 資訊，例如 Segment、可用 Bus 範圍，以及執行設定存取的介面，再從已知的根部往下找。

Root Bridge 是平台向軟體提供的根部存取與資源範圍，Root Port 則是 PCIe 階層中向下接出 Link 的 Port。兩者不要只因名稱都有 Root 就合併。Firmware 3.3 §3.1.1 說明 UEFI 的 Root Bridge 介面如何提供 PCI Memory、I/O 與 Configuration 存取；§3.5 則要求韌體配置所有 Host Bridge，並提供相關平台描述。

本章的起始條件

平台已提供 Segment 0000、Bus 00–3F 的可用範圍；本例沒有其他階層與它競爭這段 Bus Number。Root Port 00:01.0 已能存取，相關連線與 Reset 後等待條件已滿足。下游尚未完成 Bus Number 配置。軟體持有這段配置的管理權，沒有另一個執行者同時修改；Hot-Plug 與執行中的裝置重新配置另有條件，留到後續章節。

本例的搜尋策略是先往一條分支走到底，再回來處理旁邊的分支。Bus Number 依序使用 01、02、03、04，探查期間暫以 3F 作下游上限，完成後再縮到實際範圍。這是作者設計的配置策略；規格定義 Register 與路由行為，並未要求每個平台照這個編號順序，也未禁止為熱插拔保留額外 Bus Number。

PCI Firmware 3.3 §3.1.1，p.32；§3.5，pp.34–35。Base 6.0 §7.1，Figures 7-1／7-2，pp.903–904。Host Bridge 的實作與 Root Complex 內部編號具有平台差異，本例將已知起點列為前提，不由 Endpoint 反推平台設定。

2. 第一筆讀取，要取得什麼證據？

對一個待探查的位置，先讀 Configuration Header 的 Vendor ID。Base 6.0 建議用它判斷 Function 是否存在；在這個欄位看到 FFFFh，表示沒有 Function。可是軟體看到的讀值與 PCIe Completion Status 並不是同一件事：Root Complex 可能把某種交易結果轉成軟體可見的資料。

UR 是 Unsupported Request，表示該要求無法依適用規則被接受。RRS 是 Base 6.0 的 Request Retry Status，表示在規格允許的情況下，接收端暫時不能處理要求。RRS 不是要求遺失，也不是可在任何時刻任意使用的忙碌通知。

3. 還不知道下一層有多深，Subordinate 要先填多少？

先沿已就緒的正常案例往下找。讀取 Bridge 的 Header Type 與 PCIe 類型，再依 Figure 7-14 找到 Secondary（0x19）與 Subordinate（0x1A）；兩者各為 8 bits、可讀寫。Secondary 先指定下一層 Bus，Subordinate 暫時涵蓋仍可能分配的範圍，讓後續查詢有路可走。

本例已知平台可用上限是 3F，因此用 3F 作暫時上限，沒有任意擴到 FF。每次先完成必要的 Configuration Write，再探查新的下游位置；寫入完成的確認依平台存取機制處理，不把 CPU 已送出存取當成遠端已完成設定。

4. 讀到 0xFFFF0001，是什麼裝置？

先不要把它拆成一般 Vendor／Device ID。若 Root Port 支援並已啟用 Configuration RRS Software Visibility，而且 Configuration Read 包含 Vendor ID 的兩個 bytes，Root Complex 在收到 RRS 時，會讓軟體讀到 Vendor ID = 0001h；同筆讀取的其他 bytes 則回報全 1。

獨立的就緒情境

假設目標剛經過規格允許回 RRS 的 Reset，尚未回報 Configuration-Ready，也尚未成功完成重設後的設定要求；沒有 Immediate Readiness 等禁止 RRS 的條件。Root Port 使用自身的可見性控制，已找到 PCIe Capability 起點 0x70；以下讀值均成功取得。這個情境用來解釋暫時未就緒，與前節已具備就緒條件的正常枚舉時間表分開閱讀。

查詢次序是先由 Figure 7-21 找 Root Capabilities 與 Root Control 的位移，接著用 Figure 7-34／Table 7-31 查能力，再用 Figure 7-33／Table 7-30 查啟用狀態，最後回 §2.3.2 解釋 0001h 的特殊意義。它是 PCI-SIG 為此用途保留的值，不對應任何已分配的 Vendor ID。

若只讀 16-bit Vendor ID，特殊值會是 0x0001；本例讀了 32 bits，才看到 0xFFFF0001。若沒有啟用這項可見性，或讀取沒有同時涵蓋 Vendor ID 的兩個 bytes，就不能要求 Root Complex 用這個資料格式回報；適用時由 Root Complex 重新發出設定要求。

教材不把「等固定一秒」當成所有 Reset 的共同答案。重試期限要連同 Reset、Readiness 與平台策略判斷；用完允許的等待仍未就緒，應記為初始化或存取未完成，不能假裝已取得有效 Vendor ID。

5. 對 Endpoint 讀設定時，Type 1 到哪裡變成 Type 0？

這一節的 Type 指 Configuration Request 的封包類型，不是 Configuration Header 的布局。Header Type 1 的 Bridge 也會接受對自身設定空間的 Type 0 Request；兩者名稱相同，不代表一一配對。

一般路由規則可整理為下面的分支。前提是符合本章的正常傳統配置，且要求的 Device／Function 與其他欄位也有效。

案例推演：目標是 03:00.1。Root Port 的下一層是 Bus 01，而目標 Bus 03 位於其下游範圍，所以外部 Link 上仍送 Type 1 給 Switch。Switch 再辨識 Bus 03 正好是 Downstream A 的 Link 所對應的 Bus，便在送向 Endpoint 前轉成 Type 0。Endpoint 最後以 Function 1 與 Register 位移處理要求。

Switch 內部是邏輯設定拓樸；本例沒有假設內部真的有另一條實體 PCIe Link，或每個 virtual Bridge 都要在實體線路上產生一份封包。這裡只描述規格要求的對外路由結果。

路由規則的來源

Base 6.0 §7.3.2–§7.3.3，pp.912–913。Endpoint 對 Type 1 Configuration Request 依 UR 處理；Root Port／Switch 對有效的本地 Type 0 Request 則處理自身設定空間。本節沒有將 Type 0／Type 1 的角色延伸到所有其他 TLP。

裝置的 Requester ID 從哪裡來？

前一節沿路由找到 Endpoint；現在換到 Endpoint 自己發出要求的方向。Non-Flit Configuration Request 的 Figure 2-33 同時有 Requester ID 和 Destination ID：前者是這筆設定要求的發起者，後者指出要設定的 Function。兩者有不同角色，不能拿主機發起設定時的 Requester ID 當成 Endpoint 日後發起交易的身分。

讀 §2.2.6.2：Function 必須從由它完成的 Type 0 Configuration Write 擷取 Bus 與 Device Number，並將擷取值用在它自身發起要求的 Requester ID。規格建議只在成功完成的要求上擷取；本例已假設成功。Function Number 仍是該 Function 的身分，因此本例正常組成的 Requester ID 是 0300h，不是主機那筆 Configuration Write 的 Requester ID。

如果平台之後需要重新配置 Bus Number，先依 §6.4 完成相關工作停止與未完成交易的協調。假設新配置將同一 Function 設為 04:00.0，且它完成新的 Type 0 Configuration Write，Function 便需重新擷取新的 Bus／Device 值；後續自身發起的要求使用更新後的身分。本例不表示軟體可以在交易仍進行時直接改號。

首次 Configuration Write 之前，Function 不得發起 Non-Posted Request（需要 Completion 的要求），因為回覆需要有效的 Requester ID。規格對 Root Complex 內的 Functions 存取系統開機裝置有例外；本例一般 Endpoint 不套用該例外。完成設定寫入後，仍須檢查 Bus Master Enable、資源與裝置初始化；取得身分本身不代表可以立即開始 DMA。

已知目標 BDF，讀取卻失敗時，先檢查哪一段？

沿用本章的拓撲，目標是 Endpoint 的 03:00.1。先找到連向它的分支，再由根部向下檢查每個 Bridge 的 Secondary／Subordinate Bus Number，確認目標 Bus 是否落在該分支的設定範圍。這裡的檢查順序是查閱方法，不代表硬體一定以這個時間順序處理。

Function 不存在，和其中一個 Register 未實作，有什麼不同？

以可觀察到 PCIe Completion 的資料為例：指定未實作的 Bus、Device 或 Function 時，§7.3.1 規定回 Unsupported Request（UR）；對已實作 Function 內未實作的 Register 讀取，在沒有其他需回報的錯誤時，§7.3.3 規定回 Successful Completion，讀取資料為 0。兩者的目標與結果不同。

如果只看到軟體的讀值，仍要先確認存取是否成功、讀的是哪個 BDF 與 offset，以及平台如何呈現交易結果。Root Complex 在 §2.3.2 所述的條件下，會為依賴全 1 讀值的軟體合成 UR 讀取結果；那不是 UR Completion 自帶的 payload。RRS 的特殊值則依前面的就緒情境判讀。（Base 6.0，文件頁／PDF 頁 220–221、911、913。）

6. 能列出 BDF，就表示裝置已經可以工作嗎？

這次搜尋完成後，系統有了 Function 清單與下游路徑，但還沒有因此完成 BAR 資源配置、開啟 Memory Space，或準備驅動程式的工作資料。Vendor／Device ID 和 Class Code 能提供識別與驅動選擇線索，也不等於初始化已成功。

枚舉也不保證全由韌體一次做完。Firmware 3.3 §3.5 要求韌體配置開機與主控台裝置的完整路徑，以及所有 Host Bridge；其他裝置可以留給 OS 處理。因此，OS 看到某個 Endpoint 尚未配置，不能僅憑這件事宣告韌體違反規格。若要檢查交接，應先確認它是不是被要求完成的那條路徑。

7. 沿著不同條件調整發現流程

Root Port 只把下游上限開到 Bus 01，還沒找到 Switch 下方的 Bus 03，就能直接跳去讀 03:00.0 嗎？

不能假設走得通。先要為通往 Bus 03 的各層 Bridge 建立一致且有效的 Bus 範圍。對目前不屬於有效路徑的要求，規格允許的結果不是「幫你找到裝置」，而是按 UR 規則處理。（§7.3.3，pp.912–913。）

Function 0 的 Header Type 是 00h，可以為了保險一律掃 Function 1–7 嗎？

本章沒有 ARI／SR-IOV 等額外指示，因此不可以。Table 7-7（p.925）在 Multi-Function Device bit 清除時禁止這種探查。若 bit 設定，允許探查也不等於那些 Function 已存在。

讀到 0xFFFF0001，就把 Device ID FFFFh 當成未知型號繼續初始化，問題在哪裡？

若符合本章的 RRS 可見性條件，整個讀值是 Root Complex 為重試狀態合成的資料，尚未取得真正的 Vendor／Device ID。應處理就緒與重試，不能據此選驅動或讀取假想的裝置欄位。（§2.3.2，p.220。）

最終 Subordinate 比本例的 04 大，就一定錯了嗎？

不一定。本例採完成後緊縮到實際使用範圍的策略；平台可能依法配置並保留額外 Bus Number。要檢查的是平台授予的範圍、各分支是否一致，以及保留政策，不能把本例的數字當成唯一合法答案。

8. 找到裝置之後，還欠哪一步？

接著讀 Chapter 4：BAR、位址空間與資源配置。那一章會從裝置需要多少空間開始，算出大小與對齊，檢查沿途 Bridge Window，再分清 Memory Space Enable 與 Bus Master Enable。
