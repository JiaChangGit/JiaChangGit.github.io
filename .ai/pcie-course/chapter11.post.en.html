Connect insertion to a usable function

Managed hot-plug connects presence, power, link readiness and software configuration. Chapter 3/4 enumeration and resource allocation are reused after the applicable link and reset waits.

Specification route: Slot implementation and hot-plug capability → Figures 7-30–7-32 → Section 6.7.3 operations and notification → enumeration and resources.

PCIe Hot-Plug turns changes at a physical slot into consistent software state. Capability, notification, power, Link readiness, and resource assignment require different evidence. This report follows one insertion, then compares orderly and asynchronous removal.

Sources and assumptions

PCIe Base 6.0 and PCI Firmware 3.3 retain separate version boundaries. All values, times, and capacities are author-created examples. A separate hot-plug slot is attached to Switch Downstream Port 02:01.0, with 03:00.0 below it. The OS already owns native Hot-Plug control; SFI does not intervene, and no early-readiness mechanism is used.

Separate current state, pending events, and notification

Slot Status=0x0048 has Presence Detect State bit 6 and Presence Detect Changed bit 3 set. One reports current presence; the other records a pending event. Further slot events of the same type are ignored until that pending event is cleared. A bit is therefore neither a counter nor a complete history.

Out-of-band detection detects insertion while main power is off in this example. Generally, with In-Band PD Disable=0, Presence is the OR of in-band and applicable out-of-band detection; in-band detection requires power. Presence=1 does not establish Link Active.

0x17F8 enables Presence Changed, Command Completed, DLL State Changed, and the Hot-Plug master interrupt enable. Recording an event is distinct from receiving an interrupt, which additionally depends on the selected INTx or MSI/MSI-X enable, vector, and routing conditions.

Command completion does not authorize immediate enumeration

With the latch closed, sufficient power budget, and no previous command pending, the example writes Slot Control=0x12F8: Power On, Power Indicator Blink, Attention Indicator Off, with notification settings preserved. Any Slot Control write is a hot-plug command. Since Command Completed is supported, wait for the preceding command before another write. After one second without completion, the specification permits retrying or issuing the next command; this does not prove power succeeded.

Configuration access still requires usable resources afterward

Suppose only 0x80080000–0x800FFFFF remains available along the path: 0x80000 bytes, or 512 KiB. A new size-aligned BAR requiring 0x100000 bytes, or 1 MiB, cannot fit even if Configuration Requests succeed. Writing a BAR outside a Bridge Window does not automatically extend forwarding.

Reserving Bus Numbers and address ranges can help. Reallocation depends on Host Bridge resources, every intervening window, and software coordination. This is an author-created system deduction, not a guarantee that every hot-added card fits. Chapters 3–4 cover enumeration and BAR calculation.

The removal model determines whether coordination is possible

Orderly removal allows software to stop new work, handle outstanding work under the device protocol, and then perform the appropriate power, indicator, and removal sequence. Clearing BME does not complete earlier transactions or application work. Async removal may eliminate access before coordination, requiring invalidation and recovery of outstanding work rather than requests for evidence from an absent device.

This system sequence is an author synthesis; PCIe does not standardize every device's stop, cancel, or save operation. DPC limits error propagation without deciding application success. See Chapter 12 for its status and recovery conditions, and Chapter 13 for ownership. Sources: Base §6.7, §6.7.6 (pp.727, 741–742), §6.2.11 (pp.694–697); Firmware §4.5.

Check the interpretation

Does Presence Changed=1 with Presence=0 mean no device was ever inserted?

No. A pending event and the current state do not reconstruct a complete history. Sources: §6.7.3.1, Table 7-29.

Do Command Completed and Power Fault contradict each other?

No. The command interface can accept another command without proving power succeeded. The fault still needs handling. Sources: Tables 7-28/7-29.
