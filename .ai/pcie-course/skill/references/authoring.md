# 圖解、閱讀路線與中文校閱

## 編輯與產生導圖

導圖資料放在 `.ai/pcie-course/walks/`。以現有的 `chapter7-notify.json`、`chapter8-link.json` 或 `chapter9-reset.json` 了解欄位契約；選擇符合當前主題的圖種，不直接複製技術流程。SVG 的 `data-walk-target` 與每步 `targets` 必須一致；每步另有可見條件、來源及已登記的 `claim_ids`。`summary_html` 放在圖後、詳細步驟之前，用來呈現主旨、必要前情與短閱讀路線。

修改 JSON 後，更新對應的 authored 區塊，再建置。以 Chapter 7 為例：

```sh
python3 -B scripts/pcie_teaching.py .ai/pcie-course/chapter7.zh.html --refresh-authored
python3 -B scripts/validate_pcie_teaching.py
python3 -B scripts/build_pcie_course.py
python3 -B scripts/build_pcie_course.py --check
python3 -B scripts/validate_pcie_course.py
```

`--refresh-authored` 只重建成對 `pcie-walk` 註解之間的內容，其他正文保持原樣。不要在區塊中直接改生成結果。`curriculum.json` 的 `teaching_revision` 啟用該章導圖樣式，`revision_date` 記錄此次修訂；原始發文日期與永久網址保持穩定。

先建立 Jekyll 站點，再以 `scripts/check_pcie_browser.cjs --root <站點目錄> --output <儲存庫外的檢查目錄> --chapters 7,8,9` 檢查指定章節。此腳本用本機 Chromium，封鎖對外請求；教材版停用 JavaScript，檢查原生鍵盤操作、逐步標示、角色定位、來源展開與列印內容。它也保存畫面，仍須實際檢視文字、箭頭及上下文。來源 PDF、擷取文字與檢查截圖均留在儲存庫外。

## 先設計這一段要教會什麼

為目標機制寫一份簡短編輯筆記：讀者現在知道什麼、本段要走的正常流程、出場角色、沿途要看的規格圖表，以及何時需要補充例外。它用來安排教學，不需要把內部清單顯示為教材章節。

延用主案例時只補本章必要前情。例如中斷章承接已建立的記憶體與交易路徑，說明接下來加入裝置通知。下一章使用同一拓樸，將觀察位置放大到相鄰兩個 Port。數值屬不同案例時明說，不能把兩組不相容假設串成同一事件。

## 圖與正文共同完成解說

一張圖先回答一個具體問題。圖前交代要追蹤的對象；圖中畫出角色、動作、方向、必要條件；圖後解釋最重要的因果與下一段的接點，不逐格抄寫圖中文字。

- 時序圖：生命線是角色，箭頭是事件；等待與時間限制放在對應區間。不同 Link 的 ACK 不畫成一個端到端確認。
- 狀態圖：箭頭帶觸發條件；互斥路徑分開。簡化範圍就近說明，未畫的分支仍可能存在。
- 流程圖：前後動作、等待、條件分支清楚。閱讀順序與硬體執行順序要命名區分；閱讀路線不冒充硬體狀態機。
- 拓樸／欄位圖：保留既有元件名稱和位置；欄位圖指出本次要用的部分，其他欄位只需保留足夠定位資訊。

總覽與放大圖保持相同角色名稱、色彩和方向。圖複雜時分層；不在一張圖塞入本章所有例外。正文中影響當前判斷的前提必須立即可見。

逐步導圖保留全部流程與文字。每一步的重點應包含執行者、動作、適用條件及就近的來源；來源可以是相關條文，並非每一步都有編號 Figure。點選角色時先介紹當下責任，再提供可展開的基礎定義。程式不得把填完所有步驟當作「已學會」。

## 把規格位置變成可跟隨的閱讀路線

開頭給簡短路線，例如「Capability 結構 → 控制欄位 → 事件流程」。每段再具體指出本次 Figure／Table、欄位及閱讀目的。只解釋本次會使用的欄位，保留影響欄位有效性的型別、版本或狀態。

完整引用保留 Document、Revision、Section、Figure／Table、文件頁和 PDF 頁。多頁表格指向實際使用欄位的頁。數值假設、相對位移、實際位址、存取寬度、遮罩和單位仍保持可追溯；正文聚焦它們在流程中的用途，額外算式可放展開區。

## 自然的繁體中文

先說重點，再說運作：

- 避免：「而不是直接假設某個位址就是目標。」
  可寫：「先從清單取得結構起點，再加上目標欄位的位移。」
- 避免：「能不能得出某個結論？」
  可寫：「接下來查看 Link Status，確認目前的速率與寬度。」
- 避免：「這三次查詢回答不同問題，不能用其中一次的結果代替另外兩次。」
  可寫：「查詢分成三個部分：支援能力、控制設定，以及目前狀態。」

以上是表達方向，不能直接當成全庫替換規則。保留原本的必要前提。例如欄位在 Link down 時未定義，應明確說明有效條件；不要為了句子好讀而改成可使用舊讀值。

切換 CPU、軟體、Port、Function 時重寫主詞。「因此」前須有足以支持結果的原因；「但」只用在真正轉折；「此時」需能定位到特定步驟。正文用連貫段落，真正平行的角色或欄位才用列表／表格。

每篇術語各算兩次：第一次給正式名稱與短用途；第二次簡短提醒用途即可。教學圖中的縮寫也須有就近說明。可使用語意明確的 `<abbr title="…">`，但 title 提示不能取代前兩次可見的解釋。CPU、基本記憶體與位元操作屬讀者已知背景，不強迫逐段重教。

## 編輯完成的依據

逐段實際檢查：先前知識能否接到新段落；圖中各箭頭是否有明確對象；來源路線能否帶到本次欄位；關鍵術語是否在使用處有解釋；三版的條件和結果是否一致。

腳本可以攔截失效定位、來源缺失、數值漂移與元件不一致。它也可列出待讀的詞句，供人／AI 校閱，但沒有掃到某個詞不表示中文通順。獨立 AI 審閱是教材品質檢查，不是真人學習證據。
