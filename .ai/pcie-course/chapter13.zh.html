2. OS 開始執行時，能假設所有 PCI 裝置都已配置嗎？

不能。PCI Firmware 3.3 §3.5 要求韌體配置所有 Host Bridges，因為其硬體程式設計模型不是 PCI 規格統一定義；通往開機與主控台裝置的 PCI-to-PCI Bridges 也必須配置。其他路徑則可能尚未完成，因此 OS 不能只憑「開機成功」推定每張卡都已準備好。

對已配置的 BAR，OS 還要確認對應 I/O／Memory Enable 等交接條件及平台位址轉譯；CPU 用的位址不一定等於 BAR 內的值。這個判讀已在 Chapter 4 建立，本章只補上責任：UEFI driver 與 application 不得自行更改由韌體配置者持有的 BAR／Bridge 資源配置。OS 接手後的配置政策，也必須遵守平台可提供的範圍。

韌體應在 ACPI namespace 描述 Host Bridge，包括 _HID／_CID、_CRS 等資訊。_SEG 用來區分 PCI Segment Group；如果省略，需依其定義處理，不能把 BDF 自動當成全系統唯一識別。PCI Express Host Bridge 的 _HID／_CID 配對見 Firmware §4.1.5；namespace 的路徑與 Bus:Device.Function 是不同的識別系統。

交接與 Host Bridge 的依據

PCI Firmware 3.3 §3.5（pp.34–37）、§4.1.5（pp.45–46）。本章不重複 BAR 大小與 Bridge Window 計算，回顧 Chapter 4即可。

3. MCFG、_CRS 與 BAR 都有位址，差別在哪裡？

先問位址的用途。MCFG 描述特定 Segment／Bus 範圍的 memory-mapped Configuration Space 存取位置；_CRS 描述 Host Bridge 當前消耗與向下游提供的資源；BAR 則描述某個 Function 的裝置資源。MCFG 不是「可供 BAR 任意分配的記憶體池」。

非零 Start Bus 的 ECAM 教學案例
資料來源或目標作者假設值意義
MCFG Base Address0xE0000000以 Bus 0 為基準。
Segment Group0x0002選擇對應 Segment 的 allocation entry。
Start Bus／End Bus0x40／0x4F此 entry 支援的 Bus 範圍，含兩端。
目標 Bus／Device／Function／Offset0x42／0x03／0x01／0x180非 ARI 的設定空間目標。
算出的設定存取位址0xE4219180不是裝置 BAR 位址。

依 Firmware 3.3 §4.1.4，MCFG 的 Base Address 即使 Start Bus 非零，仍以 Bus 0 為基準。本例先確認目標在 0x40–0x4F 內，再算：

0xE0000000 + (0x42 << 20)
             + (0x03 << 15) + (0x01 << 12) + 0x180
= 0xE4219180

這個 entry 實際涵蓋的 ECAM 位址是 0xE4000000–0xE4FFFFFF，共 16 MiB。不能把 Bus Number 先減 Start Bus；那會算出 0xE0219180。也不能因 Base 是 0xE0000000，就推定前面沒有涵蓋的區域可用於其他目的。

再假設 _CRS 向下游提供 Memory 範圍 0x90000000–0x90FFFFFF，且本例沒有位址轉譯。位於其中的 BAR 候選區間仍要檢查對齊、大小、其他裝置占用與每層 Bridge Window；只在 _CRS 範圍內不等於已完成配置。反過來，剛算出的 ECAM 位址也不能寫進某張卡的 BAR 來「讓設定空間可達」。

MCFG 主要描述開機時已存在的相關 Host Bridges；對支援 Host Bridge 熱加入的情況，Firmware §4.1.3 另定義 _CBA。不要把「一般 PCIe Endpoint 熱插入」與「新增整個 Host Bridge」混為同一種平台描述更新。

4. 找到 Hot-Plug 或 AER 欄位後，OS 就可以修改嗎？

還要確認控制權。PCI Host Bridge 的 _OSC（Operating System Capabilities）讓 OS 宣告支援能力，並要求管理特定功能。它作用於該 Host Bridge 所起始的整個 hierarchy，不是對每個 Endpoint 各發一份授權。

先讀 PCI Firmware 3.3 §4.5.1 的介面識別：UUID 為 33DB4D5B-1FF7-401C-9657-7441C03DD766，Revision=1，Capabilities Buffer 有三個 DWORD。這三個 DWORD 的位元編號各自重新從 0 開始，不能把不同 DWORD 的 bit 7 混在一起。

_OSC 的三個 DWORD
DWORD送入時的用途回傳後怎麼讀
1：通用欄位bit 0=1 表示 Query；清除表示要求接管協商出的能力。檢查失敗、UUID、Revision、Capabilities Masked；回傳 bit 0 是 Reserved，不用它判斷授權。
2：Support FieldOS 告訴平台自己具備哪些軟體能力。單向宣告；OS 不以回傳修改值作為授權。
3：Control FieldOS 要求管理哪些功能。在有效回覆與正確呼叫階段下，讀各 bit 是否被保留。

控制權的回傳 1，不證明硬體一定有那個 Capability。Firmware §4.5.1 明確要求：韌體不能只因自己未明確支援某功能，就隨意拒絕 OS；OS 仍須到每個 Slot／Function 查能力。控制權的回傳 0，也不一定表示硬體沒有實作，可能是平台不允許 OS 接管。

PCI 專用介面與通用欄位分開讀

PCI Firmware 3.3 §4.5.1（pp.48–49）、Tables 4-4–4-6（pp.49–58）。通用回傳欄位補充依 ACPI 6.6 §6.2.12（官方索引摘錄，文件 p.401）：bit 1 為失敗、bit 2 為 UUID 不識別、bit 3 為 Revision 不識別、bit 4 為 Capabilities Masked。全文未取得，不據此延伸其他 ACPI 行為。Firmware §4.5.3 的 ASL 範例也使用 0x10 表示能力被遮罩。

從 Table 4-5 的輸入欄位先建立相依關係，再用 Table 4-6 的回傳定義確認責任。不能只看兩張表相同的 bit 編號，就假定輸入與輸出每一項都完全同義。

本例的 Control 請求與相依條件

2PCI Express Native PMEControl bit 4；這是 PME 事件管理，不等於所有電源功能。

所以本例 Control 請求為 (1 << 0) | (1 << 2) | (1 << 3) | (1 << 4) | (1 << 7) = 0x9D。Support=0x9F，表示 OS 宣告 bits 0–4 與 bit 7 的能力：Extended Config operation regions、ASPM、Clock PM、Segment Groups、MSI，以及 Error Disconnect Recover。本例沒有宣告其他 Support 位元，也未請求 LTR、Completion Timeout 或 SFI 控制權。

Support 的 ASPM bit 與 Control 的 native PME bit 也不能互換：前者宣告 OS 的設定能力，後者要求管理 PME 事件。Chapter 10 的 L1.2 是否能啟用，仍要檢查硬體、平台條件與適用的 LTR 等控制權。

6. 第一次 Query 被遮罩，要怎麼讀下一步？

作者情境：韌體已知此平台的 DPC 在 OS 原生控制下有相容性問題，因此保留 DPC 與 AER；允許 OS 管理 Hot-Plug、PME 與相應 PCIe Capability。假設沒有其他授權歷史，也沒有呼叫失敗或 UUID／Revision 錯誤。下表的 Support 始終是 0x0000009F，UUID／Revision／Count 也不變。

先協商，再正式接管的三次 _OSC 呼叫
呼叫送入 DWORD 1送入 Control回傳 DWORD 1回傳 Control
第一次 Query0x000000010x0000009D0x000000100x00000015

第一次的差異為 0x9D & ~0x15 = 0x88，正是 AER bit 3 與 DPC bit 7。回傳 DWORD 1 的 0x10 是 Capabilities Masked，不是「全部不支援」，也不是成功授予原本所有要求。第二次把請求調整成 0x15，Query 不再被遮罩；這時仍只是協商結果。

Query Support Flag=1 時，韌體不得因這次呼叫改動硬體設定。規格強烈建議先 Query，直到 Capabilities Masked 清除；本例之後才清 Query bit，正式要求接管，並重新檢查回傳結果。只有第三列完成後，才能按本例的有效結果判定 OS 已取得那三項控制權。

若回傳有失敗、UUID 或 Revision 錯誤，不能仍把未變的 Control Buffer 當成成功授權。本例把這些錯誤排除，是為了集中解釋遮罩協商，不代表它們可在實際判讀時忽略。

7. 控制權交出去以後，韌體與 OS 各自還能做什麼？

Hot-Plug 授權包含責任交接：韌體須安排事件走原生 device interrupt 路徑；交接後，不再更新插槽的指示燈、電源控制等狀態。PME 授權也有對應的事件路由與 Register 限制。這能避免兩個管理者同時修改同一組狀態。

同一次開機、同一 Host Bridge 的後續 _OSC 呼叫，OS 必須保留先前宣告的支援與已取得的控制請求；韌體也不得收回已授予的控制權。PCI Firmware 3.3 這套介面沒有讓 OS 自行放棄已取得控制權的機制，不能把一般 ACPI 的可能用法直接套進來。

如果 AER／DPC 沒有交給 OS，OS 不能因此任意改 Mask、Severity 或 DPC Control。不過也不能寫成「OS 永遠不得碰任何相關 Status」：Firmware 3.3 Table 4-6 對 Error Disconnect Recover（EDR）定義了有限的恢復協作期間。

8. 把位址、管理者與控制權接起來

_OSC 授予 Hot-Plug，是否就可以對每個 Downstream Port 寫 Power On？

不可以。授權涵蓋 hierarchy，但 Slot Implemented、Hot-Plug Capable、Power Controller Present，以及命令與供電條件仍要逐一確認。控制權不能取代能力。回看 Chapter 11與 Firmware §4.5.1。

Support bit 7=1，是否代表 OS 已取得 DPC Configuration？

沒有。它只宣告 EDR 支援；還要要求 Control bit 7、滿足 AER／Capability 相依條件，並完成有效的非 Query 控制轉移。依據：Tables 4-4–4-6、§4.5.2.4。

MCFG 能找到裝置、_OSC 也成功，但 BAR 沒空間，能否忽略 _CRS 限制？

不能。三者回答的是設定存取、管理權與可分配資源，彼此不能替代。若平台無法提供足夠範圍，控制權本身不會創造額外位址資源。依據：Firmware §3.5、§4.1、§4.5。
