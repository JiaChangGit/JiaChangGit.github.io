A TLP (Transaction Layer Packet) carries a request, completion, or message. First establish whether the link uses Non-Flit Mode or Flit Mode: their TLP (transaction packet) header layouts differ. We follow that choice into address, identity, length, and byte selection.

Why start with the format?

In Non-Flit Mode, locate Fmt/Type in Figure 2-4, then consult Tables 2-2 and 2-3. Fmt distinguishes header size and data presence; Type also determines routing. A Memory Read requests data without carrying that read data in its request. For example, a separate Non-Flit 32-bit-address Memory Read with Length=2 and no Prefix or Digest has only a 12-byte Request Header; its data returns in Completion packets. The Type/format determines whether Length describes data present in this packet.

For Flit Mode, restart with Figure 2-6 and Table 2-5. The eight-bit Type is a different encoding: NOP is 00h, while a 32-bit-address Memory Read is 03h. Reusing the Non-Flit decoding table misidentifies the packet.

How do extensions affect the data position?

OHC (Orthogonal Header Content, optional header extensions) is indicated in Figure 2-6. Read the presence/order rules on p.131, then Table 2-6 for the applicable A format. A Memory Request with explicit Byte Enables uses OHC-A1 in Figure 2-7. OHC follows the Header Base in A-B-C-E order.

TS (Trailer Size) describes the trailer separately from Length. Non-Flit Mode instead has its own prefix and TD (TLP Digest presence) rules. Determine the entire packet size before locating the next packet.

Follow the same write intent through both formats

Simulated data: this teaching scenario does not represent a particular device or platform. Two independent traces each contain a Memory Write from configured Endpoint 03:00.0 to 0x80001000. Assume the address and path are usable, device-initiated access is permitted, and no Prefix, IDE or TPH is present. Reserved and otherwise unused fields are zero. External evidence identifies each Link mode, and the complete logical TLP has already been recovered.

Both payloads are A0 A1 A2 A3 B0 B1 B2 B3, with Length=2 DW (Double Words, four bytes each), but only the middle four bytes are selected. First DW BE=1100b and Last DW BE=0011b. The Flit example starts after TLP reassembly; it is not a complete FLIT. Hex below follows the figures' byte 0, byte 1 order, with four bytes per line, rather than CPU DWORD read values.

Figure 2-4 splits the first byte, 0x40, into Fmt=010b and Type=00000b. Tables 2-2/2-3 identify their combination as a Memory Write with a three-DWORD Header and data. Figure 2-5 then gives Length=2 and TD=0: 12 bytes of Header, eight bytes of Data Payload and no Digest, totaling 20 bytes.

Next, Figure 2-31 locates Requester ID 03 00 in bytes 4–5, or 0x0300, corresponding to 03:00.0 here. Bytes 8–11 give address 0x80001000. Figure 2-26 and Table 2-10 locate Header byte 7=0x3C: its high nibble is Last DW BE=0011b, and its low nibble is First DW BE=1100b. The Header ends at byte 11; data starts at byte 12.

Start again with Figure 2-6: the entire first byte, 0x40, is Type. Entry #64 in Table 2-5 identifies a 32-bit-address Memory Write, a three-DWORD Header Base, and Data Payload determined by Length. Its first byte happens to match the preceding example, so that byte alone does not identify the Link mode.

Byte 1 has OHC=00001b, indicating OHC-A. Byte 2 has TS=000b, indicating no Trailer; Length remains 2. Figure 2-40 locates the 12-byte Header Base. Table 2-6 selects OHC-A1 for this Memory Request, and Figure 2-7 shows its one-DWORD layout. The BE fields are in byte 3 relative to that OHC block: overall TLP byte 12+3=byte 15, containing 0x3C.

Data therefore starts at byte 16, and the TLP totals 12+4+8=24 bytes. PV=0 in this OHC-A1 means no valid Process Address Space ID (PASID); the other unused fields are zero. OHC-A1 supplies partial-write byte selection without increasing the data payload length.

Section 2.2.5.2 explains why the extension is needed for this intent: without OHC-A1, a two-DWORD Memory Request implies First and Last DW BE=1111b. All eight bytes would be enabled, changing the intended middle-four-byte write. OHC presence affects the access performed by the receiver.

A Non-Flit decoder applied to the second trace could misread byte 7=0x00 as both BE fields and mistake OHC bytes 00 00 00 3C for the payload start, shifting data by four bytes. Correct the analyzer mode first; these artifacts do not establish that an erroneous packet actually appeared on the Link.

Why do eight payload bytes update only four bytes?

Continue the same simulated writes. Section 2.2.5.1 and Table 2-10 map each BE bit to a data byte: First DW BE bit 0 selects the lowest-address byte in the first DW; Last DW BE bit 0 selects the lowest-address byte in the last DW. First=1100b selects offsets +2 and +3; Last=0011b selects +4 and +5.

In the Non-Flit example, changing to a one-DWORD Request requires Last DW BE= 0000b; the example's 0011b cannot simply be retained. Read the conditions following Figure 2-26 together with the field locations.

Does TD=1 prove that the receiver checked ECRC?

It first indicates a TLP Digest at the end of a Non-Flit TLP. Whether ECRC (End-to-End CRC) is checked also depends on receiver capability and controls. In an author-created variation of the preceding Non-Flit Memory Write, a 12-byte Header and 8-byte Payload with TD=1 and no Prefix have a further 4-byte Digest, for a 24-byte logical TLP.

Figure 2-5 locates TD and Length; Length describes the Payload and excludes the Digest. Under §2.2.3 a mismatch between TD and the observed TLP size is a Malformed TLP, reported in association with the receiving Port. A receiver without ECRC checking support must ignore the Digest; an intermediate receiver forwarding a Multicast TLP through an MC_Overlay-enabled egress has a specific exception in §6.14.5. For supported checking, consult the conditions in §2.7.1.

TD=1 is not a record of a successful check. Do not apply this Non-Flit TD format directly to Flit Mode. Determine actual enablement and error records from the receiving component and its AER controls.

Must a device use the same transmit and receive limit?

Not necessarily. MPS (Maximum Payload Size) limits TLP data payloads; determine the transmitting and receiving Functions' limits separately. Read Max_Payload_Size Supported, Rx_MPS_Fixed, and Mixed_MPS_Supported in Device Capabilities and the Max_Payload_Size setting in Device Control, then apply §2.2.2 to the particular device and direction.

For Tx_MPS_Limit, a single-Function device uses its own setting; an ARI (Alternative Routing-ID Interpretation) device uses Function 0's setting. A non-ARI Multi-Function Device uses the common setting when all Functions agree; otherwise an implementation-selected Function supplies it. Software should not configure differing settings without knowing the implementation.

If Mixed_MPS_Supported=1, an implementation-specific mechanism can choose a target-specific value above or below Tx_MPS_Limit, up to the Function's Supported value. Host-memory targets still use Tx_MPS_Limit. Consult implementation information to determine a target-specific value.

For receive, Rx_MPS_Fixed=1 makes Rx_MPS_Limit the receiving Function's Supported value. With it clear, apply §2.2.2's single-Function, ARI, or applicable non-ARI multi-Function rules. A receiver must check payloads against its Rx_MPS_Limit; a detected violation is handled as a Malformed TLP and reported in association with the receiving Port.

Simulated data: this teaching scenario does not represent a particular device or platform. An ARI device has Functions 0 and 1. Assume their MPS settings are 128 and 256 bytes, respectively; Function 1 supports 512 bytes and has Rx_MPS_Fixed=1. When Function 1 transmits to host memory, Tx_MPS_Limit uses Function 0's 128 bytes. When Function 1 receives a TLP with data, Rx_MPS_Limit is 512 bytes. These constrain different directions; actual transmissions must also meet path and target requirements.

MPS limits data carried in a TLP. A Memory Read Request carries no requested data, so its Length is not restricted by MPS; consult Maximum Read Request Size and other applicable rules. For Flit-capable implementations, Table 7-20 requires at least 512-byte Supported and Rx_MPS_Fixed=1; these requirements do not apply uniformly to all Non-Flit devices.

When is the same Header byte no longer Byte Enables?

Return to Figure 2-26. In Non-Flit Mode, when a Memory Read or Deferrable Memory Write (DMWr) has TH=1, the positions normally holding First/Last DW BE instead carry Steering Tag ST[7:0]. Do not decode that byte directly as two BE fields.

Teaching example: for an applicable Memory Read with TH=1 and Length=1 DW, First DW BE is implied 1111b and Last DW BE 0000b. For Length greater than 1 DW, both are implied 1111b. TH may be set only when it is acceptable to complete the Request as if all requested bytes were enabled; §2.2.5.1 also discusses reads with side effects in Non-Prefetchable space.

This example concerns Non-Flit Mode field reuse. For a Flit Mode trace, use that mode's Header and OHC rules instead of applying Figure 2-26's byte position.

Why does a Read receive data when no byte is enabled?

Teaching example: a Non-Flit Mode Memory Read has Length=1 DW, First DW BE=0000b and Last DW BE=0000b. Section 2.2.5.1 requires the corresponding Completion to have Length=1 DW and a 1-DW Data Payload. Its contents are unspecified; do not treat the returned value as device data.

The zero-length Read implementation note describes a use as a flush: a Requester can use it to establish that earlier Posted Writes completed at their PCIe destination. For that use to be effective in all cases, the Read must target the same device as those Writes; the specification recommends using the address of one of those Writes. The flush applies only to traffic in the same Traffic Class as the Read. It does not establish that application data is durable on nonvolatile media.

For example, send a TC0 Posted Write, then a TC0 zero-length Read to the same device and observe its normal Completion. That supports the specification's conclusion about the earlier Write at the PCIe destination. A TC1 Write is not covered by this TC0 Read. Account for the path and applicable Attributes; issuing the Read is not the same observation as receiving its response.
