Read platform descriptions, then negotiate runtime control

Firmware establishes the boot environment; the OS uses platform descriptions and control negotiation to take over management. This chapter connects Host Bridge resources, configuration access and _OSC (Operating System Capabilities).

Specification route: PCI Firmware 3.3 Section 3.5 → platform descriptions in Section 4.1 → Support/Control in Section 4.5.1 → Query, Control and dependencies.

Locating a PCIe register does not establish permission to configure it. Firmware prepares the boot environment; the OS manages resources and features according to platform descriptions and negotiated ownership. This report separates UEFI, ACPI, and PCI Firmware responsibilities through nonzero-Start-Bus ECAM and _OSC examples.

Handoff does not imply every device was configured

Firmware §3.5 requires configuration of all Host Bridges and PCI-to-PCI Bridges leading to boot/console devices. The OS cannot assume every other path is configured. UEFI drivers/applications must not change BAR/Bridge assignments owned by the firmware configurator. Existing BAR interpretation still requires the corresponding Enables and platform translation information; CPU and BAR addresses may differ.

ACPI Host Bridge objects provide _HID/_CID, _CRS, and conditionally information such as _SEG. Segment and BDF identify the target together; a namespace path is not a BDF. Sources: PCI Firmware 3.3 §3.5 (pp.34–37), §4.1.5 (pp.45–46); BAR details in Chapter 4.

Declaring support, requesting control, and receiving ownership are distinct

PCI Host Bridge _OSC applies to its originating hierarchy. Firmware §4.5.1 specifies UUID 33DB4D5B-1FF7-401C-9657-7441C03DD766, Revision=1, and a three-DWORD buffer. DWORD 1 holds generic Query/return information. DWORD 2 is the one-way OS Support declaration; returned changes do not grant control. DWORD 3 carries Control requests and responses.

Input DWORD 1 bit 0=1 means Query; clearing it requests control. Returned bit 0 is Reserved. Return bits 1, 2, and 3 indicate failure, unrecognized UUID, and unrecognized Revision; bit 4 indicates Capabilities Masked. Preserved Control bits after an error are not successful grants.

A grant does not prove every device has the capability; a zero response does not prove absent hardware. Firmware cannot deny solely because it lacks explicit feature support; it needs explicit platform incompatibility knowledge. The OS must still inspect individual Slots/Functions.

Read a complete negotiation through its dependencies

The example requests native Hot-Plug bit 0, native PME bit 2, AER bit 3, PCI Express Capability Structure bit 4, and DPC bit 7: Control=0x9D. DPC also requires Support bit 7 for Error Disconnect Recover (EDR). Support=0x9F declares bits 0–4 and 7: Extended Config operation regions, ASPM, Clock PM, Segment Groups, MSI, and EDR. LTR, Completion Timeout, and SFI control are not requested.

Hot-Plug, PME, and AER require Control bit 4; DPC additionally requires Control bit 3. Firmware retaining DPC must retain AER. Granting DPC requires granting AER and Capability control. Bit 4's broad name does not override individual ownership rules. ASPM Support is not PME Control and does not replace L1.2 hardware, timing, or LTR requirements.

Handoff responsibilities and limited EDR exceptions

When granting Hot-Plug, firmware establishes native event routing and then stops updating slot indicators and power state. PME has corresponding routing/register restrictions. Subsequent calls within the same boot and Host Bridge must retain declared support and granted control requests; firmware cannot revoke grants. Firmware 3.3 provides no mechanism for the OS to relinquish acquired control.

Without AER/DPC ownership, the OS cannot arbitrarily modify Mask, Severity, or DPC Control. Table 4-6 nevertheless defines EDR cooperation exceptions. Between EDR Notify and the OS invocation of _OST, it permits specified Device/AER/RP PIO Status writes on the triggering Port, plus DPC Trigger Status handling. The latter is also permitted while processing subsequent hot-removal below a Port whose Trigger remains set. After the corresponding _OST returns, until downstream Function reinitialization or disablement completes, limited writes to specified downstream DPC/Device/AER Status are permitted. Firmware must honor the corresponding write prohibitions during each window.

These exceptions do not transfer full DPC Configuration ownership or remove Link-inactive/applicable-RP-Busy requirements. Determine the target, time window, notification, and _OST context together. If _OSC is absent, the OS must not enable features defined by this interface.

Keep the three evidence categories separate

Does Support bit 7=1 give the OS DPC ownership?

No. It declares EDR support; valid Control requests, dependencies, and a successful non-Query grant are still required. Sources: Tables 4-4–4-6.

Can successful MCFG access and _OSC negotiation override insufficient _CRS resources?

No. Configuration access, ownership, and resource capacity are different questions. Sources: Firmware §3.5, §4.1, §4.5.
