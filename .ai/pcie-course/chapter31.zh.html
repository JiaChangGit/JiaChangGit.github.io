想取得元件的安全量測資料，先如何交換物件？

選擇步驟後，圖中對應的元件與下方解說會加上重點標示。完整圖與所有解說會持續顯示；也可用方向鍵切換步驟。

這張圖示範request／response型協定的一回合。不是每個DOE協定都必須有相同的回應結構。

DOE（Data Object Exchange，資料物件交換）提供韌體／軟體透過設定空間交換物件的機制。CMA（Component Measurement and Authentication，元件量測與認證）可在其上使用 SPDM（Security Protocol and Data Model，安全協定與資料模型）。先完成可用的物件交換，再談內容與信任判讀。

  1. 先探索這個實例支援什麼

    同一Function可有多個實例；物件作用範圍由協定規定，不能直接推成整顆裝置。

    每個DOE（以設定空間交換資料物件的實例）必須支援Discovery。Table 6-32以Vendor ID與Protocol識別資料物件協定。

    Base 6.0 §6.30、Table 6-32，pp.843、847。

  2. 完整寫入後才觸發處理

    DW是Double Word，4 bytes。物件未寫完就Go，或Busy時再Go，行為未定義。

    確認非Busy後，逐DW寫入Write Data Mailbox；全部寫完才設Go，再等待Ready或Error。

    Base 6.0 §7.9.24.3–§7.9.24.5，pp.1297–1298。

  3. 依介面取走回應

    清除DOE Error靠Abort，不能把這個唯讀狀態當成RW1C隨意寫1清除。

    Ready時讀Read Data Mailbox，每讀一個DW後以寫入確認移出，下一次才得到後一個DW。

    Base 6.0 §7.9.24.4、§7.9.24.6，pp.1298–1299。

我要查 CMA 支援，應該先看哪個入口？

先從DOE能力找到可用實例，再走Table 6-32的Discovery。得到的Vendor ID／Protocol組合，用來判斷該實例提供何種物件。CMA（以量測與認證確認元件資訊的功能）不是看到DOE存在就必然完整支援；物件協定與相關能力仍須探索。

DOE依賴Configuration Request，並不是兩個Function可直接做P2P交換的通用通道。若系統需要中繼，須由系統軟體提供相應方式。

一份回應有多個 DW，為什麼不能一直讀同一個 Register？

作者情境：一份合法回應的長度由物件標頭與所選協定確認。Ready=1時，讀取Read Data Mailbox只取得目前DW（4-byte資料單位）；必須接著寫入確認，實例才把下一個單位放到下次讀取。少了確認步驟，就會把相同資料誤當成後續內容。

正常收完後再依協定處理物件。傳輸出錯則按Error／Abort流程恢復；§6.30.2對一般request／response處理給出1秒時限，特定協定另有要求時依其規則。Abort也有清除Ready與Error的時限，不能只設bit後立刻假定恢復完成。

物件成功交換，接收端就值得信任了嗎？

還要看SPDM（定義安全交換內容與程序的協定）與平台信任政策。Figure 6-43把協定、secured messages與DOE／MCTP承載方式分層。§6.31明確說明：Base處理PCIe特定要求，基礎架構、訊息與協定定義在所引用SPDM文件。

這章因此停在分工與判讀入口：交換成功只證明資料傳輸完成；認證還要驗證身分、量測與信任依據。本文不另編一套憑證驗證演算法，也不把新版SPDM要求偷偷套進Base 6.0。
