Record cards, Functions, and Links as different objects

A component is one physical package. A Device is a collection of Functions sharing a Bus Number and Device Number within a hierarchy. A Function is individually addressable in Configuration Space; a Port interfaces a component to a Link.

A Link comprises two adjacent Ports and their interconnecting Lanes. Each Lane has one transmit differential pair and one receive differential pair. An x4 Link has four Lanes. In this example, A's two Functions share one Port and LA; two configuration targets do not create two external Links.

The diagram uses Endpoint A as a label for the component providing Endpoint Functions. Formally, Endpoint is a Function type. Card assembly, packages, configuration targets, and external connections answer different questions.

Base 6.0, Terms and Acronyms: component, Device, Function, Lane, Link, and Port, document/PDF pp.83–85, 87, 89; §1.2, pp.100–102.

Which roles remain the same during a Read and its response?

The Switch Upstream Port faces the Root Complex; its Downstream Ports face the downstream branches. These names follow topology. The Requester initiates the transaction, while the Completer handles the original Request and produces the required response. Transmitter and Receiver describe an individual Link transfer.

Can Endpoints under different Root Ports always communicate?

Teaching example: Endpoint A and B are below different Root Ports of the same Root Complex (RC). Figure 1-2 places them in different hierarchy domains, so A's access to B must cross the RC. Base 6.0 §1.3.1 makes peer-to-peer routing between hierarchy domains optional and implementation-dependent. Enumerating both Endpoints does not establish that the RC offers this path.

When supported, an RC can use different designs: for example, take ownership of a Request, reform packets as needed and handle returning Completions, or use an internal physical or virtual Switch. Section 1.3.1 generally permits an RC to split packets while routing between domains; §1.3.3 prohibits a Switch from splitting one packet into smaller packets. Each remains subject to its applicable packet rules.

There are exceptions: an RC must not split a Deferrable Memory Write Request; splitting a Vendor-Defined Message is subject to 128-byte boundary conditions. Practical analysis also needs platform routing, Bridge Windows, the target BAR and access policy. The topology alone establishes the path through the RC, not delivery to B.

Base 6.0 §1.3 and Figure 1-2, pp.102–103; §§1.3.1 and 1.3.3, pp.103–104 and 106–107; Deferrable Memory Write: §6.32.

Why does an Endpoint sometimes have no Link partner?

The add-in card in the earlier example is an Endpoint connected outside a Port. Figure 1-2 also shows a Root Complex Integrated Endpoint (RCiEP) inside the Root Complex. It is still a Function that supports Configuration Requests, but it does not appear in the external hierarchy domains exposed by Root Ports or inside Switches.

Teaching example: suppose a readable Function identifies its Device/Port Type as RCiEP. Check fields applicable to that type: an RCiEP must not implement Link Capabilities, Link Control, Link Status, or their version 2 registers. Missing those registers does not establish that an external Link failed. A different Device/Port Type needs its own applicability rules.

An RCiEP may be associated with an optional Root Complex Event Collector (RCEC), which terminates error and PME (Power Management Event) messages from associated RCiEPs. Check the RCEC's Endpoint Association Extended Capability to establish an association. RCECs are optional; do not assume every RCiEP has one. If an RCiEP is associated with an RCEC, it must signal PME and errors through that RCEC and cannot be associated with more than one.

All three Endpoint types use a Type 0 Configuration Header, but their constraints differ. Compare §§1.3.2.1–1.3.2.3 before applying a field-specific rule.

Which two fields establish a Function's role?

At the selected Function, read the 8-bit Header Type at offset 0x0E. The low seven bits select the header layout and bit 7 indicates possible multiple Functions. Then locate the PCI Express Capability and read its 16-bit register at base + 0x02; Device/Port Type in bits 7:4 identifies the role. The first field selects the layout used to read the second.

What information do BDF, Segment, and Requester ID retain?

Under conventional addressing, BDF contains an 8-bit Bus Number, a 5-bit Device Number, and a 3-bit Function Number. The first four digits of 0000:03:00.1 identify the Segment; the remaining 03:00.1 is the BDF within that Segment. These numbers describe a logical identification location, not a physical slot number.

As a further teaching assumption, 03:00.0 has also been discovered in Segment 0001. This is a second logical scope created for the example, not a downstream branch of the preceding table. Dropping the Segment would incorrectly merge distinct records.

When 0000:03:00.1 originates a Request, its 16-bit Requester ID is formed as follows in this example:

Requester ID = (Bus << 8) | (Device << 3) | Function
             = (0x03 << 8) | (0x00 << 3) | 0x1
             = 0x0301

Example deduction: 0x0301 preserves the BDF but does not encode Segment 0000 into those 16 bits. This conclusion applies only to the Requester ID field. It does not mean that all PCIe packets lack Segment information: some Base 6.0 Flit Mode packets have separate related fields. BDF is also not a permanent hardware identity. If records come from different configurations at different times, matching or changed BDF values alone cannot establish whether they describe the same physical device.

What evidence should the next observation include?

For a speed/width report, retain the Port, its direct Partner, the time, and the field name. For a tool's Endpoint label, return to Header Type and Device/Port Type. For one captured Request, identify the Link and direction before assigning transfer roles. These records let later training, error, and Completion evidence refer to the same object.

The simulated snapshot supplies neither a full training history nor a unique fault diagnosis. BDF is not used as a permanent hardware identity.
