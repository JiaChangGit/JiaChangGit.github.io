Version and scope

Register definitions follow PCI Express Base Specification Revision 6.0, with Segment context from PCI Firmware Specification Revision 3.3. Page numbers refer to the PDFs used by this course; printed and PDF page numbers coincide. The example uses conventional Bus/Device/Function (BDF (Bus, Device, and Function identifier)) addressing, without Alternative Routing-ID Interpretation (ARI) or the identification scheme of Flattening Portal Bridge (FPB). Those mechanisms introduce additional discovery, numbering, or routing rules; ARI in particular changes how the Device/Function bits are interpreted. The example also excludes SR-IOV and Phantom/Shadow Functions. The latter mechanisms can use additional Function identifiers and are left to advanced chapters.

Why are a card, a Function, and a Port different objects?

A card describes physical assembly; a Function is the object software identifies and configures individually. A card can expose several Functions and may contain a Switch and several Endpoints. Read the configuration topology to select the Function, and use assembly information separately to identify its card.

A Switch's Upstream Port faces the Root Complex, while its Downstream Ports face downstream components. Software sees each Switch Port as a PCI-to-PCI Bridge, with those bridges connected through an internal logical Bus. This does not turn external PCIe Links into a shared parallel bus, nor does each Bridge imply a separate chip.

Keep both views when reading a topology: Links describe connections between adjacent hardware components, while Bridge configuration describes the paths that software can identify toward downstream components.

Specification locations for the Switch and its logical topology

Base 6.0 §1.3.3, pp.106–107, with Figure 1-3 on p.107; §7.1, pp.903–904, with Figures 7-1 and 7-2 on p.904. The first explains Switch connections and bridge presentation; the latter contrasts the configuration structure visible to software. The example's internal Switch Bus connects only the virtual bridges for Downstream Ports. Endpoints sit at the other ends of external Links.

Which two fields establish a Function's role?

At the selected Function, read the 8-bit Header Type at offset 0x0E. The low seven bits select the header layout and bit 7 indicates possible multiple Functions. Then locate the PCI Express Capability and read its 16-bit register at base + 0x02; Device/Port Type in bits 7:4 identifies the role. The first field selects the layout used to read the second.

Which downstream path reaches 0000:03:00.1?

The example places a Root Port and a Switch with two Downstream Ports in Segment 0000. Endpoint A's two Functions are on Bus 03, while Endpoint B is on Bus 04. Secondary Bus Number identifies the Bus immediately downstream of a Bridge. Subordinate Bus Number bounds the upper end of its downstream Bus Number range. Target Bus 03 is within the Root Port's 01–04, the Upstream Port's 02–04, and Downstream Port A's 03–03 ranges. Downstream Port B covers only 04–04, so it is outside the path to this target.

These ranges check the known topology; they do not establish that every number in a range has a populated Bus. A Bridge's own BDF (Bus, Device, and Function identifier) also differs from the Bus it leads to: 02:01.0 is on Bus 02 and has Secondary 03. This chapter does not derive a Bridge's own BDF from Primary Bus Number. Base 6.0 retains that field for legacy compatibility, and PCIe generally does not use it.

What information do BDF, Segment, and Requester ID retain?

Under conventional addressing, BDF contains an 8-bit Bus Number, a 5-bit Device Number, and a 3-bit Function Number. The first four digits of 0000:03:00.1 identify the Segment; the remaining 03:00.1 is the BDF within that Segment. These numbers describe a logical identification location, not a physical slot number.

As a further teaching assumption, 03:00.0 has also been discovered in Segment 0001. This is a second logical scope created for the example, not a downstream branch of the preceding table. Dropping the Segment would incorrectly merge distinct records.

When 0000:03:00.1 originates a Request, its 16-bit Requester ID is formed as follows in this example:

Requester ID = (Bus << 8) | (Device << 3) | Function
             = (0x03 << 8) | (0x00 << 3) | 0x1
             = 0x0301

Example deduction: 0x0301 preserves the BDF but does not encode Segment 0000 into those 16 bits. This conclusion applies only to the Requester ID field. It does not mean that all PCIe packets lack Segment information: some Base 6.0 Flit Mode packets have separate related fields. BDF is also not a permanent hardware identity. If records come from different configurations at different times, matching or changed BDF values alone cannot establish whether they describe the same physical device.

Do changed observations support the same conclusions?

In this snapshot, select Segment 0000, follow the Bus 03 range through branch A, and read Function 1 separately. Its traditional Requester ID is 0x0301 when it originates a Request. Keep the Segment and snapshot with that result when comparing records.

Does a Header Type read of 0x80 prove that Function 1 exists?

No. Table 7-7 (pp.924–925) establishes a Type 0 header and that the device may contain multiple Functions. Function 1 still needs valid discovery evidence before it can be reported as present. That evidence is a separate teaching assumption in this example.

If the target becomes 0000:04:00.0, does its path still pass through Downstream Port A?

No. In this snapshot, Bus 04 lies within Downstream Port B's 04–04 range, outside A's 03–03 range. The path still passes through the same Root Port and Upstream Port; only the downstream Switch branch changes. (Base 6.0 §7.5.1.3.3–§7.5.1.3.4, p.937.)

Can two records with BDF 03:00.0 be treated as the same Function?

Not yet. First establish the Segment and the configuration time represented by each record. The example's 0000:03:00.0 and 0001:03:00.0 are different Functions. Across different times, a matching BDF alone also does not establish the same hardware identity. (Firmware 3.3 §1.3, pp.8–9; Base 6.0 §2.2.6.2, p.156.)
