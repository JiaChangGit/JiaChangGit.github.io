D0 identifies a Function power state; system grants and active power mechanisms still constrain consumption. Power Budgeting reports demand under specified conditions. DPA (Dynamic Power Allocation) adjusts a Function allocation within D0. Read the demand data first, then follow a complete reduction/increase example.

Establish whose consumption is being reported

A Function is a software-visible unit; an add-in card can contain several Functions and Devices. Table 6-10 Power Budgeting Deployments (p.743) determines reporting scope from capability placement. For a multifunction Device with Power Budgeting in exactly one Function, the data covers the Device. When multiple Functions implement it, their data is per-Function and is summed according to the table.

Establish that scope before calculating watts. A multi-device card can report at card or Device level; adding every readable value without that distinction can count the same demand twice. Section 6.8.1 separately describes firmware allocations and the budget manager's responsibilities. The platform chooses its management process.

Function 0 covers all consumption, with no other Device or external power source. It draws from 12 V and 3.3 V rails and is currently in D0. Assume System Allocated=0, Extended Power Budgeting Supported=0 and exactly four non-extended data entries. Separately, the platform has already granted sufficient power under the applicable form factor and system budget.

Index 4 exceeds this case's four entries, so Data returns all zeros. Table 7-122 also defines alternative power-range encodings when Base Power exceeds EFh under its stated conditions. F0h cannot always be treated as 240 W.

System Allocated=0 makes this case relevant to the responsible budget manager. If the bit is 1, the Device's budget is already included in the system budget; software must ignore its reported data for budgeting decisions to avoid counting it again. The Device still consumes power.

Does reporting 26 W grant the card 26 W?

Power Budgeting reports demand. Check the active grant mechanism separately. Under §6.9, Downstream Port Slot Capabilities supply the Slot Power Limit. Set_Slot_Power_Limit Message carries it to the Upstream Port across the same Link, where Device Capabilities exposes Captured Slot Power Limit Value/Scale. The limit applies to the entire adapter.

Before receiving a higher grant, the card must obey the applicable form-factor initial limit. The Slot mechanism does not permit an arbitrary lower value either. Section 6.8.3 separately defines Power Limit PM Sub State and Out of Band Power Limit mechanisms with distinct priority rules. Power Limit Enable and Power Limit PM Sub State may be configured through Configuration Writes only while all Device Functions are in D0uninitialized; changing them after any Function leaves that state has undefined behavior.

The runtime example therefore uses DPA. Power Budgeting has up to eight PM Sub States; DPA has up to 32 substates. Their numbers have no automatic correspondence. Function D0/D1 states and Link L1.1/L1.2 states describe still other mechanisms.

Source: §6.8.3 Power Limit Mechanismsm (title as printed) and §6.9 Slot Power Limit Control, document/PDF pp.744–746.

DPA is optional for applicable Endpoint Functions in D0. Substates run contiguously from 0 through Substate_Max. Substate 0 has the highest allocation; successive allocations must not increase. During a reduction, Status must retain the higher allocation until completion. While Substate Control=2 but Substate Status still reports 0, reserve 26 W; do not give the difference to another card yet. Once Substate Status reports 2, the Function must obey its 10 W allocation.

During an increase, Substate Status must already indicate the higher allocation. Observing target 0 alone therefore does not establish completion. Prepare the 26 W budget before issuing the request, then use the target's maximum transition latency and any necessary Device information for subsequent actions. Status describes the allocation the Function must obey, not instantaneous sensed power or guaranteed application performance.

Section 6.16 permits a new target before the previous transition completes. The Device may alter an ongoing transition, or compare against the latest target after completion and transition again. Our case avoids intervening requests to show the two directions clearly. Preserve every Control write when interpreting a real trace; one final Status does not reconstruct that history.

Does writing 1 enable Substate Control?

Check the attribute first. Substate Control Enabled is RW1C (write one to clear), in Status bit 8, not DPA Control. Hardware sets it after a Conventional Reset or FLR (Function Level Reset); software cannot directly set it back to 1.

For example, with Status=0102h in substate 2, writing 0100h to Status clears Enabled. Subsequent target writes to Control no longer directly initiate DPA transitions. This allows Device-specific software to take over allocation; its policy depends on that software and Device mechanism. Disabled does not promise a permanent 10 W allocation.

Source: §6.16, document/PDF p.777; §7.9.12.4 / Table 7-254, pp.1239–1240.

Will normal operation resume automatically after emergency reduction?

Emergency Power Reduction State is an optional fail-safe intended to prevent system damage and overrides the normal power mechanisms discussed here. Read Emergency Power Reduction Supported and Emergency Power Reduction Initialization Required in Device Capabilities 2, then use Table 6-16 to identify allowed triggers. Continue into §6.24's text for exit behavior.

For example, Supported=10b permits the applicable form-factor mechanism only if that form factor actually defines such a request. Vendor-specific and autonomous triggers also follow Table 6-16. There is no universal standard Configuration-bit write sequence that triggers every platform.

Initialization RequiredEntryExit
0The Function may reduce performance or enter a Device-specific dormant state; its Upstream Port remains operating and outstanding requests must complete normallyNormal operation resumes without software intervention
1The Function ceases normal operation; its Upstream Port may enter DL_Down. If it stays DL_Up, outstanding requests must still complete normallySoftware intervention is required. If the port entered DL_Down, all Functions are reset and full reconfiguration is required

Initialization Required=1 can also leave the port in DL_Up, so accessible Configuration Space alone does not establish that software reinitialization is unnecessary. Notification of required reinitialization and external signaling details require platform, form-factor or vendor documentation. Power Budgeting must also report the appropriate emergency-state consumption; the normal D0 26 W value cannot simply be reused.

Which PF/VF power belongs in the same allocation?

A PF (Physical Function) and VF (Virtual Function) have distinct roles in SR-IOV (Single Root I/O Virtualization). A PF may implement Power Budgeting, covering all associated VFs; VFs must not implement it. VF DPA allocation is likewise managed through its associated PF; VFs must not implement DPA Capability.

Some or all Functions of a general multifunction Device may implement DPA; their allocations are summed. One Function's DPA may also account for Functions lacking it, with implementation-specific associations. Do not copy the single-function case into an extra 26 W allocation for every VF.

D-states follow §5.10 separately. PFs must implement Power Management Capability; VFs may implement it. A VF without it behaves as if programmed into its PF's equivalent power state. When a VF implements it, putting the PF in a lower-power state than the VF has undefined behavior; software should lower the VFs first. That differs from changing DPA allocation while remaining in D0.

Source: §§5.10–5.10.1, document/PDF p.655; §6.16.1, p.778; §7.8.1, p.1090.
