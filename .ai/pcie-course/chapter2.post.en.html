Starting from an already discovered Function, this chapter queries Device Serial Number (DSN). The feature selects the list; pointers locate its structure; register definitions then determine how to read and assemble the serial number.

Version and assumptions

Definitions follow PCI Express Base Specification Revision 6.0. Addresses and values are author-created, not measurements. The target is an already discovered ordinary Type 0 PCI Express Endpoint, not an RCiEP or VF; ARI, SR-IOV, and RCRB lists are excluded. Reads succeed, the snapshot is stable, and the platform can access the full Configuration Space. The example does not support Flit Mode, allowing its AER (Advanced Error Reporting) Header to use Version 2. Printed and PDF page numbers coincide.

Separate the target, configuration offset, and CPU address

Segment and BDF (Bus, Device, and Function identifier) select the Function. A byte offset then selects a Register in its 4096-byte Configuration Space: the first 256 bytes are PCI-compatible, and 0x100–0xFFF is the extended region. ECAM (Enhanced Configuration Access Mechanism) provides CPU memory-mapped configuration access. The platform supplies its physical mapping; the offset alone is only a position within the selected Function.

The conventional Capability list starts through the Header's Capabilities Pointer, at 0x34 for the Type 0/1 layouts used here. The Extended list starts independently at 0x100. The PCI Express Capability belongs to the conventional list; DSN belongs to the Extended list. A name containing PCIe does not establish which list to use.

An ID of zero is different from a Next pointer of zero

A conventional Capability normally starts with an ID in the low byte and a Next pointer in the high byte of a 16-bit read. The teaching list follows 0x40 → 0x50 → 0x70 → 0xD0 → 0, representing PM, Null, PCIe, and MSI-X.

Next already gives a byte offset from the beginning of the Function. Read at that offset directly; DWORD alignment does not change its unit. After finding DSN, distinguish data location from display order

Figure 7-242/Table 7-221 identify DSN as ID 0003h. Figure 7-241 then places its Lower DW and Upper DW at structure offsets +0x04 and +0x08. The example reads 0x33221100 at 0x184 and 0x77665544 at 0x188, each as 32 bits.

Register integer = (0x77665544 << 32) | 0x33221100
                 = 0x7766554433221100

Table 7-222 separately maps Register bytes to EUI-64 bytes. Written from the highest EUI byte to the lowest, the example is 00-11-22-33-44-55-66-77. These values illustrate reconstruction, not an allocated or usable product identifier. Real values must follow the IEEE company identifier and manufacturer extension rules, and the value alone does not authenticate hardware.

DSN is optional. An ordinary Multi-Function Device implementing DSN must implement it in Function 0; other Functions implementing it must return the same value. DSN therefore does not replace the Function Number in BDF (Bus, Device, and Function identifier).

A read value is not automatically safe to write back

Read the Attributes column with the field definition. RO does not mean hardware state can never change. RW1C (write one to clear) clears a status bit when written as one; writing zero has no effect. In an illustrative four-bit RW1C (write one to clear) field reading 1001b, writing 0001b clears only bit 0, leaving 1000b if no new event occurs. This is an attribute example, not an actual Register.

Software must preserve the read value when writing RsvdP (reserved, preserve on writes) bits, whereas RsvdZ (reserved, write zero) requires zero on writes. Reserved fields cannot all use the same update rule. A failed read is not a valid indication of absence, and a successful zero read does not prove that a meaningful Register exists there. Establish the entry point and valid result before interpreting the format.

Attributes and evidence limits

Base 6.0 §7.4, Table 7-2, pp.913–915. Unimplemented Registers return successful zero reads absent other errors: §7.3.3, p.913. An all-zero Extended Header at 0x100 indicates no Extended Capabilities: §7.6.1, p.1009. That rule differs from a conventional Null Capability ID of zero.

Apply the complete query to changed values

The worked query starts at 0x100, reaches DSN at 0x180, and reads its data at 0x184 and 0x188. Next locates a different structure; a data offset locates a field in the current structure. The following variations apply that distinction.

If 0x180 returns 0x24010003, does the DSN Lower DW move to 0x244?

No. 0x240 points to the next structure. The current DSN remains at 0x180, with its Lower DW at 0x184. (Figure 7-241, p.1205; Table 7-39, p.1010.)

Does failure to find DSN in the conventional list prove lack of support?

No. DSN belongs to the Extended list and requires an interface that can access it. Searching the wrong list or lacking access is not valid absence evidence. (§7.6.1, p.1009; §7.9.3, p.1205.)
