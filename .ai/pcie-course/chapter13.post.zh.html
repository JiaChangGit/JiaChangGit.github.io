先看本章的角色與路徑

韌體先建立開機環境，OS 再依平台描述與控制權協商接手管理。本章把 Host Bridge 資源描述、設定空間位置與 _OSC（Operating System Capabilities，作業系統能力協商方法）串成一條閱讀路線。

前情提要：BAR 與 Bridge Window 的計算回到 Chapter 4；Hot-Plug、PME、AER 與 DPC 的硬體機制已在前章建立，現在確認由誰管理。

規格路線：Firmware 3.3 §3.5 的交接要求 → §4.1 的平台描述 → §4.5.1 的 Support／Control 欄位 → Query、Control 與依賴條件。

找到 PCIe 欄位，不代表目前的軟體有權設定它。韌體先建立開機環境，OS 再依平台描述與協商結果管理資源及功能。本篇分清 UEFI、ACPI、PCI Firmware 的角色，並以非零 Start Bus 的 ECAM 與 _OSC 協商案例說明常見誤判。

交接不保證每個裝置都已配置

Firmware §3.5 要求韌體配置所有 Host Bridges，以及通往開機／主控台裝置的 PCI-to-PCI Bridges；OS 不能假定其他路徑也都完成。UEFI drivers／applications 不得自行變更由韌體配置者持有的 BAR／Bridge 配置。OS 判讀既有 BAR，仍需對應 Enable 與平台轉譯資訊，CPU 位址未必等於 BAR。

Host Bridge 在 ACPI namespace 中提供 _HID／_CID、_CRS 等描述，並依條件提供 _SEG 等資訊。Segment 與 BDF 須一起辨識目標；namespace 路徑不是 BDF。依據：PCI Firmware 3.3 §3.5（pp.34–37）、§4.1.5（pp.45–46）；BAR 細節見 Chapter 4。

宣告支援、要求控制與實際授權是三件事

PCI Host Bridge 的 _OSC 涵蓋該 Host Bridge 所起始的 hierarchy。Firmware §4.5.1 定義 UUID=33DB4D5B-1FF7-401C-9657-7441C03DD766、Revision=1、三 DWORD Buffer。DWORD 1 放通用 Query／回傳資訊；DWORD 2 是 OS 單向宣告的 Support Field，回傳修改不作授權；DWORD 3 是 Control 請求與回覆。

送入 DWORD 1 bit 0=1 是 Query，清除才要求接管；回傳 bit 0 是 Reserved。回傳 bit 1、2、3 分別是處理失敗、UUID 不識別、Revision 不識別，bit 4 是 Capabilities Masked。發生錯誤時，不可把保留的 Control bit 當成成功授權。

授權 1 不證明每個裝置都有該能力；回傳 0 也不等於硬體沒有實作。韌體不能只因自己未支援功能就任意拒絕；應有明確的平台不相容依據。OS 仍須查每個 Slot／Function。

用相依條件解讀一次完整協商

本例要求 native Hot-Plug bit 0、native PME bit 2、AER bit 3、PCI Express Capability Structure bit 4 與 DPC bit 7，Control=0x9D。DPC 還要求 Support bit 7 的 Error Disconnect Recover（EDR）支援。Support=0x9F 宣告 bits 0–4 與 bit 7：Extended Config operation regions、ASPM、Clock PM、Segment Groups、MSI、EDR。未請求 LTR、Completion Timeout 或 SFI。

Hot-Plug、PME、AER 需搭配 Control bit 4；DPC 另需 Control bit 3。韌體保留 DPC 時必須保留 AER；授予 DPC 則須同時授予 AER 與 Capability。bit 4 的概括名稱不能推翻個別控制權。Support ASPM 也不等於 Control PME，更不替代 L1.2 的硬體、時序與 LTR 條件。

交接後的責任，以及有限的 EDR 例外

授予 Hot-Plug 時，韌體須安排原生事件路由，之後不再更新插槽指示燈與電源狀態；PME 也有相應路由與 Register 限制。同次開機、同一 Host Bridge 的後續呼叫須保留已宣告支援與已取得的請求，韌體不能收回已授權項目；Firmware 3.3 沒有讓 OS 自行放棄已取得控制權的機制。

未獲 AER／DPC 控制權，不能任意改 Mask、Severity 或 DPC Control；但 Table 4-6 定義 EDR 協作例外。從 EDR Notify 到呼叫 _OST 前，OS 可處理觸發 Port 的指定 Device／AER／RP PIO Status，並可寫 DPC Trigger Status；處理其後 Trigger 仍為 1 的下游熱移除時，也允許處理該 Trigger。對應 _OST 返回後，到下游 Function 重新初始化完成或停用前，又有針對下游指定 DPC／Device／AER Status 的有限權限。各期間韌體須遵守對應的禁止寫入規則。

這不是交出完整 DPC Configuration，也不免除 Link inactive／適用 RP Busy 等硬體條件。完整判讀要同時確認對象、時間窗、通知與 _OST；沒有 _OSC 時，OS 不得啟用該介面定義的功能。

確認三類證據沒有混用

Support bit 7=1 就代表 DPC 歸 OS 管理嗎？

沒有；它宣告 EDR 支援，仍需合法 Control 請求、相依功能及非 Query 的有效授權。依據：Tables 4-4–4-6。

MCFG 存取成功、_OSC 也成功，可以忽略 _CRS 不足嗎？

不能。設定存取、控制權與資源容量是不同問題。依據：Firmware §3.5、§4.1、§4.5。
