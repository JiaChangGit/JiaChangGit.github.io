After parsing a TLP (Transaction Layer Packet), follow the receiver into validity and acceptance checks. An AtomicOp (Atomic Operation) performs an atomic read-modify-write; DMWr (Deferrable Memory Write) supports shared work submission. Both return completions, with different operation and status rules.

What happens after a request reaches the receiver?

The previous chapter established the packet structure. Here, the Data Link Layer has checked transmission integrity, and the Transaction Layer applies packet formation and request-specific rules. Start at Figure 2-81 (p.206), follow the valid-format path, then separate Requests from Completions.

The first decision explicitly says Ignoring Reserved Fields. A receiver must ignore values in Reserved fields; a nonzero Reserved value alone does not establish a Malformed TLP. Other constrained fields retain their own mandatory or optional checks. This rule concerns fields marked Reserved, not Reserved encodings within active fields such as Fmt/Type; those follow their mode-specific rules. A TLP determined to be Malformed must be discarded.

For a Request, continue to Figure 2-83 (p.213): determine type support, then apply the rules for that Request. The dashed programming-model check is optional. It permits certain devices to handle accesses that violate their programming model as Completer Abort; it is not a mandatory stage of every transaction. The flowchart directs the analysis, while sections 6.15 and 6.32 supply the operation-specific rules for CAS and DMWr.

What must support an atomic update?

An AtomicOp (Atomic Operation) reads a target location, potentially updates it, and returns its original value in one transaction. The read-modify-write sequence is atomic with respect to accesses to that location. First establish the operation in section 6.15, then follow its actual path.

Does a successful CAS always replace the value?

No. CAS (Compare and Swap) writes its swap operand only when the original value equals the compare operand. A mismatch is also a normal execution result. The requester compares the returned original value with its submitted compare operand. Successful Completion (SC) has no separate comparison-match flag.

Why does an 8-byte Request operate on only 4 bytes?

Read the CAS row and 32 Bits column of Table 2-15 (p.162): Request Length=2 DW, carrying two operands totaling 8 bytes. The target read, possible write, and returned original value each use one 32-bit value. A DW (Double Word) is 4 bytes.

Then read the natural-alignment and 4-KB-boundary rules on p.163. The address is divisible by 4. The target range 0x80001FFC–0x80001FFF occupies the final 4 bytes of a 4-KB page without crossing it. Adding all 8 Request Data bytes to the target address would falsely flag a boundary violation. Both CAS operands act on one location, not two adjacent locations.

Which Completion fields have AtomicOp-specific meaning?

Use Figure 2-73 (p.196) to locate Requester ID and Tag and confirm 0300h / 2Ah; Chapter 5 explains matching. The successful response is CplD with Length=1 DW, Byte Count=4, and original value 7. A 2-DW Request does not require a 2-DW Completion.

Section 2.2.9.1 specifies that AtomicOp Completion Byte Count equals the operand size and Lower Address is Reserved. Although the target's low seven address bits are 7Ch, do not use Lower Address to reconstruct this result. For a Non-Flit AtomicOp Request with TH=0, First/Last DW BE are also Reserved. Memory Read byte-enable and Split Completion calculations do not apply to this example.

How does DMWr retry differ from a CAS mismatch?

DMWr (Deferrable Memory Write, a non-posted write whose acceptance may be deferred) supports uses such as shared work queues. It requires a Completion but does not compare and exchange an operand. For a temporary condition, the completer may return Request Retry Status (RRS), leaving the target unchanged.

【模擬資料】Teaching assumptions, not measurements of a particular device or platform. A separate path and completer support DMWr, all required controls are enabled, and DMWr Requester Enable is 1. A first submission encounters a temporarily unavailable queue; the completer returns RRS without enqueuing the item. The requester may later submit a new Request under its implementation policy. A successful submission then proceeds according to the queue interface; acceptance of an item and completion of its work are separate events.

Can a timed-out CAS simply be sent again?

First identify the retry layer. Data Link Replay protects one transmission between adjacent partners and prevents duplicate delivery. A requester-generated new CAS causes another operation. See Chapter 8 for that distinction.

Completion Timeout records the requester's failure to receive a required response. For the preceding CAS, at least two timelines remain possible: the Request never reached the target, or the target performed the comparison and replacement but the requester did not receive the Completion. A requester-side Timeout alone cannot distinguish them.

Recovery therefore cannot treat an unconfirmed operation as unexecuted and blindly issue it again. Preserve the original Request, Requester ID/Tag, path traces, and error evidence, then follow the platform or device synchronization and recovery protocol. A later memory value may reflect other agents' updates and cannot replace the missing Completion. This is an analysis boundary derived from the response mechanism; Base 6.0 supplies no universal software-retry algorithm.

A normal SC also needs request-specific interpretation. CAS returns the original value to establish whether replacement occurred. A split Memory Read needs all required Completions. Section 2.8 timeout ranges detect abnormal conditions and must not estimate normal service latency. If a subsequent Request must follow observation of an AtomicOp at the completer, section 6.15.2 requires the requester to wait for its Completion before issuing that Request.

Atomicity applies to the target operation. For Root Ports supporting AtomicOps, section 6.15.3.1 additionally requires host-memory accesses on behalf of an AtomicOp to be atomic relative to processor/device accesses to that range and to preserve processor atomic-operation atomicity. The complete synchronization algorithm, publication ordering at other locations, and software memory attributes still require platform and CPU documentation; one CAS does not establish those conditions.

Reading route: §2.8 Completion Timeout Mechanism, pp.259–260; §6.15.2, p.774; §6.15.3.1, p.775. Replay versus software retry is applied here without repeating its state machines.

Are Locked Transactions the same mechanism?

Locked Transactions have different section 6.5.1 restrictions: only the Root Complex may initiate them; PCI Express Endpoints must not support locked accesses; new software must not cause locked accesses to I/O devices. They are not an unrestricted fallback for unsupported AtomicOps.
