先看本章的角色與路徑

AER（Advanced Error Reporting，進階錯誤回報）提供錯誤狀態、回報控制及相關紀錄。本章先走正常的錯誤回報路徑，再解釋遮罩與 DPC 隔離如何改變軟體看到的資訊。

前情提要：Chapter 5 的交易識別用來解讀有效的 Header Log；Chapter 7 的通知概念用來理解 Root 端如何把事件交給軟體。

規格路線：Figure 6-1 的分類 → Status／Mask／Severity → Figure 6-3 的回報路徑 → Root 紀錄 → 保存與清除 → DPC 分支。

PCIe 錯誤判讀需要串起偵測、回報、接收與隔離的證據。Status 記錄錯誤，不保證訊息送達；Source ID 識別回報者，不直接指出根本原因。本篇以 AER 與 DPC 的兩個獨立案例說明這些界線。

版本與假設

依 PCIe Base 6.0，所有值與事件順序均為作者設計，使用普通非 SR-IOV Function。AER 案例不支援 Flit Mode／End-End TLP Prefix，且未啟用 DPC；後面的 DPC 是另一事件。假設管理者有相應權限，讀取期間沒有未說明的新事件。

先建立從 Function 到 Root 的證據關係

Correctable Error 可由協定恢復，但可能影響效能。Uncorrectable Error 影響功能，並依嚴重程度分為 Non-Fatal／Fatal；Non-Fatal 不能解成工作已成功，Fatal 也不是某顆晶片損壞的直接診斷。AER 提供比基本錯誤回報更細的狀態、遮罩、嚴重程度與 Log；沒有 AER 不等於完全沒有錯誤回報。

依序查看來源 Function 的 Status、偵測當時的 Mask／Severity／Device Control、有效 Header Log，再到 Root Error Status／Source ID 比對。若可能有隔離，另查 DPC Status。不同時間的設定不能自動套回事發時刻。依據：§6.2.1–§6.2.4（pp.669–679）、Figure 6-1（p.670）。

清除前，先保存能互相比對的紀錄

作者建議先保存狀態、設定、FEP、有效 Log 與 Root／DPC 證據，並確認並行變化；多個 Register 的讀取不是自動原子快照。清除 FEP 指向的 Status 後，硬體可能換入下一筆 Log，所以先清再讀會破壞關聯。

啟用 Multiple Header Recording 且 FEP 有效時，規格建議依 FEP 逐筆處理，不清其他 Status；確定沒有 Header 的 masked error 有列明例外。PCI Status 與 AER Status 也不會互相連帶清除。依據：§6.2.4.2（pp.679–681，註腳 108）、§6.2.7.1（p.691）。

清掉通知後，Link 為什麼還沒有回來？

Figure 7-300 把 DPC Trigger Status 放在 bit 0，DPC Interrupt Status 放在 bit 3。兩者都能寫入 1 清除，但作用不同：bit 3 處理中斷狀態；bit 0 維持隔離，清除後才允許 LTSSM離開 Disabled，回到 Detect 嘗試建立 Link。

這裡刻意拆成兩次寫入，讓通知與隔離的差別容易看清楚；規格沒有要求每套軟體都採這個拆法。真正必須遵守的是釋放條件。也因此，不能把讀出的 0x000B 原樣寫回，當成只清中斷的操作：那會同時對 bit 3 與 bit 0 寫 1，連隔離也一起釋放。

下圖的等待分支接到 §6.2.11：軟體必須先讀到 Link Status 的 Data Link Layer Link Active=0，才能釋放 DPC；若過早清除，結果為 undefined（規格未定義）。本例是 Switch Downstream Port，DPC RP Busy 不適用；支援 RP Extensions 的 Root Port 則還須等待該 bit 為 0。

隔離期間又來一筆 Memory Read，誰回覆？

接著讀 §2.9.3 Transaction Layer Behavior During Downstream Port Containment。假設 Root Complex 送來一筆新的、格式合法的 Memory Read，原本應由 02:01.0 轉送到 03:00.0 的 BAR；它在 Port 已處於 DPC 時才提交給下游傳送路徑。這筆 Request 由 Port 丟棄，並由 Port 產生錯誤 Completion（交易回覆）。

為了知道回覆哪種錯誤，回到 Figure 7-299／Table 7-263：本例 DPC Control=0x000A，bit 2 的 DPC Completion Control=0，因此回覆 Completer Abort（CA，完成端中止）；若該 bit=1，才改回 Unsupported Request（UR，不支援的要求）。此 Completion 的 Completer ID 是 Downstream Port 02:01.0，因為這次由它終止 Request；前面 DPC Error Source ID 的 03:00.0 則是觸發隔離訊息的回報者。

在這個情境中收到 CA，是 Port 依 DPC 規則產生的結果，無法據此宣稱 Endpoint 已接受或執行該次讀取。若換成隔離前就已送出的 Request，且 DPC 使 Completion 無法回來，本例沒有 Root Port Extensions 的代回覆機制，Requester 仍可能遇到 Completion Timeout。新的 Request 如何被終止，與舊 Request 是否已完成，要分別追蹤。

解除隔離後，還有哪些恢復工作？

Table 7-264 說明，清除 DPC Trigger Status 後，Port 離開 DPC，LTSSM 必須回 Detect。這只是重新嘗試訓練；接著還要觀察 Link 與 Data Link 恢復，並依 §6.6.1 遵守 Conventional Reset（一般重設）之後首次 Configuration Read 的適用時序，才能繼續恢復設定與驅動程式。等待條件連回 Chapter 9，不在這裡重複全部 Reset 流程。

解除隔離也會改變紀錄的判讀條件：DPC Trigger Status=0 後，DPC Trigger Reason 已不再有效，應使用先前保存的快照分析本次事件。規格允許在釋放要求已滿足後清除 Trigger Status，不必等所有相關錯誤 Status 都變成 0；因此，清空整片錯誤紀錄並不是恢復的必要前提。裝置如何重建工作、處理先前在途資料及恢復應用服務，則仍須裝置、驅動與平台的恢復程序。

確認證據的限制

FEP=14，但 Status bit 14=0，還能用 Log 指認最新 Timeout 嗎？

不能，FEP 已無效。非零 Log 不能取代有效條件。依據：§6.2.4.2。

Status=0 能否證明從未發生錯誤？

不能；狀態可能已清除或重設，也須考慮偵測與實作條件。依據：§6.2.4.2、Table 7-135。
