TPH (TLP Processing Hints) conveys intended data use. LTR (Latency Tolerance Reporting) conveys service-latency needs. OBFF (Optimized Buffer Flush/Fill) tells endpoints when activity has a lower incremental platform power cost. Start with direction and purpose before decoding fields.

Locate steering information

Read Processing Hint mapping in Table 6-13, then Steering Tags in 6.17.2. A Steering Tag is a system-specific processing-resource hint, not a universal CPU number. Software discovers the supported mode and table location before programming tags. For a function, the table may be in the TPH Requester Extended Capability or combined with MSI-X, but not both. Basic memory-access controls remain unchanged.

Decode a valid latency requirement

Author example: Requirement=1, Value=10, Scale=010b in an LTR message. Figure 6-15 makes this 10×1,024 ns=10,240 ns. With Requirement=0, value/scale are ignored rather than decoded as a zero-latency requirement. Enable LTR only with RC and all intermediate-switch support, enabling closest to the Root Port first. The RC is strongly encouraged, not required, to honor reported worst-case service latency.

Use an activity hint without inventing a command

OBFF indicates low incremental platform power cost. CPU Active, OBFF, and Idle identify different platform availability. The endpoint combines those hints with buffering and workload needs. WAKE# and message forms have their own restrictions, and non-D0 functions must not respond to OBFF/CPU Active signaling. A hint is not a new access permission or a mandatory immediate action.
