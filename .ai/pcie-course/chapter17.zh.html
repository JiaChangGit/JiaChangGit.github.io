credit、Ack 和 Completion 各自在哪一步發生？

選擇步驟後，圖中對應的元件與下方解說會加上重點標示。完整圖與所有解說會持續顯示；也可用方向鍵切換步驟。

先追蹤一筆普通非 Flit 傳輸，再分別看確認訊息與空間回報。兩條回報路徑不是固定先後的時序。

FC（Flow Control，流量控制）確認相鄰接收端有空間；重送機制處理 Link 上的資料傳輸錯誤；Completion（完成回覆）則回到交易本身。這一章把三者放在同一條路徑，從發送前的空間檢查，走到接收、回報與後續處理。

  1. 傳送前先確認接收空間

    圖中一條 Link 的可用空間，不代表最終目的端已接收或處理這筆交易。

    FC（傳送前檢查相鄰緩衝資源的機制）逐 Link 追蹤 credit。要求還沒送出前，發送端就必須確認對方有足夠的標頭與資料接收資源。

    Base 6.0 §2.6，pp.235–237。

  2. 在這一條 Link 檢查完整性

    LCRC（Link Cyclic Redundancy Check，鏈結循環冗餘檢查）保護單一 Link；Flit 模式改在 Flit 層重送，不使用這組 Ack／Nak DLLP。

    普通非 Flit 傳輸由序號與 LCRC 檢查，接收端回 Ack 或 Nak；傳送端保留副本以供重送。

    Base 6.0 §3.6.2、§3.6.3，pp.288、300。

  3. 釋放空間後更新資源

    交易是否完成仍依要求種類與完成回覆判讀，不能由一個 Ack 或 UpdateFC 判定。

    接收資料往前處理，空出的緩衝由流量控制更新回報。重送同一筆資料由鏈結層處理，交易層不會每次重送再消耗一份新 credit。

    Base 6.0 §2.6，pp.235–236。

一筆寫入到底要用哪些 credit？

先用 Table 2-44 把資源分成 Posted、Non-Posted、Completion 三類，再各分 Header（標頭）與 Data（資料），得到六種追蹤。接著到 Table 2-45 找具體要求種類。一般 Memory Write 使用 PH 與 PD；Memory Read 要求使用 NPH，它回來的資料另使用 CplH 與 CplD。

作者案例：假設普通非 Flit Memory Write 帶 20 bytes 資料。資料 credit 一單位為 4 DW，也就是 16 bytes，因此要 1 PH 與向上取整的 2 PD。即使還有很多資料 credit，只要 PH 不足，發送端仍須等待足夠的標頭資源。數值只示範分類與取整，不代表某裝置的實際緩衝容量。

Ack 成功，為什麼仍可能需要端到端檢查？

LCRC（保護相鄰鏈結傳輸的循環冗餘檢查）與序號能處理單一 Link 上的損壞或遺失。可是封包還要穿過 Switch 內部，之後才到下一條 Link；內部產生的損壞不一定會被每段鏈結的檢查抓到。§2.7 因此另外定義 ECRC（End-to-End CRC，端到端循環冗餘檢查）。

ECRC（由來源產生、供端到端檢查的摘要）涵蓋沿途不變的欄位，是否產生與檢查有能力及啟用條件。Data Poisoning（資料已知不可靠的標記）又是另一種資訊：它讓消費資料的一方知道資料有問題，並非替資料修復。實際錯誤處理接回 Chapter 12。

改成 Flit 模式後，要換哪一段模型？

在 Flit 模式，重送單位改成 Flit，完整性資訊包含 Flit 的 LCRC、FEC（Forward Error Correction，前向錯誤更正）與序號。§3.6.3 前的規則明確說明：不再用 Ack／Nak DLLP 做重送確認。下一章會拆開 Flit 的內容與保護方式。

流量控制仍追蹤交易資源，但還可能使用 Shared FC（共享流量控制）與專用 credit。先辨識模式與協商出的功能，再選對資源模型；不能把上圖普通非 Flit 的每條箭頭原封不動套上去。

空間已釋放，為何發送端還要等？

釋放空間到送出 UpdateFC 需要時間，線路傳送與對端接收也有延遲。Appendix H 用有效資料上限、封包額外開銷、Link 寬度等項目，說明更新延遲數值的由來。它是資訊性附錄，不能把其中公式改稱每個實作都必須使用的內部演算法。

實際追蹤停頓時，先問缺的是哪類 credit，再看更新是否已發送及到達。若根本是重送等待，則回到序號、確認與重送緩衝，不要把它記成接收端空間不足。
