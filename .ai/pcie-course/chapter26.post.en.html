Several Functions may share one Link while retaining distinct Transaction identities and resources. This chapter follows one SR-IOV (Single Root I/O Virtualization) case from ARI interpretation through RID/BAR allocation, readiness, memory decoding and Reset, then distinguishes Shadow Functions.

Identify the participants and assumptions

Use the Port/Link model in Chapter 1 and allocation background in Chapter 4. Root Port → Switch → Endpoint has two Links. The single Endpoint Port serves one PF and three VFs to be created. Configuration, Transaction identity and resources belong to individual Functions; speed, width and LTSSM belong to their shared Link.

Simulated data: topology, fields and timings are author-created, not hardware measurements. PF RID=0300h is the lowest-numbered PF and is in D0. Software is ARI-aware; sufficient Bus Numbers and upstream resource Windows are available, with no conflicting Function identities. Initially VF Enable=0 and VF MSE=0. This case has no VF Resizable BAR, FRS support, or shorter reported/platform VF Enable Time.

Does 0314h mean Device 2, Function 4, or Function 20?

Section 6.13 divides a conventional 16-bit RID (Routing ID) into Bus [15:8], Device [7:3] and Function [2:0]. ARI (Alternative Routing-ID Interpretation) instead interprets the low byte as an 8-bit Function Number without increasing RID width. Thus 0314h conventionally displays as Bus 03h/Device 02h/Function 04h, but means Bus 03h/Function 14h, decimal20, for this ARI Device. ARI does not itself create VFs; creation remains controlled through the associated PF's SR-IOV Control.

Figure 6-13 identifies the Switch Downstream Port immediately above the Endpoint. Check its Device Capabilities 2.ARI Forwarding Supported [5] and Device Control 2.ARI Forwarding Enable [5]; both are set here. An ARI Endpoint below the Switch does not require enabling every ancestor Port.

In the Device, find ARI Extended Capability ID=000Eh, Version=1. Table 7-157's Next Function Number links non-VF Functions from Function 0. For VFs that field is undefined: use First VF Offset/VF Stride instead. Shadow Functions do not enter this list either.

The PF's ARI Capable Hierarchy is a separate hint that the immediately upstream Downstream Port has ARI enabled. Software should match it to that Port's ARI Forwarding Enable; it is set here. It resides in the lowest-numbered PF and affects the Device. Do not change it while any PF has VF Enable set; it does not replace the Port's forwarding control.

Find VF 3's memory range independently

Figure 9-9 separates the PF's ordinary BAR from the VF BAR in its SR-IOV Capability. A VF's own Type0 Header BARs are hardwired zero. Configure the group through the PF's VF BARs, not by programming a separate Header BAR in each VF.

After selecting the 64 KiB System Page Size, sizing the 64-bit Prefetchable VF BAR0/1 pair returns low DW=FFFF000Ch and high DW=FFFFFFFFh. Remove the low four attribute bits to obtain address mask FFFFFFFFFFFF0000h. Invert across 64 bits and add 1: each VF aperture is 10000h=64 KiB.

Hardware reflects the greater requirement of System Page Size and VF BAR Size. This optional mechanism is not used in the numeric case.

VF Enable does not permit immediate BAR access

Separate initialization waiting, Configuration readiness and Memory decoding. Assume unlisted Control bits are zero and keep ARI Capable Hierarchy [4] set: 0010h is disabled, 0011h has VF Enable=1/VF MSE=0, and 0019h additionally sets VF MSE [3]. After enabling, Requests to the VFs must wait until at least 100 ms, a PF FRS (Function Readiness Status) Message with reason VF Enabled, or the applicable reported/platform VF Enable Time. The case has no early alternatives, so no Configuration Request is sent at 50 ms.

At 120 ms the VF returns Configuration RRS (Request Retry Status). Such retry status is permitted within the 1.0 s interval after VF Enable, and the RC/software must allow at least 1.0 s before declaring a VF broken for not returning Successful Completion to a valid Configuration Request. Each RRS does not restart that interval.

At 180 ms SC (Successful Completion) establishes one Memory-readiness condition. VF MSE remains clear, so Memory access is still disabled. At 181 ms Control=0019h enables decoding; with Function-specific initialization also complete, the example accesses VF 3 at 90020010h. Other specified FRS,1.0 s or applicable reported/platform VF Enable Time paths can establish Memory readiness. Simply waiting100 ms is not equivalent to those conditions.

After a VF has successfully responded to a Request, it must not return Configuration RRS without an intervening disable or other valid Reset. Clearing VF Enable destroys VFs; no field in the PF's SR-IOV Capability may then be accessed until at least 1.0 s has elapsed or a PF FRS Message with reason VF Disabled is received. Do not immediately poll Control or rewrite NumVFs.

FFFFh Vendor ID and clear MSE have VF-specific meanings

Unlike ordinary Function probing, §§7.5.1.1.1–7.5.1.1.2 require a VF's raw Vendor ID and Device ID to return FFFFh. Virtualization software should present its PF's Vendor ID and the PF's VF Device ID field respectively. At the 180 ms read, first inspect the SC Completion, then interpret FFFFh using the VF-specific rule rather than an ordinary absence shortcut.

A VF's Command.Memory Space Enable is ROZ (Read Only Zero). The PF's VF MSE controls Memory decoding for the associated Active VFs. I/O Space Enable is also hardwired zero; VFs do not support I/O Space. A VF's own Bus Master Enable instead controls its ability to initiate Memory Requests. That direction differs from host access to VF resources; PF BME does not represent every VF.

Once their individual Bus Master Enable and device conditions are satisfied, two VFs may issue Memory Reads with Tag 05h. Match returned Completions using Requester IDs0310h and 0312h as well as Tag; equal Tags do not make one Transaction. A healthy shared Link does not establish each Function's resource, BME, Transaction or device-initialization state.

For interrupt details return to Chapter 7. With allocated resources VFs may use MSI, MSI-X or both, but must not implement INTx. Internal allocation, scheduling and VM assignment remain platform/device policy.

Why can a Shadow identity issue Requests without independent Configuration?

Shadow Functions borrow Requester ID/Tag resources of otherwise unimplemented Functions to extend a Requester's Outstanding Request capacity. Characteristics come from the associated Function; this does not create another assignable VF. Locate ID=002Dh, Version=1, then use Figure 7-365 and Tables 7-320–7-322.

Continuing the simulated case: assume PF 0300h implements one Shadow Function and 0320h is otherwise unused. Number of Shadow Functions=0 is N−1 encoded, hence one Instance. The first entry atH+0Ch contains Shadow Function Number=0020h, a16-bit BDF offset. Add 0300h+0020h=0320h; it is not an absolute Function Number replacement.

Assume translation/access-control resources have been prepared, Phantom Functions Enabled=0, and no Outstanding Non-Posted Requests before enabling Shadow Functions. Changing its Enable while such Requests are outstanding, or enabling it together with Phantom Functions, has undefined behavior.

Requester ID 0320h may now issue Memory Read. Ordinary Posted Requests are also permitted, but MSI/MSI-X Requests must not use Shadow Transaction ID resources. Configuration access to 0320h, absent errors with other behavior, must return UR rather than independent Configuration Space. This differs from a created VF returning SC with FFFFh ID fields.

A Shadow Function Number greater than 7 requires ARI; without ARI the Shadow must remain in the same Device. Software must update translation resources before Requests, otherwise behavior is undefined. Relate the identity back to its PF/Capability while still considering its separate RID throughout the path.
