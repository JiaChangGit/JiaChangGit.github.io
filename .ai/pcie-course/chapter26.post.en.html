SR-IOV (Single Root I/O Virtualization) lets system images share device resources. A PF (Physical Function) manages associated VFs (Virtual Functions). Each VF has a Routing ID and resource aperture; calculate identity and address separately before enabling use.

Calculate the third VF identity

Configure NumVFs and applicable ARI Capable Hierarchy first, then read First VF Offset and Stride because those values may change with configuration. Table 9-1 computes VF N as PF RID + First VF Offset + (N−1)×Stride, using unsigned 16-bit arithmetic. RID means Routing ID. In an author-valid configuration, PF RID=0300h, offset=0010h, stride=0002h, and three VFs yield RIDs 0310h, 0312h, and 0314h. Deployment must also ensure unique IDs and available bus-number space.

Calculate a VF aperture separately

A VF BAR in SR-IOV describes the per-VF aperture. The first VF uses the configured base; each subsequent VF advances by one aperture, as Figure 9-9 shows. Continuing the author example, base 90000000h and per-VF size 10000h put VF 3 at 90020000h. This address is unrelated in units to its RID 0314h. Reserve the full range and select a System Page Size from supported sizes.

Distinguish ARI, VFs, and shadow resources

ARI (Alternative Routing-ID Interpretation) reinterprets the traditional Device/Function portion as an eight-bit function number. ARI (the alternate ID interpretation) does not create VFs. Shadow Functions use the transaction-ID resources of otherwise unimplemented functions to support more outstanding requests; they inherit the associated function’s characteristics rather than becoming independent VFs. VF Resizable BAR is also distinct from a PF’s normal Resizable BAR.
