Preserve evidence along an error-reporting path

AER (Advanced Error Reporting) supplies error status, reporting controls and related records. Follow normal error reporting before comparing masked errors and DPC containment. Chapter 5 provides transaction context and Chapter 7 provides notification context.

Specification route: Classification in Figure 6-1 → status, mask and severity → reporting in Figure 6-3 → root records → preservation and clearing → DPC.

PCIe error analysis connects detection, reporting, reception, and containment. Status does not prove that a message arrived; Source ID identifies a reporter rather than the physical root cause. Two separate AER and DPC examples show how to respect those boundaries.

Version and assumptions

Based on PCIe Base 6.0. All values and event sequences are author-created, using ordinary non-SR-IOV Functions. The AER example supports neither Flit Mode nor End-End TLP Prefixes and has DPC disabled. The later DPC example is a separate event. The manager has appropriate ownership, and no unspecified concurrent events occur.

Connect evidence from the Function to the Root

Correctable Errors can be recovered by the protocol but may affect performance. Uncorrectable Errors affect functionality and are classified Non-Fatal or Fatal. Non-Fatal does not establish successful work, and Fatal does not directly diagnose a failed chip. AER adds detailed status, masks, severity, and logs to baseline reporting; absence of AER does not imply absence of all reporting.

Inspect source Status, the Mask/Severity/Device Control settings at detection, valid Header Logs, and then Root Error Status/Source ID. Check DPC separately if containment is possible. Later configuration reads do not automatically reconstruct earlier settings. Sources: §6.2.1–§6.2.4 (pp.669–679), Figure 6-1 (p.670).

Preserve correlated records before clearing

The author recommends saving status, configuration, FEP, valid logs, and Root/DPC evidence while checking for concurrency. Separate register reads are not automatically an atomic snapshot. Clearing the status indicated by FEP can advance hardware to another log, destroying the original association if done before capture.

With Multiple Header Recording enabled and valid FEP, the specification recommends processing records through FEP rather than clearing unrelated status; it lists an exception for masked errors known to lack recorded headers. PCI Status and AER Status are also cleared independently. Sources: §6.2.4.2 (pp.679–681, footnote 108), §6.2.7.1 (p.691).

Why does the Link remain down after acknowledging the interrupt?

Figure 7-300 places DPC Trigger Status in bit 0 and DPC Interrupt Status in bit 3. Both clear on a write of 1, but they have different effects: bit 3 handles interrupt status; bit 0 keeps containment active. Clearing bit 0 permits the Link Training and Status State Machine (LTSSM) to leave Disabled and return to Detect to attempt Link establishment.

Simulated data: this teaching scenario does not represent a particular device or platform. Continue the separate DPC event above: 02:01.0 received ERR_NONFATAL from 03:00.0 and DPC Status reads 0x000B. This example saves evidence, clears only interrupt status, and then waits for containment-release conditions. The upstream management path to the Switch remains available; the disabled Link is the one from 02:01.0 to 03:00.0. No new DPC event or concurrent software write occurs.

Writing the read value 0x000B back is not an interrupt-only acknowledgment: it writes 1 to both bit 3 and bit 0, releasing containment as well.

The waiting branch below follows §6.2.11: software must observe Data Link Layer Link Active=0 in Link Status before releasing DPC. Releasing it earlier has undefined results. DPC RP Busy is Reserved on this Switch Downstream Port; a Root Port supporting RP Extensions must additionally wait for that bit to read 0.

Who responds to a new Memory Read during containment?

Follow §2.9.3, Transaction Layer Behavior During Downstream Port Containment. Assume the Root Complex sends a new, valid Memory Read targeting a BAR in 03:00.0 through 02:01.0. It is submitted for downstream transmission after the Port is already in DPC. The Port discards this Request and generates an error Completion.

Figure 7-299 and Table 7-263 determine the status: DPC Control=0x000A has DPC Completion Control, bit 2, cleared, so the response is Completer Abort (CA). Setting that bit instead selects Unsupported Request (UR). The Completion's Completer ID identifies Downstream Port 02:01.0, which terminates this Request. The earlier DPC Error Source ID of 03:00.0 identifies the sender of the message that triggered containment.

CA in this scenario comes from the Port's DPC handling; it does not establish that the Endpoint accepted or executed the read. A Request transmitted before containment, whose Completion is prevented from returning by DPC, is a different case. Without the Root Port Extensions completion-synthesis mechanism in this example, its Requester may encounter Completion Timeout. Track termination of the new Request separately from completion of earlier work.

What remains after containment is released?

Table 7-264 requires the Port to leave DPC and the LTSSM to transition to Detect when DPC Trigger Status clears. Training is only being attempted. Software still observes Link and Data Link recovery, honors the applicable §6.6.1 timing for the first Configuration Read following Conventional Reset, and restores configuration and driver operation. Chapter 9 covers the reset and readiness conditions.

Release changes log interpretation too: DPC Trigger Reason is invalid when DPC Trigger Status is clear, so analyze this event using the saved snapshot. Once release requirements are met, the specification permits clearing Trigger Status regardless of other status bits associated with the triggering event. Clearing every error record is therefore not a prerequisite for release. Rebuilding device work, resolving earlier outstanding data and restoring application service still require device, driver and platform recovery procedures.

Check the evidence limits

Can FEP=14 identify the latest Timeout when Status bit 14 is clear?

No. FEP is invalid; a nonzero log cannot replace the validity condition. Source: §6.2.4.2.

Does Status=0 prove an error never occurred?

No. Status may have been cleared or reset, and detection and implementation conditions also matter. Sources: §6.2.4.2, Table 7-135.
