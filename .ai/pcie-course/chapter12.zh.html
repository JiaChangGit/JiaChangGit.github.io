1. 一個錯誤訊息，能告訴我們多少事情？

Correctable Error 表示協定可自行恢復的錯誤，仍可能降低效能；Uncorrectable Error 則影響功能，並分為 Non-Fatal 與 Fatal。Non-Fatal 不等於工作已成功，Fatal 也不是「一定已損壞某顆晶片」的硬體診斷。這些分類提供回報與處理政策所需的嚴重程度。

本例 Severity bit 14=0，Completion Timeout 被設定為 Non-Fatal；bit 18=1，Malformed TLP 被設定為 Fatal，但後者已 Mask。Device Control bit 1=1 允許 Non-Fatal 回報，所以在本例前提下，Completion Timeout 產生 ERR_NONFATAL。Device Control bit 2 也開啟 Fatal 回報，仍不會解除個別 Malformed TLP Mask。這是明確設定後的快照，不宣稱 Severity 值是重設預設值。

3. Header Log 看起來像封包，就能直接解碼嗎？

先檢查有效性。Advanced Error Capabilities and Control 的低五位為 0x0E，也就是 First Error Pointer（FEP）=14；它指向 Uncorrectable Error Status 的 bit 14。本例該 bit=1，因此 FEP 有效，對應 Completion Timeout。不是看到 Log 非零，就能認定它屬於目前關心的事件。

Completion Timeout 也不能一律期待有 Request Header。本例 bit 12=1，表示 Completion Timeout Prefix/Header Log Capable；Multiple Header Recording Capable／Enable bits 9、10 均為 0。再加上沒有 Flit／End-End Prefix，這才得到本例的四個 DWORD Log 容量與解讀前提。

5. 為什麼不能一開始就把所有 Status 寫 1 清掉？

因為清除不只是讓畫面乾淨。當軟體清掉 FEP 所指的錯誤時，硬體可能更新下一筆 Header 與 FEP；若先清除再讀 Log，就可能把兩個時間點的資料拼成同一個事件。

  1. 先記下管理對象、時間與當時設定；保存相關 AER Status、Mask、Severity、FEP、有效 Log，以及 Root／DPC 的對應證據。
  2. 依 FEP 與能力確認 Log 的格式及有效範圍；若資料可能並行變動，重新核對關聯，不能假定多個 Register 的讀取是原子快照。
  3. 完成該筆紀錄處理後，才對相應 RW1CS bit 寫 1。若啟用 Multiple Header Recording，依 FEP 逐筆處理，再重新讀狀態。

前兩步是作者整理的蒐證方式；第三步的硬體清除語意來自規格。Base 6.0 建議在多筆 Header 記錄啟用且 FEP 有效時，不要清除 FEP 以外的 Status bit；規格也列有確定沒有 Header 紀錄的 masked error 例外。它不是一條「所有錯誤情境都一次寫固定遮罩」的操作口訣。

另外，清 PCI Status 不會連帶清 AER Status，反方向也一樣。對照不同紀錄時，須記下是哪個 Register 在什麼時候被清除。

6. 如果啟用 DPC，為什麼 Root 可能看不到原本的 ERR_NONFATAL？

以下換成另一個事件案例。02:01.0 的 DPC Extended Capability 位於 0x300；這是一個 Switch Downstream Port，不使用 Root Port Extensions。Downstream Port Containment（DPC）可在觸發後停止下游 PCIe 流量，使問題先被限制在受影響的分支。

Trigger Enable=10b 表示 Port 自己偵測到未遮罩的 Uncorrectable Error，或收到 ERR_NONFATAL／ERR_FATAL 時可觸發。Reason=(0x000B >> 1) & 3 = 1，所以本次原因是收到 ERR_NONFATAL；此時 Source ID 才具有這裡要用的意義。若 Reason=00b 表示 Port 自己偵測到錯誤，就不能照用 Source ID 猜來源。

觸發 DPC 的這個 ERR_NONFATAL 會被 Port 丟棄，不再往上游轉送。DPC 可另外以中斷或 ERR_COR 通知管理者，但本例 DPC ERR_COR Enable=0，只啟用 DPC 中斷；中斷是否到達仍要看向量與平台設定。因此不能要求 Root AER 一定同時出現上一節的 0x24 快照。

隔離期間又來一筆 Memory Read，誰回覆？

接著讀 §2.9.3 Transaction Layer Behavior During Downstream Port Containment。假設 Root Complex 送來一筆新的、格式合法的 Memory Read，原本應由 02:01.0 轉送到 03:00.0 的 BAR；它在 Port 已處於 DPC 時才提交給下游傳送路徑。這筆 Request 由 Port 丟棄，並由 Port 產生錯誤 Completion（交易回覆）。

為了知道回覆哪種錯誤，回到 Figure 7-299／Table 7-263：本例 DPC Control=0x000A，bit 2 的 DPC Completion Control=0，因此回覆 Completer Abort（CA，完成端中止）；若該 bit=1，才改回 Unsupported Request（UR，不支援的要求）。此 Completion 的 Completer ID 是 Downstream Port 02:01.0，因為這次由它終止 Request；前面 DPC Error Source ID 的 03:00.0 則是觸發隔離訊息的回報者。

在這個情境中收到 CA，是 Port 依 DPC 規則產生的結果，無法據此宣稱 Endpoint 已接受或執行該次讀取。若換成隔離前就已送出的 Request，且 DPC 使 Completion 無法回來，本例沒有 Root Port Extensions 的代回覆機制，Requester 仍可能遇到 Completion Timeout。新的 Request 如何被終止，與舊 Request 是否已完成，要分別追蹤。

解除隔離後，還有哪些恢復工作？

Table 7-264 說明，清除 DPC Trigger Status 後，Port 離開 DPC，LTSSM 必須回 Detect。這只是重新嘗試訓練；接著還要觀察 Link 與 Data Link 恢復，並依 §6.6.1 遵守 Conventional Reset（一般重設）之後首次 Configuration Read 的適用時序，才能繼續恢復設定與驅動程式。等待條件連回 Chapter 9，不在這裡重複全部 Reset 流程。

解除隔離也會改變紀錄的判讀條件：DPC Trigger Status=0 後，DPC Trigger Reason 已不再有效，應使用先前保存的快照分析本次事件。規格允許在釋放要求已滿足後清除 Trigger Status，不必等所有相關錯誤 Status 都變成 0；因此，清空整片錯誤紀錄並不是恢復的必要前提。裝置如何重建工作、處理先前在途資料及恢復應用服務，則仍須裝置、驅動與平台的恢復程序。

7. 先保存，再逐項解讀錯誤

AER Status=0，是否足以證明從開機至今都沒有錯誤？

不足。紀錄可能已被清除或重設，部分欄位也取決於實作與偵測條件。應先確認蒐證時間範圍與清除紀錄。依據：§6.2.4.2、Table 7-135。

FEP=14，但 Status bit 14 已清除，仍可把 Header Log 當成最新 Timeout 嗎？

不可以。FEP 此時無效；Log 看起來合理並不能補足有效性條件。依據：§6.2.4.2、Table 7-140。

DPC Source ID=03:00.0，能否斷言 03:00.0 的硬體必須更換？

不能。先確認 Trigger Reason 允許解讀 Source ID；即使有效，也只識別觸發訊息的回報者。還需交易、相鄰元件與平台證據才能判斷原因。依據：Table 7-265。
