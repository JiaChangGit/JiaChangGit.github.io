Function Level Reset (FLR) resets one Endpoint Function while preserving the shared Link and other ordinary Functions. Software quiesces work, handles outstanding traffic, triggers reset, waits for readiness, and restores the settings needed to resume work.

Version and example

Base 6.0. Ordinary Functions 03:00.0 and 03:00.1 share a Link to 02:01.0, without Single Root I/O Virtualization (SR-IOV). Read values and times are authored assumptions; PCI Express Capability is at 0x70.

Follow the normal reset sequence

Chapters 6–8 established memory access, interrupt notification, and Link operation. Here, keep that Link running while rebuilding the target Function. The reading route follows the software task: Figure 7-24 for support, Figure 7-26 for outstanding traffic, Figure 7-25 for the trigger, then §6.6.2 for waiting and restoration.

  1. Check Function Level Reset (FLR, the per-Function mechanism) support in Device Capabilities bit 28.
  2. Coordinate other accessors, stop new work, and handle existing Requests. The example in the implementation note on p.727 clears Command and checks Transactions Pending, which tracks outstanding Non-Posted Requests requiring Completions.
  3. Write Initiate FLR in Device Control. The Function completes this Configuration Write before starting reset.
  4. In this example, wait 100 ms, then attempt Configuration access. If subsequent initialization still needs time, Request Retry Status (RRS) tells software to retry later. Satisfy any remaining old-transaction wait before initialization.
  5. Restore fields by their access rules, rebuild the device interface and notification path, then resume work.

The following sections explain the field values and exceptions along this route.

Stopping new Requests does not remove old Completions

Bus Master Enable (BME)=0 does not recall Requests already sent. Transactions Pending tracks this Function's Non-Posted Requests, which may complete or terminate through timeout. It does not cover all Posted Writes, CPU accesses, or external work, and FLR completion itself must clear it.

In the authored scenario, FLR occurs before an old Memory Read (MRd) with transaction Tag=0x13 returns. Immediate Tag reuse could misassociate a late Completion with a new transaction. Software must coordinate other accessors, stop device work and Direct Memory Access (DMA) and interrupt activity, then handle outstanding transactions. The p.727 Implementation Note offers an algorithm that clears Command and polls Pending or waits sufficiently before FLR; it does not replace device-specific quiescence.

FLR completion, readiness, and old-transaction waits are separate

The initiating Configuration Write must receive its Completion before FLR starts. The Function must complete FLR within 100 ms, but subsequent device-specific initialization can take longer. If it still needs initialization after that limit, it must return Request Retry Status (RRS) for Configuration Requests. After returning a non-RRS Completion, it cannot return RRS again until another reset.

If Transactions Pending=1 at initiation, software must allow old Completions to arrive or reach reasonable certainty that they will not arrive before initialization. Using the pre-FLR Completion Timeout is recommended. If timeout was disabled, the delay is system dependent but at least 100 ms. Function Readiness Status (FRS) Configuration-Ready can permit earlier Configuration access without proving all prior Requests completed. Requests during FLR may be silently discarded; arbitrary memory-mapped I/O (MMIO) polling is not a standard completion indication.

Conventional Reset uses different timing origins. Without Device Readiness Status (DRS) or another applicable early-readiness exception, a Downstream Port supporting above 5 GT/s requires at least 100 ms after Link training completes. Authored example: reset ends at t=0 ms, training finishes at t=40 ms, and the first Configuration Request is no earlier than t=140 ms. The corresponding branch for a Port supporting only up to 5 GT/s counts from reset exit. Without Readiness Notifications, at least 1 s after Conventional Reset exit must be allowed before declaring failure from missing Successful Completion; this is distinct from first-access timing.

Restore fields by meaning, not by replaying a dump

FLR clears request-enabling controls such as BME and Message Signaled Interrupts (MSI) Enable, while preserving explicitly listed Max_Payload_Size, Active State Power Management (ASPM) Control, Read Completion Boundary (RCB), hardware-initialized (HwInit), and sticky fields. Link state machines and Virtual Channel 0 (VC0) remain intact. §6.6.2 contains the full exception list, including additional Flit-capable requirements. Sticky does not mean preserved across every power/reset condition.

Recovery must distinguish read-only (RO), read/write-one-to-clear (RW1C), trigger controls, and writable settings. Rebuild necessary resources, device interfaces, interrupts, and DMA conditions before restarting work. FLR does not clear host buffers for software, and PCIe Base does not define every device's queue reconstruction.

Check the scope

Does a lack of Link retraining mean FLR failed?

No. FLR must not affect the Link. Check the Function's reset and recovery conditions.

Can all DMA buffers be reclaimed when Pending=0 after FLR?

No. Old-transaction waits, quiescence, coordination with other accessors, and platform DMA lifetime rules still matter.
