Connect a device resource to the CPU access path

A BAR (Base Address Register) describes a device resource and its allocation interface. Determine type and size, allocate an aligned base, cover the range with every bridge window, then enable the applicable decoding.

Specification route: Figures 7-10–7-12 and Table 7-9 → bridge-window rules and Figure 7-14 → Command controls in Figure 7-5 and Table 7-4.

Discovering a Function is followed by resource allocation and forwarding setup. BARs describe the Endpoint's own resources, Bridge Windows determine which address ranges reach downstream, and Command bits control permitted accesses. All three must be consistent.

Versions and assumptions

Fields follow Base 6.0; address views and handoff follow PCI Firmware 3.3, which is not its matching edition. The example is an ordinary Type 0 PCI Express Endpoint, not a VF, without Enhanced Allocation or Resizable BAR. Values are author-created, with no hardware operation. During sizing the driver is not using the device, no transactions are outstanding, and MSE/BME are clear. Software saves original BARs and confirms configuration write completion. Printed and PDF page numbers coincide.

Identify the format before calculating size

A BAR resides in Configuration Space; it is not a workload buffer. A Type 0 Header has six DWORD locations, and a 64-bit BAR consumes two consecutive locations. A Bridge's Type 1 Header has only two BAR locations, distinct from its downstream Memory Windows.

A Memory BAR has bit 0 clear; bits 2:1 encode 32-bit as 00b and 64-bit as 10b, with Prefetchable in bit 3. An I/O BAR has bit 0 set and address bits beginning at bit 2, so the Memory BAR's four-bit mask does not apply. This example uses no I/O BAR: an ordinary PCIe Endpoint must not depend on OS allocation of I/O resources and must not generate I/O Requests.

Prefetchable expresses permitted behavior such as reads without side effects and tolerance of write merging, not current CPU cache state. A Prefetchable BAR on this ordinary Endpoint must support 64-bit addressing; a non-Prefetchable BAR may be 32-bit.

Size probes require the correct 32-bit or 64-bit width

The specified method disables the corresponding decoding, saves the original BAR, writes all ones, reads it back, and masks the encoding bits. Invert and add one within the intended width. Restore the original value, or establish a consistent new allocation before re-enabling decoding. Clearing BME does not remove earlier outstanding transactions; their absence is a separate assumption here.

MSE and BME control different behavior

Command is a 16-bit Register at 0x04. Bit 0 controls I/O Space, bit 1 MSE controls received Memory accesses, and bit 2 BME controls Function-originated Memory/I/O Requests. A Type 1 Port's BME also controls forwarding those Requests upstream, without blocking Completions.

With resources, windows, platform mapping, and the device interface ready, Command=0x0002 on the Endpoint and all three Bridges permits the example's CPU MMIO read while prohibiting Endpoint-originated DMA Memory Requests. BME does not block the read's Completion. BME=0 also prohibits MSI/MSI-X because they use in-band Memory Writes.

Changing the Endpoint to 0x0006 adds permission to originate the relevant Requests, but does not prepare buffers, device work, platform translation, or upstream Port BME. Do not update Command by blindly writing back a DWORD that includes Status at 0x06, since Status contains RW1C bits.

Why can Configuration Space be readable while a Memory Read fails?

Configuration access selects a Function and Register using BDF and an offset; a Memory Read selects its target by memory address. In the existing example, place 0x80004120 inside BAR0 and each Bridge Window, then inspect Memory Space Enable (MSE) along the receiving direction.

Is every byte inside a BAR readable?

The BAR defines an address range, while the device interface defines which Registers can be used. The example assumes only that +0x120 is a readable Register; it does not define +0x3000, although that offset is also inside BAR0. Base 6.0 §7.5.1.2.1 (p.930) permits a Function to return UR for unused locations its programming model never accesses. The device interface and transaction evidence are needed to assess an actual access.

Keep allocation and handoff conclusions separate

Firmware 3.3 §3.5 (pp.34–35) uses I/O/Memory Enable and ROM Enable to determine corresponding resource configuration, not BME to establish BAR validity. Enabled resources must be correctly configured by firmware, but drivers still prepare device-specific work.

Can the 16 KiB BAR move to 0x80005000?

No. Its lower 14 bits are not all zero, violating natural alignment. The example's 0x80004000 base meets the requirement. (§7.5.1.2.1, p.930.)

Do correct windows permit a successful MMIO read when Endpoint MSE is clear?

Success cannot be expected. With MSE clear, the Endpoint handles received Memory Space accesses as UR. A forwarding path does not replace target enablement. (Table 7-4, p.918.)
