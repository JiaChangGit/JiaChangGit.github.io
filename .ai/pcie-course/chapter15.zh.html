要求到了接收端，什麼時候才算完成？

圖中兩條分支代表不同要求種類。先把其中一種要求走完，不把兩種操作接成同一次交易。

前章已能定位 TLP（Transaction Layer Packet，交易層封包）的欄位。現在沿接收端追蹤：先檢查封包，再決定目標是否接受。AtomicOp（Atomic Operation，原子操作）與 DMWr（Deferrable Memory Write，可延後的記憶體寫入）都有完成回覆，但各自保證的操作與回覆狀態不同。

    鏈結層已驗過的封包，也可能在交易層出現格式或語意錯誤。

    Figure 2-81 的入口在資料鏈結層完整性檢查之後。交易層仍要判斷封包是否合法，再分成要求與完成回覆。

    Base 6.0 §2.3，pp.204–205。

  2. 正常操作按要求種類執行

    兩者均須先確認路徑與端點的相應能力，不由封包有編碼推定全系統支援。

    原子操作在目的位置完成讀改寫並回傳原值；可延後寫入可讓接收端針對暫時條件回覆重試狀態。

    Base 6.0 §6.15，pp.772–774；§6.32，pp.857–858。

  3. 由回覆結果接續後續工作

    Completion Timeout（完成回覆逾時）的範圍不是正常服務延遲，不能拿它估算一般效能。

    要求者收到成功或其他完成狀態後，按該種類的語意處理。若一直收不到必要回覆，才進到完成逾時與恢復。

    Base 6.0 §2.8，p.259。

鏈結收到資料，為什麼還不能直接執行？

沿 Figure 2-81 閱讀時，先停在 §2.3 的入口：資料鏈結層已驗證完整性，交易層才接手處理。接著核對標頭、保留欄位與格式規則，再依 Type 分流。Malformed TLP（格式錯誤封包）必須丟棄；後續的要求處理與完成回覆處理分別在 §2.3.1、§2.3.2。

因此，追蹤一次讀取時，要分開記錄「Link 已收到」、「交易層已接受」與「要求者已收齊回覆」。這三個時點由不同角色觀察。

要讓兩個裝置共用計數器，該查哪裡？

先讀 §6.15 的 AtomicOp（把讀取、修改與寫回合成原子操作）種類，再到 Device Capabilities 2 查完成端能力與沿路的 Routing Supported，最後核對 Device Control 2 的 Requester Enable 與 Egress Blocking。軟體如何發現發起端本身的能力，不在 Base 6.0 定義範圍，不能編造一個共通查詢 bit。

操作送入資料回傳與更新
FetchAdd加數回傳原值，寫回相加結果
Swap新值回傳原值，寫入新值
CAS比較值與交換值回傳原值；只有相等才交換

作者案例：假設完成端支援 32-bit FetchAdd，路徑與權限均有效，目標原值為 7，加數為 1。完成端原子地寫入 8，回覆 7。若後續要求必須等這次操作被觀察到，要求者須先等原子操作的完成回覆，再發下一筆要求（p.774）。

共享工作佇列暫時沒空間，可以怎麼回覆？

DMWr（可由接收端暫時拒收的非 Posted 寫入）在 §6.32 定義。當暫時條件使操作無法成功時，完成端可以回 Request Retry Status（要求重試狀態）；此時目標保持原樣，完成端也不能假設要求者一定會重送。這不是錯誤回報。

作者情境：第一筆提交碰到暫時條件而收到重試狀態，工作尚未加入目標。發起端之後是否重試及如何通知軟體，須依其實作介面處理。若重送後收到成功，才按成功語意接續工作。不要把普通 Memory Write 的「沒有成功回覆」模型套進來。

一直等不到回覆時，怎麼接到恢復？

Completion Timeout（等待必要完成回覆的逾時機制）由要求者監督。Memory Read 若分成多筆完成回覆，要等全部回覆收到才算完成。即使先收到部分資料，也不能把整筆要求標成完成。逾時的設定範圍用於偵測異常，規格明確禁止用它估計正常回應時間。

Locked Transactions（鎖定交易）則是 §6.5 的相容機制：只有 Root Complex 可發起，並可能阻擋沿路其他流量。PCI Express Endpoint 被禁止支援鎖定存取，新軟體也不得使用會對 I/O 裝置產生鎖定存取的指令。它與可選的 AtomicOp 不可混為同一種保證。
