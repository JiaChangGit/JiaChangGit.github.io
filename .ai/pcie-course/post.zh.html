系統能列出 PCIe 裝置，不代表裝置已能處理資料；規格定義了某項功能，也不代表眼前的裝置一定支援。本章先建立系統觀，再用一個完整案例練習：如何從設定空間找到能力欄位，並把「支援什麼」與「目前如何運作」分開。

版本範圍

欄位依 PCI Express Base Specification Revision 6.0，韌體背景依 PCI Firmware Specification Revision 3.3。後者 §1.2（p.7）參考的是 Base 5.0，因此不能把兩份文件視為同版配套。下列頁碼均對應本課程採用的 PDF，文件頁與 PDF 頁序相同。

裝置接上後，還要完成哪些工作？

Root Complex 把 CPU／記憶體子系統接到 I/O 階層；Root Port 對外建立 Link，Switch 可以延伸連接路徑，Endpoint 提供裝置功能。Link 連接相鄰兩端，Lane 是構成 Link 的通道；x4 表示 4 個 Lane，不是 4 個裝置。

軟體辨識與設定的基本對象是 Function。一張卡可以有多個 Function；本例用 0000:03:00.0 表示 Segment、Bus、Device、Function，其中 Bus、Device、Function 常合稱 BDF。Segment 是邏輯分組，不是額外的硬體元件；這組識別號也不是記憶體位址。

兩端硬體先具備建立 Link 的條件，系統軟體再發現 Function、配置資源，驅動程式則準備裝置的工作介面。這是理解依賴關係的教學整理，實際平台可能分階段處理。Firmware 3.3 §3.5 要求韌體設定開機與主控台裝置的完整路徑，以及所有 Host Bridge，卻不保證每個 Endpoint 都已配置完成。

由 CPU 操作裝置介面BAR 所描述的資源及裝置暫存器；若經記憶體映射存取，稱為 MMIO（Memory-Mapped I/O，記憶體映射 I/O）。

BAR 是設定空間中的 Base Address Register，不是資料緩衝區。能讀取設定空間，尚不足以證明 MMIO 或 DMA 已準備好。

系統觀的規格位置

要查支援速率，為什麼不能只讀目前速率？

能力說明可以支援什麼，控制欄位說明相關設定，狀態則描述目前結果。本題先查本端的支援集合，再查 Link 的目前速率；這兩份資料不能互相代替。

每個 Function 的 PCIe 設定空間為 4096 bytes。PCI Express Capability 位於前 256 bytes 的傳統 Capability 清單，不能因名稱含有 PCI Express，就跳去找 Extended Capability。（Base 6.0 §7.2／Figure 7-3，pp.905–906；§7.5.3，p.951。）

教學假設

以下拓樸、位置與讀值由作者設計，不是實機量測。目標為已找到的一般 PCI Express Endpoint，並非整合於 Root Complex 的端點（Root Complex Integrated Endpoint，RCiEP），也不是虛擬化的 Virtual Function（VF）。本例使用傳統 BDF 編址，不使用 Alternative Routing-ID Interpretation（ARI，另一種解讀 Function 識別號的方式）；設定讀取均成功。Link 已建立，查詢期間維持穩定，且已實作本題使用的 Link Capabilities 2 速率向量。所有 offset 都是該 Function 設定空間內的 byte 位移，不是 CPU 實體位址。

設定空間採小端序，所以 0x7001 的低位址 byte 是 0x01（Base 6.0 §7.5.1.1，p.916）。清單位置與順序可以改變；0x70 不能寫成通用常數。

若清單已結束卻沒找到目標，或讀取失敗，就不能繼續把某個位置當成該結構。讀不到資料也不等於已取得「不支援」的有效回覆。

Capability Version 2 不等於 PCIe Gen2，也不能單獨保證舊硬體實作了速率向量。本例已另列實作前提；採用 Base 6.0 解讀欄位，也不表示裝置必然支援 64 GT/s。舊硬體分支見 §7.5.3.18 的實作說明（p.1000）。

找到結構後，怎麼把讀值轉成答案？

先看 Figure 7-21（p.952），將欄位相對位移加到起點；接著先查能力的 Figure 7-38／Table 7-35（pp.998–1000），再回到狀態的 Figure 7-29／Table 7-26（pp.978–979）。順序由問題決定，圖用來定位，表格與條文用來判讀。每一步都要確認版本與適用對象，不能只從欄位名稱推測它的意義。

Link Capabilities 2：0x70 + 0x2C = 0x9C，讀 32 bits → 0x0180001E
Link Status        ：0x70 + 0x12 = 0x82，讀 16 bits → 0x0043

Supported Link Speeds Vector 在整個 Register 的 bits 7:1。先用遮罩保留，再右移成欄位值：

(0x0180001E & 0x000000FE) >> 1 = 0x0F

欄位內 bits 0–3 都為 1，分別表示支援 2.5、5、8、16 GT/s；bits 4–5 為 0，未宣告 32、64 GT/s；bit 6 為保留位元。欄位 bit 0 原本位於 Register bit 1，兩種編號不要混用。完整讀值保留 bits 23、24，是 Table 7-35 對支援 16 GT/s 以上裝置的偵測能力要求；它們不證明路徑中已有 Retimer。

Link Status 則使用編碼，不是另一個支援 bitmap：

Current Link Speed：0x0043 & 0x000F = 3
Negotiated Link Width：(0x0043 & 0x03F0) >> 4 = 4

代碼 3 對應速率向量的欄位 bit 2，也就是 8 GT/s；寬度 4 表示 x4。這些遮罩以表中讀取寬度為前提，不能直接套到不同位置的 32-bit 讀值。

Table 7-26 指出，Link 未建立時，這兩個欄位為 undefined。0x0043 本身不能證明 Link 已建立；也不能僅憑 bit 13 為 0 就認定 Link 中斷，因為該狀態位是否實作取決於回報能力（Table 7-23、Table 7-26，pp.969、979）。

目前只有 8 GT/s，可以認定裝置有問題嗎？

案例推演：在假設成立時，本端宣告支援至 16 GT/s，目前 Link 為 8 GT/s、x4。這尚未解釋較低速率的原因；還要查對端能力、相關設定及連線狀態。x4 也不是最大寬度的證據，GT/s 更不能直接當作應用程式的 GB/s。有效傳輸量還受 Lane 數、編碼、封包及工作負載影響（Base 6.0 §1.2，pp.101–102）。

換一個條件，原來的判斷還成立嗎？

Capability 起點改為 0x90，還能到 0x9C 查能力嗎？

不能。依 Figure 7-21（p.952），Link Capabilities 2 應為 0x90 + 0x2C = 0xBC，Link Status 為 0x90 + 0x12 = 0xA2。起點是新教學假設，相對位移不變。

Current Link Speed 為 4，是同時支援兩種速率嗎？

不是。有效的 Link 狀態下，編碼 4 表示目前為 16 GT/s。支援集合仍須另外查向量。（Table 7-26、Table 7-35，pp.978、998。）

Link 已中斷，手上仍有 0x0043 這筆讀值，能報成目前 8 GT/s、x4 嗎？

不能。Table 7-26（p.978）將 Link 未建立時的速率與寬度定為 undefined；看似合理的數字不能取代有效條件。
