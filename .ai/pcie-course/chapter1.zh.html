一張卡、多個 Function，究竟共用了什麼？

Function 是軟體可在 Configuration Space（設定空間）中個別定址的功能。一個 Device 是一組具有共同 Bus Number 與 Device Number 的 Function；實體卡則是組裝單位，可能裝有一個或多個 component。這三種對象的數量各有意義，需要分開記錄。

資料往回傳時，Requester 和 Port 的名稱會改變嗎？

先以 Root Complex（連接主機與 I/O 階層的根部）為方向基準。Switch 的 Upstream Port 朝向根部，Downstream Port 朝向下游；封包改變方向時，Port 的名稱仍由拓撲決定。

接著追蹤卡 A 的 Function 1 發出的 Memory Read（讀取 Memory Space 的要求）。Requester 是發起這筆交易的 Function；Completer 負責處理 Request，並在需要時產生 Completion。Transmitter 與 Receiver 則描述某一次 Link 傳輸的傳送端與接收端。下面沿往返路徑逐段對照。

Switch 為什麼會在設定空間裡變成多個 Bridge？

回到開頭的圖。Root Port 在本章的設定模型中呈現為一個 PCI-to-PCI Bridge，也就是連接上、下游匯流排的橋接功能。Switch 則呈現為多個邏輯 Bridge：Upstream Port 接到內部邏輯 Bus，各個 Downstream Port 再接出外部 Link。軟體可以沿這些關係找到下游。

PCI-to-PCI Bridge 是設定模型裡連接上、下游匯流排的橋接功能。Upstream 指朝向 Root Complex 的方向；Downstream 指離開 Root Complex、朝階層下游的方向。Switch 的 internal bus 是邏輯表示，不是把外部 PCIe Link 改成共享的平行匯流排。

找到 Endpoint，為什麼有時沒有可配對的 Link？

前面案例的插卡是接在 Port 外部的 Endpoint。Figure 1-2 還有另一種位置：Root Complex Integrated Endpoint（RCiEP，整合在 Root Complex 內的 Endpoint）。它仍是一個 Function，支援 Configuration Request，但它位於 Root Complex 內部，不出現在 Root Port 對外的 hierarchy domain 或 Switch 中。

【模擬資料】假設某個可讀取設定空間的 Function，Device/Port Type 識別為 RCiEP。此時應查 RCiEP 適用的欄位；規格要求它不實作 Link Capabilities、Link Control、Link Status 及其 2 版 Register。不能只因讀不到這些 Register，就判斷有一條 Link 斷線。若 Function 是另一種 Device/Port Type，仍須依該類型查它的適用規則。

RCiEP 也可能與可選的 Root Complex Event Collector（RCEC，Root Complex 事件收集器）關聯。RCEC 處理相關 RCiEP 的錯誤與 PME（Power Management Event，電源管理事件）訊息；要確認關聯，查 RCEC 的 Endpoint Association Extended Capability。RCEC 是可選的，不能假設每個 RCiEP 都有一個。若某個 RCiEP 已關聯 RCEC，規格要求其 PME 和錯誤經由該 RCEC，且它最多只關聯一個 RCEC。

三種 Endpoint 都使用 Type 0 Configuration Header，但限制並不相同。讀 §1.3.2.1–§1.3.2.3 時，可先比對下表，再按實際欄位回到對應規則。

以 Downstream A 為例，0x01 & 0x7F = 1 先選出 Type 1 Header。設讀到的 16-bit Capabilities Register 為 cap，則 (cap & 0x00F0) >> 4 = 6，才得到 Switch Downstream Port。cap & 0x000F = 2 則表示 Capability Version 2，與 Type 6 是不同欄位，也不是連線的 PCIe 世代。

Header Type 為 0x80，就代表有 8 個 Function 嗎？

不是。先做 0x80 & 0x7F = 0，可知 Header Layout 仍是 Type 0；bit 7 為 1，只表示這個 Device 可能含有多個 Function，允許軟體探查其他 Function，並未回報數量。卡 A 的 Function 1 存在，是題目已確認的另一筆資料，不能只從 0x80 推出。

Table 7-7 也規定，若此 bit 為 0，軟體不得探查 Function 0 以外的 Function，除非 ARI、SR-IOV 等其他機制另有指示。本章已排除這些機制；不能為了練習，就把「一律掃完 0–7」當成通用規則。

確認類型後，為什麼還要看欄位適用性？

以 Data Link Layer Link Active（回報 Data Link 是否處於 DL_Active 的位元）為例：先讀 Link Capabilities 的 Data Link Layer Link Active Reporting Capable，確認這個 Port 是否提供回報。未實作回報時，Link Status 的對應位元固定讀為零；這個零值不能拿來判定 Link 失效。對端點所在的 LA，應先查看 Downstream Port A 的有效回報，再依需要補上端點與協定紀錄。

若讀到的是 Root Complex Integrated Endpoint，就先回到 §1.3.2.3：這種 Function 沒有外部 Link，規格禁止它實作 Link Capabilities、Link Control、Link Status 及其對應的 2 Registers。同一份解碼表用在不同 Function 上，必須先選出實際適用的欄位。

03:00.1 的每一段究竟選了誰？

Bus、Device、Function 合稱 BDF。在傳統編址下，Bus Number 有 8 bits，Device Number 有 5 bits，Function Number 有 3 bits。先選定 PCI Segment Group（本章簡稱 Segment），再選其中的 Bus，接著選 Device 與 Function，才能定位本章的設定對象。

另一個 Segment 也有 03:00.0，會衝突嗎？

新增教學假設：系統另有 Segment 0001，其中一條 Root Port 路徑接到 0001:03:00.0。這與圖中的 0000:03:00.0 是兩個不同的設定對象；只有省略 Segment，才會看起來相同。紀錄資料時，應把 Segment 與 BDF 一起保留。

反過來，同一份穩定快照、同一個 Segment 裡，03:00.0 和 03:00.1 具有相同的 Bus 與 Device，指向同一個 Device 的兩個 Function。至於它們在實體上裝在哪張卡，還需要實體配置的資訊；本例是題目另行給定卡 A 的組裝方式。

要找 Bus 03，為什麼沿著 Downstream A？

角色已經查清楚，接著要確認橋接關係。對本章採用的一般 Type 1 Bridge 而言，Secondary Bus Number 指出緊接在下游的 Bus；Subordinate Bus Number 則標出其下游階層涵蓋的最高 Bus Number。兩個值一起讀，才分得清「下一層是哪個 Bus」與「整個下游範圍到哪裡」。

閱讀順序是：先由 Header Layout 確認 Type 1，再看 Type 1 Configuration Space Header 的 Figure 7-14，找到 0x19 與 0x1A，最後讀 §7.5.1.3.3 與 §7.5.1.3.4 的欄位定義。兩個 offset 都從該 Function 的設定空間起點計算，各讀 8 bits；它們不以 PCIe Capability 為起點。

封包裡的 Requester ID 和 BDF 有什麼關係？

當某個 Function 發出交易要求時，Requester ID 用來識別要求者。本章的傳統格式把 Bus、Device、Function 放進 16 bits；因此，先理解 BDF，後面閱讀交易封包才知道這個欄位在指誰。封包如何配對要求與回覆，會在 Chapter 5 再談。

Requester ID = (Bus << 8) | (Device << 3) | Function
03:00.1 → (0x03 << 8) | (0x00 << 3) | 1 = 0x0301
02:02.0 → (0x02 << 8) | (0x02 << 3) | 0 = 0x0210

案例推演：要把 0x0210 還原，先取 (id >> 8) & 0xFF = 0x02 得到 Bus，再取 (id >> 3) & 0x1F = 0x02 得到 Device，最後取 id & 0x07 = 0 得到 Function。它對應圖中的 Downstream B，而不是 Bus 02 上的 Function 0x10。

這個算式把要求來源的 BDF 編成識別號。封包經過 Downstream B 時，要求者仍是原先發出要求的 Function；Switch 轉送時必須保留 Transaction ID。因此要分別記錄「誰發出要求」與「要求經過哪些 Bridge」。

此外，0000:03:00.0 與 0001:03:00.0 的傳統 16-bit 編碼都會是 0x0300。因此只拿到這 16 bits，仍缺少判定 Segment 的情境。這不等於宣稱封包完全沒有 Segment 資訊：PCIe 6.0 的部分 Flit Mode 格式另有 Segment 欄位，不能與這個 16-bit 欄位混為一談。

規格依據：Requester ID 與 Segment 的邊界

先看 Base 6.0 §2.2.4.2 的 Table 2-8（p.147）、Figures 2-20／2-22（p.148）辨認非 ARI 的位元分配，再讀 §2.2.6.2（pp.156–157）的 Requester ID 規則。前幾張圖展示的是目的地 ID routing，不能把圖上的封包 byte offset 套到所有 Requester ID；本章只取 BDF 的編碼關係。p.157 也明定 Switch 轉送要求時不得修改 Transaction ID，並把 Segment 定義為獨立欄位。Flit Mode 的獨立 Segment 資訊見 §2.2.1.2，pp.134–139。本章只做欄位識別與編碼，沒有把傳統 BDF 的拆法延伸到 ARI。

記住 BDF，下一次開機就能認出同一張卡嗎？

跨次開機比對硬體時，先保留每筆紀錄所屬的配置快照。BDF 描述目前設定拓樸中的位置；Bus Number 由配置流程建立，同一硬體可能因拓樸或分配方式改變而取得不同位置。若要追蹤實體個體，還要取得可信的裝置身分或平台位置資訊。

換一次快照來想

假設另一次配置把卡 A 所在的 Bus 從 03 改為 05，其他相關路徑也已正確調整。原 Function 1 在新快照中就以 0000:05:00.1 被定位，傳統 Requester ID 也成為 0x0501。這是作者用來說明配置結果可能改變的情境，不表示每次開機都會重新編號。

若要跨開機追蹤實體裝置，就需要另外取得可信的裝置身分或平台位置資訊。Vendor ID、Device ID 描述廠商與裝置類型，不能單獨充當每一件產品的唯一序號。這類長期識別需求與本章的「選定目前哪個 Function」不同，不能用一組 BDF 同時回答。

規格依據與推論範圍

Base 6.0 §2.2.6.2（pp.156–157）說明 Bus／Device Number 的設定、捕獲與執行期間可改變的性質；另外， §7.5.1.1.1–§7.5.1.1.2（p.917）的 Vendor ID／Device ID 定義，也支持上述區分。換成 Bus 05 是教學推演；規格不要求每次開機更改 BDF，也未由這些 ID 保證實體個體的唯一性。
