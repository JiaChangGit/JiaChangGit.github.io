1. 系統列出的是卡，還是 Function？

軟體會對每個 Function 分別讀取設定資料。Function 是可個別辨識與設定的功能；同一個 Device 可以提供一個或多個 Function。一張實體卡還可能包含 Switch 及多個元件，因此要由實際組裝資訊另行確認卡片數量。

看到同一件硬體時，我們可能在談不同的對象

2. Switch 為什麼會在設定空間裡變成多個 Bridge？

回到開頭的圖。Root Port 在本章的設定模型中呈現為一個 PCI-to-PCI Bridge，也就是連接上、下游匯流排的橋接功能。Switch 則呈現為多個邏輯 Bridge：Upstream Port 接到內部邏輯 Bus，各個 Downstream Port 再接出外部 Link。軟體可以沿這些關係找到下游。

PCI-to-PCI Bridge 是設定模型裡連接上、下游匯流排的橋接功能。Upstream 指朝向 Root Complex 的方向；Downstream 指離開 Root Complex、朝階層下游的方向。Switch 的 internal bus 是邏輯表示，不是把外部 PCIe Link 改成共享的平行匯流排。

6. 封包裡的 Requester ID 和 BDF 有什麼關係？

當某個 Function 發出交易要求時，Requester ID 用來識別要求者。本章的傳統格式把 Bus、Device、Function 放進 16 bits；因此，先理解 BDF，後面閱讀交易封包才知道這個欄位在指誰。封包如何配對要求與回覆，會在 Chapter 5 再談。

Requester ID = (Bus << 8) | (Device << 3) | Function
03:00.1 → (0x03 << 8) | (0x00 << 3) | 1 = 0x0301
02:02.0 → (0x02 << 8) | (0x02 << 3) | 0 = 0x0210

案例推演：要把 0x0210 還原，先取 (id >> 8) & 0xFF = 0x02 得到 Bus，再取 (id >> 3) & 0x1F = 0x02 得到 Device，最後取 id & 0x07 = 0 得到 Function。它對應圖中的 Downstream B，而不是 Bus 02 上的 Function 0x10。

這個算式把要求來源的 BDF 編成識別號。封包經過 Downstream B 時，要求者仍是原先發出要求的 Function；Switch 轉送時必須保留 Transaction ID。因此要分別記錄「誰發出要求」與「要求經過哪些 Bridge」。

此外，0000:03:00.0 與 0001:03:00.0 的傳統 16-bit 編碼都會是 0x0300。因此只拿到這 16 bits，仍缺少判定 Segment 的情境。這不等於宣稱封包完全沒有 Segment 資訊：PCIe 6.0 的部分 Flit Mode 格式另有 Segment 欄位，不能與這個 16-bit 欄位混為一談。

規格依據：Requester ID 與 Segment 的邊界

先看 Base 6.0 §2.2.4.2 的 Table 2-8（p.147）、Figures 2-20／2-22（p.148）辨認非 ARI 的位元分配，再讀 §2.2.6.2（pp.156–157）的 Requester ID 規則。前幾張圖展示的是目的地 ID routing，不能把圖上的封包 byte offset 套到所有 Requester ID；本章只取 BDF 的編碼關係。p.157 也明定 Switch 轉送要求時不得修改 Transaction ID，並把 Segment 定義為獨立欄位。Flit Mode 的獨立 Segment 資訊見 §2.2.1.2，pp.134–139。本章只做欄位識別與編碼，沒有把傳統 BDF 的拆法延伸到 ARI。

7. 記住 BDF，下一次開機就能認出同一張卡嗎？

跨次開機比對硬體時，先保留每筆紀錄所屬的配置快照。BDF 描述目前設定拓樸中的位置；Bus Number 由配置流程建立，同一硬體可能因拓樸或分配方式改變而取得不同位置。若要追蹤實體個體，還要取得可信的裝置身分或平台位置資訊。

換一次快照來想

假設另一次配置把卡 A 所在的 Bus 從 03 改為 05，其他相關路徑也已正確調整。原 Function 1 在新快照中就以 0000:05:00.1 被定位，傳統 Requester ID 也成為 0x0501。這是作者用來說明配置結果可能改變的情境，不表示每次開機都會重新編號。

若要跨開機追蹤實體裝置，就需要另外取得可信的裝置身分或平台位置資訊。Vendor ID、Device ID 描述廠商與裝置類型，不能單獨充當每一件產品的唯一序號。這類長期識別需求與本章的「選定目前哪個 Function」不同，不能用一組 BDF 同時回答。

規格依據與推論範圍

Base 6.0 §2.2.6.2（pp.156–157）說明 Bus／Device Number 的設定、捕獲與執行期間可改變的性質；另外， §7.5.1.1.1–§7.5.1.1.2（p.917）的 Vendor ID／Device ID 定義，也支持上述區分。換成 Bus 05 是教學推演；規格不要求每次開機更改 BDF，也未由這些 ID 保證實體個體的唯一性。

8. 串接角色、路徑與識別號

串起本章案例：在 Segment 0000 選定目標 03:00.1，沿下游 Bus 範圍走到 A 分支，再以自己的設定資料確認 Function 角色。若它發起要求，傳統 Requester ID 為 0x0301。下面逐項改變條件，說明哪一部分需要重新查證。

只讀到 Header Type = 0x01，就可以把這個 Function 標成 Switch Downstream Port 嗎？

還不行。依 Figure 7-8／Table 7-7，低 7 bits 只確定它採 Type 1 Header。下一步要找到 PCIe Capability，沿 Figure 7-21 到相對 offset 0x02，再依 Figure 7-23／Table 7-19 解碼 Device/Port Type；值為 6 才是本題要辨識的 Switch Downstream Port。Root Port 與 Upstream Port 也使用 Type 1 Header。

我只知道 Header Type = 0x80，可以把其他七個 Function 都標成「存在」嗎？

不能。Table 7-7 的 bit 7 只允許探查，沒有列出存在的 Function。正確的紀錄是「Type 0 Header；Device 可能含有多個 Function」，再保留各 Function 是否存在的獨立查詢結果。即使只有一個 Function，也可能看到這個 bit 為 1。

紀錄只有 Requester ID = 0x0300，能判定是卡 A 的 Function 0 嗎？

在本章的傳統格式下，可先還原為 BDF 03:00.0；還缺少 Segment 及這筆紀錄所屬的配置快照。若 Segment 是 0001，就不是圖中的卡 A；若是不同時刻的配置，也不能直接沿用舊圖。先補齊範圍與時間，再對照 Function。

圖中的兩條分支都連到 Device 00，是不是把同一個裝置畫了兩次？

沒有。卡 A 是 Bus 03 的 Device 00，卡 B 是 Bus 04 的 Device 00；BDF 的 Bus 部分不同。若要沿圖查到卡 B，先由 Type 1 Header 的 Figure 7-14 找到 Secondary／Subordinate 欄位，再使用本例 Downstream B 的 04–04 範圍。不能只拿 Device Number 00 比對。

9. 知道查誰之後，下一步看什麼？

現在可以先用 Segment 與 BDF 選定 Function，再用 Header Layout 與 Device/Port Type 判斷該怎麼讀它。Chapter 2 將整理設定空間的完整查詢方法：傳統與 Extended Capability 從哪裡開始、指標怎麼走，以及欄位寬度、版本與存取屬性如何影響解讀。
