Start ordering analysis with TC (Traffic Class), transaction types, and attributes. RO (Relaxed Ordering) and IDO (ID-Based Ordering) can permit passing under specific conditions; they do not remove an application’s data dependency.

Read row-passes-column literally

Columns are earlier transactions; rows are later transactions. The table asks whether the later can pass the earlier. Read the a/b explanations on pp.223–224 before applying an entry. In the author example, same-requester/same-TC posted data and notification writes without an applicable relaxation follow A2a: the later must not pass the earlier. That ordering does not independently define persistence or CPU memory-barrier requirements.

Start with the communication model

Use Figure E-1 and Appendix E to distinguish one-entity communication from mixed host-memory/P2P interaction. E.4.1 shows how relaxed passing can change the final memory result in a multi-entity dependency. Appendix D examines receive-to-transmit resource dependencies; it does not define every platform’s cross-TC dependency rules. System mapping must respect the actual model.

Quiesce all relevant traffic before renumbering

Section 6.4 requires blocking new device requests and driver accesses, completing work serviced by the device, completing issued non-posted requests, and ensuring posted requests reached their destinations. Transactions Pending covers only part of that work. Coordinate with the driver and track outstanding traffic before changing IDs; a cleared control bit is not proof of full quiescence.

Use Message Code Usage as an index

Table F-1 maps a message purpose to code, routing, and Msg/MsgD, then points to its defining section. Use it to return to page requests, invalidation, or LTR formats. The table itself warns that newer messages defined elsewhere may not be captured by this Base 6.0 edition.
