Start ordering analysis with TC (Traffic Class), transaction types, and attributes. RO (Relaxed Ordering) and IDO (ID-Based Ordering) can permit passing under specific conditions; they do not remove an application’s data dependency.

Read row-passes-column literally

Columns are earlier transactions; rows are later transactions. The table asks whether the later can pass the earlier. Read the a/b explanations on pp.223–224 before applying an entry. In the author example, same-requester/same-TC posted data and notification writes without an applicable relaxation follow A2a: the later must not pass the earlier. That ordering does not independently define persistence or CPU memory-barrier requirements.

How do we use the table for two transactions?

Teaching assumptions: Each row is independent. Both transactions use the same Traffic Class (TC) and are compared at the same forwarding point. Put the earlier transaction in the Table 2-42 column, the later transaction in the row, then read the corresponding text beneath the table.

Start with the communication model

Use Figure E-1 and Appendix E to distinguish one-entity communication from mixed host-memory/P2P interaction. E.4.1 shows how relaxed passing can change the final memory result in a multi-entity dependency. Appendix D examines receive-to-transmit resource dependencies; it does not define every platform’s cross-TC dependency rules. System mapping must respect the actual model.

Does permitted passing make a multi-device workload safe?

Teaching scenario based on Appendix E.4.1: Device Y writes host memory, then sends a peer-to-peer (P2P) write to notify Device Z. Once Z sees the notification, it writes the same memory location.

Use Figure E-1 to locate Y, Z, the Switch, and the Root Complex, then order the three transactions at the observation point. Assume Y and Z use the same TC for their writes and compare them at a common Root Complex processing point. The first two originate at Y; Z's later write has a different Requester ID. If Z's Posted Write has IDO set and the other conditions of Table 2-42 A2b hold, the Root Complex may allow it to pass Y's waiting write, changing the final memory value.

Requester IDs alone cannot express this cross-device data dependency. Evaluate the entities, TLPs, path, and synchronization before enabling IDO. The appendix mentions possible synchronization; the exact protocol is platform and device specific.

Appendix D covers a different issue: cross-TC packets can form circular dependencies on finite buffer resources, creating deadlock. An absence of general ordering across TCs does not eliminate system-level dependencies.

Quiesce all relevant traffic before renumbering

Section 6.4 requires blocking new device requests and driver accesses, completing work serviced by the device, completing issued non-posted requests, and ensuring posted requests reached their destinations. Transactions Pending covers only part of that work. Coordinate with the driver and track outstanding traffic before changing IDs; a cleared control bit is not proof of full quiescence.

What must stop before changing a Bus Number?

Teaching scenario: A driver prepares to reconfigure an Endpoint. Under §6.4, coordinate with the driver to stop new device-generated Requests and new software Requests to the device, then establish that Requests being serviced by the device have completed.

Device Status.Transactions Pending addresses completion of Non-Posted Requests issued by that function. It does not by itself establish delivery of earlier Posted Writes. Check their destination using the relevant TC, ordering attributes, and device synchronization mechanism.

Section 6.4 describes host reads of the device flushing device writes to system memory using TC0; other TCs need suitable synchronization. This specific path still requires the RO, IDO, and platform memory conditions to be respected. P2P traffic needs an explicit synchronization protocol between devices even with TC0.

Use Message Code Usage as an index

Table F-1 maps a message purpose to code, routing, and Msg/MsgD, then points to its defining section. Use it to return to page requests, invalidation, or LTR formats. The table itself warns that newer messages defined elsewhere may not be captured by this Base 6.0 edition.

How does a code lead to its full format?

Teaching scenario: Appendix F Table F-1 lists Invalidate Request as Message Code 0000 0001b, Routing 010b, type MsgD. Follow its reference to §10.3.1 for the message fields and handling conditions.

For Function Readiness Status (FRS), Table F-2 lists PCI-SIG-Defined VDM Subtype 0000 1001b. That is a subtype, not the general Message Code in Table F-1. Continue to §2.2.8.6.3 and Chapter 34 for the associated readiness events and queue.

The tables are indexes for Base 6.0 and may omit messages or subtypes introduced in other specifications. Use the referenced definition for full applicability.
