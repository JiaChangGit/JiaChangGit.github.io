Trace a read request and its completion

An MMIO (Memory-Mapped I/O) read starts with a host request and returns device data. PCIe carries these exchanges in TLPs (Transaction Layer Packets). Chapter 4 supplies the configured address path; this example follows a four-byte read.

Specification route: Transaction classes in Table 2-1 → request identity and Memory Request format → Completion format → fragmentation and boundaries.

After resource allocation, an access still has to become a Request and find its way back as a Completion. This chapter follows an MMIO read through routing, transaction identity, length, and byte selection, then explains why one Request may receive several Completions.

Identify the transaction before expecting a response

A Transaction Layer Packet (TLP) carries a transaction. The Requester issues it and the Completer services its target; these roles change with the transaction. Memory Requests route by address, while Completions return by the original Requester ID. Requester ID and Tag identify an outstanding transaction. One Requester must not reuse a Tag across simultaneous outstanding Requests requiring Completion. Base 6.0 also defines larger-Tag capabilities and enables, so Tags are not universally eight bits.

Translate a 4-byte read into packet fields

Assume a platform Requester ID of 0x0000 and Tag 0x12 for a 4-byte read at 0x80004120. This ID is a platform assumption, not something inferred directly from the Root Port BDF. MRd uses Fmt=000b, Type=00000b, Length=1 DW, First BE=1111b, and Last BE=0000b, without a Request data payload. The 3 DW header follows the 32-bit target address format, not the width of the data being read.

The successful CplD uses Fmt=010b and Type=01010b, preserves Requester ID/Tag, and supplies Completer ID=0x0300. Length=1 DW, Status=SC, Byte Count=4, and Lower Address=0x20. If the four valid bytes are 78 56 34 12 and the example Register is defined as little-endian, the value is 0x12345678.

A separate legal 6-byte read of 0x80004121–0x80004126 uses aligned address 0x80004120, Length=2, First BE=1110b, and Last BE=0111b. The successful response occupies 2 DW but contains six valid bytes: Byte Count=6 and Lower Address=0x21. Disabled non-Prefetchable bytes must not be read at the Completer. The device interface must permit this access.

Both responses have SC, BCM=0, and the same Requester ID/Tag. Byte Count includes the current fragment and the data still to follow. One Request's responses stay in increasing address order; responses for different Transaction IDs may pass each other and must not be combined into one Completion.

A separate restriction prohibits a Memory Request from crossing 4 KiB. Reading 32 bytes at 0x40001FF0 reaches 0x4000200F and requires two 16-byte Requests. A Receiver may check this boundary; if its implemented check detects a violation, it treats the TLP as Malformed. The absence of an error record does not establish that the Request was legal. This example is an ordinary Non-Flit Mode Memory Read; Chapter 15 covers AtomicOp alignment separately.

An unsuccessful read Completion carries no valid read data and terminates the Request. UR/CA are not zero data, and RRS is not a general MMIO retry status.

How do we separate replies when two devices use the same Tag?

Match each Completion to its Request using both Requester ID and Tag, then inspect Status, Length, Byte Count, and Lower Address to reconstruct the data range. Grouping first shows which bytes belong to which read.

Both Lower Address values are 0x00 because the low seven bits of each starting address are zero. The field alone cannot reconstruct a full address. Completer ID and complete endpoint records are absent, so B’s data coverage still needs other Completion fields and Requester acceptance checked. Why inspect low bits when larger and smaller Tags are concurrent?

The previous table selects permitted values before sending. Section 2.2.6.2 also requires a Requester using larger and smaller Tags concurrently to prevent an outstanding larger Tag from aliasing a smaller one if an insufficiently capable Completer responds to the larger-Tag Request.

Teaching example: One Requester ID has two outstanding Reads: Tag 100h to path A, which it assumes supports 10-bit Tags, and Tag 00h to 8-bit path B. Full path support for A has not been verified. The original Tags differ, but both have low 8 bits 00h.

Suppose A's Request encounters an error and an intermediate component without 10-bit Completer capability responds, losing the upper Tag bits in this response and returning 00h. Matching that response only to Requester ID and the low Tag can confuse A's abnormal response with B's result. This is an assumed failure example, not a claim that all components truncate identically.

The p.159 implementation note Using Larger Tags and Smaller Tags Concurrently gives one partition: reserve low 8-bit values 00h–0Fh for smaller Tags and do not use those low values in larger 10-bit Tags. Each of these 16 low values corresponds to three valid 10-bit high-bit combinations; removing 48 from the original 768 leaves 720 10-bit values, alongside 16 smaller values.

This is one implementation approach, not a required universal partition. The requirement is to prevent the alias; actual concurrency also depends on device resources and path conditions. Use Table 2-11 from the previous section first to select the permitted range for each Request.

Where does a cross-Hierarchy Completion return?

The earlier examples match a Requester ID and Tag within one PCIe Hierarchy. In Flit Mode across Hierarchies, Segment information also helps the path identify the destination Hierarchy. Chapter 3's Segment capture example explains how a Function obtains its Segment.

[Simulated data] This teaching example does not represent a particular device or platform. Endpoint A is in Segment 02h and Endpoint B is in Segment 03h; both have Segment Captured set. A sends a Non-Posted Memory Read to B. Assume every Link is in Flit Mode, address routing and platform peer-to-peer support have been established, and the Root Complex (RC) passes this Request without taking ownership. A's OHC-C carries Requester Segment 02h with Requester Segment Valid (RSV) set.

Check the distinction

Is a 128-byte first response with Byte Count=256 incorrect?

No. The count includes the next 128 bytes still needed for the Request. Length describes this fragment's payload.
