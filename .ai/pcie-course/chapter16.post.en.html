TC (Traffic Class) labels a packet. VC (Virtual Channel) associates traffic with queues, buffers, and flow-control resources. Follow one Link's map through configuration, dual-end enablement, and initialization before considering arbitration and end-to-end service.

Where do TC and VC take effect?

TC (Traffic Class) is an invariant TLP label. VC (Virtual Channel) selects queues, buffers, and flow-control resources through each Link's map. Section 2.5.1 explicitly notes that TLPs carry no VC ID field: a Port associates a TLP with a VC through its TC/VC Map.

Start with Table 2-43 (p.233). Its VC0, VC1 row gives TC0–TC6/VC0 and TC7/VC1 as an example. TC0 is fixed to VC0; software configures other supported TCs. A TC must not map to multiple VCs within a Port or Endpoint Function.

Then read the upper example in Figure 2-88 (p.234). TC7 uses VC0 on the Endpoint–Switch Link and VC1 on the Switch–Root Complex Link. The TC7 label stays unchanged; its local resources change. VC IDs and maps must match across each Link, while different Switch Ports can have different configurations.

Both ends support VC1. How does it become usable?

Configure matching VC IDs and TC/VC Maps, enable both ends, then confirm that both VC Negotiation Pending bits are clear. VC Enable is a control. VC Negotiation Pending reports unfinished negotiation. Enable=1 at one end alone does not complete the process.

Assign the maps and VC ID before enabling

In Table 7-207 (pp.1189–1191), each TC/VC Map[7:0] bit selects its corresponding TC. At both ends, remove TC7 from VC0, changing its map from FFh to 7Fh. Assign resource 1 VC ID[26:24]=1 and Map=80h, with VC Enable[31]=0. TC7 remains quiesced while no enabled VC temporarily carries it.

With all other bits assumed zero, resource 1's 32-bit Control snapshot is 01000080h. After both ends are prepared, set VC Enable at each end; the snapshot becomes 81000080h. Software updates fields according to their attributes and preserves RsvdP bits; these values illustrate how the fields compose a readback.

Read both Status registers; do not write Pending

Table 7-208 (pp.1191–1192) defines VC Negotiation Pending as Status bit 1, RO, updated by hardware. Its value is defined only while the Link is DL_Active and that VC Enable=1. A displayed zero while the VC is disabled does not establish completed negotiation.

After all intended VCs have been enabled, software may set All VCs Enabled (Port VC Control bit 4) to aid buffer allocation. Leaving it clear must still allow correct operation of enabled VCs. Once set, changing a VC Enable in this Capability while the Link is up has undefined behavior; it is not an ordinary live-switching mechanism.

When two VCs are eligible, which uses the Link first?

First identify the arbitration participants. For a Switch, read Figure 6-8 (p.708) from left to right: routing selects the Egress Port, whose map selects the VC. Traffic from different Ingress Ports competing for the same egress VC undergoes Port Arbitration. Different VCs at that egress then compete for the shared Link through VC Arbitration. The TLP's TC number alone determines neither decision.

Continue to Figure 6-9 (p.709): read VC ID and Relative Priority, then the priority-group boundary. The specification defines default relative priority in ascending VC ID order. With Strict Priority, the higher VC ID is serviced first. A group using RR (Round Robin) or WRR (Weighted Round Robin) instead requires its arbitration capabilities, selection, and tables; VC IDs alone do not determine every actual transmission order.

The simulated configuration has Low Priority Extended VC Count=0. Under section 6.3.3.2, all VCs therefore use Strict Priority. When both VCs at one transmitter have eligible traffic, VC1 has higher relative priority than VC0. This is not bandwidth reservation inherent in TC7; TC7 is simply mapped to this example's VC1.

Priority cannot bypass a packet's missing credit. Conversely, sustained high-priority traffic can starve lower-priority traffic. Section 6.3.3.2.1 requires regulation of high-priority traffic with Strict Priority and sufficient service for lower-priority transactions to avoid timeouts. Bandwidth and latency guarantees also need the end-to-end contract introduced next.

What establishes service guarantees for periodic data?

An Isochronous Contract connects the requester, completer, and fabric-resource responsibilities. In Figure A-1 (p.1521), first follow one complete flow: Device A exchanges upstream Read/Write Requests and returning Read Completions with the Root Complex; Device B to Device C is a separate peer-to-peer flow. Each model needs its own path and service capabilities checked.

Then compare the two Figure A-2 timelines (p.1522). Oversubscription leaves too little service opportunity for other traffic. A concentrated injection burst causes congestion. The contract therefore requires both resource reservation and traffic regulation. Section A.2 relates period T, transaction count N, budgeted payload Y, and latency L. Merely mapping TC7 to VC1 establishes no such contract.

This is a reading entry point, not a complete isochronous configuration. System software must also check aggregate requirements when flows share a VC/TC. Non-isochronous assignment policies are not a universal Base 6.0 platform configuration.
