PTM (Precision Time Measurement) relates component-local time to shared PTM Master Time. Establish the time source and roles, then follow timestamps across successive request/response dialogs. It is not simply a broadcast of a CPU clock value.

Follow discovery into configuration

Use Figure 7-310 for layout, Figure 7-311/Table 7-274 for ID 001Fh, Figure 7-312/Table 7-275 for requester/responder/root capability and local granularity, then Figure 7-313/Table 7-276 for Enable, Root Select, and effective granularity. One capability instance controls a switch; do not assume each switch Downstream Port contains its own PTM capability.

Keep each timestamp in its dialog

The requester captures t1 on transmit and t4 on receive; the responder captures t2 on receive and t3 on transmit. A later ResponseD incorporates historical information. Place each value at its role and dialog before using Equation 6-2. In the author deduction, keeping only the latest response while losing the previous local timestamps leaves the calculation incomplete; missing history is not zero.

Retain the accuracy context

Section 6.21.3 requires the associated Downstream Port enabled before its Upstream Port. For endpoints, Effective Granularity uses the maximum Local Clock Granularity along the PTM source path. The implementation note on p.796 warns that asymmetric retimer delay affects accuracy. Enabled PTM does not make arbitrary component clocks exactly identical.
