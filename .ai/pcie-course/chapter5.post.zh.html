【模擬資料】本章封包欄位與讀值為教學用途建立，不代表特定硬體或平台。

先看本章的角色與路徑

一次 MMIO（Memory-Mapped I/O，記憶體映射輸入輸出）讀取，會由主機端提出要求，再由目標端回覆資料。PCIe 用 TLP（Transaction Layer Packet，交易層封包）承載這些交換。

前情提要：Chapter 4 已完成本例的 BAR、Bridge Window 與解碼配置。現在沿同一路徑觀察一筆 4-byte 讀取。

規格路線：交易類別 Table 2-1 → Request 的 ID／Tag 與 Memory Request 格式 → Completion 格式 → 分段與邊界條件。

位址配置完成後，還要理解一次存取如何形成 Request，以及 Completion 如何回到要求者。本章以一筆 MMIO 讀取串起路由、交易配對、長度與位元組範圍，接著用分段回覆說明「一筆要求」為何不一定只有一個回覆。

版本與假設

依 Base 6.0 的 Non-Flit Mode。沿用普通 Endpoint 03:00.0、BAR0=0x80004000；資源、映射與 Link 均已就緒。數值為作者推演。案例為 TC0、RO／IDO／No Snoop／TH 均為零，不使用 ATS、PASID、IDE、AtomicOp 或 DMWr。CPU 存取如何轉成 TLP 由平台決定，本例另假設一筆 4-byte 存取產生一個 MRd。

先辨認交易，再決定要等待什麼

Transaction Layer Packet（TLP）承載交易。Requester 提出要求，Completer 服務目標；這些角色隨交易改變。Memory Request 依位址送往目標，Completion 則依原 Requester ID 回送。Requester ID 與 Tag 配對尚待完成的交易，同一 Requester 不得讓兩筆同時未完成、需要 Completion 的要求共用 Tag。Base 6.0 另有較大 Tag 的能力與啟用條件，不能把它永遠視為 8 bits。

把 4-byte 讀取對到封包欄位

假設平台以 Requester ID=0x0000、Tag=0x12，讀取裝置 0x80004120 的 4 bytes。這個 Requester ID 是平台假設，不能由 Root Port BDF 直接推定。MRd 使用 Fmt=000b、Type=00000b、Length=1 DW、First BE=1111b、Last BE=0000b；Request 本身沒有資料 Payload。3 DW Header 的選擇來自本例的 32-bit 目標位址格式，不是因為資料剛好是 32 bits。

成功 CplD 使用 Fmt=010b、Type=01010b，保留原 Requester ID／Tag，Completer ID=0x0300。Length=1 DW、Status=SC、Byte Count=4，Lower Address=0x20。若四個有效 bytes 為 78 56 34 12，且本例 Register 定義為 little-endian，值為 0x12345678。

若另讀取 0x80004121–0x80004126 的 6 bytes，並假設裝置允許該存取，Request 要用對齊位址 0x80004120、Length=2、First BE=1110b、Last BE=0111b。成功回覆 Payload 占 2 DW，但有效資料只有 6 bytes；Byte Count=6、Lower Address=0x21。未啟用的 non-Prefetchable bytes 不得在 Completer 被讀取。

Byte Count 不一定等於這個回覆的 Payload

另假設 Endpoint 從有效 DMA 位址 0x40001000 讀 256 bytes，Requester ID=0x0300、Tag=0x13，BME 與映射都已準備好。Requester 的最大讀取要求為 512 bytes；Completer 的有效 Payload 上限及 RCB 都為 128 bytes，路徑接收能力相容。這筆 Length=64 DW 的要求，可按下表回覆：

作者推演的兩段成功回覆
資料範圍LengthByte CountLower Address
0x40001000–0x4000107F32 DW256 bytes0x00
0x40001080–0x400010FF32 DW128 bytes0x00

兩個回覆皆為 SC、BCM=0，並保留相同的 Requester ID／Tag。Byte Count 包含目前片段及後續尚待回傳的資料。同一要求的回覆按位址遞增；不同 Transaction ID 的回覆可交換順序，也不得合併成一個 Completion。

另一項獨立限制是 Memory Request 不得跨 4 KiB：從 0x40001FF0 讀 32 bytes 會到 0x4000200F，必須拆成兩筆各 16 bytes 的要求。接收端可以選擇檢查跨界；若已實作的檢查發現違規，便視為 Malformed TLP（格式錯誤的封包）。沒有錯誤紀錄不代表原要求一定合法。這是 Non-Flit Mode 的一般 Memory Read；AtomicOp 的對齊另見 Chapter 15。

若讀取回覆失敗，Cpl 不帶有效讀取資料並終止該要求；UR／CA 不能當成讀到零，RRS 也不是 MMIO 的通用重試結果。

兩個裝置用了相同 Tag，回覆要怎麼分？

先把每個 Completion 的 Requester ID（原要求者識別號）和 Tag（要求者分配的交易標籤）一起對回原始 Request，再用 Status、Length、Byte Count 和 Lower Address 檢查資料範圍。完成分組後，才知道哪筆讀取還缺哪些資料。

【模擬資料】同一段 Trace 中有兩筆讀取

沿用前節的 256-byte DMA 讀取，另假設 Endpoint 04:00.0 同時提出一筆讀取。兩者都使用 Tag 0x13，但 Requester ID 不同。本例為 Non-Flit Mode，TC0、BCM=0；所有 bytes 都啟用，Payload 與 Length 相符，兩筆 Completion 都是 SC 且 EP=0。B 的最大讀取要求至少為 128 bytes，回覆路徑的有效 Payload 上限至少為 128 bytes；其他路徑與位址映射條件均已滿足。

觀察點在 Root Port 與 Switch 之間；下表是工具已辨識的邏輯交易紀錄，假設擷取範圍涵蓋這兩筆 Request 和表內 Completion，且已排除 Replay 的重複顯示。擷取結束後是否還有封包，並不在資料中。螢幕較窄時，可左右滑動表格。

紀錄Requester ID／Tag要求範圍或 Completion 欄位
Request A0x0300／0x13讀取 0x40001000–0x400010FF，共 256 bytes。
Request B0x0400／0x13讀取 0x40002000–0x4000207F，共 128 bytes。
Completion A10x0300／0x13Length=32 DW、Byte Count=256、Lower Address=0x00。
Completion B10x0400／0x13Length=32 DW、Byte Count=128、Lower Address=0x00。

先配對：A1 的識別組合是 0x0300／0x13，所以對應 A；B1 對應 0x0400／0x13 的 B。Tag 雖然相同，兩筆 Transaction ID 仍不同。每個 Requester 必須在自己的未完成要求中維持 Tag 唯一，並不需要替整個系統預留同一個 Tag。

再核對範圍：在本例全 byte 啟用的條件下，A1 的 32 DW 是 128 bytes，對應 0x40001000–0x4000107F；Byte Count=256 包含這 128 bytes 和後面還要返回的 128 bytes。這段 Trace 尚未看到 A 的 0x40001080–0x400010FF。B1 的 128 bytes 則覆蓋 B 要求的完整範圍，不能拿來填補 A。

兩個 Completion 的 Lower Address 都是 0x00，因為各自起始位址的低 7 bits 都為 0；這個欄位不足以單獨還原完整位址。表中沒有提供 Completer ID 或各端的完整紀錄，因此 B 的資料範圍雖已覆蓋，仍需核對 Completion 的其他欄位及 Requester 接收結果。A 的後半段可能在擷取結束後返回、未被擷取，或尚未返回；現有資料不足以判定 Timeout 或指定故障位置。

用兩個問題確認理解

第一個回覆帶 128 bytes，Byte Count=256，是錯誤嗎？

不是。它還包含這筆要求後續的 128 bytes；本片段大小另由 Length 表示。

只看到 Base 6.0，就能套 Figure 2-31 解所有封包嗎？

不能。本章選用 Non-Flit Mode；Flit Mode 的 Header 定義在 §2.2.1.2，布局不同。
