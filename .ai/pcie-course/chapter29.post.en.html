A BAR (Base Address Register) describes a resource. Resizable BAR lets software select among supported sizes, but allocation still needs ancestor windows and platform address space. Connect size selection back to Chapter 4’s address path before considering EA and FPB.

Read support, policy, and sequencing together

Figure 7-174 locates each capability/control pair; Figure 7-176/Table 7-152 lists sizes; section 7.8.6 defines sequencing. In the author scenario, a device supports 256 MiB and 1 GiB but the platform can allocate only 256 MiB. Support alone cannot create the larger range. Before resizing, quiesce affected use, clear Memory Space Enable, select size, reprogram the now-undefined BAR, and validate the route before enabling decode. A PF’s normal Resizable BAR does not change SR-IOV settings.

Avoid counting an EA resource twice

EA (Enhanced Allocation) describes resources beyond ordinary BAR/Base-Limit mechanisms in permitted topologies. Start with applicability in 6.23, then entry layout in 7.8.5. When an entry associates a resource with an equivalent BAR, that BAR must not request the same resource and is hardwired to zero. Bridge EA need not inclusively report every downstream resource; software must still search downstream functions. Basic decode-enable rules remain.

Separate identity scope from resource translation

Hierarchy ID supplements Routing ID with system/RC and hierarchy identity so equal numeric IDs in different hierarchies are not mistaken for one function. FPB (Flattening Portal Bridge) addresses bus-number waste and non-contiguous allocation. Figures 6-28 through 6-30 locate logical bridges and show bit-vector assignment of resource bins to the Secondary Side. It is an explicitly supported/configured mechanism, not a universal removal of ordinary bridge rules.
