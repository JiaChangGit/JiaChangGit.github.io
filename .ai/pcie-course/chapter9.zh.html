1. 只想重新初始化 03:00.0，該選哪種 Reset？

本例要讓 03:00.1 繼續工作，因此選擇只影響 03:00.0 的重設機制。Base 6.0 的 Conventional Reset（一般重設）涵蓋 Cold、Warm、Hot 三種；FLR 則只重設指定的普通功能，保留 Link（相鄰埠間連線）與其他普通功能的狀態。

依影響範圍選擇重設機制
機制如何發生本例需注意的範圍
Cold Fundamental Reset供電後必須發生的 Fundamental Reset。影響接受該重設的元件；不能當成只重設 03:00.0。
Warm Fundamental Reset沒有移除再接回主電源，由硬體觸發 Fundamental Reset。Base 未定義通用的 Warm Reset 產生方式，需看平台與 form factor。
Hot Reset透過 Link 的 in-band 機制傳播 Conventional Reset。這條 Link 下游的元件受影響；若往下還有 Switch，範圍可能延伸到整個分支。
FLR對支援 FLR 的 Endpoint Function 寫入 Initiate FLR。重設指定普通 Function，不得改變 Link 狀態，也不得影響其他普通 Function。

虛擬化有額外的相依關係：SR-IOV（把一個裝置提供成多個虛擬功能的機制）中，PF（Physical Function，管理虛擬功能的實體功能）收到 FLR 時會清除 VF Enable（虛擬功能啟用位），使其 VFs（Virtual Functions，虛擬功能）不再存在。因此，這類重設還要納入其所管理的虛擬功能。

PERST#（硬體提供的重設訊號）是提供給元件或卡片時使用的 Fundamental Reset 訊號名稱，但 Base 沒有替所有插槽形式規定一套通用的板級時序。不能把某張卡的 PERST# 操作方法當成 PCIe 所有平台都成立的步驟。

在 Root Port 或 Switch Downstream Port 設定 Bridge Control 的 Secondary Bus Reset，必須送出 Hot Reset。以本例來說，重設 02:01.0 的次級側會波及 03:00.0 與 03:00.1；若改在 Switch 更上游發起，還可能影響另一分支的 04:00.0。應先沿 Chapter 1 的拓樸畫出範圍，再決定能否操作。

3. 停止發送新請求後，舊交易怎麼處理？

BME（裝置發送許可）清零後，裝置停止發出適用的新請求；先前已送出的請求仍可能在系統中傳遞。Transactions Pending 也只反映此 Function 發出的 Non-Posted Requests；它沒有計算所有 Posted Writes、CPU 對裝置的存取，或裝置在外部介面的工作。

考慮一個作者假設的情境：03:00.0 已送出 Tag（交易識別標記）=0x13 的 MRd（Memory Read，記憶體讀取），Completion（完成回覆）還在路上。FLR 讓 Function 丟失先前交易的追蹤資訊；若軟體立即恢復工作，Function 又將同一 Tag（交易識別標記）用於新 MRd（記憶體讀取），遲到的舊 Completion（完成回覆） 就可能被誤認為新交易的回覆。這是規格所提醒的 stale Completion 風險。

停工時，各欄位實際追蹤哪些事情
觀察可以判斷不能據此判斷
BME=0禁止其適用的新 Request 發送。所有舊 Completion 都已回來。
FLR 前 Transactions Pending=0其追蹤的 Non-Posted Requests 已完成或被 Completion Timeout 終止。所有 Posted Writes 與外部工作均已完成。
FLR 後 Transactions Pending=0符合 FLR 完成時必須清除此 bit 的要求。證明沒有任何舊 Completion 仍在系統中。

因此，應先停止其他軟體對 Function 的存取，依裝置介面停止新工作、協調 DMA 與中斷，再處理 PCIe 未完成交易。規格的 Implementation Note 提供一種安排：清除整個 Command、輪詢 Transactions Pending，待它清除或已等待足夠時間確信剩餘回覆不會到達後，再發起 FLR。這是範例演算法，不是所有裝置都只要照抄這幾步就完成停工。

4. 100 ms 到了，是哪一件事完成了？

上圖的正常流程已在重設前處理舊交易。現在把等待條件拆開來看，以便處理「觸發時仍有未完成請求」的情況。規格要求 Function 在觸發後 100 ms 內完成 FLR；但 Function 特有的後續初始化可能還需要時間。若超過這個時限後仍需要初始化，它收到 Configuration Request 時必須回 RRS（要求稍後重試）。當它已對 Configuration Request 回過非 RRS 的 Completion，就不能在下一次 Reset 前又回 RRS。

若發起 FLR 時 Transactions Pending=1，軟體在初始化前還必須留出足夠時間，讓相關 Completion 到達，或合理確信它們不會再到達。規格建議參考 FLR 前的 Completion Timeout；若當時 timeout 被停用，等待時間由系統決定，但不得少於 100 ms。不能拿 FLR 後的預設 timeout 值替換這個判斷。

若支援 Function Readiness Status（FRS，功能就緒狀態通知），收到 Configuration-Ready 訊息可讓系統軟體提早發出 Configuration Requests，但這不保證 Function 先前發出的 Requests 都已完成。FLR 進行中，收到的 Request 可以被靜默丟棄；不要用任意 MMIO（Memory-Mapped I/O，記憶體映射 I/O）讀取當成標準 FLR 完成檢查。

時間與存取規則

§6.6.2（pp.725–727）。觸發 FLR 的 Configuration Write 必須先獲得 Completion，再開始 FLR；進行中的 Request／Completion 處置與後續 RRS 規則見 p.726。FRS 是有條件的就緒通知，不取代對 stale Completion 的等待。

5. 如果用的是 Hot Reset，能套同一套等待方式嗎？

Conventional Reset（一般重設）要另外選擇等待起點；它取決於連接埠的速率能力與就緒通知。例如在無法確定可用 DRS（Device Readiness Status，裝置就緒狀態通知）、且沒有其他適用的提早就緒機制時：若 Downstream Port 只支援到 5 GT/s，至少從 Conventional Reset 結束等待 100 ms；若它支援高於 5 GT/s，則至少從 Link training 完成後等待 100 ms，才向緊鄰下游裝置發出 Configuration Request。

作者時間例：Reset 在 t=0 ms 結束，一個支援 16 GT/s 的 Port 到 t=40 ms 才完成 Link training。上述分支的第一個 Configuration Request 最早在 t=140 ms，而不是 t=100 ms。這個時間不是保證裝置已成功完成初始化；它仍可能依法回 RRS。

Immediate Readiness（立即就緒）、DRS（裝置就緒通知）、Readiness Time Reporting（就緒時間回報），以及系統已知的特定裝置需求，可能改變可存取時間，必須依各自條件判斷。未使用 Readiness Notifications 時，在 Conventional Reset 結束後至少要容許 1.0 s，才能因有效 Configuration Request 尚未取得 Successful Completion 而判定裝置故障；這與前述第一次可送 Request 的等待是不同規則。

Conventional Reset 的時間分支

§6.6.1（pp.722–723）。本例選用支援高於 5 GT/s、無提早就緒例外的分支。RRS 的 Host 可見性與合法使用時機已在 Chapter 3說明；不要把 RRS 當成一般 MMIO 的重試狀態。

6. FLR 後，能把整份 Configuration dump 寫回去嗎？

軟體要按欄位用途與存取屬性恢復設定。RO（唯讀）欄位不用寫回；RW1C（寫 1 清除）欄位寫回原值會清除狀態；觸發控制與共享欄位則各有使用條件。FLR 的基本要求是把 Function Register 與專屬狀態機回到指定的初始化值，但 §6.6.2 明列了一批保留例外。

恢復設定前先分類
欄位／狀態FLR 行為或注意事項

舊回覆還可能到達時，為什麼要延後恢復工作？

重設會讓功能失去舊交易的追蹤資訊。若立即重用交易標記，遲到的回覆可能被配給新交易；因此要依觸發時的狀態與重設前的逾時設定，完成必要等待。重設後 Pending 清零是規定的狀態變化，不能代替這段等待。

電源狀態切換也會影響初始化，該從哪裡接著讀？

D3hot→D0 的行為還受到 No_Soft_Reset（不進行軟重設）欄位影響。既有 Chapter 10 會從 PMCSR（電源管理控制與狀態暫存器）說明；電源狀態切換有自己的條件，不保證等同本章的功能重設。
