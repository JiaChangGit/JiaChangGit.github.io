P2P (Peer-to-Peer) describes device-to-device traffic. Direct routing still depends on topology support, addresses, permissions, and ACS (Access Control Services) controls. Follow one request before separating redirection, blocking, and multicast.

Combine capability, control, and direction

Discover support in Capability, then active configuration in Control. Add packet type, direction, and AT (Address Type). Translation Blocking checks upstream Memory Requests and does not affect completions. In the author scenario, A writes to B through a switch ingress with P2P (peer-to-peer traffic) Request Redirect enabled. The request goes toward RC validation rather than automatically taking a direct sibling path; the RC validation algorithm is not architected here.

Trace request and completion directions separately

Request and Completion Redirect are separate controls that preserve ordering. Section 6.12.1 describes completion redirection, including Relaxed Ordering conditions; section 6.12.6 supplies ordering interactions. Draw both directions explicitly instead of assuming a symmetric route and identical checks.

Apply the multicast hit conditions

Figure 6-14 partitions a multicast range into group windows. Section 6.14.1 limits a hit to enabled Memory Writes or Address Routed Messages, both Posted Requests. A Non-Posted Memory Request in the same window remains unicast. In an author-valid configuration with 1000h windows and address offset 2500h, the group formula selects group 2; membership and permissions still need configuration. A multicast hit also changes routing and ACS applicability: only ACS Source Validation can still apply.
