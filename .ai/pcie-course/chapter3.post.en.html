Enumeration establishes usable configuration paths before discovering downstream Functions. It must also distinguish valid identity, temporary unreadiness, and failed access. This chapter connects Bridge Bus Number programming with those different results.

Versions and teaching assumptions

Fields and transactions follow Base 6.0; platform and handoff context follows PCI Firmware 3.3, which is not its matching edition. The example is author-created, not a hardware procedure. It uses conventional BDF without ARI, SR-IOV, or FPB. The platform supplies Segment 0000, Bus 00–3F, and an accessible Root Port at 00:01.0. Links and waiting requirements are satisfied; software exclusively manages this configuration, with no competing hierarchy using these Bus Numbers. Printed and PDF page numbers coincide.

The platform supplies an entry point; Function reads supply evidence

Software starts with platform-provided Host/Root Bridge information: Segment, Bus ranges, and configuration access services. It does not search arbitrary physical memory. The Root Bridge's platform interface differs from a Root Port's external Link role. Firmware 3.3 requires all Host Bridges to be configured so that the OS can manage their downstream devices.

Vendor ID is the specification's recommended presence probe, with FFFFh indicating no Function. Software-visible data is not necessarily Completion payload: for software depending on all-one responses, the Root Complex synthesizes that value from a Configuration Request's UR result. Failed access or an unconfigured path cannot establish that a physical card is absent merely from arbitrary buffer contents.

0xFFFF0001 is not an ordinary Vendor/Device ID

RRS (Request Retry Status) is Base 6.0's status for temporary inability to service a Request in specified circumstances. It is legal only under the applicable Reset/Readiness conditions, not as a general busy response at any time.

A separate readiness scenario

Assume the target has just undergone a Reset permitting RRS, has not successfully completed a subsequent Configuration Request, and has no Configuration-Ready, Immediate Readiness, or other prohibiting condition. The Root Port manages visibility through its own control bit, with its PCIe Capability already located at 0x70. This scenario is separate from the normal enumeration below.

Open a temporary downstream range, then finalize it

The example follows one branch to completion before returning to its sibling. It temporarily uses the platform's 3F limit as Subordinate, then narrows the range to the discovered topology. This is a teaching strategy, not a mandatory universal algorithm.

Teaching sequence for Bus Number assignment
StepAction
1Set Root Port 00:01.0 to Secondary=01, Subordinate=3F.
2Find Switch Upstream Port 01:00.0; set Secondary=02, Subordinate=3F.
3Find Downstream A at 02:01.0; set Secondary=03, Subordinate=3F.
4Confirm 03:00.0 and 03:00.1; after completing this branch, narrow A's Subordinate to 03.
5Return to Bus 02 and set Downstream B at 02:02.0 to Secondary=04, Subordinate=3F.
6Confirm 04:00.0; narrow B to 04, then finalize the Upstream Port and Root Port at 04.

Header Type 80h at 03:00.0 only permits probing other Functions; Function 1's presence is separate evidence. Header Type 00h at 04:00.0, without another mechanism indicating otherwise, prohibits blanket probing of Functions 1–7. Ordinary Link partners use Device 0 in this example, while internal Switch Downstream Ports can use other Device Numbers.

Figure 7-14 locates Secondary/Subordinate at 0x19/0x1A, each eight bits, with meanings on p.937. Configuration Writes must complete before software uses the new path. The example does not derive a Bridge's own BDF from Primary Bus Number. A platform with reservation requirements need not narrow its final limit to 04.

Header Type and Configuration Request Type are distinct

Configuration Header Type 1 describes a Bridge layout. Configuration Request Type 1 routes toward a deeper target. For 03:00.1, the Root Port's next Bus is 01, so the Request continues to the Switch as Type 1. The Switch recognizes Bus 03 as Downstream A's immediate downstream Bus and converts it to Type 0 before sending it to the Endpoint. A Bridge also processes valid Type 0 Requests targeting its own Configuration Space.

This describes externally visible routing, without assuming the Switch's internal logical Bus is another physical PCIe Link. Targets outside valid ranges follow UR handling. (Base 6.0 §7.3.2–§7.3.3, pp.912–913.)

Discovery does not finish resource and workload setup

Enumeration provides Function inventory, bridge paths, and identity clues, not proof that MMIO or DMA is ready. Firmware 3.3 §3.5 (pp.34–35) requires the specified boot/console paths and all Host Bridges to be configured; other devices may be left to the OS. An arbitrary unconfigured Endpoint alone does not establish a firmware violation.

Can 0xFFFF0001 be treated as Device ID FFFFh when selecting a driver?

Not under the example's RRS conditions. It is synthesized unreadiness data, not actual identity. Handle readiness and retry instead of initializing an unknown product. (§2.3.2, p.220.)

Is a final Subordinate above 04 necessarily an enumeration error?

No. Check the platform's granted range, branch consistency, and reservation policy. 04 is this example's finalized result, not a universal constant.
