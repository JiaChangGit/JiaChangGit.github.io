DOE（Data Object Exchange，資料物件交換）提供韌體／軟體透過設定空間交換物件的機制。CMA（Component Measurement and Authentication，元件量測與認證）可在其上使用 SPDM（Security Protocol and Data Model，安全協定與資料模型）。先完成可用的物件交換，再談內容與信任判讀。

要查支援哪些協定，如何走訪 Discovery？

先從同一個 Function 的 Extended Capability List 找到 DOE（Data Object Exchange，資料物件交換）實例。每個實例都必須支援 DOE Discovery，但一個 Function 可以有多個實例，各自支援的協定也可能不同。DOE 使用 Configuration Request；Function 不能透過它直接對另一個 Function 發起 P2P 交換。

回覆準備好後，每個 DWORD 要怎麼取走？

以同一個模擬實例為例，假設 DOE Interrupt Enable=0，軟體輪詢 D+0Ch 的 Status。Busy 是 bit0、Error 是 bit2、Data Object Ready 是 bit31；它們代表不同狀態。假設處理後讀到 80000000h：Ready=1、Busy=0、Error=0，表示有物件可讀。

依 §7.9.24.6，每次從 D+14h 的 Read Data Mailbox 讀出目前 DWORD，接著對同一 Register 寫入任意值，確認移出這個 DWORD；下一次讀取才會取得下一個。假設回覆如下：

讀取順序讀得 DWORD讀完後的動作
Header 100000001h寫入任意值確認
Header 200000003h寫入任意值確認
內容01000001h寫入任意值確認最後一個 DWORD

Header 的 Length=3 確認這個回覆共三個 DWORD。再依 Figure 6-42／Table 6-31 解碼內容：Vendor ID=0001h、Data Object Protocol=00h、Next Index=01h。Index 00h 描述 Discovery 本身；Next Index=01h 告訴軟體下一次查詢要將 Request 內容改成 00000001h。

假設 Index 01h 的回覆內容為 00010001h，表示 Vendor ID=0001h、Protocol=01h（CMA/SPDM）、Next Index=00h，走訪至此結束。索引只在這個實例的 Discovery 清單中有意義，不固定代表某個協定。若 Vendor ID=FFFFh，Index 無效或超出範圍，其他兩個欄位為 undefined，不可拿 Next Index 繼續走訪。

最後一個 DWORD 也要寫入確認；如果沒有其他物件等候，硬體才清 Ready。若有多個物件連續可讀，Ready 可以保持為一。讀取後漏掉確認，會再次讀到同一個 DWORD；Ready=0 時的讀值 00000000h 也不是一筆可用資料。

看到 Error 時，如何回到可接收狀態？

DOE Error 是唯讀狀態，不是 Write 1 to Clear。軟體對 D+08h 的 DOE Abort 寫 1，實例須在一秒內清除 Error 與 Ready；Abort 讀回固定為零。Abort 後 Busy 仍可能暫時為一，須等它清除，才能再次送出物件。若同一個實例可能由多個軟體工作者使用，還須在完整 request／response 交換期間協調所有權。

對 request／response 協定，若沒有協定專屬時限，§6.30.2 要求從 Go 起一秒內完成處理並在需要回覆時設 Ready；否則同一時限內須設 Error。這是裝置的規格要求，單次輪詢看到 Busy 並不足以推論已逾時。FLR 會中止進行中的 DOE transfer，但不必然重設內部處理引擎。

DOE Interrupt Status 是另一個 RW1C 狀態；清它不等於清 DOE Error。中斷是否存在、是否啟用及向量選擇要另查 DOE Capabilities、Control 和 MSI／MSI-X 設定。DOE 層錯誤與所承載的協定錯誤也要分開判讀。

物件成功交換，接收端就值得信任了嗎？

還要看SPDM（定義安全交換內容與程序的協定）與平台信任政策。Figure 6-43把協定、secured messages與DOE／MCTP承載方式分層。§6.31明確說明：Base處理PCIe特定要求，基礎架構、訊息與協定定義在所引用SPDM文件。
