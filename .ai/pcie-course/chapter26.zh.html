一個裝置提供很多 Function，身分與資源怎麼算？

先由 PF 配置數量與資源，再分別推算路由身分和記憶體範圍，最後確認 VF 的啟用與解碼條件。

SR-IOV（Single Root I/O Virtualization，單根 I/O 虛擬化）讓多個系統映像共用裝置資源。PF（Physical Function，實體功能）管理相關設定，VF（Virtual Function，虛擬功能）則有自己的 Routing ID 與資源範圍。先把身分與位址分開，再讀啟用流程。

  1. 先設定會影響資源的條件

    NumVFs 只能在 VF Enable=0 時變更；ARI Capable Hierarchy 另有全裝置的停用條件。

    PF（管理這組虛擬功能的實體功能）先確認數量、Supported／System Page Size 與相關資源。

    Base 6.0 §9.2.1，pp.1445–1446。

  2. 分別計算身分與記憶體

    Routing ID 的 offset 不是 byte address，VF（提供個別資源介面的虛擬功能）也不支援 I/O Space。

    Table 9-1 用 PF Routing ID、First VF Offset 與 Stride 算身分；Figure 9-9 用 VF BAR 與 aperture 算記憶體範圍。

    Base 6.0 §9.2.1.1.1、§9.2.1.2，pp.1445–1447。

  3. 最後啟用並檢查存取

    開啟可見的功能與允許記憶體解碼是相應的控制條件，不能由已算出位址推定已可使用。

    VF Enable 控制啟用；VF 記憶體空間要同時滿足 VF Enable 與 VF MSE。

    Base 6.0 §9.2.1.1.1，p.1446。

要找到第 3 個 VF，該看哪張表？

先把所需的 NumVFs 與 ARI Capable Hierarchy 配好，再讀 First VF Offset 與 VF Stride；這些欄位可能受前述配置影響。接著用 Table 9-1 計算第 N 個身分：PF RID＋First VF Offset＋(N−1)×Stride，採 16-bit 無號運算。RID 是 Routing ID（路由識別碼）。

作者案例：假設合法配置中的 PF RID=0300h、First VF Offset=0010h、Stride=0002h，NumVFs=3，則三個 VF 的 RID（封包使用的路由識別碼）為 0310h、0312h、0314h。實際部署還要確保所有 PF／VF 身分不重疊，並保留所需 Bus Number。

VF 的 BAR 要乘數量，還是每個 VF 都寫一份？

SR-IOV 能力內的 VF BAR 描述每個 VF 的 aperture（位址視窗大小）。第一個 VF 從所配置基址開始，後續 VF 依固定 aperture 連續推算；Figure 9-9 把 PF 與 VF 的範圍分開。

接續作者案例：某 VF BAR 的第一個基址為 90000000h，每 VF aperture 為 10000h。第 3 個 VF 的起點為 90020000h，這與前節 RID=0314h 是不同單位的結果。配置時還要確認上層資源容納全部範圍，並以 Supported Page Sizes 選合法 System Page Size。

ARI 和 Shadow Function 是更多 VF 的同義詞嗎？

ARI（Alternative Routing-ID Interpretation，替代路由識別碼解讀）把傳統的 Device／Function 欄位改讀為 8-bit Function Number，使單一 Bus 上可表達更多 Function。ARI（用不同方式解讀同一個 16-bit 身分）是識別與轉送規則，並不自行建立虛擬功能。

Shadow Functions（影子功能）則借用未實作 Function 的交易識別資源，讓要求者有更多未完成要求。它沿用關聯功能的特性，不能當成另一個獨立 VF 交給軟體管理。VF Resizable BAR 也有自己的能力結構，應與 PF 的普通 Resizable BAR 分開讀。
