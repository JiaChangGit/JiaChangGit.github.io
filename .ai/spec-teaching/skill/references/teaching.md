# 如何教人、如何表達

## 從一個問題開始

先確定本段要讓讀者理解哪個關係，再選文字或圖表。開頭的總覽要讓讀者知道系統中有哪些角色、正在觀察哪一段，以及本篇準備解釋什麼。前情只保留接下來會使用的關係。

例如要教查詢某項能力，先說明軟體要確認的功能，再帶讀查詢入口、目標物件、回覆結構與欄位，最後接到後續設定。不能只列 Figure 編號，也不能在還沒解釋查詢方法時要求新手自行作答。

章內可以用「為什麼要先查這個欄位？」帶出原因，用「讀到這個值後，下一步查哪裡？」銜接後續。答案直接帶讀實際步驟。章末可以串接完整案例，不設評分、通過門檻或為了測驗而隱藏資訊。

## 圖與文字各自補足什麼

| 要理解的關係 | 選用形式 | 圖中要交代 |
|---|---|---|
| 元件與路由 | 拓樸／關係圖 | 角色、連接、方向與觀察位置 |
| 不同元件之間的事件 | 時序圖 | 執行者、事件、先後與等待條件 |
| 狀態何時改變 | 狀態圖 | 狀態、觸發與轉換條件 |
| 操作依賴與選擇 | 流程圖 | 動作、等待、互斥分支及恢復入口 |
| bit／byte 與欄位關係 | 欄位圖／表格 | 位置、編碼、單位、有效條件與用途 |
| 相似機制如何選擇 | 比較表 | 具體比較維度及適用條件 |

不強制每節都放圖，不強制每張 Spec 圖重畫。總覽與放大圖沿用角色名稱、位置與顏色。箭頭帶實際事件；互斥分支不畫成先後步驟；簡化的範圍在圖旁說明。

逐步功能保留完整圖與全部必要解說，只標示當前角色、事件及段落。點選角色先說明它在這一步的責任，基本名詞可另外展開。離線、停用 JavaScript 和列印都要保留教學內容。

圖前交代追蹤對象，圖後補充關鍵原因及下一段的接點，不逐格複述。數值用來解釋欄位與流程，須正確驗算，但不以大量算題取代教學。

## 把 Figure 串成路線

先給簡短路線，再在對應步驟就近標出來源。每一步需要說清楚：現在查哪張圖或哪段條文、看哪個欄位、哪些前提影響有效性，以及這項資訊如何帶到下一步。有些規則只有條文，不能硬補 Figure。

NVMe 圖表情境每冊先帶讀一個既有完整情境。該情境仍只有一個正式位置，接著列其他情境與圖表索引；保留直接查欄位、圖號的入口。查詢回覆與規格定義各有用途：Spec 教讀法，作者假設值用來示範判讀；兩者標示清楚。

來源短標示在相關段落旁可見；完整文件名、版本、Section、Figure／Table、文件頁、PDF 頁可展開。大表指到實際使用欄位的頁面。保留原網址與圖表錨點，跨篇只補必要背景，完整原理回到主要文章。

## 中文語句

先寫主詞、動作與對象，再接原因、結果與條件。切換 Host、controller、namespace、CPU、Port 或 Function 時，重新寫出主詞。代詞「它」「此時」「這個值」要有明確指涉。

「因此」前須有足以支持結果的原因；「不過」表真正轉折；「如果」說明適用條件。可以多寫幾句交代前提，不為精簡省略語意，也不以斜線、箭頭和英文片語代替完整中文。

| 避免的說法 | 改寫方向 |
|---|---|
| 而不是直接假設某個位址就是目標 | 先從清單取得結構起點，再加上目標欄位的位移。 |
| 能不能得出某個結論？ | 接下來查看狀態欄位，確認目前的速率與寬度。 |
| 這三次查詢回答不同問題，不能用其中一次代替另外兩次 | 查詢分成三部分：支援能力、控制設定，以及目前狀態。接著逐項說明查詢方法。 |

以上是表達方向，不是全庫替換規則。規格真正的禁止、未定義、保留值及失敗條件仍要明確解釋。不得把 should 改成 shall，或替 undefined 行為指定固定錯誤結果。

英文關鍵字／縮寫每篇前兩次就近解釋；第一次給正式名稱與本段用途，第二次簡短提醒用途即可。圖內首次出現者就在圖旁解釋。後文優先採穩定的中文說法，不反覆塞全名。CPU 與基本位元運算屬已知背景，不必重教。

## 版面與三版本

正文採易讀單欄，標題、留白、圖表、來源及案例維持共同層級。PCIe 主色藍、NVMe 主色綠；實際來源依名稱與版本辨識，不要求每份 Spec 另配一色。必要時用文字、線型和標籤補充，避免只靠顏色。

繁中 HTML 提供完整分步教學；中英文文章保留同一主線、核心圖、代表案例及條件。縮短時省略次要延伸，保留能讓讀者理解本篇的推理。英文自然改寫，兩種語言的技術含義對等。

「有沒有教清楚」由校閱角色、條件、圖文銜接與完整案例來判斷。腳本只能找出待檢查處；沒有真人閱讀資料時，不宣稱讀者已經學會。
