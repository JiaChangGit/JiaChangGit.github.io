如果系統列出兩個 PCIe Function，機器裡就一定有兩張卡嗎？如果兩筆紀錄都寫著 03:00.0，又能確定它們指向同一個對象嗎？要回答這些問題，得先把實體連接、設定空間中的拓樸，以及識別號的範圍分開。

版本與適用範圍

欄位依 PCI Express Base Specification Revision 6.0；Segment 的背景依 PCI Firmware Specification Revision 3.3。本章採傳統 Bus／Device／Function 編址，不使用 ARI（Alternative Routing-ID Interpretation）、SR-IOV（Single Root I/O Virtualization）或 FPB（Flattening Portal Bridge）Routing ID 機制。這些機制涉及額外的發現、編號或路由規則，留待後續章節；其中 ARI 會改變 Device／Function 位元的解讀。頁碼均為本課程採用 PDF 的文件頁／PDF 頁，兩者相同。

1. 系統列出的是卡，還是 Function？

先想像一張插入主機的擴充卡。卡是實體組裝的單位；軟體卻不是替整張卡讀取一份共同的設定空間。軟體會找出可辨識的 Function，再分別讀取各自的設定資料。同一個 Device 可以只有一個 Function，也可以有多個 Function；一張卡內還可能有 Switch 及多個元件，所以不能把這幾個數量畫上等號。

看到同一件硬體時，我們可能在談不同的對象
用語這一層在回答什麼問題？不能直接推得什麼？
實體卡、封裝元件裝在哪裡，如何連到主機？不能只憑卡的數量，推算 Function 的數量。
Device在傳統編址下，同一個 Bus 上的哪個 Device Number？Device Number 不是插槽號，也不是產品型號。
Function這個 Device 中，要讀取哪一個軟體可辨識對象的設定空間？一個 Function 不一定對應一張卡或一個獨立封裝。
Port元件透過哪個介面連接相鄰的 PCIe Link？Port 的實體編號不能當成 BDF 裡的 Device Number。

這裡的 Device 特別指設定模型中的位置。「這個裝置」在日常說法裡也可能指整張卡或整顆晶片；後續只要涉及位址，就會寫出 Device Number 或完整 BDF，避免混淆。

2. Switch 為什麼會在設定空間裡變成多個 Bridge？

在本章使用的設定模型中，Root Port 表現為一個 PCI-to-PCI Bridge。Switch 則由多個邏輯 Bridge 組成：Upstream Port 的下游是 Switch 內部的邏輯 Bus；每個 Downstream Port 再從這個 Bus 接出一條外部 Link。這個安排讓軟體能沿著橋接關係認識整棵樹。

PCI-to-PCI Bridge 是設定模型裡連接上、下游匯流排的橋接功能。Upstream 指朝向 Root Complex 的方向；Downstream 指離開 Root Complex、朝階層下游的方向。Switch 的 internal bus 是邏輯表示，不是把外部 PCIe Link 改成共享的平行匯流排。

教學假設：已完成發現與配置的快照

下圖的編號與元件由作者設計，不是規格指定的固定拓樸，也不是實機量測。所有列出的 Function 都已確認存在，相關設定讀取成功，查詢期間拓樸不變。Requester ID 的案例也不使用 Phantom／Shadow Functions；這些機制可借用額外的 Function 識別號，留待交易進階內容再談。卡 A 內的一個 Device 提供 Function 0 與 Function 1，卡 B 提供另一個單功能 Device。圖中省略 CPU、記憶體及其他路徑；Bus Number 的配置過程留到 Chapter 3。

先從上方一路往下讀：Root Port 的下一層是 Bus 01；到了 Switch Upstream Port，下一層才是內部 Bus 02；兩個 Downstream Port 再分別接到 Bus 03 和 Bus 04。所以 02:01.0 是橋接功能本身的位置，03:00.1 才是它下游的目標 Function。

3. 03:00.1 的每一段究竟選了誰？

Bus、Device、Function 合稱 BDF。在傳統編址下，Bus Number 有 8 bits，Device Number 有 5 bits，Function Number 有 3 bits。先選定 PCI Segment Group（本章簡稱 Segment），再選其中的 Bus，接著選 Device 與 Function，才能定位本章的設定對象。

另一個 Segment 也有 03:00.0，會衝突嗎？

新增教學假設：系統另有 Segment 0001，其中一條 Root Port 路徑接到 0001:03:00.0。這與圖中的 0000:03:00.0 是兩個不同的設定對象；只有省略 Segment，才會看起來相同。紀錄資料時，應把 Segment 與 BDF 一起保留。

反過來，同一份穩定快照、同一個 Segment 裡，03:00.0 和 03:00.1 具有相同的 Bus 與 Device，指向同一個 Device 的兩個 Function。至於它們在實體上裝在哪張卡，還需要實體配置的資訊；本例是題目另行給定卡 A 的組裝方式。

4. 只知道 BDF，怎麼查它是 Endpoint 還是 Port？

BDF 告訴你查詢對象的位置，卻沒有直接編碼它的角色。要判斷 02:01.0 是什麼，先查 Header Type，再到該 Function 的 PCI Express Capability 查 Device/Port Type。前者決定標頭版面；後者才區分 Root Port、Switch Port 或 Endpoint。

Header Type 為 0x80，就代表有 8 個 Function 嗎？

不是。先做 0x80 & 0x7F = 0，可知 Header Layout 仍是 Type 0；bit 7 為 1，只表示這個 Device 可能含有多個 Function，允許軟體探查其他 Function，並未回報數量。卡 A 的 Function 1 存在，是題目已確認的另一筆資料，不能只從 0x80 推出。

Table 7-7 也規定，若此 bit 為 0，軟體不得探查 Function 0 以外的 Function，除非 ARI、SR-IOV 等其他機制另有指示。本章已排除這些機制；不能為了練習，就把「一律掃完 0–7」當成通用規則。

5. 要找 Bus 03，為什麼沿著 Downstream A？

角色已經查清楚，接著要確認橋接關係。對本章採用的一般 Type 1 Bridge 而言，Secondary Bus Number 指出緊接在下游的 Bus；Subordinate Bus Number 則標出其下游階層涵蓋的最高 Bus Number。兩個值一起讀，才分得清「下一層是哪個 Bus」與「整個下游範圍到哪裡」。

閱讀順序是：先由 Header Layout 確認 Type 1，再看 Type 1 Configuration Space Header 的 Figure 7-14，找到 0x19 與 0x1A，最後讀 §7.5.1.3.3 與 §7.5.1.3.4 的欄位定義。兩個 offset 都從該 Function 的設定空間起點計算，各讀 8 bits；它們不以 PCIe Capability 為起點。

這裡練習的是把已知快照與欄位對上，沒有執行 Configuration Write。Bus Number 怎麼分配、尚未配置時如何搜尋，以及 Configuration Request 如何轉送，分別留到枚舉與交易章。也不要把這張 Bus 範圍表當成 Memory BAR 的位址窗口；它們處理的識別與資源不同。

6. 封包裡的 Requester ID 和 BDF 有什麼關係？

當某個 Function 發出交易要求時，Requester ID 用來識別要求者。本章的傳統格式把 Bus、Device、Function 放進 16 bits；因此，先理解 BDF，後面閱讀交易封包才知道這個欄位在指誰。封包如何配對要求與回覆，會在 Chapter 5 再談。

Requester ID = (Bus << 8) | (Device << 3) | Function
03:00.1 → (0x03 << 8) | (0x00 << 3) | 1 = 0x0301
02:02.0 → (0x02 << 8) | (0x02 << 3) | 0 = 0x0210

案例推演：要把 0x0210 還原，先取 (id >> 8) & 0xFF = 0x02 得到 Bus，再取 (id >> 3) & 0x1F = 0x02 得到 Device，最後取 id & 0x07 = 0 得到 Function。它對應圖中的 Downstream B，而不是 Bus 02 上的 Function 0x10。

這個算式只編碼身分，不表示所有經過 Downstream B 的要求都要改成 0x0210。Requester 是發出該要求的對象；沿途經過哪個 Bridge，是另一件事。把橋接路徑上的 BDF 都當成要求者，會失去原本要追蹤的 Function。

此外，0000:03:00.0 與 0001:03:00.0 的傳統 16-bit 編碼都會是 0x0300。因此只拿到這 16 bits，仍缺少判定 Segment 的情境。這不等於宣稱封包完全沒有 Segment 資訊：PCIe 6.0 的部分 Flit Mode 格式另有 Segment 欄位，不能與這個 16-bit 欄位混為一談。

規格依據：Requester ID 與 Segment 的邊界

先看 Base 6.0 §2.2.4.2 的 Table 2-8（p.147）、Figures 2-20／2-22（p.148）辨認非 ARI 的位元分配，再讀 §2.2.6.2（pp.156–157）的 Requester ID 規則。前幾張圖展示的是目的地 ID routing，不能把圖上的封包 byte offset 套到所有 Requester ID；本章只取 BDF 的編碼關係。p.157 也明定 Switch 轉送要求時不得修改 Transaction ID，並把 Segment 定義為獨立欄位。Flit Mode 的獨立 Segment 資訊見 §2.2.1.2，pp.134–139。本章只做欄位識別與編碼，沒有把傳統 BDF 的拆法延伸到 ARI。

7. 記住 BDF，下一次開機就能認出同一張卡嗎？

BDF 描述的是目前設定拓樸中的位置，不是製造時刻在硬體上的序號。Bus Number 由設定流程建立；若拓樸或配置方式改變，同一件硬體可能出現在不同位置。只比對兩次紀錄的 BDF，既不能保證相同位址仍是原來的硬體，也不能因位址改變就判定硬體被換掉。

換一次快照來想

假設另一次配置把卡 A 所在的 Bus 從 03 改為 05，其他相關路徑也已正確調整。原 Function 1 在新快照中就以 0000:05:00.1 被定位，傳統 Requester ID 也成為 0x0501。這是作者用來說明配置結果可能改變的情境，不表示每次開機都會重新編號。

若要跨開機追蹤實體裝置，就需要另外取得可信的裝置身分或平台位置資訊。Vendor ID、Device ID 描述廠商與裝置類型，不能單獨充當每一件產品的唯一序號。這類長期識別需求與本章的「選定目前哪個 Function」不同，不能用一組 BDF 同時回答。

規格依據與推論範圍

Base 6.0 §2.2.6.2（pp.156–157）說明 Bus／Device Number 的設定、捕獲與執行期間可改變的性質；另外， §7.5.1.1.1–§7.5.1.1.2（p.917）的 Vendor ID／Device ID 定義，也支持上述區分。換成 Bus 05 是教學推演；規格不要求每次開機更改 BDF，也未由這些 ID 保證實體個體的唯一性。

8. 換一個條件，你會怎麼查？

題目一：只讀到 Header Type = 0x01，就可以把這個 Function 標成 Switch Downstream Port 嗎？

還不行。依 Figure 7-8／Table 7-7，低 7 bits 只確定它採 Type 1 Header。下一步要找到 PCIe Capability，沿 Figure 7-21 到相對 offset 0x02，再依 Figure 7-23／Table 7-19 解碼 Device/Port Type；值為 6 才是本題要辨識的 Switch Downstream Port。Root Port 與 Upstream Port 也使用 Type 1 Header。

題目二：我只知道 Header Type = 0x80，可以把其他七個 Function 都標成「存在」嗎？

不能。Table 7-7 的 bit 7 只允許探查，沒有列出存在的 Function。正確的紀錄是「Type 0 Header；Device 可能含有多個 Function」，再保留各 Function 是否存在的獨立查詢結果。即使只有一個 Function，也可能看到這個 bit 為 1。

題目三：紀錄只有 Requester ID = 0x0300，能判定是卡 A 的 Function 0 嗎？

在本章的傳統格式下，可先還原為 BDF 03:00.0；還缺少 Segment 及這筆紀錄所屬的配置快照。若 Segment 是 0001，就不是圖中的卡 A；若是不同時刻的配置，也不能直接沿用舊圖。先補齊範圍與時間，再對照 Function。

題目四：圖中的兩條分支都連到 Device 00，是不是把同一個裝置畫了兩次？

沒有。卡 A 是 Bus 03 的 Device 00，卡 B 是 Bus 04 的 Device 00；BDF 的 Bus 部分不同。若要沿圖查到卡 B，先由 Type 1 Header 的 Figure 7-14 找到 Secondary／Subordinate 欄位，再使用本例 Downstream B 的 04–04 範圍。不能只拿 Device Number 00 比對。

9. 知道查誰之後，下一步看什麼？

現在可以先用 Segment 與 BDF 選定 Function，再用 Header Layout 與 Device/Port Type 判斷該怎麼讀它。Chapter 2 將整理設定空間的完整查詢方法：傳統與 Extended Capability 從哪裡開始、指標怎麼走，以及欄位寬度、版本與存取屬性如何影響解讀。
