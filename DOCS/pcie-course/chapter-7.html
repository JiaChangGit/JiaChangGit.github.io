裝置把資料放回記憶體後，軟體還需要知道有事情待處理。中斷提供通知；真正發生了什麼、完成了多少工作，仍要依裝置介面查閱。本章先分清 INTx、MSI 與 MSI-X，再從 Chapter 2 找到的 Capability 出發，算出 MSI-X Table entry 的位址，追蹤一次遮罩與通知。

版本與案例前提

來源為 PCI Express Base Specification Revision 6.0。沿用普通 Endpoint 03:00.0、MSI-X Capability 基底 0xD0，以及 Chapter 4 的 16 KiB BAR0，基底 0x80004000。不使用 SR-IOV、Enhanced Allocation 或 TPH；封包採 Non-Flit Mode，案例中資料與中斷都用 TC0、IDO=0。平台已完成資源映射，Endpoint 與路徑所需的 MSE／BME 均正確。

所有欄位讀值、事件、Table 位置與中斷 Address／Data 都是作者假設。設定流程描述系統軟體與裝置的分工，不是對實機執行的指令。

1. 都叫中斷，為什麼要分三種機制？

先選對規格中的機制
機制PCIe 上如何通知設定與判讀重點
INTx emulation使用 Assert_INTx／Deassert_INTx Message 模擬電位式中斷。PCI 相容機制；不是 PCIe Link 上另外拉一條傳統 INTx 訊號線。
MSI將系統指定的資料寫到指定的位址。Capability ID=0x05；Address／Data 與控制欄位位於設定空間。
MSI-X同樣發出 DWORD Memory Write。Capability ID=0x11；每個 entry 的 Address／Data 位於 Memory Space 的 Table。

MSI/MSI-X 的名稱雖然有 Message，實際使用的 TLP 類型是 Memory Write，不是 Msg／MsgD。這個區別會影響封包格式、路由與 BME 條件；它也沒有對應的一般 Completion。INTx 的 assert／deassert 才是這裡使用 Message TLP 的機制。

如果 Function 能產生中斷，Base 6.0 要求支援 MSI、MSI-X 或兩者；INTx 相容機制可以不實作。一個 Function 可以同時具有 MSI 與 MSI-X Capability，但系統不得同時啟用兩者；啟用 MSI 或 MSI-X 時，也不得改用 INTx 要求服務。運作中任意切換機制可能遺失或重複事件。

機制與互斥條件來源

§6.1–§6.1.4（pp.659–661）、§6.1.4.3–§6.1.4.4（pp.663–664）。Capability ID 見 Table 7-40（p.1013）、Table 7-48（p.1022）。MSI/MSI-X 的 Memory Write 格式也見 §2.2.7.1.1 前的說明（p.166）。

2. 如果查到的是 MSI，先看哪幾個欄位？

這一節另外使用一個獨立的 MSI 對照案例，不表示前面那個 Function 又多出未列在清單中的 Capability。先找到 ID=0x05，再看相對位移 +0x02 的 Message Control。假設讀到 0x0184：

MSI 對照案例的控制欄位
欄位解碼對後續閱讀的影響
Multiple Message Capable，bits 3:1010b：要求 4 個向量不是直接把二進位 010 當成 2 個。
Multiple Message Enable，bits 6:4；MSI Enable，bit 0000b；0MSI 尚未啟用；不能把 MME 的單向量編碼當成已在送中斷。

系統若只配置 2 個向量，可在 MSI 關閉時把 MME 設為 001b，完成 Address、Data 與遮罩設定後再啟用；配置數量不得超過能力。MSI 最多支援 32 個向量，且使用 2 的冪次編碼。MSI-X 的 Table Size 則是 N−1，不能套用同一套算法。

MSI 的四種布局取決於 32／64-bit Address 與是否支援 PVM。普通 PCI Express Endpoint 若實作 MSI，必須支援 64-bit Message Address；不能把 Legacy Endpoint 的選擇權原封不動套上來。MSI Message Control 的 RW 欄位由系統軟體管理，裝置驅動程式不能直接修改；本章的「配置」是指這個系統軟體流程。

3. 找到 MSI-X Capability 後，怎麼走到 Table？

回到 03:00.0。Chapter 2 已用傳統 Capability 清單找到 0xD0，這裡直接從該處往下讀，不重走清單。Figure 7-56 告訴我們：Control 在 +0x02，Table 定位值在 +0x04，PBA 定位值在 +0x08。

MSI-X 定位案例的設定讀值
Function 內位移寬度假設讀值欄位
0xD016 bits0x0011ID=0x11，Next=0。
0xD216 bits0x0007Table Size 編碼 7；MSI-X Enable 與 Function Mask 都為 0。
0xD432 bits0x00002000Table Offset／Table BIR。
0xD832 bits0x00003000PBA Offset／PBA BIR。

BAR Indicator Register（BIR）的低 3 bits 選擇哪個 BAR，其餘 bits 才是位移。本例兩個 BIR 都是零，因此都使用 BAR0。位移已經以 byte 為單位；遮掉 BIR 即可，不能再把結果左移 3 bits。

N = (0x0007 & 0x07FF) + 1 = 8
Table BIR = 0x00002000 & 0x7 = 0
Table offset = 0x00002000 & 0xFFFFFFF8 = 0x2000
Table base = 0x80004000 + 0x2000 = 0x80006000
PBA base = 0x80004000 + (0x00003000 & 0xFFFFFFF8) = 0x80007000

8 個 entries 各占 16 bytes，因此 Table 使用 0x80006000–0x8000607F。Pending Bit Array（PBA）每個 entry 對應 1 bit，按 QWORD 組織；8 個 entries 需要 1 個 8-byte QWORD，位於 0x80007000–0x80007007。兩者都落在 BAR0 內，也沒有重疊。

此外，Table／PBA 與不屬於 MSI-X 的其他可用 Register 不得共用同一個自然對齊 4 KiB 範圍。本例將一般 Register 放在 BAR0 的第一頁、Table 放在第三頁、PBA 放在第四頁，因此 Chapter 5 的 BAR0+0x120 不會混入 MSI-X 所在的頁面。這項配置是案例的額外假設；僅知道 BAR 大小並不足以推知內部分布。

4. Entry 3 的位址，和它發出中斷的位址，是同一個嗎？

不是。Table entry 是 CPU 設定裝置中斷行為的位置；entry 裡存的 Message Address 則是裝置發出中斷時要寫入的平台目的地。中斷不會因為 entry 位於 BAR0，就被送回同一個 BAR。

Entry 從零編號，所以 entry 3 是第四個。由 Equation 7-1 得到 0x80006000 + 3 × 16 = 0x80006030。依 Figure 7-57 的四個 DWORD，再逐一找到：

PCI Memory 位址Entry 內位移／欄位假設設定
0x80006030+0x00，Message Address0xFEE01000
0x80006034+0x04，Message Upper Address0x00000000
0x80006038+0x08，Message Data0x00000045
0x8000603C+0x0C，Vector Control初始讀回 0x00000001；保留其他 bits，只在適當時機清除 bit 0。

這組 Message Address／Data 假設由平台中斷配置機制提供，且已能正確導向中斷接收端。數字本身不代表本教材已定義 CPU 編號或中斷控制器格式；那些是平台規格的責任。尤其 0x45 不是 Table index，不能反推 entry 69。

發送時，裝置向 0xFEE01000 送出 1 DW 的 MWr，Payload 為 0x00000045，四個 bytes 都啟用。MSI-X 不會自行修改 Message Data 的低位元。此例的 Upper Address 為零，因此使用 32-bit 目的位址格式；RO 與 No Snoop 必須為零，IDO 本例也設為零。

5. 是不是先把 Enable 設為 1，再慢慢填 Table？

要先控制會不會發出訊息，再填入有效目標。以下是作者選擇的一種初始化安排，不是規格唯一指定的逐步演算法。假設裝置尚未產生活動事件，系統已配置中斷接收資源，其他 entries 保持遮罩；MSI-X Table／PBA 的 Memory 存取及中斷上行路徑都已準備好。

讓 entry 3 安全進入可通知狀態
步驟系統與裝置的狀態原因
1. 保持遮罩系統軟體將 Function Mask 設為 1，MSI-X 仍關閉；Message Control 讀回 0x4007。Table Size 的 7 是 RO 讀值；此處只改可寫控制位元。
2. 填 entryentry 3 的 Mask=1 時，填入 Address、Upper Address 與 Data，保留 Vector Control 其他 bits。不得在 entry 未遮罩時修改 Address／Data／適用的 Steering Tag。
3. 啟用並確認設定可見系統軟體啟用 MSI-X，保持 Function Mask=1；Control 讀回 0xC007。MSI 必須關閉；並由平台 I/O 存取規則確保 Table 更新已按要求生效。
4. 開放此 entry清 entry 3 的 Mask bit，再清 Function Mask；Control 讀回 0x8007。只有配置好的 entry 3 開放，其餘 entries 仍保持各自的 Mask。
5. 允許裝置開始工作依裝置介面啟動工作及事件來源。避免在通知路徑尚未準備好時產生活動事件。

Message Control 的 RW 欄位由系統軟體管理，規格不允許裝置驅動程式直接修改這些欄位；驅動程式應透過系統提供的介面協調。設定 Table／PBA 時，軟體必須使用對齊的完整 DWORD 或 QWORD 存取，不能以 byte 存取代替。若要遮罩原本未遮罩的 entry，不能同時用一個 QWORD 更新 Message Data 與 Vector Control，因為 Data 可能先改變；應先按規定以 DWORD 寫入 Mask。

Function Mask=1 時，即使 entry 的 Mask=0，仍不得送出該訊息。清除 Function Mask 也不會把每個 entry 的 Mask bit 一起清零。這兩層遮罩必須分別讀取，不能只看其中一個。

6. 遮罩期間發生三次事件，PBA 會記錄數字 3 嗎？

不會。Pending bit 表示該 entry 有待送的訊息，不是事件計數器。假設 MSI-X 已啟用、Function Mask=0，而 entry 3 的 Mask=1；在這段期間，裝置發生了本來應透過 entry 3 通知的事件。裝置不得送該訊息，必須將對應 Pending bit 設為 1。

依 Equation 7-2，entry 3 對應 PBA 的 QWORD 0、bit 3。本例若其他 bits 都為零，讀到的 QWORD 是 0x0000000000000008。再發生兩次相同通知需求，這個值仍可能是 8，不能據此說只發生一次。實際事件數量要看裝置自己的事件佇列或狀態。

同一 Pending bit 的兩種後續情境
後續條件裝置應如何處理
事件仍待處理；軟體解除有效遮罩裝置必須安排送出訊息，送出後清除 Pending bit。不是保證解除遮罩的當下 CPU 已進入處理常式。
仍在遮罩期間，但底層事件已依裝置介面被處理裝置必須清除 Pending，避免稍後解除遮罩時送出不必要的訊息；若又發生新事件，再重新設 Pending。

PBA 不使用 RW1C 清除方式。規格建議軟體只讀、不寫 Pending bits；若寫入，結果未定義。也不能把 PBA=0 當成「CPU 已完成服務」：它可能只是訊息已經送出，CPU 還沒開始執行處理常式。

7. 中斷到了，先前的 DMA 資料就能使用了嗎？

本例讓同一 Function 的資料寫入與 MSI-X 都使用 TC0。MSI-X 是 Posted Request，且 RO 必須為零；適用的排序規則不允許它越過該 Function 先前送出的 Posted 寫入。§6.1.4.7 進一步要求系統保證：由該訊息引發的中斷處理常式，能觀察到先於該訊息到達的 Posted 更新。因此，不必為了沖出這些先前寫入，額外讀一次裝置 Register。

這項保證不免除 Chapter 6 的映射與同步前提，也不把「收到中斷」變成所有工作都完成的通用證據。處理常式仍應依裝置介面找出完成項目。若資料與中斷使用不同 TC，裝置必須另外確保同步，不能直接沿用本例的同 TC 推理。

訊息接收順序也不保證處理常式的執行順序。若裝置一定要先服務事件 A 才能服務 B，就需要相應交握，不能只以先送 A、後送 B 達成。MSI/MSI-X 本身也不保證固定的中斷延遲。

通知與資料順序的適用範圍

§6.1.4 的跨 TC 同步說明與屬性限制（p.661）；§6.1.4.7（p.667）規定資料可見性、接收端獨立處理與服務順序；延遲不保證見 §6.1.4（p.660）。若多個 entries 共用同一向量，仍可能需要讀裝置狀態辨識事件來源；那是辨識用途，不是前述資料一致性的 flush。

8. 把查詢與通知串起來

Table Size 讀到 7，是 7 個、8 個，還是 128 個 entries？

是 8 個，因為 MSI-X 使用 N−1 編碼。不要套用 MSI 的 2 的冪次編碼。這也只代表 Table 容量，不代表系統已配置 8 個互不相同的中斷向量。（Table 7-49，p.1022。）

entry 3 的 Mask 已清除，卻還有 Function Mask=1，能送出訊息嗎？

不能。Function Mask 使所有 entries 都按被遮罩處理，不改變各 entry 自己的 Mask 值。（§6.1.4.5，p.664；Table 7-49，p.1022。）

只知道 MSI-X Enable=1，是否足以證明某項工作會通知 CPU？

不足。還要核對目標 entry、Address／Data、兩層遮罩、BME 與平台接收資源，以及裝置是否真的產生該事件。Capability 的存在、控制位元與事件結果是不同證據。

我要更新未遮罩 entry 的 Message Data，先寫 Data 再設 Mask 可以嗎？

不可以。未遮罩時改 Address／Data 的結果未定義。先按規定遮罩並確保更新順序，再修改內容，完成後才解除遮罩。（§6.1.4.2、§6.1.4.5，pp.662–665。）
