Reset 的範圍與恢復條件

從單一 Function 的 FLR 查詢，判斷重設範圍、舊 Completion、就緒時間與設定恢復。

「把裝置重設」還不是一個完整的操作描述。必須先知道要影響哪個 Function、哪條 Link，以及 Reset 後如何重新取得安全可用的狀態。本章以同一張卡上的兩個 Function 為例，從選擇重設範圍開始，再處理尚未完成的交易與設定恢復。

版本與案例

採 PCI Express Base 6.0。主案例是普通多 Function Endpoint 的 03:00.0 與 03:00.1，不含 SR-IOV；兩者共用連往 Switch Downstream Port 02:01.0 的 Link。數值、時間點與作業情境由作者假設。PF 的 FLR 會清除 VF Enable，使其 VFs 不再存在，不能把本例「其他普通 Function 不受影響」直接套到 PF／VF 關係。

1. 只想重新初始化 03:00.0，該選哪種 Reset？

先看 03:00.1 是否仍在工作。如果它必須繼續運作，就不能隨意把兩者共用的 Link 或整張卡一起重設。Base 6.0 將 Conventional Reset 與 Function Level Reset（FLR）分開；前者涵蓋 Cold、Warm、Hot，後者以 Function 為單位。

依影響範圍選擇重設機制
機制如何發生本例需注意的範圍
Cold Fundamental Reset供電後必須發生的 Fundamental Reset。影響接受該重設的元件；不能當成只重設 03:00.0。
Warm Fundamental Reset沒有移除再接回主電源，由硬體觸發 Fundamental Reset。Base 未定義通用的 Warm Reset 產生方式，需看平台與 form factor。
Hot Reset透過 Link 的 in-band 機制傳播 Conventional Reset。這條 Link 下游的元件受影響；若往下還有 Switch，範圍可能延伸到整個分支。
FLR對支援 FLR 的 Endpoint Function 寫入 Initiate FLR。重設指定普通 Function，不得改變 Link 狀態，也不得影響其他普通 Function。

PERST# 是提供給元件或卡片時使用的 Fundamental Reset 訊號名稱，但 Base 沒有替所有插槽形式規定一套通用的板級時序。不能把某張卡的 PERST# 操作方法當成 PCIe 所有平台都成立的步驟。

在 Root Port 或 Switch Downstream Port 設定 Bridge Control 的 Secondary Bus Reset，必須送出 Hot Reset。以本例來說，重設 02:01.0 的次級側會波及 03:00.0 與 03:00.1；若改在 Switch 更上游發起，還可能影響另一分支的 04:00.0。應先沿 Chapter 1 的拓樸畫出範圍，再決定能否操作。

Reset 分類與範圍來源

2. 我要查 FLR，依序看哪些 Figure？

先走 Chapter 2 的 Capability 清單，確認找到 PCI Express Capability，而不是直接假設某個位址有 FLR。本例已知 Capability 在 0x70、Device/Port Type=Endpoint。接著依下表查能力、未完成交易與觸發控制。原始讀值是作者假設，欄位定義則來自規格。

Initiate FLR bit 的讀值永遠是零，不能輪詢它等待「由 1 變 0」。同一 bit 在 PCI Express-to-PCI/PCI-X Bridge 的意義是 Bridge Configuration Retry Enable，因此 Function 類型是解碼前提。

3. BME 已清零，為什麼還不能立即重新開始？

BME 控制新的 bus-master Request，不會把先前已送出的 Request 從系統中收回。Transactions Pending 也只反映此 Function 發出的 Non-Posted Requests；它沒有計算所有 Posted Writes、CPU 對裝置的存取，或裝置在外部介面的工作。

考慮一個作者假設的情境：03:00.0 已送出 Tag=0x13 的 MRd，Completion 還在路上。FLR 讓 Function 丟失先前交易的追蹤資訊；若軟體立即恢復工作，Function 又將同一 Tag 用於新 MRd，遲到的舊 Completion 就可能被誤認為新交易的回覆。這是規格所提醒的 stale Completion 風險。

不同觀察值能支持的結論
觀察可以判斷不能據此判斷
BME=0禁止其適用的新 Request 發送。所有舊 Completion 都已回來。
FLR 前 Transactions Pending=0其追蹤的 Non-Posted Requests 已完成或被 Completion Timeout 終止。所有 Posted Writes 與外部工作均已完成。
FLR 後 Transactions Pending=0符合 FLR 完成時必須清除此 bit 的要求。證明沒有任何舊 Completion 仍在系統中。

因此，應先停止其他軟體對 Function 的存取，依裝置介面停止新工作、協調 DMA 與中斷，再處理 PCIe 未完成交易。規格的 Implementation Note 提供一種安排：清除整個 Command、輪詢 Transactions Pending，待它清除或已等待足夠時間確信剩餘回覆不會到達後，再發起 FLR。這是範例演算法，不是所有裝置都只要照抄這幾步就完成停工。

4. 100 ms 到了，是哪一件事完成了？

規格要求 Function 在觸發後 100 ms 內完成 FLR；但 Function 特有的後續初始化可能還需要時間。若超過這個時限後仍需要初始化，它收到 Configuration Request 時必須回 RRS。當它已對 Configuration Request 回過非 RRS 的 Completion，就不能在下一次 Reset 前又回 RRS。

若發起 FLR 時 Transactions Pending=1，軟體在初始化前還必須留出足夠時間，讓相關 Completion 到達，或合理確信它們不會再到達。規格建議參考 FLR 前的 Completion Timeout；若當時 timeout 被停用，等待時間由系統決定，但不得少於 100 ms。不能拿 FLR 後的預設 timeout 值替換這個判斷。

若支援 Function Readiness Status（FRS），收到 Configuration-Ready 訊息可讓系統軟體提早發出 Configuration Requests，但這不保證 Function 先前發出的 Requests 都已完成。FLR 進行中，收到的 Request 可以被靜默丟棄；不要用任意 MMIO 讀取當成標準 FLR 完成檢查。

時間與存取規則

§6.6.2（pp.725–727）。觸發 FLR 的 Configuration Write 必須先獲得 Completion，再開始 FLR；進行中的 Request／Completion 處置與後續 RRS 規則見 p.726。FRS 是有條件的就緒通知，不取代對 stale Completion 的等待。

5. 如果用的是 Hot Reset，能套同一套等待方式嗎？

不能只記住「Reset 後等 100 ms」。Conventional Reset 的等待起點會受 Port 速率能力與就緒通知影響。例如在無法確定可用 DRS、且沒有其他適用的提早就緒機制時：若 Downstream Port 只支援到 5 GT/s，至少從 Conventional Reset 結束等待 100 ms；若它支援高於 5 GT/s，則至少從 Link training 完成後等待 100 ms，才向緊鄰下游裝置發出 Configuration Request。

作者時間例：Reset 在 t=0 ms 結束，一個支援 16 GT/s 的 Port 到 t=40 ms 才完成 Link training。上述分支的第一個 Configuration Request 最早在 t=140 ms，而不是 t=100 ms。這個時間不是保證裝置已成功完成初始化；它仍可能依法回 RRS。

Immediate Readiness、DRS、Readiness Time Reporting，以及系統已知的特定裝置需求，可能改變可存取時間，必須依各自條件判斷。未使用 Readiness Notifications 時，在 Conventional Reset 結束後至少要容許 1.0 s，才能因有效 Configuration Request 尚未取得 Successful Completion 而判定裝置故障；這與前述第一次可送 Request 的等待是不同規則。

Conventional Reset 的時間分支

§6.6.1（pp.722–723）。本例選用支援高於 5 GT/s、無提早就緒例外的分支。RRS 的 Host 可見性與合法使用時機已在 Chapter 3說明；不要把 RRS 當成一般 MMIO 的重試狀態。

6. FLR 後，能把整份 Configuration dump 寫回去嗎？

不能。應按欄位用途與存取屬性恢復設定，避免把 RO、RW1C、觸發控制或不應改動的共享欄位當成一般記憶體。FLR 的基本要求是把 Function Register 與專屬狀態機回到指定的初始化值，但 §6.6.2 明列了一批保留例外。

恢復設定前先分類
欄位／狀態FLR 行為或注意事項
BME、MSI Enable 等發送許可會清除，Function 在 Link 上停止相應的新 Request 發送；恢復工作前重新建立必要條件。
Max_Payload_Size、ASPM Control、RCB 等明列欄位不因 FLR 回到初始化值。不能因為同在 Device／Link Control 就把整個 Register 一起清零。

7. 先確認哪個條件，才能下結論？

FLR 之後 Link 沒有重新訓練，是不是 Reset 失敗？

不是。FLR 本來就不得影響 Link 狀態；應依 Function 的重設、就緒及恢復條件判斷。（§6.6.2，pp.724–726。）

FLR 後 Transactions Pending=0，可否立即回收所有 DMA buffer？

不能只靠這個 bit。FLR 本身會清它，且它只涵蓋指定的 Non-Posted 交易。仍須滿足舊交易等待、裝置停工及平台 DMA 生命週期條件；也要防止其他軟體繼續存取。

用 D3hot→D0 代替 FLR，是否一定得到乾淨的初始狀態？

不一定。No_Soft_Reset 會影響這個電源轉換的行為，不能把它當成通用的 Function 重設。下一章會用 PMCSR 的實際欄位說明。
