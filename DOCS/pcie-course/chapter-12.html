錯誤證據、回報與隔離

收到 PCIe 錯誤通知時，最先要做的是保存能互相比對的證據。哪個 Function 偵測到錯誤、哪個訊息到達 Root Port，以及是否已啟動隔離，可能是三個不同問題。本章用 AER 與 DPC 的兩個獨立案例，練習從欄位推出有根據的結論。

版本與假設

本章依 PCI Express Base 6.0。數值與事件順序均為作者假設，採普通非 SR-IOV Function。AER 案例不支援 Flit Mode 或 End-End TLP Prefix，也未啟用 DPC；另一個 DPC 案例另列快照，不能把兩者當成同一次事件。範例假設管理者有權讀取與處理相關紀錄；控制權見 Chapter 13。

1. 一個錯誤訊息，能告訴我們多少事情？

Correctable Error 表示協定可自行恢復的錯誤，仍可能降低效能；Uncorrectable Error 則影響功能，並分為 Non-Fatal 與 Fatal。Non-Fatal 不等於工作已成功，Fatal 也不是「一定已損壞某顆晶片」的硬體診斷。這些分類提供回報與處理政策所需的嚴重程度。

由近到遠整理錯誤證據
紀錄位置回答的問題證據限制
Function 的 Device Status／AER Status這個 Function 記錄了哪類偵測結果？不保證訊息已送達，也不是事件次數。
AER Mask／Severity／Device Control偵測時如何記錄與回報？事後讀值不一定等於事發當時設定。
Root Error Status／Source IDRoot Port 收到哪些類別，第一個回報者是誰？回報者不一定是造成根本問題的元件。
Header Log／First Error Pointer目前保存的錯誤對應哪個交易內容？有有效性、容量、封包模式與錯誤種類限制。
DPC Status是否已隔離下游，觸發原因是什麼？不能替應用工作判定成功或復原完成。

Advanced Error Reporting（AER）是在基本錯誤回報之外，提供個別錯誤狀態、遮罩、嚴重程度與相關紀錄的 Extended Capability。即使沒有找到 AER，也不能直接說「裝置沒有任何錯誤回報能力」。

2. Status 有兩個 bit，為什麼只回報一個錯誤？

先依 Chapter 2 的 Extended Capability 清單找 ID=0x0001，再用 Figure 7-154 解 Header。下面是 Endpoint 03:00.0 的快照；AER base 剛好是 0x100，不是固定位置。假設先前紀錄已清理、設定自事件前保持不變，期間沒有其他錯誤，且沿途的錯誤訊息轉送已正確啟用。

Uncorrectable Error Status，0x104，32 bits0x00044000Figure 7-155

Header 表示 ID=0x0001、Version=2、Next=0；即使讀的是 Base 6.0，也不能自行套用只適合較新 Capability／Flit 的佈局。本例沒有 Flit 或 Prefix，因此 Version=2 符合條件。

Status 的 bit 14=1 是 Completion Timeout；bit 18=1 是 Malformed TLP。Mask bit 18=1、bit 14=0，因此這兩個已記錄的錯誤中，只有 Completion Timeout 未被遮罩：0x00044000 & ~0x00040000 = 0x00004000。這個運算只挑出本例的未遮罩狀態，還不是完整的回報判定演算法。

個別錯誤被 Mask 時，Status 仍可設起來；但不會為該次錯誤發出 Error Message，也不會把它存進 Header Log、TLP Prefix Log 或 First Error Pointer。不能把「Mask=1」解成「沒有發生」，也不能把 Severity=Fatal 解成「無論 Mask 為何都必須送出 Fatal 訊息」。

本例 Severity bit 14=0，Completion Timeout 被設定為 Non-Fatal；bit 18=1，Malformed TLP 被設定為 Fatal，但後者已 Mask。Device Control bit 1=1 允許 Non-Fatal 回報，所以在本例前提下，Completion Timeout 產生 ERR_NONFATAL。Device Control bit 2 也開啟 Fatal 回報，仍不會解除個別 Malformed TLP Mask。這是明確設定後的快照，不宣稱 Severity 值是重設預設值。

完整通知還要經過沿途 Bridge 的轉送條件、Root Port primary interface 的傳送允許，以及 Root 端的中斷設定。實際查詢時，從 Figure 6-3 沿來源到 Root 的路徑檢查；不能只讀 Endpoint 的一個 Enable 就結案。Unsupported Request、Advisory Non-Fatal 等類型另有規則，不宜把本例簡化式照搬過去。

3. Header Log 看起來像封包，就能直接解碼嗎？

先檢查有效性。Advanced Error Capabilities and Control 的低五位為 0x0E，也就是 First Error Pointer（FEP）=14；它指向 Uncorrectable Error Status 的 bit 14。本例該 bit=1，因此 FEP 有效，對應 Completion Timeout。不是看到 Log 非零，就能認定它屬於目前關心的事件。

Completion Timeout 也不能一律期待有 Request Header。本例 bit 12=1，表示 Completion Timeout Prefix/Header Log Capable；Multiple Header Recording Capable／Enable bits 9、10 均為 0。再加上沒有 Flit／End-End Prefix，這才得到本例的四個 DWORD Log 容量與解讀前提。

0x11C0x000000403 DW Memory Read Header，Length=64 DW。
0x1200x030013FFRequester ID=0x0300、Tag=0x13、First／Last DW BE 均為 0xF。
0x1240x40001000Request 起始位址。
0x128不解讀本例是 12-byte Header，第四個 DWORD 未定義。

因此這筆未如期完成的 Request 要讀 64 × 4=256 bytes，範圍為 0x40001000–0x400010FF。Header 顯示的是等待 Completion 的 Request，不是「超時回來的 Completion」。這個案例延用 Chapter 5 的交易欄位，不重教 TLP 全部格式。

Figure 7-161 特別規定 DWORD 讀取後的排列方式：封包 Header byte 0 位於第一個 Log DWORD 的 bits 31:24。上表已按 DWORD 數值解讀，不能再套一次普通 byte dump 的直覺而把位元組反轉。若是 Flit Mode，要改看 Logged TLP was Flit Mode、Header Log Size、Logged TLP Size，以及 Type／OHC，不能仍只拿前三個 DWORD 套本例。

這份 Log 可以定位某筆 Request 及其等待結果；它不能單獨證明原因在 Endpoint、Completer、Link、路由或平台。Masked 的 Malformed TLP 沒有本次 Header 紀錄，也不能把現在這份 MRd Header 逕自歸給它。

4. Root Port 記錄 03:00.0，是否代表它就是故障來源？

先區分「送出錯誤訊息的 Function」與「造成根本問題的元件」。Root Error Source Identification 記錄第一個相應類別訊息的 Requester ID；例如 Endpoint 等不到讀取回覆而回報 Timeout，Root 看到 Endpoint 的 ID 並不奇怪。

Root Port 收到單一 Non-Fatal 訊息的快照
Root AER base=0x100 的位置值判讀
Root Error Command，0x12C0x00000002開啟 Non-Fatal 中斷回報。
Root Error Status，0x1300x00000024bit 2、bit 5=1；Multiple、Fatal、Correctable 均未設。
Error Source Identification，0x1340x03000000高 16 bits=0x0300，是第一個 Uncorrectable 訊息的 Requester ID。

(0x03000000 >> 16) & 0xFFFF = 0x0300，依一般 BDF 編碼解為 03:00.0。本例 Root AER 的中斷向量編號設為 0，因此完整 Status 的高位沒有額外數值。Root primary interface 的傳送條件也已滿足；若要斷言 CPU 實際收到中斷，還要確認 MSI／MSI-X 或 INTx 的傳送與平台路由，不能只憑 0x24。

Root Error Status 的更新不受 Root Error Command 或 Root Control 的值控制，但仍有前述 primary interface 傳送允許條件。假如後來又收到另一個 Uncorrectable Message，Multiple bit 會設起來，第一個 Source ID 仍保留；這個欄位不是完整的回報者清單。

5. 為什麼不能一開始就把所有 Status 寫 1 清掉？

因為清除不只是讓畫面乾淨。當軟體清掉 FEP 所指的錯誤時，硬體可能更新下一筆 Header 與 FEP；若先清除再讀 Log，就可能把兩個時間點的資料拼成同一個事件。

  1. 先記下管理對象、時間與當時設定；保存相關 AER Status、Mask、Severity、FEP、有效 Log，以及 Root／DPC 的對應證據。
  2. 依 FEP 與能力確認 Log 的格式及有效範圍；若資料可能並行變動，重新核對關聯，不能假定多個 Register 的讀取是原子快照。
  3. 完成該筆紀錄處理後，才對相應 RW1CS bit 寫 1。若啟用 Multiple Header Recording，依 FEP 逐筆處理，再重新讀狀態。

前兩步是作者整理的蒐證方式；第三步的硬體清除語意來自規格。Base 6.0 建議在多筆 Header 記錄啟用且 FEP 有效時，不要清除 FEP 以外的 Status bit；規格也列有確定沒有 Header 紀錄的 masked error 例外。它不是一條「所有錯誤情境都一次寫固定遮罩」的操作口訣。

另外，清 PCI Status 不會連帶清 AER Status，反方向也一樣。對照不同紀錄時，須記下是哪個 Register 在什麼時候被清除。

6. 如果啟用 DPC，為什麼 Root 可能看不到原本的 ERR_NONFATAL？

以下換成另一個事件案例。02:01.0 的 DPC Extended Capability 位於 0x300；這是一個 Switch Downstream Port，不使用 Root Port Extensions。Downstream Port Containment（DPC）可在觸發後停止下游 PCIe 流量，使問題先被限制在受影響的分支。

DPC 的獨立事件快照
欄位與位置值由欄位得知的狀態
Header，0x300，32 bits0x0001001DID=0x001D、Version=1、Next=0。
DPC Control，0x306，16 bits0x000ATrigger Enable=10b；Interrupt Enable=1。
DPC Status，0x308，16 bits0x000BTrigger Status=1；Reason=01b；Interrupt Status=1。
DPC Error Source ID，0x30A，16 bits0x0300觸發訊息的 Requester ID。

Trigger Enable=10b 表示 Port 自己偵測到未遮罩的 Uncorrectable Error，或收到 ERR_NONFATAL／ERR_FATAL 時可觸發。Reason=(0x000B >> 1) & 3 = 1，所以本次原因是收到 ERR_NONFATAL；此時 Source ID 才具有這裡要用的意義。若 Reason=00b 表示 Port 自己偵測到錯誤，就不能照用 Source ID 猜來源。

觸發 DPC 的這個 ERR_NONFATAL 會被 Port 丟棄，不再往上游轉送。DPC 可另外以中斷或 ERR_COR 通知管理者，但本例 DPC ERR_COR Enable=0，只啟用 DPC 中斷；中斷是否到達仍要看向量與平台設定。因此不能要求 Root AER 一定同時出現上一節的 0x24 快照。

Trigger Status=1 時，硬體要求 LTSSM 進入 Disabled。軟體必須讓 Port 留在 DPC，直到 Link Status 的 Data Link Layer Link Active 讀為 0；若是支援 RP Extensions 的 Root Port，還必須等 DPC RP Busy=0。本例是 Switch Port，不能把 Reserved 的 RP Busy 當成有效進度指標。

對 Interrupt Status bit 3 寫 1 只是清中斷狀態；對 Trigger Status bit 0 寫 1 則會釋放 DPC，讓 LTSSM 回 Detect 嘗試訓練。後者須先符合上述條件與恢復政策，並在後續設定存取遵守 Conventional Reset 的時序。不能為了「消除錯誤」而先寫掉 Trigger Status，也不能把它清為 0 當成裝置、驅動與應用都已恢復。

7. 根據證據回答，不補上沒有讀到的事

AER Status=0，是否足以證明從開機至今都沒有錯誤？

不足。紀錄可能已被清除或重設，部分欄位也取決於實作與偵測條件。應先確認蒐證時間範圍與清除紀錄。依據：§6.2.4.2、Table 7-135。

FEP=14，但 Status bit 14 已清除，仍可把 Header Log 當成最新 Timeout 嗎？

不可以。FEP 此時無效；Log 看起來合理並不能補足有效性條件。依據：§6.2.4.2、Table 7-140。

DPC Source ID=03:00.0，能否斷言 03:00.0 的硬體必須更換？

不能。先確認 Trigger Reason 允許解讀 Source ID；即使有效，也只識別觸發訊息的回報者。還需交易、相鄰元件與平台證據才能判斷原因。依據：Table 7-265。
