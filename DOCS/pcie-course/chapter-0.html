電腦能列出一個 PCIe 裝置，不代表裝置已經可以傳資料；規格定義了某項功能，也不代表眼前的裝置一定支援。本章從這兩個差別出發，先認識系統裡的角色，再帶你完成一次查詢：一個裝置端的 Port 支援哪些連線速率，而這條 Link 現在使用哪個速率？

你只需要懂基本程式、CPU 與記憶體概念。讀到最後，應該能說明查詢的對象、資料的位置、欄位的意義，以及證據還不足以回答哪些問題。先理解每一步的理由，圖號可以在需要時再查。

本章採用的版本

欄位與圖表以 PCI Express Base Specification Revision 6.0 為準；韌體與作業系統的關係以 PCI Firmware Specification Revision 3.3 為主要依據。Firmware 3.3 §1.2（文件頁／PDF 頁 7）的參考文件列的是 Base 5.0，兩份文件的版本不能視為同一組配套。另附 UEFI 2.11 與 ACPI 6.6 的官方背景閱讀；它們不取代本章引用的 Base 6.0 欄位定義。

1. CPU 已經能存取記憶體，為什麼還需要 PCIe？

先想一個需求：程式準備好一塊記憶體，希望網路裝置把資料送出去。CPU 必須告訴裝置要做什麼，裝置必須取得資料，工作完成後還要讓軟體知道結果。這些互動需要共同的傳輸方式與軟體介面。

PCI Express，簡稱 PCIe，是連接系統與周邊裝置的互連架構。它定義如何發現與設定裝置，也定義元件之間如何以封包傳遞讀取、寫入及其他要求。至於「傳送哪一種網路封包」或「讀取哪一個儲存區塊」，還需要裝置本身的介面規格與驅動程式。

教學情境

本章用網路裝置說明角色，用一個簡化的 PCIe Endpoint 練習讀欄位。這些情境由作者設計；沒有假設特定廠牌，也沒有把任何一組讀值當成實機量測。

因此，學 PCIe 可以先分成三個問題：系統如何認識這個裝置、軟體如何使用它，以及底層如何把要求送到對方。後續課程會沿著這三個問題展開。

2. 從 CPU 到裝置，途中有哪些角色？

先看一個簡化系統。Root Complex 把 CPU／記憶體子系統接到 I/O 階層；Root Port 是這個階層向外建立 PCIe Link 的介面。Endpoint 則是執行裝置功能的端點。若需要接出更多路徑，中間可以加入 Switch。

I/O
Input/Output，輸入與輸出。在這裡指系統與周邊裝置之間的互動。
Port、Link 與 Lane
Port 是連接介面；Link 是相鄰兩端之間的連線；Lane 是構成 Link 的傳輸通道。每個 Lane 各有一組傳送與接收差動訊號對。x4 表示這條 Link 使用 4 個 Lane，不表示接了 4 個裝置。

圖中的 CPU、Root Complex 與記憶體只是邏輯角色。實際產品可以把其中幾個角色整合在同一顆晶片內，所以看到 Root Complex 這個名稱時，不要先假設它一定是主機板上另一顆獨立晶片。

一張卡就是一個 Function 嗎？

不一定。軟體辨識與設定的基本對象是 Function。一個實體裝置可以提供多個 Function，各自有設定空間。傳統編址會用 Bus、Device、Function 三個號碼定位，常合稱 BDF；如果系統有多個 Segment，還要先指定 Segment。Segment 是由韌體管理、供 OS 使用的邏輯分組；不同 Segment 可以重複使用相同的 Bus 號碼，但同一個 Segment 內的 Bus 號碼必須唯一。它不是圖上額外插入的一個硬體元件。

教學假設

後面的查詢對象記成 0000:03:00.0，依序表示 Segment 0000、Bus 03、Device 00、Function 0。這只是方便閱讀的定位記法，號碼由本例假設；它不是 BAR 位址，也不能拿來直接當成記憶體位址。

3. 裝置接上以後，為什麼還不能立刻使用？

連線建立、裝置被發現、資源完成配置，以及驅動程式準備好，是不同的事情。下表以一個需要在開機時使用的裝置為例，整理各項工作之間的依賴；實際平台可能分階段處理，也可能由韌體與 OS 分別完成一部分。

教學流程：從連線到工作
先要完成的工作誰在處理完成後能說明什麼
電源、重置與就緒條件適當，兩端建立 Link平台與裝置硬體；Link 的初始速率與寬度協商由兩端硬體處理相鄰兩端具備通訊條件；尚未證明驅動程式已可使用裝置
讀取設定空間，發現 Function 並辨識其結構韌體或 OS 的系統軟體系統知道有哪些 Function；這個過程通常稱為 enumeration，亦即枚舉
配置位址資源與橋接器轉送範圍，設定必要控制韌體或 OS，依平台與啟動階段分工裝置的相關資源已有可用的配置；仍要符合各項啟用條件
設定裝置自己的工作介面與資料結構該裝置的驅動程式裝置才具備執行這項工作的軟體環境

這裡的韌體是主機平台韌體，和網卡或 SSD 裡執行的裝置韌體不是同一個角色。UEFI（Unified Extensible Firmware Interface）定義 OS 與平台韌體之間的介面；UEFI 環境也提供 PCI 裝置存取服務。OS 是 Operating System，也就是作業系統。

交接時也不能假設「韌體早已把每個裝置都設好了」。Firmware 3.3 §3.5 要求韌體設定開機與主控台所需裝置，以及通往它們的完整路徑；同節另要求設定所有 Host Bridge。Host Bridge 是主機與 PCI 位址空間之間的橋接角色；不要把「所有 Host Bridge」讀成「所有 Endpoint」。

ACPI（Advanced Configuration and Power Interface）則提供硬體、軟體介面及資料結構，支援 OS 主導的組態與電源管理。它和 UEFI 各有工作範圍；後續課程會在需要查平台資源與控制權時，再展開相關表格與方法。

4. 讀設定空間、讀裝置暫存器與 DMA，有什麼不同？

暫存器可以先理解成硬體提供給軟體讀取或設定的欄位集合。設定空間裡有暫存器，裝置自己的操作介面也可能有暫存器；看到「register」這個字，還需要確認它位於哪種空間。

從目的分辨三種存取
現在想做什麼讀取或操作的對象應先找哪一類資料
辨識 Function，查詢 PCIe 能力與連線狀態該 Function 的 Configuration Space，設定空間設定標頭、Capability 結構與欄位定義
透過記憶體映射介面操作裝置分配給裝置的記憶體位址範圍BAR 描述的資源與裝置本身的暫存器規格
讓裝置搬移工作資料軟體準備並映射給裝置使用的記憶體DMA 緩衝區、裝置可用位址及存取條件
BAR
Base Address Register，基底位址暫存器，位於設定空間，用來描述或設定裝置的位址資源。BAR 不是資料緩衝區本身。
MMIO
Memory-Mapped I/O，記憶體映射 I/O。CPU 透過被映射的位址存取裝置介面；這種存取不能一概視為普通 RAM 讀寫。
DMA
Direct Memory Access，直接記憶體存取。在本章的情境中，由裝置發起資料存取；CPU 仍需先安排工作、緩衝區與必要設定。

例如，讀取 Link Status 是在查設定空間；寫入網路裝置的工作暫存器，則可能走 BAR 所對應的 MMIO 範圍。裝置接著讀取傳送資料，是另一筆由裝置發起的存取。這三件事可能出現在同一項工作裡，但它們回答的問題不同。

本章只讀設定空間，不做資源配置或實際 DMA。CPU 看到的位址和裝置使用的位址也不保證相同；後續談資源配置與位址轉譯時，會把這個差別展開。

5. 打開規格後，怎麼知道該先看哪裡？

先把需求寫成一句能查證的問題。本章要問的是：「指定 Port 宣告支援哪些速率？它所在的 Link 目前使用哪個速率？」前半句在問能力，後半句在問狀態。如果另外問「軟體希望它使用哪個速率」，才需要再查看相關控制欄位；三者不能互相代替。

PCIe 每個 Function 的設定空間擴充為 4096 bytes。前 256 bytes 保留 PCI 相容區域，其中有設定標頭與傳統 Capability 清單；後面的區域可放 PCI Express Extended Capabilities。PCI Express Capability 本身位於前 256 bytes 的清單裡，不要因為名稱帶有 PCI Express，就直接跳去找 Extended Capability。

Capability 是一組用來描述或控制特定能力的結構。它在設定空間中的起點不必固定；軟體要先沿指標找到它，再加上結構內的相對位移。因此，規格標示的「Offset 2Ch」還不是本例的最終存取位置。

讀欄位前的三個記法

0x2C 與規格常用的 2Ch 都表示十六進位；一個十六進位數字對應 4 個 bits。bit 0 是最低位元，bits 7:1 包含 7、6、5、4、3、2、1，共 7 個位元。位移若以 byte 為單位，就不能把它當成 bit 數來相加。

& 表示位元 AND，用遮罩保留指定位置；>> 表示向右位移。後面的例子會把每次運算的目的寫出來。

6. 完整案例：支援哪些速率，現在又跑多少？

教學假設，不是規格原文或實機讀值

系統已找到 0000:03:00.0，可正常讀取它的設定空間。目標是有實體 Link 的一般 PCI Express Endpoint，不是 Root Complex Integrated Endpoint（整合於 Root Complex 的端點，簡稱 RCiEP），也不是虛擬化的 Virtual Function（VF）。本例使用傳統 BDF 編址，不使用 Alternative Routing-ID Interpretation（ARI，另一種解讀 Function 識別號的方式）。Link 已建立，而且查詢期間沒有重新訓練或狀態變動；本題使用的 Link Capabilities 2 速率向量也已實作。以下數值由作者設計，並依 Base 6.0 的欄位規則檢查。

第一步：我真的可以從這個標頭找 Capability 嗎？

先用 Header Type 的低 7 bits 判斷標頭形式：0x00 & 0x7F = 0，所以使用 Figure 7-10 的 Type 0 配置。bit 7 另有多功能裝置的意義，不應混進標頭類型。接著查 Status 的 bit 4：(0x0010 & 0x0010) != 0，確認 Capabilities List 為 1。

現在依 §7.5.1.1.11，讀取 offset 0x34 的 Capabilities Pointer。規格要求軟體在使用這個指標前遮掉最低兩個 bits，因此本例得到 0x40 & 0xFC = 0x40。這個值告訴我們第一個結構從哪裡開始，還沒有告訴我們它是 PCIe Capability。

第二步：第一個 Capability 不是我要的，接著去哪裡？

在 0x40 讀到 0x7001。低 8 bits 的 ID 是 0x01，本例對照 Figure 7-18／Table 7-14，得知這是 Power Management（電源管理）Capability。高 8 bits 的 Next Pointer 是 0x70，所以接著移到 0x70。不需要為了通過這個節點，就把它的所有電源欄位讀完。

在 0x70 讀到 0x0010。依 Figure 7-22／Table 7-18，ID 0x10 表示 PCI Express Capability；高 8 bits 為 0，表示此結構沒有下一個清單節點。我們已找到目標，記下結構起點 cap_base = 0x70。

  1. 設定標頭
    0x34 → 0x40
    找到清單入口
  2. PM Capability
    ID 0x01 / Next 0x70
    依 Next Pointer 往下找
  3. PCIe Capability
    ID 0x10 / Next 0
    記下起點 0x70

這條路徑是本例的安排。其他裝置的 Capability 起點與順序可以不同，不能把 0x70 寫成通用常數。如果清單走到結尾仍未找到目標，或出現循環等不合理資料，就沒有足夠依據繼續套用這份結構。這是讀取資料時的檢查原則，不代表所有「讀不到」都能解成不支援。

第三步：找到 PCIe Capability，就能直接讀任何欄位嗎？

還要核對版本與適用對象。在 cap_base + 0x02 = 0x72 讀到 0x0002。依 Figure 7-23／Table 7-19，bits 3:0 為 2，表示 Capability Version 2；bits 7:4 為 0，表示 PCI Express Endpoint，與本例假設一致。

這裡的 Version 2 是這個 Capability 結構的版本，不表示裝置是「PCIe Gen2」，也不是在宣告支援 Base 2.0 的全部功能。相同地，本章拿 Base 6.0 當參考文件，不代表這個例子一定支援 64 GT/s。

Base 6.0 §7.5.3 會依元件類型說明哪些暫存器適用。RCiEP 就不能照本例套用一般外部 Link 的欄位。另外，Version 2 本身不保證較早期硬體已實作 Link Capabilities 2 的速率向量；§7.5.3.18 的實作說明（p.1000）另外交代舊硬體的判讀方式。本例假設該欄位已實作，後面也會取得非零的向量值，因此不需要在此展開舊硬體分支。

第四步：怎麼從結構起點算出讀取位置？

Figure 7-21 把 Link Capabilities 2 放在相對位移 0x2C，Link Status 放在 0x12。兩個值都要加到剛找到的 cap_base：

Link Capabilities 2：0x70 + 0x2C = 0x9C（讀 32 bits）
Link Status        ：0x70 + 0x12 = 0x82（讀 16 bits）

0x70 + 0x0C = 0x7C 是另一個 Register：Link Capabilities。名稱相近，位置卻不同。本題要列出支援速率集合，因此使用 Link Capabilities 2 裡的 Supported Link Speeds Vector。

第五步：如何把能力讀值轉成支援速率？

在 0x9C 讀到 0x0180001E。Figure 7-38／Table 7-35 把 Supported Link Speeds Vector 放在整個 Register 的 bits 7:1。先遮掉其他 bits，再把欄位移到最低位置：

保留 bits 7:1：0x0180001E & 0x000000FE = 0x0000001E
右移 1 bit   ：0x0000001E >> 1 = 0x0F = 0001111b

右移後，表格所說的「欄位內 bit 0」才對應 0x0F 的最低位元。它原本位於 Register 的 bit 1。這兩種編號差 1，讀表時要先看清楚表格是在說整個 Register，還是欄位內的位置。

因此，這個 Port 宣告支援 2.5、5.0、8.0 與 16.0 GT/s。在 PCIe 規格中，GT/s 以每個 Lane、每個方向的編碼位元傳輸速率計算；它不是應用程式每秒取得的 GB 數。若要估算有效資料量，還要考慮 Lane 數、編碼方式、封包開銷與實際工作負載，本題先不做這個換算。

為什麼假設值是 0x0180001E，而不是 0x0000001E？

這裡提供的是完整 32-bit 讀值。Base 6.0 Table 7-35（文件頁／PDF 頁 999–1000）要求：宣告支援 16.0 GT/s 或更高速率時，Register bits 23 與 24 的 Retimer Presence Detect Supported、Two Retimers Presence Detect Supported 必須為 1。因此本例保留這兩個 bits，得到 0x0180001E。它們表示偵測能力，不是本例路徑已裝有 Retimer 的證據。這些能力的詳細用途留待後續章節，本題只取 bits 7:1。

第六步：目前速率是另一個 bitmap 嗎？

不是。Link Status 的 bits 3:0 是 Current Link Speed，儲存的是編碼值。本例在 0x82 讀到 0x0043，所以：

目前速率代碼：0x0043 & 0x000F = 3
協商後寬度  ：(0x0043 & 0x03F0) >> 4 = 4

Table 7-26 把速率代碼 3 對應到 Supported Link Speeds Vector 的欄位內 bit 2，也就是 8.0 GT/s；寬度值 4 表示 x4。不能把代碼 3 當成 3 GT/s，也不能把它當成同時設定了兩個支援位元。

同一張表也指出，Link 未建立時，Current Link Speed 與 Negotiated Link Width 的值是 undefined，不能用來判斷目前有效連線。本例已把 Link 建立且穩定列為前提；單靠這個 0x0043 並不能自行證明前提成立。這個 16-bit 假設值中，bits 15:10 都是 0；但不能因此把 bit 13 的 Data Link Layer Link Active 為 0 解讀成 Link 已中斷，因為該 bit 是否實作還取決於元件的回報能力。實際查詢仍須依適用狀態確認連線。

第七步：現在可以下什麼結論？

案例推演：在本例前提成立時，所查 Port 宣告支援 2.5／5.0／8.0／16.0 GT/s，而其 Link 目前以 8.0 GT/s、x4 運作。這個讀值尚未說明為什麼沒有使用 16.0 GT/s。

還需要另一端的能力、相關控制設定與連線狀態，才能繼續分析。x4 是目前協商的寬度，並不能證明最大支援寬度也是 x4。也不能只憑這些欄位就宣稱裝置故障、平台已啟用所有功能，或應用程式一定能達到某個吞吐量。這些都是不同的問題，需要各自的證據。

7. 換一個條件，你還能做出相同判斷嗎？

先自己回答，再展開解說。這幾題分別檢查位置、編碼、有效條件與證據範圍，不需要背圖號。

如果 PCIe Capability 改從 0x90 開始，還能去 0x9C 讀 Link Capabilities 2 嗎？

不能沿用本例的絕對 offset。應重新計算 0x90 + 0x2C = 0xBC；Link Status 則是 0x90 + 0x12 = 0xA2。結構內位移不變，清單找到的起點變了，最終讀取位置也會改變。

依據：Base 6.0 Figure 7-21，p.952；起點 0x90 是新的教學假設。

如果 Current Link Speed 讀到 4，可以說它同時支援兩種速率嗎？

不可以。這是編碼欄位；在 Link 已建立等前提成立時，代碼 4 指向速率向量的欄位內 bit 3，表示目前為 16.0 GT/s。支援集合仍須讀取 Supported Link Speeds Vector。

依據：Base 6.0 Table 7-26、Table 7-35，pp.978、998；代碼 4 是本題假設。

Link 已經中斷，手上仍有 0x0043 這筆讀值，可以把它報成目前的 8.0 GT/s、x4 嗎？

不可以。兩個欄位在 Link 未建立時沒有可用來描述當前連線的有效語意。應先確認連線狀態，再決定是否採用這次速率與寬度讀值；數字看起來合理，並不會讓無效條件消失。

依據：Base 6.0 Table 7-26，p.978。

系統已能讀取網路裝置的設定空間，是否表示裝置已能從記憶體取走封包資料？

還不能這樣判斷。設定空間可讀，只說明目前已能進行這種設定存取。裝置自己的工作介面、記憶體映射、資料緩衝區及發起存取所需條件，仍可能尚未準備完成。要證明資料工作可執行，需要往資源配置與驅動程式初始化繼續查。

依據：Base 6.0 §1.4，pp.108–109；Firmware 3.3 §3.1–§3.2、§3.5，pp.32–35。情境由作者設計。
