DMA
Direct Memory Access，裝置直接存取記憶體

DMA（Direct Memory Access，直接記憶體存取）讓裝置發起記憶體交易。要讓一次工作正確完成，軟體還需交接緩衝區所有權，並處理平台要求的同步。

前情提要：Chapter 5 已建立 Request／Completion 的概念。本章沿著軟體準備工作、裝置寫入資料、軟體接手結果的過程，區分 PCIe 排序與 CPU／快取同步的責任。

閱讀路線：DMA 位址與映射背景 → 描述項發布 → Base Table 2-42 的交易排序 → 封包屬性與主機接手條件。

    本例已具備適用的映射及裝置位址範圍；CPU 指標與 DMA 位址依平台規則處理。

    由平台的 DMA 映射機制取得裝置可使用的位址，確認方向、範圍與緩衝區生命週期。

    Linux 6.12 DMA API HOWTO：CPU and DMA addresses、Types of DMA mappings。

    此處的同步須使用平台與作業系統定義的介面；PCIe 排序表本身不定義 CPU 的全部記憶體模型。

    先準備描述項與資料，再依平台要求執行記憶體及 I/O 同步，最後通知裝置有新工作。

    Linux 6.12 memory barriers：dma_wmb／dma_rmb／dma_mb、Kernel I/O barrier effects。

    裝置先寫結果資料，再以另一筆交易寫完成旗標；判讀這兩筆交易時，保留 TC、Requester ID 與 RO 等適用條件。

基本責任

DMA 描述誰發起資料搬移；實際 PCIe 仍使用適用的 Memory Request 等交易。

版本與範圍

PCIe 交易依 Base 6.0，案例沿用 Non-Flit Mode、普通 Endpoint 03:00.0。不使用 ATS、PASID、SR-IOV、Peer-to-Peer 或 IDE；除非題目另行更改，所有案例均為同一 Function、同一方向、TC0、RO=0、IDO=0、No Snoop=0。DMA 映射與記憶體同步只用 Linux 6.12 官方文件補充必要背景，不宣稱它們是 PCIe Register 定義，也不在本章展開某一款 IOMMU 的頁表格式。

1. DMA 是另一種特殊的 PCIe 封包嗎？

Direct Memory Access（DMA，直接記憶體存取）描述的是裝置搬移資料的方式。放到本章的 PCIe 案例裡，裝置讀主記憶體會發出 MRd，裝置寫主記憶體會發出一般 MWr；封包仍使用 Chapter 5 的交易種類。CPU 先準備工作，再由裝置發出交易，不需要 CPU 逐筆把 Payload 搬進裝置 Register。

Endpoint 與沿途 Port 的 BME 必須允許相應的上游要求，這是 Chapter 4 的啟用條件。但 BME=1 不會替驅動程式配置緩衝區、不會驗證描述項，也不等於取得任意主記憶體的存取權。

2. CPU 手上的指標，可以直接寫進 DMA 描述項嗎？

必須先確認那個數值屬於哪個位址空間。Linux 6.12 的 DMA 指引區分 CPU 虛擬位址、CPU 實體位址與裝置使用的 DMA 位址；平台可能透過 IOMMU 或 Host Bridge 映射它們。IOMMU 是處理 I/O 存取位址轉譯與保護的平台機制，本章只借用這個背景，不假設所有系統都採同一種硬體。

3. 描述項先寫好，再寫「可以開始」，為什麼仍要同步？

假設描述項包含三項資料：緩衝區位址 0x40001000、長度 256 bytes，以及表示裝置可以開始取用的 OWN 旗標。這個 OWN 是作者為案例命名的欄位，不是 PCIe 共通欄位。裝置介面另行規定：只有取得 OWN 後才讀取其餘欄位。

若 CPU 在原始程式中依序寫入位址、長度、OWN，並不能只靠這個書寫順序，證明裝置必定按同一順序觀察到更新。Base 6.0 §2.4.2 明確指出：裝置以單筆讀取觀察到正在更新的記憶體時，更新順序與粒度不由一般 PCIe 讀取規則保證。一次讀完描述項，也不等於取得原子的完整快照。

以 Linux 6.12 的 consistent memory 為例，dma_wmb()／dma_rmb() 用來建立 CPU 與 DMA 裝置之間共享記憶體存取的順序；這些 barrier 本身不提供 MMIO 順序保證。Coherent allocation 也不能省略必要的 memory barrier。若使用 streaming mapping，則還要依 DMA API 處理 CPU 與裝置之間的同步。這些介面各有適用前提，不應濃縮成「加一個 barrier 就全部解決」。

同步規則的閱讀入口

Base 6.0 §2.4.2（p.228）說明 PCIe 不保證的更新順序與粒度。平台補充採 Linux 6.12 memory barriers 的 dma_* barrier 與 Kernel I/O barrier effects 段落，以及 DMA mapping Guide 的 Types of DMA mappings、Using Streaming DMA mappings。此處是責任對照，不是可直接套到任意驅動程式的初始化程式碼。

4. 資料寫入後再寫完成旗標，兩筆 TLP 能互換順序嗎？

TLP
Transaction Layer Packet，交易層封包

換成裝置產生結果。假設同一 Function 先以一筆 MWr 寫入 64 bytes 的資料 D，再以另一筆 MWr 把完成旗標 F 設為 1。D 位於 0x40001000，F 位於 0x40001FF0；兩者都在本例有效的 DMA 映射內。此時問題是：後送出的 F 能不能越過先送出的 D？

查 Table 2-42 時，欄代表先發出的交易，列代表後發出的交易。D 與 F 都是 Posted Request，因此看 A2。相同 TC、沒有適用的放寬條件時，A2a 規定後面的 Posted Request 不得越過前面的 Posted Request。本例便不能讓 F 在 PCIe 路徑中越過 D。

表中的 Yes、No、Y/N 不是「成功、失敗、不確定」。Yes 表示為避免 deadlock，後者必須能越過前者；No 表示禁止越過；Y/N 表示規格容許實作選擇。也因此，「PCIe 有強排序」不等於所有種類的 TLP 都按同一總順序排隊。

回到 CPU：A2a 只回答兩筆交易在適用路徑內能否互相越過。CPU 是否以正確的映射和同步方式觀察 F、再使用 D，仍要滿足上一節的交接條件。不能拿一條封包排序規則代替整套記憶體使用協定。

排序表應該連同哪些條文閱讀？

§2.4.1 Table 2-42（p.222）給出欄列與符號；A2a／A2b（p.223）給出 Posted 對 Posted 的條件。A2b 的註解指出部分使用方式會禁止 RO-enabled Posted Request 越過先前 Posted Request，因此 RO=1 是可能放寬的條件，並非必定超車。不同 TC 的界線見 p.222；No Snoop 不影響排序見 p.224。案例排除另有規則的 Flow-Through IDE。

5. 設定欄位允許 RO，是否代表每個封包都用了 RO？

不是。設定空間決定允許使用的行為；真正的 TLP Attribute 才描述這筆交易。本例延續 PCIe Capability 位於 0x70，因此 Device Control 位於 0x78。假設這個 16-bit Register 讀回 0x2810：

欄位由 0x2810 取得的值能證明的事情

bit 11：Enable No Snoop1仍須符合 No Snoop 使用條件，不能讓所有交易一律設為 1。
bits 14:12：Max_Read_Request_Size010b最大讀取要求為 512 bytes，與 Chapter 5 的 DMA 讀取案例相容。

接著看 Figure 2-29：Attr[1] 是 RO、Attr[0] 是 No Snoop、Attr[2] 是 ID-Based Ordering（IDO）。它們在 Non-Flit Header 裡並不全部相鄰，必須再對 Figure 2-5 的實際位置；不可直接把這三個 bits 當成連續的欄位取值。

RO=1 表示適用的順序限制可以放寬，不是「這筆資料比較不重要」。No Snoop=1 表示該交易不期待硬體強制快取一致性；Device Control 的許可還要求發送端能保證目標位址沒有存在系統任何 cache 中。它不是清除 CPU cache 的命令。反過來，No Snoop=0 也不會替軟體完成描述項所有權交接。

IDO 另有獨立的 Request／Completion 啟用控制及身分條件；本章固定為零，避免把不同 Requester 或 PASID 的例外混入同一 Function 的基本案例。到了中斷章，還會看到 MSI/MSI-X 的 RO 與 No Snoop 必須為零，因此「Enable=1」也不能凌駕特定交易的禁止條件。

6. 把排序與平台同步放回同一案例

裝置以一筆 MRd 讀完整描述項，是否保證所有欄位來自同一個更新時間點？

沒有。單一 TLP 不會自動把正在變動的資料變成原子快照。Base 6.0 §2.4.2（p.228）甚至說明可能觀察到部分更新；需要裝置介面與平台共同建立有效的所有權及同步方式。

在同一 TC 中，先寫 D，再以 RO=1 寫 F；觀察到 D 在前，就能證明所有實作都必須如此嗎？

不能。容許重排並不要求每次重排。這次觀察只能說明這次的結果，不能把「允許」改寫成「禁止」。要證明保序，應檢查適用的欄位與路徑限制。（A2b，p.223。）

Device Control 的 Enable No Snoop=1，可以省掉所有 cache 與 barrier 的考量嗎？

不行。它只提供有條件的發送許可，而且 No Snoop 不改變交易順序。軟體仍須遵循平台的記憶體介面；欄位含義見 Table 7-21（p.961）。

BAR0 與 BME 都正確，裝置仍把 CPU 指標 p 當成 DMA 位址使用，問題解決了嗎？

沒有。BAR0 解決裝置資源的存取，BME 控制要求的發送許可；兩者都不負責把 p 轉成這個裝置可用的 DMA 位址。請回到 位址對照表 確認描述項實際交給裝置的是哪一種值。

7. 接著讓軟體知道有工作完成

資料與狀態已按介面約定交接後，裝置還需要通知軟體處理。Chapter 7 會從 Capability 找到 MSI-X Table，設定一個 entry，並追蹤遮罩、Pending 與中斷寫入。
