Chapter 4 已經替裝置配置好位址。現在假設 CPU 要讀取 0x80004120 的 4 bytes：這個動作如何變成 PCIe 封包？裝置怎麼知道要回給誰？本章沿著一次讀取往返，再把同一套判讀方法用在部分位元組存取與較大的讀取上。

版本與案例前提

欄位依 PCI Express Base Specification Revision 6.0。本章明確使用 Non-Flit Mode；Flit Mode 的 Header 布局不同，不能直接套用下列 Fmt／Type 位置。沿用 Chapter 4 的普通 Endpoint 03:00.0、BAR0 與 Bridge Window，且 Link、解碼、平台映射與裝置 Register 介面均已就緒。所有讀值與封包欄位都是作者推演，沒有擷取實機封包。案例使用 TC0、RO=0、IDO=0、No Snoop=0、TH=0，不使用 ATS、PASID、IDE、AtomicOp 或 DMWr。

本章的位址是 PCIe 交易使用的位址。CPU 指令如何轉成一個或多個交易，仍由處理器與平台決定；案例另行假設這次 4-byte 存取產生一個 Request。

1. 讀取時，誰提出要求，誰負責回覆？

Transaction Layer Packet（TLP，交易層封包）承載要求與回覆。提出這筆要求的一方稱為 Requester；服務目標位址並回覆的一方稱為 Completer。這兩個名稱隨交易改變：CPU 讀裝置時，平台代表 CPU 發出要求；裝置讀主記憶體時，裝置反而是 Requester。

本例假設平台選用 Requester ID 0x0000，並配置尚未使用的 Tag 0x12。這是平台端的教學假設，不能只看 Root Port 的 BDF 就推定 CPU 存取必定使用那個 ID。Endpoint 的 Completer ID 則為 0x0300，來自已完成設定的 03:00.0。

Requester ID 與 Tag 合起來辨識一筆尚待完成的交易。同一 Requester 不得讓兩筆同時未完成、需要 Completion 的要求共用 Tag。本例只用較小的合法 Tag；Base 6.0 還定義較大的 Tag 能力與啟用條件，因此不能把 Tag 永遠說成 8 bits。

先看哪幾張圖？

先看 §2.1.2 Figure 2-2（p.117），分清 Header 與可能存在的 Payload；再看 §2.2.6.1–§2.2.6.2 Figures 2-27／2-28（pp.152–154），理解 Transaction ID。Completer ID 見 §2.2.9.1 Figures 2-74／2-75（p.197）。圖中的路徑是作者整理，不是規格原圖。

2. 有寫入，就一定會有 Completion 嗎？

要先辨認交易類型。Posted Request 不要求回傳一般 Completion；Non-Posted Request 則需要 Completion 結束該要求。名稱不是在描述「軟體有沒有等待」，也不是在表示工作成功與否。

先依用途選擇交易，再判斷回覆
交易要求如何找到目標成功時的交易層回覆
Memory Read（MRd）依 Memory 位址Non-Posted；以一個或多個 CplD 回傳資料。
一般 Memory Write（MWr）依 Memory 位址Posted；沒有對應的普通 Completion。
Configuration Read／Write依目標 ID；沿 Chapter 3 的 Type 1／Type 0 規則Non-Posted；讀取回 CplD，寫入回 Cpl。
I/O Read／Write依 I/O 位址，供相容用途兩者都是 Non-Posted；不能套用 Memory Write 的結論。
Message Request依該 Message 規定；可能依位址、ID 或隱含目的地交易層屬 Posted；上層協定仍可能另外定義回應。

因此，CPU 寫入裝置的通知 Register 後，不能等待一個並不存在的 MWr Completion，也不能因為沒有 Completion 就推定錯誤。裝置何時完成工作，必須依裝置介面的狀態或通知判斷。PCIe 另外有 DMWr、AtomicOp 等交易；它們有自己的 Completion 規則，本章的「一般 MWr」不包括這些類型。

3. 如何把「讀 4 bytes」對到 Request 與 Completion？

先用 Table 2-3 找到 MRd，再看 Figure 2-31 的 32-bit 位址格式。不要因為要讀「32-bit 資料」就選 3 DW Header；Header 的選擇與目標位址格式有關。本例的位址可用 32 bits 表示，因此採 3 DW Header。DW 是 Double Word，這裡固定為 4 bytes。

本例的單筆讀取欄位
欄位MRd Request成功的 CplD
Fmt／Type000b／00000b010b／01010b
Requester ID／Tag0x0000／0x120x0000／0x12
目標位址／Completer IDAddress=0x80004120Completer ID=0x0300
Length1 DW，要求 4 bytes；Request 本身沒有資料 Payload。1 DW，這個回覆帶 4 bytes。
First／Last DW BE1111b／0000b沒有這組 Request 欄位。
Completion Status／Byte Count／Lower Address不是 Request 欄位。SC=000b／4 bytes／0x20

這裡有三個必須分開的量。Request 的 Length 表示要存取多少個 DW；CplD 的 Length 表示這個回覆帶多少個 DW；Byte Count 則表示連同這個回覆在內，這筆 Memory Read 還要回傳多少 bytes。因為本例一次回完，後兩者剛好對應相同的 4 bytes。

Byte Enable（BE）決定哪些位元組有效。Length=1 DW 時，First DW BE 控制唯一的 DW，Last DW BE 必須為零。Lower Address 是本次回傳第一個有效位元組位址的低 7 bits，因此 0x80004120 & 0x7F = 0x20。它不是完整目標位址；Completion 回程依 Requester ID 路由，不靠這 7 bits 找 CPU。

假設四個有效資料 bytes 按位址遞增為 78 56 34 12，且這個裝置 Register 定義為 little-endian，軟體便可解讀為 0x12345678。這個 Register 意義和數值是教學假設，不是 PCIe 為所有 MMIO 裝置統一定義的值。

4. 如果只讀中間 6 bytes，Length 要填 6 嗎？

不行，Length 的單位是 DW。另作一個教學假設：裝置在這段範圍提供可合法讀取的連續 bytes，現在要讀 0x80004121–0x80004126。這六個 bytes 橫跨兩個對齊的 DW，因此 Request 使用對齊位址 0x80004120、Length=2。

部分位元組讀取的範圍
對齊 DW位址由低至高的 bytes有效範圍與 BE
第一個 DW0x120、0x121、0x122、0x123（BAR0 內位移）只讀後三個 bytes；First BE=1110b。
最後一個 DW0x124、0x125、0x126、0x127（BAR0 內位移）只讀前三個 bytes；Last BE=0111b。

因為目標是 non-Prefetchable 資源，未啟用的兩個 bytes 不得在 Completer 被讀取。成功且一次回完時，CplD 的 Payload 仍占 2 DW，但有效資料只有 6 bytes；Byte Count=6，Lower Address=0x21。軟體不能把兩端的無效 bytes 當成額外有效 Register 資料。

這個例子也提醒我們：TLP 能表示某種 byte 存取，不代表每個裝置 Register 都接受這種寬度。實際能否讀取，還要看裝置介面規格。BE 的連續性也有條件；本例符合規則，不能據此假設任意長度都可隨意挖空中間 bytes。

§2.2.5.1，Figure 2-26／Table 2-10（pp.150–151）；§2.3.1.1，Table 2-40（p.217）及 Table 2-41（p.218）。Table 2-40 在 Length=2、First BE=1110b、Last BE=0111b 時給出 6 bytes。

5. 為什麼一次讀取可能收到兩個 Completion？

先把目標換成主記憶體，預習下一章的 DMA。假設 Endpoint 03:00.0 要從 DMA 位址 0x40001000 讀 256 bytes，使用 Tag 0x13。平台已準備好這段映射與讀取權限，Endpoint 及沿途的 BME 也已啟用。

本例的 Requester 最大讀取要求為 512 bytes；Completer 的有效傳送 Payload 上限為 128 bytes，路徑接收能力也相容，Read Completion Boundary（RCB，讀取回覆切分邊界）為 128 bytes。因此 256-byte 要求可以發出，但不能塞進一個 256-byte CplD。我們選擇在 128-byte 邊界切成兩份；並不宣稱所有讀取都固定這樣切。

同一筆 256-byte 讀取的兩個回覆
回覆回傳位址範圍Length（DW）Byte Count（bytes）Lower Address
第一個 CplD0x40001000–0x4000107F322560x00
第二個 CplD0x40001080–0x400010FF321280x00

Request 的 Length=64 DW；兩個回覆都帶 Requester ID=0x0300、Tag=0x13，且都假設 SC、BCM=0。第一個回覆的 Byte Count 包含尚未回傳的第二份，所以是 256，而非自己的 Payload 大小 128。第二個回覆的 Lower Address 仍為零，因為 0x80 & 0x7F = 0；Requester 要結合原要求與已收到的資料追蹤位置。

同一筆讀取的成功回覆必須依位址遞增；不同 Tag 所屬的兩筆讀取，回覆卻不必按發出順序到達。也不能把兩筆要求的資料合成一個 Completion。這就是配對不能只靠「第幾個收到」的原因。

長度、切分與順序來源

MRRS：§2.2.7.1（p.162）；有效 Payload 上限：§2.2.2 與 §2.3.1.1（p.214）；RCB、Byte Count、遞增位址：pp.215–218；不同交易的回覆順序：§2.4.1 D5a／D5b（p.224）與 §2.4.2 的例子（p.228）。本例直接給定有效上限，沒有把 Base 6.0 的所有傳送／接收上限簡化成單一 MPS 暫存器值。

6. 長度沒超過上限，就一定是合法要求嗎？

還要檢查 4 KiB 邊界。假設要從 0x40001FF0 讀 32 bytes，結尾會落在 0x4000200F。即使 MRRS 容許 32 bytes，這個 Address／Length 組合跨過了 4 KiB 邊界，仍不得作為單一 Memory Request 發出。可改成兩筆 16-byte 要求：0x40001FF0–0x40001FFF 與 0x40002000–0x4000200F，各自追蹤 Tag。

這裡談的是 Request 的邊界限制；上一節談的是同一 Request 的 Completion 切分，兩者發生在不同階段。

收到 Completion 也要先看 Status。SC 表示這次要求成功完成；UR、CA 是不同的失敗結果，不能把無資料的 Cpl 解成讀到了零。RRS 只在規定的 Configuration 情境適用，並不是普通 MMIO 讀取的通用「稍後再試」。若分段讀取中收到失敗 Completion，該回覆會終結這筆要求，不應繼續等剩餘成功片段。

邊界與失敗回覆來源

4 KiB 規則：§2.2.7.1，p.163。Status：Table 2-37，p.197；RRS 限制：§2.3.1，p.214 的說明；失敗讀取回覆與終止：§2.3.1.1，pp.214、218。接收端對部分非法封包的檢查是可選的，不代表發送端可以產生那些封包。

7. 換一個條件，判讀會怎麼改變？

第一個回覆帶 128 bytes，Byte Count 卻是 256，是否互相矛盾？

不矛盾。Byte Count 是這筆要求從目前片段起尚待回傳的量，包含目前片段。用 兩段回覆表 可算出下一段應剩 128 bytes；Payload 大小另由 Length 表達。

收到 Requester ID 相同但 Tag 不同的 CplD，可以拿來補這筆讀取缺少的資料嗎？

不能。它屬於另一個 Transaction ID。即使長度、數值或抵達時間恰好相符，也不能取代配對條件。（Figures 2-27／2-28，p.153。）

4-byte MWr 沒收到 Completion，應該重送嗎？

不能以此作為重送依據。普通 MWr 是 Posted Request，本來就沒有對應的一般 Completion；重送反而可能重複觸發 Register 的副作用。應依裝置介面定義的狀態或通知判斷進度。（Table 2-42，p.222。）

在 Base 6.0 查到 Figure 2-31，就能解所有 PCIe 6.0 封包嗎？

不能。這張圖屬於 Non-Flit Mode 的 Request 格式。先確認模式，再選 §2.2.1.1 或 §2.2.1.2 的 Header 定義；不能把版本號與模式當成同一件事。
