圖把三種機制放在同一對角色間比較，並不表示每筆交易依序執行全部提示。

TPH
TLP Processing Hints，封包處理提示
LTR
Latency Tolerance Reporting，延遲容忍度回報
OBFF
Optimized Buffer Flush/Fill，緩衝區排空與填入的活動提示

TPH（TLP Processing Hints，交易處理提示）補充資料的預期用途；LTR（Latency Tolerance Reporting，延遲容忍度回報）描述服務需求；OBFF（Optimized Buffer Flush/Fill，最佳化緩衝排空／填入）由平台提示適合集中活動的時窗。先看方向，再看各自的欄位與限制。

TLP
Transaction Layer Packet，交易層封包

  1. 先辨識誰提供資訊

    提示協助最佳化，沒有改變基本 Memory Space 的存取權限與控制。

    Endpoint 知道資料接下來如何使用，以及能等待多久；平台知道中央資源何時適合活動。

    Base 6.0 §6.17、§6.18、§6.19，pp.778–781、787。

  2. 把用途與時間分開解碼

    未宣告有效延遲需求時，Value／Scale 欄位會被忽略。

    TPH（提示資料用途的機制）查 Processing Hint 與 Steering Tag；LTR（回報服務等待需求的機制）查 Requirement、Value 與 Scale。

    Base 6.0 Table 6-13、Figure 6-15，pp.779、781。

  3. 再看平台傳回的時窗

    它是 hint；已獲允許的 bus mastering 或中斷，不會只因沒有提示就一律禁止。

    OBFF（提示適合活動時機的機制）可區分 CPU Active、OBFF 與 Idle，讓裝置考慮集中傳輸或中斷。

    Base 6.0 §6.19，p.787。

要讓資料靠近某個處理資源，先查什麼？

先讀 Table 6-13 的 Processing Hint（資料用途提示），再到 §6.17.2 看 Steering Tag（處理資源導引標籤）。標籤值是系統特定的資訊，不是通用 CPU 編號。軟體先探索 TPH Requester 的能力與表格位置，才配置適當標籤。

Steering Tag 的表可放在 TPH Requester Extended Capability，或和 MSI-X Table 共用位置，同一 Function 不可同時放在兩處。這些提示不改變 Bus Master Enable、Memory Space Enable 與 BAR 的基本限制。

MSI-X
Message Signaled Interrupts Extension，表格式訊息中斷
BAR
Base Address Register，基底位址暫存器

讀到 Value=10、Scale=2，要先做什麼？

作者案例：假設 LTR Message 的某一類延遲 Requirement=1、Value=10、Scale=010b。先用 Figure 6-15 確認需求有效，再按比例 1,024 ns 計算：10×1,024 ns＝10,240 ns。若 Requirement=0，該類沒有延遲需求，Value 與 Scale 會被忽略，不能照算成零或另一個門檻。

啟用前須確認 Root Complex 與所有中間 Switch 都支援；沿 hierarchy 啟用時，最靠近 Root Port 的裝置先啟用。Root Complex 並非必須滿足每個回報延遲，規格是強烈鼓勵其最差服務延遲不超過回報值，不能改寫成固定的完成時間保證。

平台說現在適合活動，裝置一定要立刻動作嗎？

OBFF 讓平台把低增量功耗的活動時窗往下游提示。§6.19 的 CPU Active 表示系統可供一般活動；OBFF 表示記憶體路徑可供裝置讀寫；Idle 表示平台閒置。裝置如何利用時窗仍和自身緩衝、需求與政策有關。

訊號可使用 WAKE# 或 Message，但兩者有適用限制；非 D0 的 Function 不得回應 OBFF／CPU Active。讀到這裡應把「提示如何安排活動」與「允許發起存取」分清，然後回到實際裝置的控制條件。
