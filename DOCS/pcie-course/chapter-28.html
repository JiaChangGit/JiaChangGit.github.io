ACS
Access Control Services，存取控制服務

P2P（Peer-to-Peer，同儕對同儕）描述裝置間的交易路徑。是否直達，還要看拓樸支援、位址、存取權與 ACS（Access Control Services，存取控制服務）的有效設定。本章先走一筆要求，再分清導引、阻擋與 Multicast（多播）。

  1. 先找到控制點

    同一個Switch下方的拓樸位置，不會自動消除存取控制。

    ACS（決定正常路由、阻擋或導引的存取控制）依元件與方向檢查交易。先定位是哪個 Port 收到哪個方向的封包。

    Base 6.0 §6.12，p.751。

  2. 再看要求是否被導引

    Request Redirect 不影響完成回覆；完成回覆另有自己的Redirect控制。

    啟用適用的 P2P Request Redirect 時，Switch 的下游Port會把同儕要求往Root Complex導引。

    Base 6.0 §6.12.1，p.753。

  3. 依有效條件判讀直達路徑

    Root Port 宣告某個ACS導引能力，不等於Root Complex保證提供同儕傳輸。

    確認沒有要求阻擋或導引條件，且路徑支援該交易後，才依正常路由送到目的端。

    Base 6.0 §6.12.1，p.753，footnote 121。

該先看 ACS Capability 還是 Control？

先查 Capability 確認該控制點提供什麼，再讀 Control 確認目前啟用了什麼。接著帶入封包種類、方向與 AT（Address Type，位址轉譯類型）。例如 Translation Blocking 針對收到的上游 Memory Request 檢查 AT，完成回覆不受這項控制影響。

作者情境：A 要對 B 寫入，Switch 下游入口啟用 P2P（同儕交易）的 Request Redirect。要求先往 Root Complex 導引，由平台的驗證邏輯處理；不能因 B 在同一顆 Switch 下就畫成必定直達。平台驗證的實際演算法不由 Base 統一定義。

只導引 Request，Completion 為何另有規則？

Request 與 Completion 的導引分開控制，還要維持交易排序。§6.12.1 說明 Completion Redirect 的目的，§6.12.6 再處理排序影響。分析時把要求與回覆分成兩條方向，保留 Relaxed Ordering（放寬排序屬性）等條件；不要用一條對稱箭頭省略回覆規則。

多播是不是把一般讀取送給所有人？

不是。先看 Figure 6-14 的位址範圍與群組視窗，再讀 §6.14.1 的 Multicast Hit 條件。命中的交易種類限 Memory Write 或 Address Routed Message，兩者是 Posted Request；Non-Posted Memory Request 即使位址落在視窗內，也仍依一般單播處理。

作者案例：假設已啟用合法的多播配置，視窗大小 1000h，位址距 MC_Base_Address 為 2500h。依 MCG 公式，這筆 Posted 寫入選到群組 2。群組成員與權限仍需另外配置；僅算出群組號碼還沒有建立多播目的地。

命中多播後，一般位址路由規則改由多播處理取代，ACS 也只剩適用的 Source Validation。這是 §6.14.1 的明確例外，不能套用前節所有同儕導引控制。
