1. 同一個 offset，先問它從哪裡算起

選定 Function 之後，它的 PCIe Configuration Space（設定空間）提供 4096 bytes 的位置。前 256 bytes 保留 PCI 相容布局，其後是 Extended Configuration Space（延伸設定空間）。本章的 byte offset 都只描述這份設定空間內的位置；CPU 實際執行存取所需的平台位址另由存取機制提供。

例如，0x34 是從 Function 設定空間起點計算的 Capabilities Pointer；某個結構標示的 Offset 04h，則可能是從該結構起點計算。先確認原圖畫的是整份設定空間，還是其中一個結構，再做加法。

設定空間透過記憶體映射存取，就等於裝置的 Memory BAR 嗎？

BAR
Base Address Register，基底位址暫存器

不等於。ECAM（Enhanced Configuration Access Mechanism）把 CPU 對指定記憶體範圍的存取轉成 Configuration Request；BAR 則描述裝置所需的資源。兩者都可能從 CPU 的記憶體位址發起，目的與轉換方式卻不同。

BAR
Base Address Register，基底位址暫存器

查詢介面還必須能存取所需範圍。PCI 相容存取機制只涵蓋前 256 bytes；不能用它沒有提供的能力，推論 0x100 之後的功能不存在。ECAM（將 CPU 記憶體存取轉成設定要求的機制） 的平台基址與可用 Bus 範圍要由平台提供，本章不自行猜一個實體位址。

規格依據與存取限制

Base 6.0 §7.2–§7.2.2.2，pp.905–909；Table 7-1（pp.907–908）列出 ECAM 位址中的 Bus、Device、Function 與 Register 部分。跨 DWORD 邊界或使用鎖定語意的 CPU 存取，不保證能由 Root Complex 轉成 Configuration Request（pp.907、909）。本章使用自然對齊、大小明確的設定讀取。

3. 清單中出現 ID = 0，就可以停止了嗎？

教學假設

目標為已發現的 0000:03:00.0。設定讀取均成功，資料來自同一份穩定快照，平台可以存取完整設定空間。下列位置與讀值由作者設計，未列出的欄位不視為 0。此 Function 不支援 Flit Mode；後面的 AER（Advanced Error Reporting，進階錯誤回報） Header 因而採可用的 Version 2。這個前提是為了讓範例結構彼此一致，不由清單位置推得。

案例推演：入口為 0x40 & 0xFC = 0x40。每次讀取 16 bits 後，以 value & 0xFF 取 ID，以高 8 bits 對應的 (value >> 8) & 0xFC 取得下一項的位置。

在 0x50，Null Capability 的 ID 表示這個節點沒有功能資料，Next 卻仍指向 0x70，所以繼續走到 PCIe 與 MSI-X。完成這條傳統清單後，序號查詢仍應回到延伸清單的獨立入口；兩份清單各自描述所屬能力。

本例的 MSI-X 結構存在，也不代表中斷已啟用。能力的存在、控制位設定及目前是否能使用，仍是不同問題；MSI-X 的設定流程留到中斷章。

兩個 DWORD 拼起來，就是平常書寫的 EUI-64 順序嗎？

先分清楚「Register 整數」與「識別碼的位元組順序」。本例組成的 Register 整數是 (0x77665544 << 32) | 0x33221100 = 0x7766554433221100。Table 7-222 另外規定，Register bits 7:0 對應 EUI bits 63:56，接著依 byte 對映；因此本例按 EUI 的高位元組到低位元組書寫時，是 00-11-22-33-44-55-66-77。

這組數字只示範資料重組，不主張是已配發或可以拿去使用的產品序號。真實 DSN 必須符合 Table 7-222 的 IEEE 公司識別碼與製造商延伸識別碼規則。序號也不能單獨當成身分認證證據。

DSN 的範圍還要讀 §7.9.3：一般多功能 Device 若實作這項能力，Function 0 必須實作；其他有實作的 Function 必須回報相同值。因此，找到相同 DSN 不能用來區分同一個 Device 的 Function 0 與 Function 1；目前的設定對象仍由 Segment 與 BDF（Bus、Device、Function 識別號） 選定。

原文定位與版本條件

清單：§7.6–§7.6.3，Figures 7-42／7-43、Table 7-39，pp.1008–1010。AER Header：§7.8.4.1、Figure 7-154／Table 7-134，p.1112；支援 Flit Mode 時須用 Version 3，本例已排除該情況。DSN：§7.9.3–§7.9.3.2，Figures 7-241–7-243、Tables 7-221／7-222，pp.1205–1207。RCiEP、PF／VF 有另外規則，本例不適用。Table 7-39 允許向前相容的更高 Capability Version，不能把「只接受等於 1」寫成所有版本的通用搜尋規則。

5. 讀到一個欄位，就能把原值寫回去嗎？

讀取欄位定義時，也要看表格的 Attributes（存取屬性）。這一欄說明軟體寫入會觸發什麼行為。能力查詢只需要讀取；若另有修改需求，先按屬性與當前條件組成寫值，避免把查詢所得的狀態直接回寫。

先認識會直接影響判讀的存取屬性
屬性讀值與寫入的意義常見誤判
RO軟體不能改寫；若欄位明確反映硬體狀態，值仍可能隨執行狀態改變。唯讀不等於永遠不變。
RW軟體可設定或清除，仍須遵守該欄位的額外條件。可寫不代表任何時刻、任何值都合法。
RW1C讀取狀態；寫 1 清除對應狀態，寫 0 沒有效果。把讀值原樣寫回，可能清掉原本想保留的事件。
RsvdP保留且保存。此版本讀為 0，寫入時軟體必須保存讀到的值。不能自行借來存資料。
RsvdZ保留且寫零。此版本讀為 0，寫入時軟體必須使用 0。不能對所有 Reserved 都套相同的讀改寫方式。
語義練習，不是實際 Register 配置

假設一個 4-bit 狀態欄全為 RW1C（寫入一才清除對應狀態），讀到 1001b，只想清除 bit 0。應寫 0001b；若期間沒有新事件，剩下 1000b。若把讀到的 1001b 原樣寫回，bit 3 也會一起被清掉。真實 Register 可能混合不同屬性，必須按整張欄位表組成寫值。

規格依據

Base 6.0 §7.4，Table 7-2，pp.913–915；本表取 RO、RW、RW1C（寫入一才清除對應狀態）、RsvdP（寫入時須保存讀值的保留欄位）、RsvdZ（寫入時須為零的保留欄位） 的語義。HwInit 與 Sticky 類型另有初始化和 Reset 條件，留到相關章節使用，不把未列在此表的類型視為等同 RW。

6. 找不到時，怎麼分清「不存在」與「還不知道」？

把查詢結果寫成可核對的結論
實際取得的證據可以怎麼記錄？仍不能推論什麼？
在正確清單中找到目標 ID，且已核對版本與類型。此 Function 暴露該 Capability；可繼續讀其定義欄位。不能直接宣告功能已啟用、工作已完成。
成功走完適用的清單，Next 為 0，沒有找到可選的目標。這份有效清單沒有暴露目標 Capability。不能因此宣告整張卡、其他 Function 都不支援。
有效讀取 0x100 得 0x00000000。依 §7.6.1，這個 Function 沒有 Extended Capability。不能把同樣規則套到傳統清單的 Null ID。
存取介面不支援延伸區，或這次讀取失敗。尚未取得可用的查詢結果。不能拿失敗後的 buffer 當成「支援位元全為 0」。
指標循環、超出範圍，或資料與必要結構矛盾。清單無法可靠解析，保留異常位置與讀值。不能假裝正常走到結尾。

最後一列整理教材採用的解析檢查：記下走過的 offset，檢查位置範圍與對齊，並辨認是否重訪同一節點。清單位置可以往前或往後；重訪才是循環檢查的依據。遇到無法可靠解析的資料時，保留異常位置與讀值，再釐清原因。

同樣地，成功讀到 0 不保證那裡是一個有意義的欄位。Base 6.0 §7.3.3（p.913）規定，在沒有其他需回報錯誤的情況下，對未實作 Register 的設定讀取成功回傳 0。位置與格式必須先由標頭、Capability 或明確的 Register 定義建立，不能靠讀值看起來合理來猜。

7. 串接一次完整的序號查詢

回到完整序號查詢：先選定 0000:03:00.0，從 0x100 進入延伸清單，沿 Next 找到 0x180 的 DSN，再讀 0x184 與 0x188。最後按序號定義重組位元組，並保留它在多功能 Device 中的共用範圍。以下延伸說明分別改動指標、資料位置與屬性。

讀到 0x50 的值是 0x7000，下一步是停止、讀 0x70，還是讀 0xC0？

讀 0x70。ID 0 是傳統 Null Capability，Next 0x70 從設定空間起點計算。0xC0 是把目前位置錯加上 Next 的結果。（Figure 7-384／Table 7-336，p.1315；各 Next Pointer 的定義見清單來源。）

Extended Header 改成 0x24010003，DSN 資料要到 0x244 讀嗎？

先問這個 Header 是在哪裡讀到的。若仍在 0x180，ID 0003h 代表目前這一項就是 DSN，資料仍在 0x184 與 0x188；0x240 是下一項的位置。只有目前結構真的位於 0x240，Lower DW 才在 0x244。（Figures 7-241／7-243，pp.1205–1206；Table 7-39，p.1010。）

同一個 Device 的兩個 Function 回報相同 DSN，是規格違反嗎？

不是。本章的一般多功能 Device，其他有實作 DSN 的 Function 必須回報與 Function 0 相同的值。DSN 不能拿來代替 BDF 的 Function 部分。（§7.9.3，p.1205。）

某個狀態是 RO，兩次讀值不同，就代表裝置壞了嗎？

不能這樣判定。先查欄位是否明確反映會變動的硬體狀態。RO 限制的是軟體改寫，並不禁止硬體依定義更新狀態。（Table 7-2，p.914。）

8. 查詢入口本身是怎麼找到的？

本章從一個已知存在的 Function 開始。接著的 Chapter 3 會往前追問：系統還不知道有哪些 Bus 和 Function 時，如何安排搜尋路徑？原本尚未配置的 Bridge，又如何逐步成為可查詢的下游入口？
