先看分類如何對到資源，再看多個可傳送通道如何共用實體線路。兩條 VC 分支可以並存。

VC
Virtual Channel，虛擬通道
TC
Traffic Class，流量類別

TC（Traffic Class，流量類別）是封包上的分類；VC（Virtual Channel，虛擬通道）將流量對應到佇列、緩衝與流量控制資源。本章先看映射，再用雙端配置案例走完啟用與初始化，最後接到傳送仲裁。

  1. 從封包分類找到映射

    一個類別不能在同一 Port 或 Function 被映射到多個通道；同一 Link 兩端須一致。

    §2.5 說明資源模型；§2.5.2 的 Table 2-43 列出可行的分類到通道映射。TC0 固定對應 VC0。

    Base 6.0 §2.5、§2.5.1、§2.5.2，pp.229–234；Table 2-43，p.233；Figure 2-88，p.234。

  2. 把需要隔離的流量分開

    Pending 只有在 Link 處於 DL_Active、且該 VC 已啟用時才有定義；不能用停用時的零值判定完成。

    兩端先設定對應的 VC ID 與 TC/VC Map，再分別啟用。使用之前，還要在有效條件下讀到雙端的 VC Negotiation Pending 都為零。

    Base 6.0 §7.9.1.7、§7.9.1.8，Tables 7-207／7-208，pp.1189–1192。

TC 與 VC 分別在哪裡決定？

TC（Traffic Class，流量類別）是 TLP 上的標籤，沿途保持相同；VC（Virtual Channel，虛擬通道）則由每一條 Link 的映射決定，用來對應佇列、緩衝與流量控制資源。§2.5.1 特別提醒：TLP 沒有 VC ID 欄位，接收端要依 TC/VC Map 找到該 TLP 所屬的 VC。

TLP
Transaction Layer Packet，交易層封包

先讀 Table 2-43（p.233）。在 VC0、VC1 這一列，右欄示範 TC0–TC6 對應 VC0、TC7 對應 VC1。這是一種配置範例；TC0 必須固定對應 VC0，其他受支援的 TC 則由軟體配置。同一個 TC 在一個 Port 或 Endpoint Function 內，只能映射到一個 VC。

再看 Figure 2-88（p.234）的上半部：Endpoint 到 Switch 的 Link 只有 VC0，TC7 在這一段也走 VC0；Switch 到 Root Complex 的 Link 則把 TC7 對應到 VC1。TC7 的標籤沒有改變，改變的是各段使用的資源。必須一致的是同一條 Link 兩端的 VC ID 與映射，並非整個 Switch 的所有 Ports 都採同一份配置。

兩端都支援 VC1，還要怎麼把它設成可用？

先配置兩端的 VC ID 與 TC/VC Map，再分別啟用，最後確認兩端的 VC Negotiation Pending 都已清為零。VC Enable 是控制設定；VC Negotiation Pending 表示該通道的協商是否還在進行。單看其中一端的 Enable=1，還沒有走完這段流程。

【模擬資料】以下資料為教學用途建立，不代表特定硬體或平台。本例只分析 Root Port 00:01.0 與單一 Function Endpoint 01:00.0 之間的一條 Link。兩端的資料鏈結層持續處於 DL_Active，使用 Non-Flit Mode，不支援 Flit Mode；沒有 MFVC，也沒有使用仲裁表。兩端的 Extended VC Count=1，Low Priority Extended VC Count=0，All VCs Enabled 目前保持 0。

這個 Count 不包含基本的 VC0，所以各端共有兩組 VC Resource registers。配置前，VC0 已可用，TC/VC Map 為 FFh；額外資源尚未啟用。這次要讓 TC0–TC6 留在 VC0，將 TC7 移到 VC1。兩個方向都先停止新增 TC7 交易，並確認相關未完成交易已結束，再開始修改映射。

先從 Figure 7-221 找到控制與狀態

假設已沿 Extended Capability List 找到兩端的 Virtual Channel Extended Capability：ID=0002h、Version=1，Root Port 的結構起點為 180h，Endpoint 為 200h。這些起點是各 Function 的 Configuration Space offset，不是全系統共用的地址。

Figure 7-221（p.1183）把每組資源排成 0Ch bytes。選第二組，也就是資源索引 1：Control 的相對位移是 14h + 1 × 0Ch = 20h。Status 在其所在 32-bit 列的高 16 bits，所以 16-bit Status 的相對位移是 18h + 1 × 0Ch + 2 = 26h；不能把整列起點 24h 當成 Status 的存取位置。

本例讀取對象Root Port 00:01.0Endpoint 01:00.0
VC Resource Control Register (1)，32-bit180h + 20h = 1A0h200h + 20h = 220h
VC Resource Status Register (1)，16-bit180h + 26h = 1A6h200h + 26h = 226h

接著配置 Map 與 VC ID，再啟用

讀 Table 7-207（pp.1189–1191）時，先定位 TC/VC Map[7:0]，每個 bit 對應同編號的 TC。兩端都先把 TC7 從 VC0 移除，使 VC0 的 Map 由 FFh 變成 7Fh；再把資源 1 的 VC ID[26:24] 設為 1，Map 設為 80h，此時 VC Enable[31] 先保持 0。中間暫時沒有啟用的 VC 承接 TC7，因此這段期間持續保持 TC7 流量停止。

在本例其他位元均為零的假設下，資源 1 的 32-bit Control 快照為 01000080h。等兩端的配置都備妥，再分別將 VC Enable 設為 1，快照成為 81000080h。軟體仍須依欄位屬性更新設定，保留 RsvdP 位元；這兩個數字用來解釋欄位如何組成讀值。

最後以雙端 Status 確認，不寫入 Pending

Table 7-208（pp.1191–1192）的 VC Negotiation Pending 位於 Status bit 1，屬性為 RO，由硬體更新。它只有在 Link 處於 DL_Active 且該 VC Enable=1 時才有定義。若 VC 尚未啟用，即使工具把這個 bit 顯示為 0，也不能用它確認協商完成。

啟用後的兩次觀察Root Port 的 16-bit StatusEndpoint 的 16-bit StatusTC7 的使用時機
兩端 Enable 均為 1，初始化仍在進行0000h：Pending=00002h：Pending=1繼續等待，兩端尚未都完成
兩端 Enable 仍為 1，之後再次讀取0000h：Pending=00000h：Pending=0可開始使用 VC1，仍須符合正常傳送條件

Pending 在 VC 協商完成、離開 FC_INIT2 時由硬體清除。這裡要讀取的是兩端同一個 VC 的結果；只看到 Root Port 已清零，就讓 Endpoint 使用 TC7，會漏掉另一端尚未完成的初始化。Status 不是 W1C 事件欄位，軟體不以寫入 1 的方式「完成協商」。

所有預定使用的 VCs 都已啟用後，軟體可選擇設定 Port VC Control 的 All VCs Enabled（bit 4）。它幫助硬體分配緩衝資源；保持 0 時，已啟用的 VCs 仍須正確運作。若已設為 1，Link 還在運作時再改變此 Capability 內的 VC Enable，規格定義為 undefined behavior，不能把它當成一般的即時切換方式。

完成初始化後，VC0 沒有 credit，VC1 還能走嗎？

【模擬資料】沿用前節已完成初始化的 Non-Flit 配置，以下是假設的傳送時點。從 Endpoint 向 Root Port 傳送時，TC0 的 Memory Write 映射至 VC0；TC7 的 Memory Write 映射至 VC1。VC0 的 Posted Data Credit 不足，VC1 則有足夠的 Header 與 Data Credit，TC7 也符合其他排序與傳送條件。

候選封包對應資源目前是否能參與傳送仲裁？
TC0 Memory WriteVC0 的所需 Data Credit 不足這筆封包先等待
TC7 Memory WriteVC1 的所需 Credit 充足可參與仲裁，仍須等仲裁選中

Non-Flit Mode 各 VC 的 Flow Control credit pool 獨立，所以 VC0 這筆封包受阻，不會直接扣掉 VC1 的可用 credit。這也不是「VC0 的所有封包都停住」：同一 VC 仍分成不同的 Flow Control 類別，要依候選封包實際需要的資源判斷。這裡先看 VC 之間的隔離，credit 消耗與更新接到 Chapter 17 繼續閱讀。

Flit Mode 若使用 Shared FC，資源分成專用與共享部分，不能把上面的完全獨立池模型原樣搬過去。§2.6 說明共享 credit 的使用條件；一個 VC 能參與仲裁，仍要依當時適用的資源模型判斷。

FC
Flow Control，流量控制

規格閱讀：§2.6 Ordering and Receive Buffer Flow Control，p.235；§6.3.3.1 的 Implementation Note: VC Control Logic at the Egress Port，p.709。Flow Control 保護相鄰接收端的緩衝，並不代表要求已到達最終 Completer。

兩個 VC 都能傳送時，誰先使用 Link？

先分清仲裁的對象。若流量經過 Switch，用 Figure 6-8（p.708）從左向右讀：先依地址或其他路由資訊找出 Egress Port，再依該出口的 Map 決定 VC。來自不同 Ingress Ports、但要進入同一個出口 VC 的流量，先由 Port Arbitration 決定服務順序；出口內不同 VCs 再由 VC Arbitration 競爭共同 Link。兩者都不是單看封包上的 TC 數字就能決定。

再接 Figure 6-9（p.709），先讀 VC ID 與 Relative Priority，再看右側的優先群組分界。規格確實定義 VC ID 由小到大的預設相對優先次序；若採 Strict Priority（嚴格優先），較大的 VC ID 先服務。若一組 VCs 採 RR（Round Robin，輪流服務）或 WRR（Weighted Round Robin，按權重輪流服務），則須讀對應的仲裁能力、選擇與表格，不能只按 ID 排出所有實際傳送次序。

前面的模擬配置指定 Low Priority Extended VC Count=0，依 §6.3.3.2，所有 VCs 都採 Strict Priority。因此，在同一傳送端兩個 VC 都有合格封包可送時，VC1 的相對優先權高於 VC0。這不是 TC7 自帶的頻寬保留；TC7 只是剛好映射到本例的 VC1。

優先權也不能讓缺少 credit 的封包直接傳送。反過來，若高優先流量持續占用 Link，較低優先流量可能一直得不到服務。§6.3.3.2.1 要求使用 Strict Priority 時調節高優先流量，並由系統軟體安排足夠的低優先服務，避免交易逾時。需要頻寬與延遲保證時，還要接到下一節的全路徑契約。

週期資料需要保證，還要建立什麼？

Isochronous Contract（等時性服務契約）把要求者、完成端與沿路資源的責任連在一起。讀 Figure A-1（p.1521）時，先選一條完整流向：Device A 與 Root Complex 之間，包含向上的 Read／Write Requests 與返回的 Read Completions；Device B 到 Device C 則是另一條 Peer-to-Peer 流向。兩種模型都要核對自己的路徑與服務能力。

接著看 Figure A-2（p.1522）的兩條時間軸。上方是過度配置，分配給等時性要求的資源使其他流量幾乎沒有服務空間；下方是短時間內注入過多要求而造成壅塞。因此契約同時需要資源保留與流量調節。§A.2 再把期間 T、交易數 N、每筆預算負載 Y 與延遲 L 接在一起；只把 TC7 映射到 VC1，還沒有建立這份契約。

本章先建立查閱入口，沒有宣稱已配置完整等時性服務。多個流程共用相同 VC／TC 時，系統還要核對總需求；一般非等時性服務的 TC／VC 分配政策，也不能當成 Base 6.0 對所有平台規定的固定配置。
