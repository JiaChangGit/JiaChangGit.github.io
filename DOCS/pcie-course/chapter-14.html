OHC
Orthogonal Header Content，Flit模式的擴充標頭內容

TLP（Transaction Layer Packet，交易層封包）把要求、回覆與訊息送過 PCIe。讀取封包前，先確認 Link 使用 Non-Flit Mode（非 Flit 模式）或 Flit Mode（固定傳輸單元模式）；兩者的 TLP（承載交易的封包）標頭布局不同。本章從這個分岔開始，把格式欄位接到位址、資料長度與有效 byte。

  1. 先確認目前格式

    先從觀察位置確認 Link 模式；不要只憑封包第一個 byte 猜測。

    Non-Flit Mode 先讀 Fmt 與 Type；Flit Mode 先讀 8-bit Type。相同的 byte 值，在兩種格式可能有不同意義。

    Base 6.0 §2.2.1，Figures 2-4–2-6、Tables 2-2–2-5，pp.119–123。

  2. 找出後續欄位的位置

    OHC（Orthogonal Header Content，正交標頭內容）須按 A、B、C、E 的順序出現；需要哪些內容另由封包種類決定。

    非 Flit 格式由 Fmt 說明 3 或 4 DW 標頭及資料是否存在；Flit 格式用 Type 的表列資訊，再加 OHC 與 TS。DW 是 Double Word，等於 4 bytes。

    Base 6.0 §2.2.1.1–§2.2.1.2，pp.119–123、130–132。

  3. 再讀交易內容與 byte 選擇

    Byte Enables 的細節依模式、種類及條件而異；後面的案例會比較普通 Memory Write 在兩種模式下的布局。

    依已辨識的封包種類，定位位址或目的識別碼，再讀 Length 與 Byte Enables（有效 byte 選擇）。不能把讀取要求的長度解釋成要求本身帶有同樣大小的資料。

    Base 6.0 §2.2.5.1–§2.2.5.2／Figure 2-26、Table 2-10，pp.149–152；§2.2.9，p.195。完整封包案例見下方兩種模式的帶讀。

為什麼不能只背一張標頭圖？

在非 Flit 格式，先用 Figure 2-4 找 byte 0 的 Fmt／Type，再對 Table 2-2、Table 2-3。以 Memory Read 為例，Fmt 可表示 32-bit 或 64-bit 位址布局，要求不帶資料；Memory Write 則帶寫入資料。Type 也會影響路由，因此只看 Length 還不足以找到下一個封包。例如，另一筆 Non-Flit、32-bit 位址的 Memory Read 即使 Length=2，在沒有 Prefix 與 Digest 時，Request 本身仍只有 12 bytes Header，讀取資料由後續 Completion 返回。先確認這個 Type 是否帶資料，再使用 Length 計算封包大小。

換成 Flit 格式時，從 Figure 2-6 與 Table 2-5 重新開始。Type 不再只是舊格式的五個 bits；例如 Table 2-5 的 NOP 是 00h，而 32-bit 位址 Memory Read 是 03h。若沿用非 Flit 的解碼表，第一步就會讀錯。

找到基本標頭後，怎麼走到資料？

OHC（用來補充標頭資訊的擴充內容）由 Figure 2-6 的 OHC 欄位指出。接著讀 p.131 的出現順序，再用 Table 2-6 選擇適用的 A 類布局。例如有明確 Byte Enables 的 Memory Request，要沿 Table 2-6 找到 Figure 2-7 的 OHC-A1。後面的完整案例會把它接到實際的資料起點。不要固定假設所有 Flit 標頭都是相同長度。

TS 是 Trailer Size，用來指出尾部大小與用途；它與 Length 的資料長度分開計算。非 Flit 格式另有 Prefix（標頭前的擴充內容）與 TD（TLP Digest 存在標記）。判讀工具應先完成整個格式的大小計算，再移到後一包。

用同一個寫入需求，走完兩種格式

【模擬資料】以下資料為教學用途建立，不代表特定硬體或平台。兩段獨立 Trace 都由已配置的 Endpoint 03:00.0 發出 Memory Write，目標位址為 0x80001000。本例假設位址與路徑可用、允許裝置發起存取，且沒有 Prefix、IDE 或 TPH；保留欄位及其他未使用欄位填 0。兩段 Trace 的 Link 模式已由外部資訊確認，並已取得完整的邏輯 TLP。

IDE
Integrity and Data Encryption，完整性與資料加密
TPH
TLP Processing Hints，封包處理提示

兩筆資料負載相同，都是 A0 A1 A2 A3 B0 B1 B2 B3，Length=2 DW（每個 DW 是 4 bytes）；但只要寫入中間四個 bytes。First DW BE=1100b，Last DW BE=0011b。Flit 案例從已重組的 TLP 開始，沒有把完整 FLIT 當作一筆 TLP。下列十六進位依圖中的 byte 0、byte 1 順序排列，每四個 bytes 換行；它不是 CPU 端的 DWORD 讀值表。

先讀 Non-Flit 的 20 bytes

40 00 00 02
03 00 00 3C
80 00 10 00
A0 A1 A2 A3
B0 B1 B2 B3

先用 Figure 2-4 讀第一個 byte：0x40 的 Fmt=010b、Type=00000b。查 Tables 2-2／2-3 的組合，得到帶資料、使用 3 DW Header 的 Memory Write。再用 Figure 2-5 讀 Length=2、TD=0；因此本例有 12 bytes Header、8 bytes Data Payload，沒有 Digest，合計 20 bytes。

接著換到 Figure 2-31。byte 4–5 的 03 00 是 Requester ID=0x0300，本例對應 03:00.0；byte 8–11 提供地址，得到 0x80001000。最後到 Figure 2-26／Table 2-10，讀 Header byte 7=0x3C：高四位是 Last DW BE=0011b，低四位是 First DW BE=1100b。Header 在 byte 11 結束，資料從 byte 12 開始。

再讀 Flit 格式的 24 bytes

40 01 00 02
03 00 00 00
80 00 10 00
00 00 00 3C
A0 A1 A2 A3
B0 B1 B2 B3

這次先讀 Figure 2-6，第一個 byte 的整個 0x40 都是 Type。查 Table 2-5 編號 64 的項目，得到 32-bit address Memory Write、Header Base=3 DW，Data Payload 由 Length 決定。這筆 Type 恰好與前例的第一個 byte 相同，不能用它單獨辨識 Link 模式。

byte 1 的 OHC=00001b 表示有 OHC-A；byte 2 的 TS=000b 表示沒有 Trailer，Length 仍為 2。先用 Figure 2-40 讀完 12 bytes Header Base，再依 Table 2-6 的 Memory Request 選到 OHC-A1。Figure 2-7 顯示這個擴充占 1 DW；其內部 byte 3 才是兩組 BE。換成整筆 TLP 的位置，就是 byte 12+3=byte 15，讀到 0x3C。

所以這筆的 Data Payload 從 byte 16 開始，總長度為 12+4+8=24 bytes。本例 OHC-A1 的 PV=0，沒有有效的 PASID；其餘不使用欄位為 0。OHC-A1 在這裡用來提供部分寫入所需的 BE，沒有增加資料負載的長度。

PASID
Process Address Space ID，程序位址空間識別碼

現在回到 §2.2.5.2 看這個擴充為何不能省：對這筆 2 DW Memory Request，若沒有 OHC-A1，接收端會把 First 與 Last DW BE 都視為 1111b。這會變成八個 bytes 全部啟用，已經改變原本只寫中間四個 bytes 的需求。OHC 是否存在，會直接影響接收端如何執行存取。

如果工具把第二段 Trace 當成 Non-Flit，就可能把 byte 7 的 0x00 誤讀成兩組 BE，並把 OHC 的 00 00 00 3C 當成資料起點，讓整段 payload 錯位四個 bytes。本例應先修正工具的解碼模式；這些假象不能直接當作線路上真的出現了錯誤封包。

八個 payload bytes，為什麼只寫入四個？

沿用上面的兩筆模擬資料。§2.2.5.1 與 Table 2-10 把每個 BE bit 對應到資料 byte：First DW BE 的 bit 0 對應第一個 DW 的最低位址 byte；Last DW BE 的 bit 0 則對應最後一個 DW 的最低位址 byte。1100b 選到第一個 DW 的 +2、+3；0011b 選到最後一個 DW 的 +4、+5。

兩種格式送出相同資料，也選到相同的記憶體 bytes
資料內的 offset對應位址Payload 內容依本例 BE 執行的寫入
+0、+10x80001000–0x80001001A0、A1不寫入這兩個 bytes。
+2、+30x80001002–0x80001003A2、A3寫入 A2、A3。
+4、+50x80001004–0x80001005B0、B1寫入 B0、B1。
+6、+70x80001006–0x80001007B2、B3不寫入這兩個 bytes。

因此被選取的位址範圍是 0x80001002–0x80001005，共四個 bytes，但兩筆 TLP 的 Data Payload 都仍有八個 bytes。Length 維持 2 DW，接收端不會因為部分 bytes 沒被選中，就把它們從封包裡刪掉。本例也未跨越 4-KB 邊界，BE 選取的資料連續；其他長度、對齊或非連續組合，須再依 §2.2.5.1 檢查。

在本例的 Non-Flit 格式中，若改成 1 DW Request，Last DW BE 必須為 0000b；不能把本例的 0011b 直接沿用。這項規則接在 Figure 2-26 後，圖中的位置與周圍文字要一起讀。

封包有回覆時，從哪裡接著讀？

先按 §2.2.9 確認這類要求需要 Completion（完成回覆）。Memory Read 的資料隨完成回覆返回；一般 Posted Memory Write 沒有對應的成功完成回覆。接下來到 Chapter 15，沿接收端的處理流程，確認合法性、能力與回覆結果。
