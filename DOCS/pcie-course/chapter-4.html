1. BAR 是一個資料緩衝區，還是一份資源描述？

BAR 是 Base Address Register，位於 Function 的 Configuration Header。它讓軟體辨認資源類型、查出需求大小，並寫入分配的基底位址。裝置的工作暫存器或資料區，則位於這個資源所映射的位置；讀 BAR 本身不等於讀到那些內容。

同一條路徑會同時用到三種不同的範圍
設定它描述什麼？不要拿它代替什麼？
Secondary／Subordinate Bus Number設定拓樸中的下游 Bus 範圍。不能代替 Memory Request 的位址路由範圍。
Endpoint 的 BAR這個 Function 自己要解碼的資源範圍。不能單獨保證沿途 Bridge 會轉送。
Bridge 的 Memory／Prefetchable WindowBridge 要轉送到下游的位址範圍。不是 Bridge 自己的 BAR，也不表示窗口內每個 byte 都有裝置回應。

先用 Figure 7-10 找 Type 0 Header 的 BAR 位置；遇到 Bridge，則用 Figure 7-14 分開看 BAR 與 Window。Type 0 Header 提供六個 DWORD 位置，從 0x10 到 0x24；Type 1 Header 只有兩個。64-bit BAR 會佔用連續兩個位置，所以「六個位置」不等於「六個獨立資源」。

2. 先讀哪幾個 bits，才知道後面怎麼算？

先看 BAR bit 0。為 0 時用 Memory BAR 格式，為 1 時用 I/O BAR 格式。兩者的位址遮罩不同，不能一律清掉低 4 bits。

Figure 7-11／7-12 的判讀入口
格式類型與屬性位址部分
Memory BARbit 0=0；bits 2:1 的 00b 表示 32-bit，10b 表示 64-bit；bit 3 是 Prefetchable。低 DWORD 的 bits 31:4；若為 64-bit，下一個 DWORD 接成 bits 63:32。
I/O BARbit 0=1，bit 1 保留；這個格式固定是 32-bit。bits 31:2。特定 16-bit I/O 相容配置另有大小計算規則。

Prefetchable 表示這段資源容許規格列出的讀取與合併行為，例如讀取沒有副作用，且可接受寫入合併。它不是「CPU 現在一定有快取」的狀態位，也不能拿來推論應用程式實際帶寬。

對本章的一般 PCI Express Endpoint，設為 Prefetchable 的 BAR 必須支援 64-bit addressing；非 Prefetchable BAR 可以是 32-bit。此類 Endpoint 也不得依賴 OS 配置 BAR 宣告的 I/O 資源，且不得發出 I/O Requests。本例因此只用 Memory BAR；I/O 格式保留在這裡，是為了讓讀者能辨認相容機制。

欄位與類型限制

Base 6.0 §7.5.1.2.1，Figures 7-11／7-12、Table 7-9，pp.929–930；一般 Endpoint 的限制見 §1.3.2.2，p.105。Memory Type 01b、11b 在本版為 Reserved；不要把舊版低於 1 MB 的編碼無聲套進本例。

3. 寫全 1 再讀回，為什麼能知道大小？

BAR 的位址欄位中，低位元有多少固定為 0，反映需要的自然對齊大小。規格提供的探測方法，是先停止對應位址解碼，保存原 BAR，寫全 1 再讀回；遮掉類型位元後，對指定寬度取反加 1。探測完要還原原值，才能回到原配置；若接著重新分配資源，也必須在重新啟用前完成一致的配置。

教學假設：尚未投入使用的 Function

目標沿用 0000:03:00.0。本例是受控的初始配置階段，驅動尚未使用裝置，沒有進行中的交易；Memory Space Enable 與 Bus Master Enable 均為 0。軟體保存所有待探測 BAR 原值，採對齊的 32-bit 設定存取，並確認每次寫入完成。這些前提不能簡化成「把 BME 清零，就代表所有舊交易已消失」。

本例另外假設 BAR1、BAR4、BAR5 未實作；未實作 BAR 固定回 0。探測前的 BAR0 也是 0，卻是有效、尚未分配基底的資源，所以不能只看初始值為 0，就宣告 BAR 不存在。

BAR0：先限定 32 bits，再取反

address_mask = 0xFFFFC000 & 0xFFFFFFF0 = 0xFFFFC000
size = ((~address_mask) & 0xFFFFFFFF) + 1
     = 0x00004000 = 16 KiB

這表示基底必須以 16 KiB 對齊。若用沒有固定位寬的運算工具，必須把取反限制在 32 bits；直接使用無限精度的負整數結果，會算錯大小。未實作 BAR 的全 0 探測結果也不能拿去套公式，然後宣布要分配 4 GiB。

BAR2／BAR3：兩個 DWORD 是一個 64-bit 問題

address_mask = (0xFFFFFFFF << 32) | (0xFFE0000C & 0xFFFFFFF0)
             = 0xFFFFFFFFFFE00000
size = ((~address_mask) & 0xFFFFFFFFFFFFFFFF) + 1
     = 0x00200000 = 2 MiB

低 DWORD 的 0xC 解成 Memory Type=10b、Prefetchable=1。軟體探測時必須處理兩個 DWORD，保存與還原也要包含兩者；走訪 BAR 清單時，下次應前進到 BAR4，不能把 BAR3 的全 1 再當成 I/O BAR。

探測流程與算式依據

Base 6.0 §7.5.1.2.1，pp.929–930，尤其 p.930 的「Sizing a 32-bit Base Address Register Example」與其後 64-bit 說明。自然對齊、2 的冪次大小、未實作 BAR 回 0 均見同頁。本例沒有 Resizable BAR；若有該能力，還要確認目前選用的大小與相關規則，不能直接沿用本例固定需求。

4. 知道大小後，可以挑任意空位填進去嗎？

還要同時滿足平台允許的資源範圍、BAR 位址寬度、大小對齊，以及與其他分配不重疊。以下基底是作者從假設的可用資源中選出的結果；它們不是規格推薦的固定位址。

案例推演：BAR0 的尾端是 0x80004000 + 0x4000 - 1 = 0x80007FFF；BAR2／3 的尾端是 0x120000000 + 0x200000 - 1 = 0x1201FFFFF。兩個基底各自是所需大小的整數倍。64-bit BAR 的高 DWORD 為 1，讓這段資源位於 4 GiB 以上；這不代表裝置真的有 4 GiB RAM，也不表示一次交易要搬 64 bits 的資料。

5. Endpoint 的 BAR 已經填好，為什麼還可能收不到？

位址要求還得穿過沿途的 Bridge。沿 Chapter 1 的拓樸，到目標要經過 Root Port 00:01.0、Switch Upstream Port 01:00.0，以及 Downstream A 02:01.0。三者的相關 Window 都必須涵蓋目標資源；只改最靠近 Endpoint 的那一個，無法補上上游缺少的範圍。

先看 Figure 7-14 定位，再讀 §7.5.1.3.8–§7.5.1.3.10。Memory Base／Limit 的高 12 bits 對應 Address[31:20]；Base 省略的低 20 bits 補 0，Limit 則補 1。因此 Limit 不是排除式邊界，不能再少算或多算一個 byte。

Memory Base  = (0x8000 & 0xFFF0) << 16 = 0x80000000
Memory Limit = ((0x8000 & 0xFFF0) << 16) | 0xFFFFF = 0x800FFFFF

Prefetchable Base  = (1 << 32) | ((0x2001 & 0xFFF0) << 16)
                  = 0x120000000
Prefetchable Limit = (1 << 32) | ((0x2011 & 0xFFF0) << 16) | 0xFFFFF
                  = 0x1201FFFFF

本例三個 Bridge 都實作 64-bit Prefetchable Window，所以 Base／Limit 的低 nibble 為 1，並使用 Upper 32 Bits。非 Prefetchable Memory Window 則是 1 MiB 粒度，足以涵蓋 BAR0 的 16 KiB；Prefetchable Window 剛好涵蓋另一個 2 MiB BAR。其餘分支不使用這兩段資源，平台也已保留這些範圍供本例使用。

6. MSE 與 BME，哪一個才是「啟用裝置」？

沒有一個位元能代替所有準備工作。Command Register 在 offset 0x04、寬度 16 bits；讀 Figure 7-5／Table 7-4 時，應把以下三個控制分開。

Command bits 0–2 各自控制的方向
位元對本例 Endpoint 的作用沿途 Port 還要注意什麼？
bit 0：I/O Space Enable控制是否解碼並處理收到的 I/O 存取；本例不用 I/O BAR。Type 1 的控制涉及 Primary Side 收到的 I/O 存取。
bit 1：Memory Space Enable（MSE）控制是否解碼並處理收到的 Memory 存取。各 Bridge 的相關解碼與窗口也須有效。
bit 2：Bus Master Enable（BME）允許 Function 發起 Memory／I/O Requests；一般 PCIe Endpoint 另受不得發 I/O Requests 的限制。Type 1 Port 的 BME 也控制向上游發起／轉送 Memory、I/O Requests；不阻擋 Completion 轉送。

案例推演：所有 BAR、Window 與平台映射已正確配置，且裝置介面已可接受本例讀取時，Endpoint 與路徑上各 Bridge 的 Command 若為 0x0002，表示 MSE=1、BME=0。CPU 可依已建立的路徑讀取本例 MMIO Register；Endpoint 仍不能自行發起 DMA 的 Memory Request。它回覆這筆讀取所需的 Completion，不是被 BME 禁止的 Memory Request。

7. OS 怎麼知道韌體交給它的 BAR 有效？

Firmware 3.3 §3.5 說明，OS 以 Command 的 I/O／Memory Enable，以及 Expansion ROM 的 Enable，判斷相應資源是否已由韌體配置；不使用 BME 判定 BAR 是否有效。所以交接時看到 MSE=1、BME=0，不代表 BAR 無效；資源既然已啟用，韌體就必須正確配置。

ROM
Read-Only Memory，唯讀記憶體

這項交接契約也不表示只要讀到 MSE=1，就能忽略平台映射或任意操作裝置。本章的配置表解決了位址與轉送問題；驅動程式仍要依裝置介面規格初始化工作流程。

交接規則來源

PCI Firmware Specification Revision 3.3 §3.5，pp.34–35；本段採用該版本的資源有效性判斷，沒有把 BME 當成 BAR 配置的替代證據。

8. 把型別、對齊與視窗接起來

把 16 KiB 的 BAR0 放在 0x80005000，其他條件都不變，可以嗎？

不行。0x80005000 & 0x3FFF = 0x1000，不是 16 KiB 對齊。大小正確但基底未自然對齊，仍不是合法的分配。（§7.5.1.2.1，p.930。）

BAR2 的低 DWORD 讀到 0xFFE0000C，能只用這 32 bits 判定 64-bit 資源大小嗎？

不能。先用 bits 2:1 確定它是 64-bit BAR，再把 BAR3 作為高 DWORD 一起探測與計算。低 DWORD 只是完整遮罩的一部分。（Figures 7-11、Table 7-9，p.929；64-bit 探測，p.930。）

三個 Bridge 的 Memory Window 都正確，Endpoint 的 MSE 卻為 0，CPU 讀 BAR0 還會成功嗎？

不能據此期待成功。Endpoint 的 MSE=0 時，收到的 Memory Space 存取依 UR 處理；沿途可轉送不等於終點已啟用。（Table 7-4，p.918。）

Command 從 0x0002 改成 0x0006，就證明 DMA 緩衝區位址正確了嗎？

沒有。兩者差在 BME；它不驗證裝置工作描述項、緩衝區生命週期或平台轉譯。還要建立並核對那些資料，才能讓裝置開始工作。
