本冊把前面機制放進具體矛盾情境：先確認比較的是同一對象與同一時點，再判斷證據是否足夠。相關機制使用固定連結，不重複整段教學。

先練習，再展開每題的 17 項解答。所有數字案例均為教學假設；Status 以 SCT/SC 表示，代碼後的 h 代表十六進位。

先認識本文使用的字詞

Controller / namespace
controller 接收命令並管理存取；namespace 是命令可指定的一份邏輯儲存空間。NVM subsystem 則包含 controller 與非揮發儲存資源，同一 subsystem 可以有多個 controller。
SQ / CQ / SQE / CQE
Submission Queue（SQ）是提交佇列，Completion Queue（CQ）是完成佇列；SQE 與 CQE 分別是其中的一筆命令及完成項目。QID 識別 queue，CID 區分同一 SQ 中尚未完成的命令，NSID 則識別 namespace。
Register / Identify / Feature / Log
Register 提供可存取的控制或狀態資訊；Identify 查詢物件的能力與屬性；Feature 用來讀取或變更工作設定；Log Page 回報特定種類的狀態或紀錄。FID、LID、CNS、CSI 則分別用來選擇 Feature、Log Page、Identify 資料結構及命令集。
index / offset / zero-based
index 指出清單中的第幾筆，通常從 0 起算；offset 表示與起點相隔多遠，解讀時必須確認單位。若數量欄位採 zero-based 編碼，實際數量等於欄位值加 1；但不是所有欄位看到 0 都要加 1。Dword 是 4 bytes，1 byte 是 8 bits。
Scope / reset / retention
scope 表示操作影響哪些物件；retention 表示狀態是否保留。清除 CC.EN 所觸發的 Controller Reset，是 Controller Level Reset（CLR）的一種。同屬 CLR 的不同觸發方式，仍可能採用不同的 Register 保留規則。

先把觀念接起來

教學 1 · 先排除假矛盾

比較的 controller、NSID、CSI、UUID、SEL 或時間不同，結果就可能合理不同。遇到不一致時先列出這些條件，再看是不是同一個物件的同一種資料。例如 Active List 不同不代表資料損壞，Current 與 Saved 不同也不代表 Set 失敗。

教學 2 · 每次只改一個能解釋結果的條件

建立合法基準後，只改一個參數或順序，才能知道錯誤是誰造成的。如果 NSID、PRP 與命令狀態同時不合法，回報任何一個先檢出的錯誤都可能合理。測試設計的工作是讓證據能回答問題，而不是先選一個期待的 Status 再找理由。

教學 3 · 結論也要保留證據界線

能證明違反 shall 時就明確指出；只偏離 should 時保留建議強度；規範未定義或原文互相矛盾時，說明哪一部分無法唯一判定。這不是省略答案，而是讓符合性結論可被另一位讀者重新檢查，不把猜測寫成規範要求。

Q297 宣告支援的 Command 卻失敗，第一步怎麼查？

先試著說明正常流程，並舉出一個未滿足執行條件的例子，再展開解答核對。

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    本題練習區分「支援命令」與「這次要求合法且可執行」。支援並不保證所有參數及狀態都成功。

  2. 02 它的影響範圍是什麼？

    先固定同一 controller、命令集、namespace 與測試時點，避免拿另一條路徑的能力來比。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    保存 Identify 的支援位元與 Effects.CSUPP，並記錄 CSI／UUID 選擇。

  4. 04 涉及哪些 Command 與重要欄位？

    假設支援 Format，卻回 Invalid Format；先讀原命令的 LBAF 與 namespace 可用格式。

  5. 05 正常流程及先後順序是什麼？

    先解 CQE，再逐項核對參數、namespace 狀態、Write Protection 與當時的管理操作限制。

  6. 06 成功時應回傳什麼結果？

    若只因選到不支援的 LBA Format 而失敗，這可與「支援 Format」完全一致。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    若所有前提成立卻回 Invalid Opcode，才進一步核對命令集及支援宣告是否矛盾；單次失敗不能直接定案。

  8. 08 DNR 與 More 應如何設定？

    收到 CQE 時才有 DNR 與 More 可判讀。本題沒有另行指定固定值，請依本冊的共用規則，搭配實際完成條件判斷。 本冊完整規則

  9. 09 是否產生 Asynchronous Event？

    正常完成不保證會回報非同步事件。若另有事件發生，還須確認支援能力、通知設定，以及是否有等待中的 AER。 本冊完整規則

  10. 10 是否更新 Error Information Log 或其他 Log？

    依完成結果與記錄條件核對 Error Information，不能直接用失敗命令的數量推算新增 entry 數。完整條件見本冊共用規則。 本冊完整規則

  11. 11 是否記錄於 Persistent Event Log？

    PEL 記錄符合條件的事件，不是每條命令的執行歷史。只有事件受支援且符合記錄條件時，才依規則要求新增紀錄。 本冊完整規則

  12. 12 Controller Reset 後是否保留或繼續？

    Controller Level Reset 會中止未完成的命令並重設 queue 狀態；Host 不應繼續等待舊命令的 CQE。 本冊完整規則

  13. 13 NVM Subsystem Reset 後是否保留或繼續？

    NVM Subsystem Reset 使受影響的 controllers 執行 Controller Level Reset，必須先恢復查詢通道，才能繼續檢查。 本冊完整規則

  14. 14 Power Cycle 後是否保留或繼續？

    Power Cycle 後，舊 queue 與未完成命令的追蹤關係不能沿用；Host 需重新初始化，再查實際資料與操作狀態。 本冊完整規則

  15. 15 是否影響其他 Controller 或 Namespace？

    單筆命令失敗不代表其他命令、namespace 或 controller 都失效。 本冊完整規則

  16. 16 Identify、Feature、Log 與 Command 行為是否一致？

    以同時點、單一變因的合法對照命令驗證，避免用另一組不同參數的成功取代原問題。

  17. 17 結果不符預期時，第一個要檢查什麼？

    先檢查實際 SCT／SC，而不是只看應用程式顯示的「失敗」。

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    將接受設定、目前值、保存值與實際效果拆開，才知道差異發生在哪一層。

  2. 02 它的影響範圍是什麼？

    Feature 可能屬於 controller、namespace 或其他實體，Get 必須指定相同目標。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    查 SEL=3 的能力與該 FID 的欄位定義，確認是否允許 controller 調整要求值。

  4. 04 涉及哪些 Command 與重要欄位？

    例如 KATO 可依 KAS 向上調整，讀回值大於要求不必然是錯誤；不能只做逐 bit 相等比較。

  5. 05 正常流程及先後順序是什麼？

    先保存 Set 的 SV／NSID／資料，再用 SEL=0 查 Current；需要測保存時才另查 Saved 並執行指定 reset。

  6. 06 成功時應回傳什麼結果？

    讀回合法調整後的值且實際行為符合該值，可構成成功驗證。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    若讀的是 Default 或另一 NSID，先修正查詢；若 selector 都相同且沒有允許調整或並行修改，才定位 controller 不一致。

  8. 08 DNR 與 More 應如何設定？

  9. 09 是否產生 Asynchronous Event？

    正常完成不保證會回報非同步事件。若另有事件發生，還須確認支援能力、通知設定，以及是否有等待中的 AER。 本冊完整規則

  10. 10 是否更新 Error Information Log 或其他 Log？

    依完成結果與記錄條件核對 Error Information，不能直接用失敗命令的數量推算新增 entry 數。完整條件見本冊共用規則。 本冊完整規則

  11. 11 是否記錄於 Persistent Event Log？

    Get 查詢不會產生 Set Feature Event。對 Set，先確認這個 FID 支援記錄，再判斷設定是否成功，以及值是否改變。 本冊完整規則

  12. 12 Controller Reset 後是否保留或繼續？

    先確認 Feature 作用範圍、保存能力及重設實際涵蓋的物件，再決定恢復方式。整個 subsystem 與只有部分範圍受重設時，規則不同。 本冊完整規則

  13. 13 NVM Subsystem Reset 後是否保留或繼續？

  14. 14 Power Cycle 後是否保留或繼續？

    可保存的 Feature 依 Saved 恢復；不可保存的 Feature，則依持續性及個別例外判斷。不能只用有沒有 Save 能力決定是否保留。 本冊完整規則

  15. 15 是否影響其他 Controller 或 Namespace？

    先查 Feature 的作用範圍，再判斷其他 controller 或 namespace 是否共用這項設定，以及是否會一同受影響。 本冊完整規則

  17. 17 結果不符預期時，第一個要檢查什麼？

    先確認 Get.SEL=0 以及 FID 的作用範圍。

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    通知指出曾發生符合條件的事件；後續 Log 可能是目前狀態，不一定保存事件發生時的完整快照。

  2. 02 它的影響範圍是什麼？

    讀取範圍與事件的 controller、namespace 或 Group 必須相符。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

  2. 02 它的影響範圍是什麼？

    Firmware 的 slot 與啟用可由同 Domain 的 controllers 共用，查詢必須在相關範圍內。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    查 FRMW、LID03h 的 CAFS／NAFS／FRS，以及 Identify.FR。

  4. 04 涉及哪些 Command 與重要欄位？

    保存 Commit Action、Slot 與 CQE；某些結果要求 CLR、Subsystem 或 Conventional Reset，不是任意 reset 都能替代。

  5. 05 正常流程及先後順序是什麼？

    先確認 Commit 有效，再執行指定啟用步驟，恢復後讀 FR 與目前 slot。

  6. 06 成功時應回傳什麼結果？

    若新映像版本字串與舊版相同，FR 沒變不證明沒啟用；還需 slot 與其他可靠版本證據。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    啟用失敗可回復可用映像；PEL 的 New Firmware Revision 是要求的新版本，不自動證明已成為目前版本。

  8. 08 DNR 與 More 應如何設定？

    收到 CQE 時才有 DNR 與 More 可判讀。本題沒有另行指定固定值，請依本冊的共用規則，搭配實際完成條件判斷。 本冊完整規則

  9. 09 是否產生 Asynchronous Event？

    開始不經 Reset 的韌體啟用時，受影響 controller 在 Firmware Activation Notices 啟用下回報 Firmware Activation Starting。 本冊完整規則

  10. 10 是否更新 Error Information Log 或其他 Log？

    用 Firmware Slot Information 區分目前 Active 與下次 Reset 預定 Active，再用 Identify.FR 確認真正執行的版本。 本冊完整規則

  11. 11 是否記錄於 Persistent Event Log？

    支援 PEL 時，Firmware Commit 完成記錄 Event02h，含舊版本、要求啟用的新版本、CA、slot 與 Status。 本冊完整規則

  12. 12 Controller Reset 後是否保留或繼續？

    Download 後、Commit 完成前若發生 Controller Level Reset，已下載的暫存映像部分必須丟棄。 本冊完整規則

  13. 13 NVM Subsystem Reset 後是否保留或繼續？

    Subsystem Reset 會影響其涵蓋的 controllers，並可滿足明確要求此 Reset 的待啟用映像。 本冊完整規則

  14. 14 Power Cycle 後是否保留或繼續？

    若在要求啟用的 Commit 尚未完成時進入 D3cold，恢復後可使用原映像或該次新映像，必須實際查證。 本冊完整規則

  15. 15 是否影響其他 Controller 或 Namespace？

    同一 domain 的 controllers 共用 firmware slots，該 domain 使用相同映像；單一 domain 時即涵蓋 subsystem。 本冊完整規則

  16. 16 Identify、Feature、Log 與 Command 行為是否一致？

    把 pending slot、active slot、實際 FR 與 Firmware Commit／Reset 事件分開核對。

  17. 17 結果不符預期時，第一個要檢查什麼？

    先檢查 Commit Action 與是否做了正確類型的啟用。

  1. 01 這個功能要解決什麼問題？

    Sanitize 的命令完成只表示操作已被接受並啟動；清除媒體可在背景繼續。

  2. 02 它的影響範圍是什麼？

    先分 Subsystem 與 Namespace Sanitize，並查正確 NSID 的結果。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    查 SANICAP、命令類型、Sanitize Status 及支援的完成事件。

  4. 04 涉及哪些 Command 與重要欄位？

    SPROG 是進度，SOS 是操作狀態；不能只看到 SPROG=FFFFh 就忽略 SOS 與 verification state。

  5. 05 正常流程及先後順序是什麼？

    保存啟動 CQE，持續查狀態；有完成 AER 時再查相同操作的最終結果。

  6. 06 成功時應回傳什麼結果？

    啟動成功後 SOS=進行中可以正常；真正完成時才應切換相應完成狀態並符合事件／Log 順序。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    若已確認同一操作完成，Log 卻持續顯示進行中，先排除新的 Sanitize、錯誤 scope 或舊快取回覆。

  8. 08 DNR 與 More 應如何設定？

    收到 CQE 時才有 DNR 與 More 可判讀。本題沒有另行指定固定值，請依本冊的共用規則，搭配實際完成條件判斷。 本冊完整規則

  9. 09 是否產生 Asynchronous Event？

    依狀態轉移回報 Sanitize Operation Completed、Completed With Unexpected Deallocation 或 Entered Media Verification State，AER 的 LID=81h。 本冊完整規則

  10. 10 是否更新 Error Information Log 或其他 Log？

    Sanitize Status 在啟動 CQE 張貼前更新，之後隨狀態轉移更新；它跨 Reset 與斷電保留。 本冊完整規則

  11. 11 是否記錄於 Persistent Event Log？

    支援對應 PEL 事件時，進入 Processing 記錄 Sanitize Start（09h）；進入 Idle、Restricted Failure 或 Unrestricted Failure 記錄 Completion（0Ah）。 本冊完整規則

  12. 12 Controller Reset 後是否保留或繼續？

    Sanitize 背景操作不因 Controller Level Reset 而中止。 本冊完整規則

  13. 13 NVM Subsystem Reset 後是否保留或繼續？

    NVM Subsystem Reset 也不提供中止 Sanitize 的方法。 本冊完整規則

  14. 14 Power Cycle 後是否保留或繼續？

    斷電期間無法進行媒體處理，但重新供電後 Sanitize 仍須依保存的狀態繼續，不可當成從未開始。 本冊完整規則

  15. 15 是否影響其他 Controller 或 Namespace？

    Subsystem Sanitize 限制整個 subsystem 的相關存取；Namespace Sanitize 則針對指定 namespace，但所有可存取它的 controller 都受限制。 本冊完整規則

  16. 16 Identify、Feature、Log 與 Command 行為是否一致？

    比對命令、Log、AER 及 PEL 的同一次操作，分清「命令完成」與「清除完成」。

  17. 17 結果不符預期時，第一個要檢查什麼？

    先檢查你稱為「完成」的證據到底是哪一種。

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    啟動命令成功不代表測試成功；測試結束要由 Current Operation 與結果紀錄一起確認。

  2. 02 它的影響範圍是什麼？

    確認查同一 controller／共享操作範圍，並使用正確的 Log 版本與完整長度。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    查 OACS、DSTO、EDSTT 與 LID06h；結果最新在前，有 20 筆結果位置。

  4. 04 涉及哪些 Command 與重要欄位？

    Current Operation、Completion Percentage、DSTR、DSTC 與 VDINFO 分別描述進行狀態、結果及欄位有效性。

  5. 05 正常流程及先後順序是什麼？

    保存開始前結果，啟動一次測試，等 Log 顯示結束，再與最新結果比對。

  6. 06 成功時應回傳什麼結果？

    規範要求結果更新與 Current Operation 回到 idle 的順序一致；讀到 idle 時應能查到本次應記錄的結果。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    Idle 時送 Abort 可成功但不新增結果；不能把這種情況誤判為漏記一次測試。

  8. 08 DNR 與 More 應如何設定？

    收到 CQE 時才有 DNR 與 More 可判讀。本題沒有另行指定固定值，請依本冊的共用規則，搭配實際完成條件判斷。 本冊完整規則

  9. 09 是否產生 Asynchronous Event？

    本規格沒有通用的 Device Self-test Completed AER。 本冊完整規則

  10. 10 是否更新 Error Information Log 或其他 Log？

    短程／延伸測試完成或被中止時，先建立最新 Self-test Result，再將目前操作設為 idle。 本冊完整規則

  11. 11 是否記錄於 Persistent Event Log？

    PEL 沒有通用的逐次 Self-test 結果事件；完整測試歷史以 LID06h 為主。 本冊完整規則

  12. 12 Controller Reset 後是否保留或繼續？

    影響執行 controller 的 Controller Level Reset 必須中止短程測試；延伸測試則必須跨 CLR 保留，並在重設完成後恢復。 本冊完整規則

  13. 13 NVM Subsystem Reset 後是否保留或繼續？

    Subsystem Reset 會對其範圍內的 controller 造成 CLR：短程測試被中止，延伸測試必須恢復。 本冊完整規則

  14. 14 Power Cycle 後是否保留或繼續？

    延伸測試必須在電源恢復後繼續；短程測試則不具有這項延續要求。 本冊完整規則

  15. 15 是否影響其他 Controller 或 Namespace？

    測試由收到命令的 controller 執行，NSID 決定包含哪些 namespace。 本冊完整規則

  16. 16 Identify、Feature、Log 與 Command 行為是否一致？

    Short 遇 CLR 會中止，Extended 具有不同持續性；用測試種類與中斷時間解釋結果代碼。

  17. 17 結果不符預期時，第一個要檢查什麼？

    先確認真的曾啟動測試，而非只成功送出 idle Abort。

Q308 Shutdown 與 Unsafe Shutdowns 計數不符直覺，如何判斷？

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    計數不能只按 Host 寫了 Normal 或 Abrupt 分類；需看主電源移除時的實際完成狀態。

  2. 02 它的影響範圍是什麼？

    Base2.4 使用 Unexpected Power Loss Count（UPL）；它是裝置記錄的失電事件，不是 Host 呼叫 Shutdown 的次數。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    保存 SMART 計數、CC.SHN、CSTS.SHST 及實際失電時點。

  4. 04 涉及哪些 Command 與重要欄位？

    一般條件為主電源移除時 SHST 尚未 10b；適用的帶外 Ignore Shutdown 情況另看媒體是否仍活躍。

  5. 05 正常流程及先後順序是什麼？

    先讀基準計數，發出 shutdown，觀察狀態，再於指定時點斷電，恢復後比較。

  6. 06 成功時應回傳什麼結果？

    Abrupt 也可能達到 Shutdown Complete 後才失電，因此不能要求每次 Abrupt 都增加 UPL。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    Normal 要求若尚未完成就掉電，仍可能計數增加；沒有失電的 controller reset 也不能自動算一次。

  8. 08 DNR 與 More 應如何設定？

    本次 MMIO 存取沒有 NVMe CQE，因此 DNR／More 不適用。 本冊完整規則

  9. 09 是否產生 Asynchronous Event？

    Register 存取本身不產生成功事件。若另外發生硬體錯誤等事件，則依該事件自己的條件判斷。 本冊完整規則

  10. 10 是否更新 Error Information Log 或其他 Log？

    不要求每次 Register 讀寫都新增錯誤紀錄。先保留 Register 值及時間，再補充 controller 當時允許讀取的診斷資料。 本冊完整規則

  11. 11 是否記錄於 Persistent Event Log？

    一般 Register 存取不是 PEL 事件。若操作同時引發 Reset 或硬體錯誤，再依支援能力與對應事件條件判斷。 本冊完整規則

  12. 12 Controller Reset 後是否保留或繼續？

    清除 CC.EN 後，I/O queue 失效，Admin Queue 指標重設。即使基底位址保留，舊 completion 也不能繼續當成有效結果。 本冊完整規則

  13. 13 NVM Subsystem Reset 後是否保留或繼續？

    受影響 controller 的 queue 必須重建。這次重設的來源不同，不能直接套用清除 CC.EN 時的 Register 保留例外。 本冊完整規則

  14. 14 Power Cycle 後是否保留或繼續？

    重新初始化 queue，並重建 Host 的命令追蹤資料。記憶體中殘留的舊內容，不是新 queue 的有效命令或完成結果。 本冊完整規則

  15. 15 是否影響其他 Controller 或 Namespace？

    Controller Reset 以該 controller 為範圍；Subsystem Reset 在單 domain 涵蓋全部，multi-domain 則依實作涵蓋一個或全部 domains。 本冊完整規則

  16. 16 Identify、Feature、Log 與 Command 行為是否一致？

    比對真正失電前最後狀態，避免使用重啟後 SHST 的值倒推。

  17. 17 結果不符預期時，第一個要檢查什麼？

    先確認主電源是否真的移除，以及當時 SHST 是否已 10b。

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    狀態改變與應通知的事件條件不同；警告消失不一定與警告出現有同樣通知要求。

  2. 02 它的影響範圍是什麼？

    SMART 整體警告與 Group-specific 警告要用各自 scope 與設定。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    確認 AEC 對應位元、支援能力、是否有 outstanding AER，以及舊同類事件是否尚未確認。

  4. 04 涉及哪些 Command 與重要欄位？

    保存變化前後 CW、溫度／spare 等原始值及門檻；不要只保存應用程式的警告文字。

  5. 05 正常流程及先後順序是什麼？

    先確認達到事件條件，再查 AER 是否被其他事件占用或通知被合併，最後檢查相關 Log 的 RAE 讀取。

  6. 06 成功時應回傳什麼結果？

    已啟用且符合條件的事件，應依該類型排隊與回報規則被處理；不一定每次取樣變動都另完成一筆 AER。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    如果沒有等待中的 AER，不能要求當下就有 CQE；同樣地，不應把未處理 CQE 誤判成 controller 沒通知。

  8. 08 DNR 與 More 應如何設定？

    收到 CQE 時才有 DNR 與 More 可判讀。本題沒有另行指定固定值，請依本冊的共用規則，搭配實際完成條件判斷。 本冊完整規則

  9. 09 是否產生 Asynchronous Event？

    AER 的正常用途就是讓 controller 以完成這筆 Request 的方式回報事件。 本冊完整規則

  10. 10 是否更新 Error Information Log 或其他 Log？

    依 AET、AEI、LID 讀取對應 Log；Error 類型指向 Error Information，SMART 類型指向 SMART / Health。 本冊完整規則

  11. 11 是否記錄於 Persistent Event Log？

    PEL 是否記錄由原始事件決定，不由 AER Request 是否完成決定。 本冊完整規則

  12. 12 Controller Reset 後是否保留或繼續？

    Controller Reset 會中止尚未完成的 AER，而且這些被重設中止的 Request 不得回傳 CQE。 本冊完整規則

  13. 13 NVM Subsystem Reset 後是否保留或繼續？

    受 NVM Subsystem Reset 影響的 controller 重新建立 Admin Queue 後，須重新掛入 AER。 本冊完整規則

  14. 14 Power Cycle 後是否保留或繼續？

    Power Cycle 後，舊 AER 不是有效 Request。 本冊完整規則

  15. 15 是否影響其他 Controller 或 Namespace？

    Request 提交到特定 controller，完成也回到它的 Admin CQ；事件影響範圍則可能是 namespace、domain 或 subsystem。 本冊完整規則

  16. 16 Identify、Feature、Log 與 Command 行為是否一致？

    將 CW 時間線、AEC、AER 清單及 RAE 操作放在一起，找出真正缺少的一步。

  17. 17 結果不符預期時，第一個要檢查什麼？

    先確認事件發生時的 AEC，而不是事後才讀到的設定。

先試著說明正常流程，並舉出一個未滿足執行條件的例子，再展開解答核對。

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    事件在 Log 的排列、Header timestamp 與操作實際先後是三種不同資訊。

  2. 02 它的影響範圍是什麼？

    PEL 為 subsystem 範圍，多個 controller 的事件可能交錯，也可能受供應商允許的排序影響。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    查目前報告 context、Generation Number 與 Timestamp Origin／SYNC。

  4. 04 涉及哪些 Command 與重要欄位？

    Timestamp 可因 Host Set、reset 或 saved-value 恢復而跳變；不能把它一律當嚴格遞增序號。

  5. 05 正常流程及先後順序是什麼？

    先在同一 context 讀完整事件，依 EHL／EL 正確走訪，再用 Timestamp Change 與 Reset 事件解釋時間變化。

  6. 06 成功時應回傳什麼結果？

    規範建議新到舊排列，但允許供應商定義的事件順序；測試不能把 should 改成絕對排序要求。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    若分段讀取混用不同 context，或把 EL 不含 vendor bytes 來算，可能產生假的亂序或壞事件。

  8. 08 DNR 與 More 應如何設定？

    收到 CQE 時才有 DNR 與 More 可判讀。本題沒有另行指定固定值，請依本冊的共用規則，搭配實際完成條件判斷。 本冊完整規則

  9. 09 是否產生 Asynchronous Event？

    Base 2.4 沒有「每新增 PEL entry 就回報 PEL Changed AER」的一般事件。 本冊完整規則

  10. 10 是否更新 Error Information Log 或其他 Log？

    建立 context 固定這次要回報的事件集合；期間新事件仍要記錄，但不能混入既有 context。 本冊完整規則

  11. 11 是否記錄於 Persistent Event Log？

    PEL 的查詢不是另一筆 PEL 讀取事件。 本冊完整規則

  12. 12 Controller Reset 後是否保留或繼續？

    Controller Level Reset 後，PEL 事件內容須保留，但查詢 context 不保證仍有效。 本冊完整規則

  13. 13 NVM Subsystem Reset 後是否保留或繼續？

    Subsystem Reset 不清除持久事件；Reset 完成時還可能依支援規則新增 Power-on or Reset 事件。 本冊完整規則

  14. 14 Power Cycle 後是否保留或繼續？

    事件內容須跨 Power Cycle 保留，規範也建議設計盡量降低失電時的事件遺失。 本冊完整規則

  15. 15 是否影響其他 Controller 或 Namespace？

    PEL 是 subsystem 全域的事件歷史。 本冊完整規則

  16. 16 Identify、Feature、Log 與 Command 行為是否一致？

    用 Host 單調時間保存提交與完成，作為比對線索，但不要求它與未同步的裝置時計完全相等。

  17. 17 結果不符預期時，第一個要檢查什麼？

    先確認是否讀了同一份 context 與正確事件邊界。

    先留存最小原始證據，再依裝置可用狀態做 reset 與恢復，之後補查持續性紀錄。

    本次 MMIO 存取沒有 NVMe CQE，因此 DNR／More 不適用。 本冊完整規則

  9. 09 是否產生 Asynchronous Event？

    Register 存取本身不產生成功事件。若另外發生硬體錯誤等事件，則依該事件自己的條件判斷。 本冊完整規則

  10. 10 是否更新 Error Information Log 或其他 Log？

  13. 13 NVM Subsystem Reset 後是否保留或繼續？

    受影響 controller 的 queue 必須重建。這次重設的來源不同，不能直接套用清除 CC.EN 時的 Register 保留例外。 本冊完整規則

  15. 15 是否影響其他 Controller 或 Namespace？

    Controller Reset 以該 controller 為範圍；Subsystem Reset 在單 domain 涵蓋全部，multi-domain 則依實作涵蓋一個或全部 domains。 本冊完整規則

  16. 16 Identify、Feature、Log 與 Command 行為是否一致？

    分開 controller 回報、Host timeout 與通訊失效的證據，避免將其中一項代替全部原因。

  17. 17 結果不符預期時，第一個要檢查什麼？

    先確認 controller 角色與目前 Register 讀取是否可信。

Q312 Abort 後看見兩次 Completion，如何判斷是否重複？

先試著說明正常流程，並舉出一個未滿足執行條件的例子，再展開解答核對。

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    Abort 命令與目標命令各自有完成結果，所以總共兩筆 CQE 可以正常；真正要檢查的是目標命令是否被完成兩次。

  2. 02 它的影響範圍是什麼？

    使用 controller、SQID、CID 與 queue 使用期間識別每筆命令。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    保存 Abort 指定的 SQID／CID、Abort 自己的 CID 及 CQE.DW0.IANP。

  4. 04 涉及哪些 Command 與重要欄位？

    IANP=0 表示 Abort 已達成規定的立即中止效果，但目標命令仍須依其完成規則結束，不能因此省略目標命令的 CQE。IANP=1 則表示沒有取得這項立即效果，目標命令之後仍可能正常完成。

  5. 05 正常流程及先後順序是什麼？

    先分出 Admin Abort CQE 與原 I/O CQE，再檢查 Host 是否因 Phase 或 Head 錯誤讀了同一筆兩次。

  6. 06 成功時應回傳什麼結果？

    正常情況可以是一筆 Abort CQE 加上一筆目標命令 CQE，Host 應將兩者分別對回各自的命令。目標命令可能已經修改部分資料，因此看到 Abort 完成後，不能直接假設原命令完全沒執行而原樣重送。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    若已排除 Host 重複讀取同一 CQE，也確認 CID 沒有重用，controller 卻仍對同一次提交的目標命令產生兩筆有效 CQE，才是同一命令被完成兩次的問題。

  8. 08 DNR 與 More 應如何設定？

    收到 CQE 時才有 DNR 與 More 可判讀。本題沒有另行指定固定值，請依本冊的共用規則，搭配實際完成條件判斷。 本冊完整規則

  9. 09 是否產生 Asynchronous Event？

    正常完成不保證會回報非同步事件。若另有事件發生，還須確認支援能力、通知設定，以及是否有等待中的 AER。 本冊完整規則

  10. 10 是否更新 Error Information Log 或其他 Log？

    依完成結果與記錄條件核對 Error Information，不能直接用失敗命令的數量推算新增 entry 數。完整條件見本冊共用規則。 本冊完整規則

  11. 11 是否記錄於 Persistent Event Log？

    PEL 記錄符合條件的事件，不是每條命令的執行歷史。只有事件受支援且符合記錄條件時，才依規則要求新增紀錄。 本冊完整規則

  12. 12 Controller Reset 後是否保留或繼續？

    清除 CC.EN 後，I/O queue 失效，Admin Queue 指標重設。即使基底位址保留，舊 completion 也不能繼續當成有效結果。 本冊完整規則

  13. 13 NVM Subsystem Reset 後是否保留或繼續？

    受影響 controller 的 queue 必須重建。這次重設的來源不同，不能直接套用清除 CC.EN 時的 Register 保留例外。 本冊完整規則

  14. 14 Power Cycle 後是否保留或繼續？

    重新初始化 queue，並重建 Host 的命令追蹤資料。記憶體中殘留的舊內容，不是新 queue 的有效命令或完成結果。 本冊完整規則

  15. 15 是否影響其他 Controller 或 Namespace？

    Queue 隸屬於各自的 controller。多條 SQ 共用同一 CQ 時，才會共同受到這條 CQ 的可用空間及使用期間影響。 本冊完整規則

  16. 16 Identify、Feature、Log 與 Command 行為是否一致？

    CID 重用與 CQ 繞回必須排除，不能只憑兩張截圖顯示相同 CID 就判重複。

  17. 17 結果不符預期時，第一個要檢查什麼？

    先檢查兩筆 CQE 的 SQID／CID，哪一筆其實屬於 Abort。

  2. 02 它的影響範圍是什麼？

    Reset 結束受影響 queue 的舊使用期間，新 queue 即使沿用位址與 QID 也屬於新的期間。

共用規則：各題連到的完整解釋

這些規則在本冊只完整說明一次。返回剛才的題目可用瀏覽器「上一頁」；特定命令或 Feature 的明文例外優先。

本主題的共用條件 · 是否產生 Asynchronous Event？

AER 的正常用途就是讓 controller 以完成這筆 Request 的方式回報事件。必須分清楚事件本身、通知是否啟用、是否被遮蔽，以及是否還有 Request 可用；送出 AER 不會替 Host 啟用所有選配事件。

本主題的共用條件 · 是否更新 Error Information Log 或其他 Log？

依 AET、AEI、LID 讀取對應 Log；Error 類型指向 Error Information，SMART 類型指向 SMART / Health。AER 成功本身不要求額外新增 Error Information，且即時狀態可能在事件發生後已改變，需保存通知與讀取的時間。

本主題的共用條件 · 是否記錄於 Persistent Event Log？

PEL 是否記錄由原始事件決定，不由 AER Request 是否完成決定。先確認該 Persistent Event 受支援且符合記錄條件；不能為每筆 AER 或每次讀取 Log 強制增加一筆 PEL 紀錄。

本主題的共用條件 · Controller Reset 後是否保留或繼續？

Controller Reset 會中止尚未完成的 AER，而且這些被重設中止的 Request 不得回傳 CQE。Controller Level Reset 也會清除尚未通知的 pending event；Host 恢復後重新提交 AER，並依各 Log 的保留規則查詢狀態。

本主題的共用條件 · NVM Subsystem Reset 後是否保留或繼續？

受 NVM Subsystem Reset 影響的 controller 重新建立 Admin Queue 後，須重新掛入 AER。不要等待舊 Request 的完成；其他 controller 是否同時受影響，要依實際重設涵蓋範圍判斷。

本主題的共用條件 · Power Cycle 後是否保留或繼續？

Power Cycle 後，舊 AER 不是有效 Request。Host 重新初始化後，確認 Asynchronous Event Configuration 恢復成哪個值，再掛入新 Request；保存下來的 Log 歷史不代表舊通知也會全部重新播放。

本主題的共用條件 · 是否影響其他 Controller 或 Namespace？

Request 提交到特定 controller，完成也回到它的 Admin CQ；事件影響範圍則可能是 namespace、domain 或 subsystem。多個 controller 可因同一共享狀態各自回報，不能只靠通知數量推算獨立故障數。

命令完成、事件與紀錄 · DNR 與 More 應如何設定？

只有收到 CQE，才有 DNR 與 More 可供判讀。DNR=1 表示相同命令即使重送到此 NVM subsystem 的任一 controller，仍預期會失敗；DNR=0 則只表示可能成功。除非個別錯誤條件另有明定，不能只看 Status 名稱就要求 DNR=1。More=1 表示 Error Information Log 有這筆命令的補充資訊。SCT=SC=0 時，DNR 應為 0。

命令完成、事件與紀錄 · 是否產生 Asynchronous Event？

命令完成與非同步通知是不同機制，操作成功本身不保證會產生事件。若操作引發規範定義的事件，還要確認事件受支援、相關通知設定允許回報、事件未被遮蔽，而且 Host 已提交等待中的 Asynchronous Event Request。

命令完成、事件與紀錄 · 是否更新 Error Information Log 或其他 Log？

成功 CQE 不會單憑成功這件事，就要求新增 Error Information entry。若錯誤 CQE 的 More=1，則讀取 LID01h，並以 SQID、CID 及 Error Count 關聯紀錄。其他非成功 CQE 是否需要新增 entry，仍須依記錄規則判斷，不能直接以失敗次數推算。至於操作造成的狀態變化，則用本題列出的查詢介面重新確認。

命令完成、事件與紀錄 · 是否記錄於 Persistent Event Log？

Persistent Event Log 是選配的事件歷史，不是每條命令的執行清單。先確認 LPA 宣告的支援能力及 Supported Events Bitmap，再判斷這次操作是否符合某個事件的記錄條件。不能只因命令成功或失敗，就要求新增一筆 PEL 紀錄。

本主題的共用條件 · Controller Reset 後是否保留或繼續？

Controller Level Reset 會中止未完成的命令並重設 queue 狀態；Host 不應繼續等待舊命令的 CQE。這不代表命令先前造成的資料修改已回復，也不表示背景管理操作一定停止。先保存可取得的錯誤證據，再於恢復後依該操作的狀態或 Log 確認結果。Error Information entries 建議清除，但 Error Count 保留，因此不能用重設後沒有 entry 來否定重設前的錯誤。

本主題的共用條件 · NVM Subsystem Reset 後是否保留或繼續？

NVM Subsystem Reset 使受影響的 controllers 執行 Controller Level Reset，必須先恢復查詢通道，才能繼續檢查。它不是恢復出廠設定，也不能保證故障原因已排除。分別核對原操作的結果、目前設定及仍保留的 Log，並確認其他共用資源的 controllers 是否同時受到重設。

本主題的共用條件 · Power Cycle 後是否保留或繼續？

Power Cycle 後，舊 queue 與未完成命令的追蹤關係不能沿用；Host 需重新初始化，再查實際資料與操作狀態。SMART 累計資訊及 PEL 的持續性規則，與錯誤命令是否成功是不同問題。Error Information entries 建議清除而 Error Count 保留；因此要把斷電前保存的 SQE、CQE 及 Log，與重新上電後的觀察一起比對。

本主題的共用條件 · 是否影響其他 Controller 或 Namespace？

單筆命令失敗不代表其他命令、namespace 或 controller 都失效。先區分參數錯誤、queue 故障與 controller 故障；只有共享資源或狀態也受影響時，才擴大處理範圍。

Feature 的重設與影響範圍 · Controller Reset 後是否保留或繼續？

先確認 Feature 的作用範圍及保存能力。如果重設影響整個 NVM subsystem，可保存 Feature 的 Current 會恢復為 Saved；沒有 Saved 時，則使用 Default。不可保存且不具持續性的 Feature 回到 Default。若多個 controller 中只有部分受到重設，共用設定則依 Figure 127 判斷是否保留。個別 Feature 的明確例外，優先於這些一般規則。

Feature 的重設與影響範圍 · NVM Subsystem Reset 後是否保留或繼續？

判斷恢復方式時，不能只看 Reset 名稱，還要確認它實際涵蓋哪些物件。重設影響整個 NVM subsystem 時，使用 Figure 126；multi-domain 配置中只有部分範圍受影響時，使用 Figure 127。若 Feature 雖不可保存，卻明定具有持續性，就仍須保留，不能誤解為重設後一律清零。

Feature 的重設與影響範圍 · Power Cycle 後是否保留或繼續？

可保存的 Feature 若以 SV=1 成功更新 Saved，Power Cycle 後便依 Saved 恢復；SV=0 則不會改變 Saved。對不可保存的 Feature，另查 Figure 466 的持續性規則及個別例外。恢復後仍要讀取 Current 並驗證行為，不能只因 Saved 存在，就假設 controller 已正在使用它。

Feature 的重設與影響範圍 · 是否影響其他 Controller 或 Namespace？

其他 controller 或 namespace 是否受影響，由 Feature 的作用範圍決定。controller scope 通常只控制目標 controller；namespace、NVM Set 或 NVM subsystem 的設定，則可能由多個 controller 共同觀察。多個 Host 修改共用設定時需要協調，也不能將 NSID=FFFFFFFFh 當成所有 Feature 都適用的廣播方式。

Set Feature 的事件記錄 · 是否記錄於 Persistent Event Log？

若支援 PEL 的 Set Feature Event，還要依 Figure 252 確認這個 FID 是否允許且支援記錄。符合前提時，Set 成功且設定值改變，必須記錄；成功但只是再次設定相同值，則允許記錄。這項規則不能套用到所有 FID：Timestamp 明確禁止記成 Set Feature Event，應改依 Timestamp Change Event 的規則判斷。

本主題的共用條件 · 是否產生 Asynchronous Event？

開始不經 Reset 的韌體啟用時，受影響 controller 在 Firmware Activation Notices 啟用下回報 Firmware Activation Starting。載入失敗另有 Firmware Image Load Error；Download 每一段成功不會各自觸發啟用通知。

本主題的共用條件 · 是否更新 Error Information Log 或其他 Log？

用 Firmware Slot Information 區分目前 Active 與下次 Reset 預定 Active，再用 Identify.FR 確認真正執行的版本。失敗時另依 CQE.More 查 Error Information；slot 中已有新映像，不表示它已執行。

本主題的共用條件 · 是否記錄於 Persistent Event Log？

支援 PEL 時，Firmware Commit 完成記錄 Event02h，含舊版本、要求啟用的新版本、CA、slot 與 Status。NFR 是要求的新版本，不是啟用成功證明；Reset Event 的 FA／FREV 可補充實際啟用結果。

本主題的共用條件 · Controller Reset 後是否保留或繼續？

Download 後、Commit 完成前若發生 Controller Level Reset，已下載的暫存映像部分必須丟棄。已完成 Commit 的 slot 與待啟用安排則依 CA 及回傳的必要 Reset 類型判斷；不能只因任何 Reset 就假設新映像會啟用。

本主題的共用條件 · NVM Subsystem Reset 後是否保留或繼續？

Subsystem Reset 會影響其涵蓋的 controllers，並可滿足明確要求此 Reset 的待啟用映像。恢復後重新查 FR、slot 及能力；未完成 Commit 的暫存下載不能沿用。

本主題的共用條件 · Power Cycle 後是否保留或繼續？

若在要求啟用的 Commit 尚未完成時進入 D3cold，恢復後可使用原映像或該次新映像，必須實際查證。已完成下載但尚未完成 Commit 的暫存部分，不能當成跨斷電保存的有效 slot。

本主題的共用條件 · 是否影響其他 Controller 或 Namespace？

同一 domain 的 controllers 共用 firmware slots，該 domain 使用相同映像；單一 domain 時即涵蓋 subsystem。Host 應協調所有受影響存取者，並避免多個更新流程互相重疊。

本主題的共用條件 · 是否產生 Asynchronous Event？

Lockdown 成功不定義一個一般性的設定完成 AER。Host 應用 Lockdown Log 與目標命令結果確認；其他獨立事件才依其通知規則處理。

本主題的共用條件 · 是否更新 Error Information Log 或其他 Log？

Lockdown Log 的目前禁止清單應反映成功操作，並要用相同的介面、scope、controller 與 UUID 選擇比較。被禁止命令的錯誤 CQE 則另依 Error Information 記錄規則關聯。

本主題的共用條件 · 是否記錄於 Persistent Event Log？

Lockdown 命令本身不是專用的標準 PEL 事件。若另外修改 Lockdown Persistence Personality，須按其支援的 personality 事件規則判斷，不能把兩個操作混成同一筆紀錄。

本主題的共用條件 · Controller Reset 後是否保留或繼續？

成功建立的禁止狀態不因一般 CLR 解除；要允許命令，需合法的後續 Lockdown 操作，或符合指定的 power-cycle 解除條件。

本主題的共用條件 · NVM Subsystem Reset 後是否保留或繼續？

Subsystem Reset 不等於 Power Cycle，不能用它自動解除禁止。仍要保留相同 scope 的狀態，並考慮 personality 明定的例外。

本主題的共用條件 · Power Cycle 後是否保留或繼續？

CSEL=0 的 subsystem 禁止，LDPE=1 時跨 Power Cycle 保留，直到後續操作解除；LDPE=0 則在 Power Cycle 解除。CSEL=1／2 的禁止到 Power Cycle 為止，不因 LDPE=1 就取得跨斷電持續性。

本主題的共用條件 · 是否影響其他 Controller 或 Namespace？

CSEL 選全部、指定 controller 或指定 primary 的 secondary 群組；IFC 選收命令介面。禁止一個介面不表示其他介面也被禁止；FID scope 只限制對該 FID 的 Set Features，不能誤當成 Get 也自動禁止。

本主題的共用條件 · 是否產生 Asynchronous Event？

Create／Delete 影響 Allocated List，Attach／Detach 影響指定 controller 的 Active List。依各 controller 的事件支援與 AEC 回報變更；Admin SQ 收到 Delete 的 controller 不回報該次刪除通知，其他受影響且啟用通知的 controller 仍須依規則回報。

本主題的共用條件 · 是否更新 Error Information Log 或其他 Log？

使用 Identify 的 Allocated、Active 與 Controller List 確認目前配置；Changed Attached Namespace List04h 與 Changed Allocated Namespace List1Ch 指出曾變更的 NSID，不能代替完整現況。失敗則依 More 與 Error Information 補充欄位處理。

本主題的共用條件 · 是否記錄於 Persistent Event Log？

支援 PEL 時，Namespace Management 對應的 Change Namespace Event06h 記錄建立／刪除等規定事件。Attach／Detach 不應直接當成 Create／Delete；Write Protection 則依該 Feature 是否支援 Set Feature Event 記錄。

本主題的共用條件 · Controller Reset 後是否保留或繼續？

已完成的 namespace 配置與 Attach／Detach 跨 Reset 保留；重設的是命令通道，不是自動刪除 namespace。若 Reset 前未收到完成，恢復後須查清單確認結果，不能假設整筆操作必定回復。

本主題的共用條件 · NVM Subsystem Reset 後是否保留或繼續？

Subsystem Reset 不等於 Restore Default Namespace Configuration。恢復後重新探索原 namespace 與附加關係，再建立 I/O queues；多 domain 的實際 Reset 範圍另行確認。

本主題的共用條件 · Power Cycle 後是否保留或繼續？

Power Cycle 後，已完成的 namespace 配置與附加關係仍需保留。Write Protect 與 Permanent Write Protect 保留；Write Protect Until Power Cycle 則在實際 power cycle 轉回未保護，不能把這個例外套到全部配置。

本主題的共用條件 · 是否影響其他 Controller 或 Namespace？

建立／刪除影響 subsystem 的 namespace inventory；附加清單指定哪些 controllers 改變存取關係。共享 namespace 的保護狀態必須由所有附加的 controllers 執行，不因換路徑而解除。

本主題的共用條件 · 是否產生 Asynchronous Event？

Base 2.4 沒有「每新增 PEL entry 就回報 PEL Changed AER」的一般事件。造成紀錄的原始狀況可能有自己的通知，例如 SMART 警告或 Sanitize；必須依原始事件的條件判斷。

本主題的共用條件 · 是否更新 Error Information Log 或其他 Log？

建立 context 固定這次要回報的事件集合；期間新事件仍要記錄，但不能混入既有 context。讀取或釋放 context 不代表清空 PEL，錯誤的 Get Log 則另依 Error Information 規則處理。

本主題的共用條件 · 是否記錄於 Persistent Event Log？

PEL 的查詢不是另一筆 PEL 讀取事件。只有受支援的原始事件才依各自觸發條件記錄；高頻相同事件可依規範允許的廠商門檻抑制，不能要求無限逐筆重複。

本主題的共用條件 · Controller Reset 後是否保留或繼續？

Controller Level Reset 後，PEL 事件內容須保留，但查詢 context 不保證仍有效。恢復查詢通道後重新建立 context，不能把中斷前的半份資料接上新的 context。

本主題的共用條件 · NVM Subsystem Reset 後是否保留或繼續？

Subsystem Reset 不清除持久事件；Reset 完成時還可能依支援規則新增 Power-on or Reset 事件。報告 context 的保留是另一回事，應重新建立一致的讀取範圍。

本主題的共用條件 · Power Cycle 後是否保留或繼續？

事件內容須跨 Power Cycle 保留，規範也建議設計盡量降低失電時的事件遺失。容量淘汰、高頻抑制，以及 Sanitize 為避免洩漏使用者資料而移除或修改事件，是不同的例外，不能把它們誤認為一般斷電清空。

本主題的共用條件 · 是否影響其他 Controller 或 Namespace？

PEL 是 subsystem 全域的事件歷史。事件 Header 的 CNTLID 指出建立紀錄的 controller；影響多個 controller 的事件建議只記一次，不要求每條路徑都有一份副本。共享查詢 context 時須避免一端釋放另一端仍在讀的 context。

本主題的共用條件 · 是否產生 Asynchronous Event？

切換 Power State 或開始降速，不會自動產生同名的 AER。若溫度另外達到已設定的警告條件，才依 SMART／Health 事件與通知設定回報；HCTM 的 TMT1、TMT2 不是 Temperature Threshold Feature 的同一組門檻。

本主題的共用條件 · 是否更新 Error Information Log 或其他 Log？

SMART 的 Thermal Management transition count 與累計時間可協助確認 HCTM 行為；一般 Power State 切換沒有逐次記錄的標準 Log。成功設定不要求 Error Information entry，設定失敗時才依 CQE 與記錄條件查證。

本主題的共用條件 · 是否記錄於 Persistent Event Log？

若支援 PEL 的 Set Feature Event，先確認該 FID 可記錄且已宣告支援。符合條件的設定變更依規則記錄；自動進入 Power State 或每次降速，不等於又執行一次 Set Features。

Queue 的重設與影響範圍 · Controller Reset 後是否保留或繼續？

Host 清除 CC.EN 會觸發 Controller Level Reset：I/O SQ 與 CQ 被刪除，Admin Queue 的指標也會重設。這種重設雖然保留 AQA、ASQ、ACQ，卻不表示舊 CQE 仍然有效。Host 必須重新初始化 Admin CQ 的 Phase，啟用 controller 後，再配置並建立 I/O queue。

Queue 的重設與影響範圍 · NVM Subsystem Reset 後是否保留或繼續？

NVM Subsystem Reset 會讓受影響的 controller 執行 Controller Level Reset，Host 不能沿用舊 queue。恢復時，先重新確認傳輸及 Register 狀態，再建立 Admin 與 I/O 的操作環境。這種重設來源不同，不能直接套用清除 CC.EN 時對 AQA 等 Register 的保留例外。

Queue 的重設與影響範圍 · Power Cycle 後是否保留或繼續？

Power Cycle 後，Host 重新執行初始化及 queue 建立流程。即使 Host 記憶體中還留有舊 SQE 或 CQE 的內容，也不能把它們當成新 queue 的有效命令或完成結果。Host 必須重建指標、期待的 Phase，以及未完成命令的追蹤資料。

Queue 的重設與影響範圍 · 是否影響其他 Controller 或 Namespace？

Queue 隸屬於建立它的 controller；兩個 controller 使用相同 QID，不表示它們共用同一條 queue。相反地，同一 controller 中共用 CQ 的 SQ，確實會受到該 CQ 的空間及刪除順序影響。另外，queue 重設不等於刪除 namespace，也不會撤銷已完成的資料寫入。

Register 存取 · DNR 與 More 應如何設定？

這次 Register 存取沒有 NVMe CQE，因此 DNR 與 More 不適用。如果之後的 Admin 或 I/O 命令失敗，則解讀那筆命令實際回傳的 CQE，而不是替先前的 Register 寫入指定 Status 位元。

Register 存取 · 是否產生 Asynchronous Event？

Register 存取本身不定義一筆成功通知。若另外發生 Internal Error 等已定義事件，則依該事件的規則處理。controller 尚不能處理 Admin Queue 時，Host 仍須直接檢查初始化狀態，不能改以等待事件判斷是否已完成初始化。

Register 存取 · 是否更新 Error Information Log 或其他 Log？

規範不要求每次 Register 讀寫都建立一筆 Error Information entry。遇到初始化問題時，先保存 CAP、CC、CSTS、CRTO 及各次觀察的時間。若之後 controller 允許讀取 Log，再用錯誤與事件紀錄補足資訊。

Register 存取 · 是否記錄於 Persistent Event Log？

一般 Register 存取不是獨立的 Persistent Event。若另外發生重設、電源變化或硬體錯誤，則在支援 PEL 且符合對應事件條件時，依規則記錄。因此，不能將每次 CC 寫入都當成一次 Power-on or Reset 事件。

本主題的共用條件 · 是否影響其他 Controller 或 Namespace？

Controller Reset 以該 controller 為範圍；Subsystem Reset 在單 domain 涵蓋全部，multi-domain 則依實作涵蓋一個或全部 domains。Shutdown 的可斷電範圍還須看 CAP.CPS；共享 namespace 的其他路徑不應被當成獨立資料副本。

本主題的共用條件 · 是否產生 Asynchronous Event？

依狀態轉移回報 Sanitize Operation Completed、Completed With Unexpected Deallocation 或 Entered Media Verification State，AER 的 LID=81h。由 Admin SQ 啟動時，僅啟動該操作的 controller 回報這次通知；仍須查看 Log 分辨成功、失敗或驗證階段。

本主題的共用條件 · 是否更新 Error Information Log 或其他 Log？

Sanitize Status 在啟動 CQE 張貼前更新，之後隨狀態轉移更新；它跨 Reset 與斷電保留。用相同目標的 SOS、SANS、SPROG、SCDW10 及 GDE／NDE 比對，不以背景失敗要求原啟動命令再回第二筆 CQE。

本主題的共用條件 · 是否記錄於 Persistent Event Log？

支援對應 PEL 事件時，進入 Processing 記錄 Sanitize Start（09h）；進入 Idle、Restricted Failure 或 Unrestricted Failure 記錄 Completion（0Ah）。Completion 也包含失敗，事件 NSID 可用來分辨 subsystem 與 namespace 目標。

本主題的共用條件 · Controller Reset 後是否保留或繼續？

Sanitize 背景操作不因 Controller Level Reset 而中止。Host 重新建立查詢通道後讀同一目標的 LID81h。另需分辨 Reset 來源：傳輸層 Reset 等條件可能取消 Media Verification，使 MVCNCLD 設為 1，而不是取消整個清除操作。

本主題的共用條件 · NVM Subsystem Reset 後是否保留或繼續？

NVM Subsystem Reset 也不提供中止 Sanitize 的方法。操作的狀態與 Log 需要保留；如果原本要求 Media Verification，還要檢查 MVCNCLD 及後續 deallocation 階段。

本主題的共用條件 · Power Cycle 後是否保留或繼續？

斷電期間無法進行媒體處理，但重新供電後 Sanitize 仍須依保存的狀態繼續，不可當成從未開始。恢復後查看 SOS／SANS 與進度，不能只見 SPROG=FFFFh 就宣告成功。

本主題的共用條件 · 是否影響其他 Controller 或 Namespace？

Subsystem Sanitize 限制整個 subsystem 的相關存取；Namespace Sanitize 則針對指定 namespace，但所有可存取它的 controller 都受限制。共享韌體更新等操作另有全域限制，不能只因另一 namespace 的資料不被清除，就推論完全沒有影響。

本主題的共用條件 · 是否產生 Asynchronous Event？

本規格沒有通用的 Device Self-test Completed AER。正常完成應讀 LID06h 確認；測試發現診斷失敗時，另依 Diagnostic Failure 錯誤事件及其回報條件處理。

本主題的共用條件 · 是否更新 Error Information Log 或其他 Log？

短程／延伸測試完成或被中止時，先建立最新 Self-test Result，再將目前操作設為 idle。診斷欄位要先檢查 valid bits；不是每個失敗結果都具有有效 NSID、LBA、SCT 與 SC。

本主題的共用條件 · 是否記錄於 Persistent Event Log？

PEL 沒有通用的逐次 Self-test 結果事件；完整測試歷史以 LID06h 為主。若同時發生可記錄的硬體錯誤或 Reset，則是那些事件另行記錄，不可拿來取代 Self-test Result。

本主題的共用條件 · Controller Reset 後是否保留或繼續？

影響執行 controller 的 Controller Level Reset 必須中止短程測試；延伸測試則必須跨 CLR 保留，並在重設完成後恢復。恢復的 segment 由廠商決定，規範建議只需重做被中斷的最後 segment。

本主題的共用條件 · NVM Subsystem Reset 後是否保留或繼續？

Subsystem Reset 會對其範圍內的 controller 造成 CLR：短程測試被中止，延伸測試必須恢復。不能把重新建立 Admin Queue 與重新開始整個延伸測試當成同一件事。

本主題的共用條件 · Power Cycle 後是否保留或繼續？

延伸測試必須在電源恢復後繼續；短程測試則不具有這項延續要求。恢復後先讀 DSTOS、進度與最新結果，不能只因 power cycle 就期待兩者都新增 Reset-aborted 結果。

本主題的共用條件 · 是否影響其他 Controller 或 Namespace？

測試由收到命令的 controller 執行，NSID 決定包含哪些 namespace。DSTO.SDSO 決定同時只能有一個測試的限制是在 controller 或 subsystem；即使沒有測試其他 namespace，共享資源仍可能使其他工作變慢。
