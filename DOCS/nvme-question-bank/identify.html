BASE 2.4 / NVM 1.3 / PCIe 1.4 · Q1–68

Q44–Q53

Identify 與能力探索

把 Identify 當成多個不同的查詢入口。先問「查誰、查哪一種資料」，再選 CNS、CSI、NSID 及其他 selector。能力、目前配置與清單變更分開核對，才能找出真正矛盾。

先練習，再展開每題的 17 項解答。所有數字案例均為教學假設；Status 以 SCT/SC 表示，代碼後的 h 代表十六進位。

先認識本文使用的字詞

Controller / namespace
controller 接收命令並管理存取；namespace 是命令可以指定的一份邏輯儲存空間。多個 controller 可以屬於同一 NVM subsystem（包含 controller 與非揮發儲存資源的整體）。
SQ / CQ / SQE / CQE
Submission Queue 是提交佇列，Completion Queue 是完成佇列；SQE／CQE 是其中的一筆 entry。QID 識別 queue，CID 識別同一 SQ 內尚未完成的命令，NSID 識別 namespace。
Register / Identify / Feature / Log
Register 是可存取的控制或狀態欄位；Identify 查物件能力與屬性；Feature 查／設工作設定；Log Page 回報指定種類的狀態或紀錄。FID、LID、CNS、CSI 分別選 Feature、Log、Identify 結構及命令集。
index / offset / zero-based
index 是第幾筆，通常由 0 起算；offset 是離起點多遠，要看單位。zero-based 數量欄位的實際數量＝編碼＋1，但不是每個寫 0 的欄位都要加 1。Dword 是 4 bytes，1 byte 是 8 bits。
Scope / reset / retention
scope 指一項操作影響的物件範圍。retention 是狀態是否保留。Controller Reset（清 CC.EN）是一種 Controller Level Reset，簡稱 CLR；同一類 CLR 的不同觸發方式，Register 保留規則仍可能不同。

先選問題，再選 Identify 結構

不同 CNS 回答不同問題；「已配置」不能直接推論成「這個 controller 現在可存取」。

想知道什麼查詢入口回覆如何使用

舉例看懂：假設 Allocated List={1,2}，目前 controller 的 Active List={1}。這只能證明 namespace 2 未出現在此 controller 的 active list；不能直接判定它被刪除。下一步查 attachment 與適用的狀態，並留下 controller 身分及查詢時間。

先把觀念接起來

教學 1 · 從裝置、容量到可見性，分三次問

Identify Controller 描述這個 controller；Identify Namespace 描述指定 namespace 的格式與容量；Active List 描述目前能透過這個 controller 使用的 namespace 集合。這三份回覆互補，不能靠 Controller.NN 就認定從 NSID=1 到 NN 全都存在並可存取。

教學 2 · 欄位是位元遮罩還是索引，會改變算式

CNS 選資料結構；CSI 選命令集；某些欄位是能力 bitmap，某些是陣列 index。以 LBAF 為例，先從 FLBAS 解出正確索引，再去讀那一筆格式描述，不能把 FLBAS 原始值直接當 bytes 數。對比型別通常比死背十六進位值更有用。

教學 3 · 查詢結果也有時間

Create 成功後才查 Allocated List，Attach 成功後才查該 controller 的 Active List。若另一個管理者同時改配置，前後清單可能屬於不同時間。先釐清順序與觀察對象，再判斷是不是韌體沒有更新回覆。

Q44 Identify Controller 與 Identify Namespace 分別提供哪些重要資訊？

先試著說明正常流程與一個不符合前提的例子，再展開核對。

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    先分清 controller 能做什麼，與特定 namespace 採用什麼容量、格式和保護設定。

  2. 02 它的影響範圍是什麼？

    Controller 資料以接收命令的 controller 為觀察入口；Namespace 資料由 NSID／CNS／CSI 指定。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    基本入口為 CNS01h Controller、CNS00h NVM Namespace；CNS05h／06h 為 command-set specific，CNS08h 為 command-set independent Namespace。

  4. 04 涉及哪些 Command 與重要欄位？

    Controller 看 SN、MN、FR、MDTS、OACS、ONCS、LPA、SQES／CQES；NVM Namespace 看 NSZE／NCAP／NUSE、FLBAS／LBAF、MC／DPC／DPS、原子性及群組識別。

  5. 05 正常流程及先後順序是什麼？

    先查 Controller 和 active list，再逐 namespace 查適用的幾種結構；用目前選定 LBA format 將 block 數轉成 bytes。

  6. 06 成功時應回傳什麼結果？

    Identify 回傳 4096-byte 結構與成功 CQE。例：NSZE=8192、LBADS=12，邏輯位址空間為 8192×4096=32 MiB。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    不支援 CNS：Invalid Field（0/02h）；namespace 所屬 command set 不支援該 CNS：Invalid I/O Command Set（1/2Ch）。NSID 情況依該 CNS。

  8. 08 DNR 與 More 應如何設定？

    有 CQE 才適用。本題未另指定固定的 DNR／More 覆寫值，使用本冊 CQE 位元判讀規則。 本冊完整規則

  9. 09 是否產生 Asynchronous Event？

    此題的正常完成本身不保證 AER；另有指定事件時，確認支援、設定及 pending request。 本冊完整規則

  10. 10 是否更新 Error Information Log 或其他 Log？

    對照本題的完成結果與錯誤紀錄；新增 Entry 的條件使用本冊共用規則，不以失敗次數直接推算。 本冊完整規則

  11. 11 是否記錄於 Persistent Event Log？

    這不是逐命令歷史；只有支援且符合記錄條件的指定事件需要 PEL 紀錄。 本冊完整規則

  12. 12 Controller Reset 後是否保留或繼續？

    未完成查詢須重新送出；按欄位區分固定身分、配置與動態狀態。 本冊完整規則

  13. 13 NVM Subsystem Reset 後是否保留或繼續？

    重新探索受影響對象；重設本身不代表 namespace 被刪除或恢復出廠配置。 本冊完整規則

  14. 14 Power Cycle 後是否保留或繼續？

    重新查詢並比較；須把韌體啟用、管理變更與單純斷電分開。 本冊完整規則

  15. 15 是否影響其他 Controller 或 Namespace？

    Identify 是唯讀；不同 controller 的 active list 可能不同，應按查詢對象比較。 本冊完整規則

  16. 16 Identify、Feature、Log 與 Command 行為是否一致？

    「Controller 支援某命令」不代表每個 namespace 都有適合的格式或目前可存取；能力與 namespace 條件須相交檢查。

  17. 17 結果不符預期時，第一個要檢查什麼？

    先檢查拿到哪個 CNS 的 buffer，再依那個結構解碼，避免把 CNS08h 當 CNS00h。

Q45 Active Namespace ID List、Allocated Namespace ID List 及 Namespace Descriptor List 有什麼差異？

先試著說明正常流程與一個不符合前提的例子，再展開核對。

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    分開「可由此 controller 使用」「已配置存在」與「這個 namespace 的識別資料」。

  2. 02 它的影響範圍是什麼？

    Active list 是 controller 的視角；Allocated list 可包含未附加的 namespace；Descriptor list 是單一 NSID 的屬性集合。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    CNS02h 查 Active，10h 查 Allocated，03h 查 Namespace Identification Descriptors；Allocated 查詢還依 Namespace Management 支援。

  4. 04 涉及哪些 Command 與重要欄位？

    List 的 NSID 是分頁起點，回傳大於起點的 IDs；Descriptor 有 NIDT／NIDL／NID，描述例如 EUI64、NGUID、UUID、CSI。

  5. 05 正常流程及先後順序是什麼？

    從 NSID=0 讀起，依遞增 ID 繼續下一批；查單一 namespace 的 Descriptor 時，NSID 則是目標。不要把兩種用途混淆。

  6. 06 成功時應回傳什麼結果？

    例：Allocated={1,3,8}、Active={1,8}，表示 3 已配置但不在此 controller 的 active list；不是 namespace3 必然損壞。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    CNS02h／10h 的起點 FFFFFFFEh 或 FFFFFFFFh 須回 Invalid Namespace or Format（0/0Bh）。未支援 CNS 則為 0/02h。

  8. 08 DNR 與 More 應如何設定？

    有 CQE 才適用。本題未另指定固定的 DNR／More 覆寫值，使用本冊 CQE 位元判讀規則。 本冊完整規則

  9. 09 是否產生 Asynchronous Event？

    此題的正常完成本身不保證 AER；另有指定事件時，確認支援、設定及 pending request。 本冊完整規則

  10. 10 是否更新 Error Information Log 或其他 Log？

    對照本題的完成結果與錯誤紀錄；新增 Entry 的條件使用本冊共用規則，不以失敗次數直接推算。 本冊完整規則

  11. 11 是否記錄於 Persistent Event Log？

    這不是逐命令歷史；只有支援且符合記錄條件的指定事件需要 PEL 紀錄。 本冊完整規則

  12. 12 Controller Reset 後是否保留或繼續？

    未完成查詢須重新送出；按欄位區分固定身分、配置與動態狀態。 本冊完整規則

  13. 13 NVM Subsystem Reset 後是否保留或繼續？

    重新探索受影響對象；重設本身不代表 namespace 被刪除或恢復出廠配置。 本冊完整規則

  14. 14 Power Cycle 後是否保留或繼續？

    重新查詢並比較；須把韌體啟用、管理變更與單純斷電分開。 本冊完整規則

  15. 15 是否影響其他 Controller 或 Namespace？

    Identify 是唯讀；不同 controller 的 active list 可能不同，應按查詢對象比較。 本冊完整規則

  16. 16 Identify、Feature、Log 與 Command 行為是否一致？

    用 Descriptor 的穩定識別關聯裝置，而非永遠假設 NSID 不變；分頁期間若配置改變，需重新取得一致的清單。

  17. 17 結果不符預期時，第一個要檢查什麼？

    先確認 NSID 在此次命令中代表目標，還是「從這個 ID 之後開始列」。

Q46 Controller List、UUID List 及 I/O Command Set Identify 資料分別有什麼用途？

先試著說明正常流程與一個不符合前提的例子，再展開核對。

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    回答「由哪些 controller 存取」「用哪套 vendor 定義解讀」「哪些 command sets 能同時使用」三種不同問題。

  2. 02 它的影響範圍是什麼？

    Controller List 是關係清單；UUID List 是 vendor-specific 資訊的選擇表，不等於 namespace 的 UUID Descriptor。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    CNS12h 查某 namespace 附加的 controllers，13h 查 subsystem I/O controllers，17h 查 UUID List，1Ch 查 command-set combinations。

  4. 04 涉及哪些 Command 與重要欄位？

    CNTID 是 Controller List 的起點或特定 CNS 的目標；UIDX=0 不指定 UUID。CNS1Ch 的每個 vector 是一組可同時使用的 CSI。

  5. 05 正常流程及先後順序是什麼？

    先依問題選 CNS，再用正確 selector；CNS1Ch 選出組合後，FID19h 的 IOCSCI 使用該組合的 index，不是直接填 CSI bitmap。

  6. 06 成功時應回傳什麼結果？

    Controller List 回識別值與數量；UUID List 回有定義順序的 entries；command-set vectors 告訴 Host 可選配置，不自動啟用它們。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    未支援 CNS 回 0/02h；CNS12h 的 NSID=FFFFFFFFh 回 0/02h。UUID selector 的非法狀態另依 §8.1.31，不能當成 namespace 不存在。

  8. 08 DNR 與 More 應如何設定？

    有 CQE 才適用。本題未另指定固定的 DNR／More 覆寫值，使用本冊 CQE 位元判讀規則。 本冊完整規則

  9. 09 是否產生 Asynchronous Event？

    此題的正常完成本身不保證 AER；另有指定事件時，確認支援、設定及 pending request。 本冊完整規則

  10. 10 是否更新 Error Information Log 或其他 Log？

    對照本題的完成結果與錯誤紀錄；新增 Entry 的條件使用本冊共用規則，不以失敗次數直接推算。 本冊完整規則

  11. 11 是否記錄於 Persistent Event Log？

    這不是逐命令歷史；只有支援且符合記錄條件的指定事件需要 PEL 紀錄。 本冊完整規則

  12. 12 Controller Reset 後是否保留或繼續？

    未完成查詢須重新送出；按欄位區分固定身分、配置與動態狀態。 本冊完整規則

  13. 13 NVM Subsystem Reset 後是否保留或繼續？

    重新探索受影響對象；重設本身不代表 namespace 被刪除或恢復出廠配置。 本冊完整規則

  14. 14 Power Cycle 後是否保留或繼續？

    重新查詢並比較；須把韌體啟用、管理變更與單純斷電分開。 本冊完整規則

  15. 15 是否影響其他 Controller 或 Namespace？

    Identify 是唯讀；不同 controller 的 active list 可能不同，應按查詢對象比較。 本冊完整規則

  16. 16 Identify、Feature、Log 與 Command 行為是否一致？

    核對 CNTID 與 NSID 各自作用，不將 controller list 當 active namespace list；核對 FID19h Current 是否選到預期 vector。

  17. 17 結果不符預期時，第一個要檢查什麼？

    先確認 UIDX 是 UUID List 的索引，不是 UUID 本體，也不是 namespace ID。

Q47 NVM Set、Endurance Group、Domain 及 Secondary Controller 資訊應從哪種 Identify 資料取得？

先試著說明正常流程與一個不符合前提的例子，再展開核對。

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    建立資源歸屬關係，避免把 Set、Group、Domain 和 controller 當成同一層物件。

  2. 02 它的影響範圍是什麼？

    每種清單有自己的 ID、容量或資源欄位；本題只探索資料，不執行容量或虛擬化修改。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    先查 CTRATT 的相關能力與 OACS.VMS；CNS04h、19h、18h、14h／15h 分別對應 Set、Endurance Group、Domain、Primary／Secondary Controller。

  4. 04 涉及哪些 Command 與重要欄位？

    NVM Set Attributes 帶 ENDGID；Namespace 資料帶 NVMSETID／ENDGID；Domain entry 帶 DID、TDC、UDC；Secondary entry 帶 SCID、PCID、狀態與 VQ／VI 資源數。

  5. 05 正常流程及先後順序是什麼？

    從 namespace 群組識別向上查 Set／Group；以 Domain list 看容量歸屬；從 Primary capabilities 與 Secondary list 看已分配的 queue／interrupt 資源。

  6. 06 成功時應回傳什麼結果？

    得到可關聯的 ID 與屬性，不是所有零欄位都代表資源數為零；須先確認該能力與欄位在此配置中有效。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    未支援的 CNS 是 0/02h；某些清單起點超過現有 ID 會得到空清單，不能一律要求錯誤。

  8. 08 DNR 與 More 應如何設定？

    有 CQE 才適用。本題未另指定固定的 DNR／More 覆寫值，使用本冊 CQE 位元判讀規則。 本冊完整規則

  9. 09 是否產生 Asynchronous Event？

    此題的正常完成本身不保證 AER；另有指定事件時，確認支援、設定及 pending request。 本冊完整規則

  10. 10 是否更新 Error Information Log 或其他 Log？

    保存 SN／MN、namespace 穩定識別、FR、能力位、容量／格式／附加關係及動態欄位作比較基準。

  4. 04 涉及哪些 Command 與重要欄位？

    FR 應描述目前 active firmware；MDTS／能力需在更新後重新確認；NUSE 等動態數值不能當固定識別值。

  5. 05 正常流程及先後順序是什麼？

    先記錄改變來源：只是 Reset、Power Cycle，還是同時 Activation／管理配置；恢復後用相同 CNS／NSID／CSI 讀取，再逐欄對照定義。

  6. 06 成功時應回傳什麼結果？

    普通 Reset 不是重新命名裝置、刪除 namespace 或 Format 的操作；但若同時啟用新韌體，FR 與其可合法變更的能力不能要求沿用舊值。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    比較工作沒有新的 CQE Status；若 post-reset Identify 失敗，先分初始化未完成、無效 NSID 與選錯 CNS，不把全部差異定義成韌體錯誤。

  8. 08 DNR 與 More 應如何設定？

    有 CQE 才適用。本題未另指定固定的 DNR／More 覆寫值，使用本冊 CQE 位元判讀規則。 本冊完整規則

  9. 09 是否產生 Asynchronous Event？

    此題的正常完成本身不保證 AER；另有指定事件時，確認支援、設定及 pending request。 本冊完整規則

  10. 10 是否更新 Error Information Log 或其他 Log？

    對照本題的完成結果與錯誤紀錄；新增 Entry 的條件使用本冊共用規則，不以失敗次數直接推算。 本冊完整規則

  11. 11 是否記錄於 Persistent Event Log？

    這不是逐命令歷史；只有支援且符合記錄條件的指定事件需要 PEL 紀錄。 本冊完整規則

  12. 12 Controller Reset 後是否保留或繼續？

    未完成查詢須重新送出；按欄位區分固定身分、配置與動態狀態。 本冊完整規則

  13. 13 NVM Subsystem Reset 後是否保留或繼續？

    重新探索受影響對象；重設本身不代表 namespace 被刪除或恢復出廠配置。 本冊完整規則

  14. 14 Power Cycle 後是否保留或繼續？

    重新查詢並比較；須把韌體啟用、管理變更與單純斷電分開。 本冊完整規則

  15. 15 是否影響其他 Controller 或 Namespace？

    Identify 是唯讀；不同 controller 的 active list 可能不同，應按查詢對象比較。 本冊完整規則

  16. 16 Identify、Feature、Log 與 Command 行為是否一致？

    使用 stable ID 確認比較的是同一物件；保留 raw bytes，同時把 padding、reserved、動態欄位與真正語意差異分開。

  17. 17 結果不符預期時，第一個要檢查什麼？

    先檢查 Reset 是否同時觸發 pending firmware activation，或查到了另一個 controller／namespace。

Q53 Identify、Feature、Log Page 與實際 Command 行為不一致時，應如何定位問題？

先試著說明正常流程與一個不符合前提的例子，再展開核對。

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    用完整證據鏈判斷不一致，而不是因某個介面顯示支援就忽略當下條件。

  2. 02 它的影響範圍是什麼？

    限定 controller、NSID、CSI、時間與配置；跨 controller 或不同時點的快照未必描述相同狀態。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    Identify 查能力，Get Features 查設定，Log 查狀態／事件或效果宣告；三者用途不同。

  4. 04 涉及哪些 Command 與重要欄位？

    保存原 SQE、CQE、Identify 原始 buffer、FID 的 SEL 值、LID 與其他 selectors；明確區分 Current 和 Supported Capabilities。

  5. 05 正常流程及先後順序是什麼？

    先檢查版本／解碼→scope／selectors→合法參數→目前狀態與先後→結果；必要時用單一控制變因的教學測例重現。

  6. 06 成功時應回傳什麼結果？

    一致的意思是各介面的規範關係成立，不是所有回傳值相同；例如 CHANG=1 與 Current=0 可以同時正確。

共用規則：各題連到的完整解釋

這些規則在本冊只完整說明一次。返回剛才的題目可用瀏覽器「上一頁」；特定命令或 Feature 的明文例外優先。

命令完成、事件與紀錄 · DNR 與 More 應如何設定？

有 CQE 時，DNR=1 表示相同命令再送到此 NVM subsystem 的任一 controller 仍預期失敗；DNR=0 只表示可能成功。除非本題錯誤另有明定，不把某個 Status 固定綁成 DNR=1。More=1 表示 Error Information Log 有這筆命令的補充資訊。SCT=SC=0 時 DNR 應為 0。

命令完成、事件與紀錄 · 是否產生 Asynchronous Event？

命令完成與非同步通知是兩件事；本題操作成功本身不保證有事件。若操作引起規範列出的事件，還要核對事件支援、適用的通知設定、是否已遮蔽，以及 Host 是否掛入 Asynchronous Event Request。

命令完成、事件與紀錄 · 是否更新 Error Information Log 或其他 Log？

成功 CQE 不是要求新增 Error Information 的理由。錯誤有 More=1 時，查 LID 01h 並用 SQID、CID 和 Error Count 對應；不能把每個非成功 CQE 都當成必須新增一筆。操作改變的狀態則由本題列出的查詢介面重新讀取。

命令完成、事件與紀錄 · 是否記錄於 Persistent Event Log？

Persistent Event Log 是選配的事件歷史，不是所有命令的執行清單。先查 LPA 的支援與 Supported Events Bitmap，再判斷本次是否符合指定事件的記錄條件；不能只因命令成功或失敗就要求新增一筆。

查詢的重設與影響範圍 · Controller Reset 後是否保留或繼續？

Controller Reset 中止尚未完成的查詢；不要把沒有收到的回覆當成全零資料。重新建立查詢路徑後再讀取，按欄位判斷固定識別、目前配置及動態狀態；Reset 本身不代表 namespace 被刪除。

查詢的重設與影響範圍 · NVM Subsystem Reset 後是否保留或繼續？

重設完成後重新探索受影響 controller 與 namespace。NVM Subsystem Reset 是通訊與控制狀態的重設，不能直接推論所有儲存配置回到出廠值；另有管理操作時，依那個操作確認變更。

查詢的重設與影響範圍 · Power Cycle 後是否保留或繼續？

Power Cycle 後重新查詢版本、能力、目前格式及附加清單。固定識別資訊與持續配置不應被當成一般暫存 Feature；但韌體啟用或配置變更可能有不同結果，必須留下前後快照及事件時間。

查詢的重設與影響範圍 · 是否影響其他 Controller 或 Namespace？

Identify 只讀資料，不會建立、格式化或附加 namespace。回覆的觀察範圍依 CNS 與選擇欄位決定；另一個 controller 看到的 active list 可以不同，不能因清單不同就判定資料損壞。
