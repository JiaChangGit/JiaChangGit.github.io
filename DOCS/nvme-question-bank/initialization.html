Controller 初始化與停用

先理解 controller 如何從停用轉為就緒，再開始處理命令。讀到能力，不表示 controller 已啟用；Host 設定 EN，也還要等待 RDY。即使 RDY=1，仍可能需要依 Ready Mode 確認媒體是否可用。本冊將狀態、等待時間及允許執行的動作放在一起，說明每個階段應如何判斷。

先練習，再展開每題的 17 項解答。所有數字案例均為教學假設；Status 以 SCT/SC 表示，代碼後的 h 代表十六進位。

先認識本文使用的字詞

Controller / namespace
controller 接收命令並管理存取；namespace 是命令可指定的一份邏輯儲存空間。NVM subsystem 則包含 controller 與非揮發儲存資源，同一 subsystem 可以有多個 controller。
SQ / CQ / SQE / CQE
Submission Queue（SQ）是提交佇列，Completion Queue（CQ）是完成佇列；SQE 與 CQE 分別是其中的一筆命令及完成項目。QID 識別 queue，CID 區分同一 SQ 中尚未完成的命令，NSID 則識別 namespace。
Register / Identify / Feature / Log
Register 提供可存取的控制或狀態資訊；Identify 查詢物件的能力與屬性；Feature 用來讀取或變更工作設定；Log Page 回報特定種類的狀態或紀錄。FID、LID、CNS、CSI 則分別用來選擇 Feature、Log Page、Identify 資料結構及命令集。
index / offset / zero-based
index 指出清單中的第幾筆，通常從 0 起算；offset 表示與起點相隔多遠，解讀時必須確認單位。若數量欄位採 zero-based 編碼，實際數量等於欄位值加 1；但不是所有欄位看到 0 都要加 1。Dword 是 4 bytes，1 byte 是 8 bits。
Scope / reset / retention
scope 表示操作影響哪些物件；retention 表示狀態是否保留。清除 CC.EN 所觸發的 Controller Reset，是 Controller Level Reset（CLR）的一種。同屬 CLR 的不同觸發方式，仍可能採用不同的 Register 保留規則。

從未啟用到能送命令

重新啟用前，先確認上一輪停用已完成。啟用與停用都要觀察 RDY 的實際變化，不能只看 Host 自己寫入的 EN。

階段觀察／動作下一步的條件
停用完成CC.EN=0；CSTS.RDY=0設定 AQA、ASQ、ACQ 與 CC
啟用中Host 將 EN 從 0 設為 1，並開始計時等待 RDY=1，同時檢查 CFS 及適用的 timeout
介面就緒RDY=1；依 Ready Mode 判斷媒體限制先執行允許的 Admin 命令，再建立 I/O queue
再次停用Host 將 EN 從 1 清為 0，並停止提交新命令等待 RDY=0，才開始下一次初始化

舉例看懂：假設 CAP.TO=4，停用等待上限為 4×500 ms=2 s。這個期限用來等待 controller 停用，不是每筆 I/O 命令的 timeout。啟用時還須根據 CAP.CRMS、所選 Ready Mode 及 CRTO 決定期限，因此不能將這個 2 s 套用到所有等待情況。

先把觀念接起來

教學 1 · 先分清誰寫、誰回報

CC.EN 由 Host 寫入，表示要求啟用或停用；CSTS.RDY 由 controller 回報，表示它目前是否就緒。就像按下電源開關與系統完成開機是兩個時點，驗證時也必須記錄 EN 變化與 RDY 變化各自的時間。單看 EN=1，只能證明 Host 已要求啟用，不能證明 controller 已準備好。

教學 2 · Independent mode 為什麼需要兩個期限

Independent mode 允許管理介面先就緒，再等待媒體能夠提供服務。CRIMT 對應介面就緒的期限，CRWMT 對應媒體就緒的期限；兩者都從 EN 由 0 變成 1 時起算。例如介面在 300 ms 就緒，而媒體期限是 2 s，媒體剩下的等待時間就是 1.7 s，不會從介面就緒時重新獲得 2 s。實際採用哪個期限，仍須依 CAP.TO 與 CRTO 的比較規則決定。

教學 3 · 重設後的位元仍在，不代表物件仍在

由清除 CC.EN 觸發的 Controller Reset 會保留 AQA、ASQ、ACQ，因此 Host 不必只因這種重設就重新提供相同的基底位址。不過，Admin Queue 指標已重設，I/O queue 也已刪除。如果 Host 繼續用舊 CID 紀錄配對新 CQE，可能把前一次 queue 留下的資料當成新結果。因此，重建命令追蹤狀態也是恢復流程的一部分。

Q01 Host 應如何從 CAP 與 VS 確認 NVMe 版本、最大 Queue 大小、Timeout、Doorbell 間距、Memory Page Size 及支援的 Command Set？

先試著說明正常流程，並舉出一個未滿足執行條件的例子，再展開解答核對。

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    Host 必須先知道 controller 支援哪些配置，才能正確初始化介面。CAP 用來宣告支援能力，CC 則記錄 Host 實際選用的設定，因此不能直接把 CAP 的能力位元複製到 CC。

  2. 02 它的影響範圍是什麼？

    讀取 CAP 與 VS 只會取得目標 controller 的資訊，不會改變 queue 或媒體狀態。即使已確認 NVMe 版本，Host 仍須逐項檢查選配功能，因為版本相同不代表支援的功能完全相同。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    VS 的 MJR、MNR、TER 欄位共同表示版本。Queue 與命令集能力則由 CAP 提供：MQES+1 是單一 I/O queue 的 entry 數量上限，CQR 說明是否要求實體記憶體連續，CSS 則說明支援哪些命令集選擇方式。

  4. 04 涉及哪些 Command 與重要欄位？

    這些欄位使用不同的編碼方式。CAP.TO 以 500 ms 為單位；相鄰 Doorbell 的間距是 2^(2+DSTRD) bytes；可選的記憶體頁面大小則介於 2^(12+MPSMIN) 與 2^(12+MPSMAX) bytes。判斷啟用逾時時，還必須一併讀取 CRTO。

  5. 05 正常流程及先後順序是什麼？

    Host 先建立 NVMe Register 的位址映射，再讀取 VS 與 CAP。根據讀到的能力，選擇合法的 MPS、CSS、AMS 與 Ready Mode，接著配置 queue。若 IOCSS=1，則在啟用後以 Identify CNS 1Ch 查詢可使用的命令集組合。

  6. 06 成功時應回傳什麼結果？

    讀取成功後，Host 應能算出合法的配置範圍；這次 Register 讀取本身不會產生 CQE。例如，MQES=03FFh 表示最多 1024 個 queue 位置，而 DSTRD=2 表示相鄰 Doorbell 相隔 16 bytes。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    讀取唯讀 Register 不會以 Invalid Field CQE 回覆錯誤。至於後續設定，若 Host 把不支援的值寫入 CC.MPS 或 CC.AMS，規範可能將結果定義為 undefined behavior；此時不能要求 controller 回傳某個固定錯誤碼。

  8. 08 DNR 與 More 應如何設定？

    本次 MMIO 存取沒有 NVMe CQE，因此 DNR／More 不適用。 本冊完整規則

  9. 09 是否產生 Asynchronous Event？

    Register 存取本身不產生成功事件。若另外發生硬體錯誤等事件，則依該事件自己的條件判斷。 本冊完整規則

  10. 10 是否更新 Error Information Log 或其他 Log？

    不要求每次 Register 讀寫都新增錯誤紀錄。先保留 Register 值及時間，再補充 controller 當時允許讀取的診斷資料。 本冊完整規則

  11. 11 是否記錄於 Persistent Event Log？

    一般 Register 存取不是 PEL 事件。若操作同時引發 Reset 或硬體錯誤，再依支援能力與對應事件條件判斷。 本冊完整規則

  12. 12 Controller Reset 後是否保留或繼續？

    CAP 與 VS 分別提供能力及版本資訊。Controller Reset 後，Host 重新讀取它們，再設定 CC 中需要選擇的值；這些唯讀能力欄位本身不需要、也不是由 Host 寫回。

  13. 13 NVM Subsystem Reset 後是否保留或繼續？

    NVM Subsystem Reset 後，先確認 Register 已可存取，再重新查詢版本與能力。若這次重設同時啟用新韌體，更要以恢復後的實際回覆為準。

  14. 14 Power Cycle 後是否保留或繼續？

    Power Cycle 後，Host 重新讀取 CAP 與 VS。本題只是查詢能力與版本，沒有因這次讀取而需要保存的 Host 設定。

  15. 15 是否影響其他 Controller 或 Namespace？

    讀取 Register 不會改變其他 controller 或 namespace。不過，不同 controller 可以有不同能力，因此不能拿其中一個 controller 的回覆代替全部。

  16. 16 Identify、Feature、Log 與 Command 行為是否一致？

    驗證時，應確認 CC.CSS 選用的命令集符合 CAP.CSS 宣告的能力及 Identify 回報的組合。同樣地，Create Queue 的 QSIZE 必須符合 MQES 限制。Admin Queue 則另受 AQA 的 4096 個位置上限約束，不能與 I/O queue 的上限混為一談。

  17. 17 結果不符預期時，第一個要檢查什麼？

    先檢查欄位的位元位置、little-endian 解讀方式，以及數量是否採 zero-based 編碼。例如，MQES=1023 代表 1024 個位置；如果只配置 1023 個，便是漏算了編碼中的加 1。

Q02 AQA、ASQ、ACQ 與 CC 各欄位應按照什麼順序設定？設定錯誤時可能發生什麼？

先試著說明正常流程，並舉出一個未滿足執行條件的例子，再展開解答核對。

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    Host 必須先準備 Admin SQ 與 CQ 的記憶體，再把位置與大小告訴 controller。這樣 controller 啟用後，才有可用的通道接收管理命令並回報結果。

  2. 02 它的影響範圍是什麼？

    這些設定影響目標 controller 的管理介面。若 queue 位址填錯，controller 就可能無法讀取命令或寫入完成結果，導致後續 Identify、Get Features 等命令都無法正常完成。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    先從 CAP 確認可用的 MPS 範圍、CSS、AMS 與 CRMS，再檢查 AQA 對 Admin Queue 長度的限制。Host 選用的配置必須同時符合這些條件。

  4. 04 涉及哪些 Command 與重要欄位？

    AQA.ASQS 與 ACQS 儲存的是 entry 數量減 1；ASQ 與 ACQ 則提供實體起始位址，且必須依 CC.MPS 對齊。CC 還需設定 CSS、MPS、AMS 與 CRIME。若使用 NVM I/O，IOSQES 與 IOCQES 分別設為 6 與 4。

  5. 05 正常流程及先後順序是什麼？

    先等待前一次重設完成，確認 RDY=0，再配置實體連續的 Admin Queue 記憶體，並把 Admin CQ 的 Phase 初始化為 0。接著，在 EN=0 時寫入 AQA、ASQ、ACQ 及合法的 CC 設定。將 EN 設為 1 後，等待 RDY=1。I/O entry 大小則必須在建立 I/O Queue 前設定完成。

  6. 06 成功時應回傳什麼結果？

    初始化成功後，Host 可以透過 Admin Queue 提交 Identify。不過，I/O Queue 仍需另外建立；若採 Independent mode，也不能只憑 RDY=1 就認定所有媒體都已就緒。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    例如，以 AQA size=0 的配置啟用 controller、在 EN=1 時修改 MPS，或選用不支援的 MPS／AMS，都可能落入規範所稱的 undefined behavior。這些是 Register 使用方式的問題，不能擅自規定 controller 必須回傳 Invalid Field CQE。

  8. 08 DNR 與 More 應如何設定？

    本次 MMIO 存取沒有 NVMe CQE，因此 DNR／More 不適用。 本冊完整規則

  9. 09 是否產生 Asynchronous Event？

    Register 存取本身不產生成功事件。若另外發生硬體錯誤等事件，則依該事件自己的條件判斷。 本冊完整規則

  10. 10 是否更新 Error Information Log 或其他 Log？

    不要求每次 Register 讀寫都新增錯誤紀錄。先保留 Register 值及時間，再補充 controller 當時允許讀取的診斷資料。 本冊完整規則

  11. 11 是否記錄於 Persistent Event Log？

    一般 Register 存取不是 PEL 事件。若操作同時引發 Reset 或硬體錯誤，再依支援能力與對應事件條件判斷。 本冊完整規則

  12. 12 Controller Reset 後是否保留或繼續？

    清除 CC.EN 後，I/O queue 失效，Admin Queue 指標重設。即使基底位址保留，舊 completion 也不能繼續當成有效結果。 本冊完整規則

  13. 13 NVM Subsystem Reset 後是否保留或繼續？

    受影響 controller 的 queue 必須重建。這次重設的來源不同，不能直接套用清除 CC.EN 時的 Register 保留例外。 本冊完整規則

  14. 14 Power Cycle 後是否保留或繼續？

    重新初始化 queue，並重建 Host 的命令追蹤資料。記憶體中殘留的舊內容，不是新 queue 的有效命令或完成結果。 本冊完整規則

  15. 15 是否影響其他 Controller 或 Namespace？

    Queue 隸屬於各自的 controller。多條 SQ 共用同一 CQ 時，才會共同受到這條 CQ 的可用空間及使用期間影響。 本冊完整規則

  16. 16 Identify、Feature、Log 與 Command 行為是否一致？

    驗證時，先確認 Register 的編碼正確，再確認 Admin CQ 能收到與原命令 CID 相符的 Identify 完成結果。CC.EN=1 只表示 Host 已要求啟用，單憑這個值還不足以證明初始化完成。

  17. 17 結果不符預期時，第一個要檢查什麼？

    先確認 ASQ、ACQ 指向的是裝置可存取的位址，再檢查頁面對齊與實際配置長度。一般程式使用的虛擬位址，不能直接當成 queue 的實體基底位址。

Q03 Host 設定 CC.EN 後，應如何根據 CAP.TO 與 CSTS.RDY 判斷 Controller 是否成功 Enable？

先試著說明正常流程，並舉出一個未滿足執行條件的例子，再展開解答核對。

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    Host 寫入啟用要求後，controller 還需要時間準備。這題要分辨「已要求啟用」與「已能處理命令」，並選對等待期限，避免過早重設；在 Base 2.4 中，判斷時也必須納入 CRTO。

  2. 02 它的影響範圍是什麼？

    這裡判斷的是目標 controller 的啟用狀態。至於媒體是否已可存取，還要配合所選的 Ready Mode，不能只看一個 RDY 值。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    讀取 CAP.CRMS、CC.CRIME、CRTO.CRWMT／CRIMT 及 CAP.TO，確認目前採用哪種 Ready Mode 及等待期限。不能假設所有啟用情況都只需要查看 CAP.TO。

  4. 04 涉及哪些 Command 與重要欄位？

    計時從 CC.EN 由 0 變成 1 開始，Host 則透過 CSTS.RDY 觀察是否就緒。CRTO 的單位是 500 ms：With Media 模式使用 CRWMT；Independent 模式先以 CRIMT 判斷介面就緒期限，再以 CRWMT 判斷媒體就緒期限。

  5. 05 正常流程及先後順序是什麼？

    Host 先記錄 Ready Mode 與啟用時間，再持續讀取 RDY、CFS。當 RDY=1 時，才能開始提交該模式允許的命令。若初始化失敗，還須依失敗條件判斷後續處理，因此不能把每次讀到 RDY=1 都解讀成媒體健康。

  6. 06 成功時應回傳什麼結果？

    正常情況在適用期限內 RDY=1。例：CRIMT=2、CRWMT=20，分別是 1 s 的介面就緒期限與 10 s 的媒體期限，兩者都從 Enable 起算。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    透過 Register 啟用 controller，不會產生 CQE。若媒體尚未就緒，只有符合對應條件的命令，才能回報 Namespace Not Ready（SCT=0, SC=82h）或 Admin Command Media Not Ready（0/24h）。

  8. 08 DNR 與 More 應如何設定？

    透過 Register 啟用 controller，不會產生 CQE，因此這個動作本身沒有 DNR 或 More。Independent mode 在合法等待期間，若命令因媒體尚未就緒而失敗，可以回報 DNR=0；超過 CRWMT 後，就不得繼續以相同的暫時性理由回報 DNR=0。More 則依 Error Information Log 是否有該命令的補充資訊設定。

  9. 09 是否產生 Asynchronous Event？

    Register 存取本身不產生成功事件。若另外發生硬體錯誤等事件，則依該事件自己的條件判斷。 本冊完整規則

  10. 10 是否更新 Error Information Log 或其他 Log？

Q07 Controller 初始化後可能進入哪些 Ready Mode？Host 應如何處理暫時或限制性的 Ready 狀態？

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    Ready Mode 決定 controller 何時可以開始服務。Independent 模式允許管理命令在媒體初始化完成前先開始執行，但媒體仍必須在規定的期限內就緒。

  2. 02 它的影響範圍是什麼？

    這裡討論兩種模式：Controller Ready With Media，以及 Controller Ready Independent of Media。它們規定的是介面與媒體的就緒關係，而不是額外定義一組可任意解讀的 degraded-ready 狀態碼。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    CAP.CRMS 中的 CRWMS、CRIMS 分別宣告兩種模式的支援能力。當 CAP.CRMS=11b 時，Host 可以透過 CC.CRIME 選擇要使用的模式。

  4. 04 涉及哪些 Command 與重要欄位？

    CRIME=0 選擇 With Media，CRIME=1 選擇 Independent。判斷當下允許執行哪些命令時，要一起檢查 CSTS.RDY、CRTO.CRIMT／CRWMT，以及 Figure 84 的命令分類。

  5. 05 正常流程及先後順序是什麼？

    Host 必須在啟用前選好模式。若選擇 Independent 模式，RDY=1 後可先執行不依賴媒體的查詢；需要媒體的命令若收到允許的暫時性 Status，則延後處理。同時仍要追蹤從 Enable 開始計算的 CRWMT，不能重新起算。

  6. 06 成功時應回傳什麼結果？

    With Media 模式正常就緒時，controller 應已能處理所要求的媒體存取。Independent 模式的 RDY=1 則先表示介面及適用命令已可服務，尚不能據此認定所有 namespace 都已就緒。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    在規範允許的條件下，controller 可以回傳 0/82h 或 0/24h；其中 0/24h 只適用於 Independent 模式下特定的 Admin 命令。超過媒體就緒期限後，若仍以同一個暫時等待理由回報 DNR=0，就不符合該期限的要求。

  8. 08 DNR 與 More 應如何設定？

    本題的 Register 讀寫沒有 DNR 或 More。若命令因媒體尚未就緒而回報 CQE，則另依條件判斷：允許等待期間可以使用 DNR=0，但超過 CRWMT 後，不得繼續以相同的暫時性理由回報 DNR=0。More 仍用來表示 Error Information Log 是否有補充資訊。

  9. 09 是否產生 Asynchronous Event？

    Register 存取本身不產生成功事件。若另外發生硬體錯誤等事件，則依該事件自己的條件判斷。 本冊完整規則

  10. 10 是否更新 Error Information Log 或其他 Log？

    不要求每次 Register 讀寫都新增錯誤紀錄。先保留 Register 值及時間，再補充 controller 當時允許讀取的診斷資料。 本冊完整規則

  11. 11 是否記錄於 Persistent Event Log？

    若符合 §3.5.4.1 的初始化失敗條件，而且 controller 支援 PEL，必須記錄 NVM Subsystem Hardware Error Event，原因為 Controller Ready Timeout Exceeded。正常選用某種 Ready Mode，本身不會要求產生這筆錯誤事件。

  12. 12 Controller Reset 後是否保留或繼續？

    清除 CC.EN 後，I/O queue 失效，Admin Queue 指標重設。即使基底位址保留，舊 completion 也不能繼續當成有效結果。 本冊完整規則

  13. 13 NVM Subsystem Reset 後是否保留或繼續？

    受影響 controller 的 queue 必須重建。這次重設的來源不同，不能直接套用清除 CC.EN 時的 Register 保留例外。 本冊完整規則

  14. 14 Power Cycle 後是否保留或繼續？

    重新初始化 queue，並重建 Host 的命令追蹤資料。記憶體中殘留的舊內容，不是新 queue 的有效命令或完成結果。 本冊完整規則

  15. 15 是否影響其他 Controller 或 Namespace？

    Queue 隸屬於各自的 controller。多條 SQ 共用同一 CQ 時，才會共同受到這條 CQ 的可用空間及使用期間影響。 本冊完整規則

  16. 16 Identify、Feature、Log 與 Command 行為是否一致？

    同時核對 CAP 宣告、CC 選擇、timeout 與命令行為。CSTS.PP 是另一種暫停處理指示，不是第三個 Ready Mode。

  17. 17 結果不符預期時，第一個要檢查什麼？

    先問正在失敗的命令是否需要媒體，再看它是否真的屬 Figure 84 允許的種類。

Q08 Controller Enable、Disable、Controller Reset、NVM Subsystem Reset 與 Shutdown 有什麼差異？

先試著說明正常流程，並舉出一個未滿足執行條件的例子，再展開解答核對。

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    這幾個動作分別處理開始服務、停止並重設，以及移除電源前的準備。先分清它們的目的，才能避免用 Reset 取代原本需要的正常 Shutdown。

  2. 02 它的影響範圍是什麼？

    啟用或清除 CC.EN 的作用對象是單一 controller。NVM Subsystem Reset 則依規範涵蓋相應的 subsystem 或 domain 範圍；Shutdown 也另有 controller 與 subsystem 層級，必須先確認使用的是哪一種。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    CAP.NSSRS 可用來確認是否支援 NSSR。判斷 Shutdown 的作用範圍時，則還要查看 CAP 宣告的 shutdown 能力與 CSTS.ST。

  4. 04 涉及哪些 Command 與重要欄位？

    Enable：EN 0→1。Controller Reset：EN 1→0。NSSR.NSSRC 寫 4E564D65h 觸發支援的 subsystem reset。正常 controller shutdown 用 CC.SHN=01b，觀察 CSTS.SHST=10b。

  5. 05 正常流程及先後順序是什麼？

    若準備正常移除電源，Host 應先協調 I/O，再送出 Shutdown 通知，並等待關機處理完成。若目的是故障恢復，則選擇合適的 Reset，之後重新建立命令處理環境。

  6. 06 成功時應回傳什麼結果？

    不同動作有不同的完成判斷：啟用時等待 RDY=1；停用或重設時檢查對應的狀態轉移；Shutdown 則等待 SHST=10b。Shutdown 完成不表示所有 Register 都已回到重設值。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    Register 操作本身沒有 CQE。Shutdown 過程中，controller 可以對適用命令回報 Commands Aborted due to Power Loss Notification（0/05h）；但不能因此把所有 Reset 中未完成的命令，都預期為相同 Status。

    一般 Register 存取不是 PEL 事件。若操作同時引發 Reset 或硬體錯誤，再依支援能力與對應事件條件判斷。 本冊完整規則

Q09 Controller Reset 後，哪些 Register、Admin Queue、Feature 與 I/O Queue 需要重新設定？

先試著說明正常流程，並舉出一個未滿足執行條件的例子，再展開解答核對。

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    重設後，Host 需要重新建立可用的命令處理環境。這樣才能把新命令與上一輪的 queue 指標、Phase 及未完成命令分開處理。

  2. 02 它的影響範圍是什麼？

    本題只討論清除 CC.EN 所觸發的 Controller Reset。FLR 與 NVM Subsystem Reset 來自不同觸發方式，不能直接套用這裡的 Register 保留規則。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    先查看 §3.7.2 的重設例外，以及各 Register 的 Reset 欄，確認哪些值會保留。Feature 則還要考慮作用範圍、是否可保存設定，以及 Figure 126、127、466 的恢復規則。

  4. 04 涉及哪些 Command 與重要欄位？

    這種重設會保留 AQA、ASQ、ACQ、指定的 PMR Register 與 CMBMSC，但仍會重設 Admin Queue 的指標，並刪除所有 I/O SQ／CQ。Host 因此需要重新配置 CC。Feature 的恢復方式則另行判斷：可保存設定者依重設範圍恢復 Saved，沒有 Saved 時使用 Default；不可保存設定者依持續性規則處理。HMB 也需要重新配置。

  5. 05 正常流程及先後順序是什麼？

  6. 06 成功時應回傳什麼結果？

    重建成功後，新命令應能在新建立的 queue 上正常完成。即使沿用相同的 QID 或記憶體位址，也不表示上一輪 queue 可以接續使用。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

Queue 的重設與影響範圍 · Controller Reset 後是否保留或繼續？

Host 清除 CC.EN 會觸發 Controller Level Reset：I/O SQ 與 CQ 被刪除，Admin Queue 的指標也會重設。這種重設雖然保留 AQA、ASQ、ACQ，卻不表示舊 CQE 仍然有效。Host 必須重新初始化 Admin CQ 的 Phase，啟用 controller 後，再配置並建立 I/O queue。

Queue 的重設與影響範圍 · NVM Subsystem Reset 後是否保留或繼續？

NVM Subsystem Reset 會讓受影響的 controller 執行 Controller Level Reset，Host 不能沿用舊 queue。恢復時，先重新確認傳輸及 Register 狀態，再建立 Admin 與 I/O 的操作環境。這種重設來源不同，不能直接套用清除 CC.EN 時對 AQA 等 Register 的保留例外。

Queue 的重設與影響範圍 · Power Cycle 後是否保留或繼續？

Power Cycle 後，Host 重新執行初始化及 queue 建立流程。即使 Host 記憶體中還留有舊 SQE 或 CQE 的內容，也不能把它們當成新 queue 的有效命令或完成結果。Host 必須重建指標、期待的 Phase，以及未完成命令的追蹤資料。

Queue 的重設與影響範圍 · 是否影響其他 Controller 或 Namespace？

Queue 隸屬於建立它的 controller；兩個 controller 使用相同 QID，不表示它們共用同一條 queue。相反地，同一 controller 中共用 CQ 的 SQ，確實會受到該 CQ 的空間及刪除順序影響。另外，queue 重設不等於刪除 namespace，也不會撤銷已完成的資料寫入。

Register 存取 · DNR 與 More 應如何設定？

這次 Register 存取沒有 NVMe CQE，因此 DNR 與 More 不適用。如果之後的 Admin 或 I/O 命令失敗，則解讀那筆命令實際回傳的 CQE，而不是替先前的 Register 寫入指定 Status 位元。

Register 存取 · 是否產生 Asynchronous Event？

Register 存取本身不定義一筆成功通知。若另外發生 Internal Error 等已定義事件，則依該事件的規則處理。controller 尚不能處理 Admin Queue 時，Host 仍須直接檢查初始化狀態，不能改以等待事件判斷是否已完成初始化。

Register 存取 · 是否更新 Error Information Log 或其他 Log？

規範不要求每次 Register 讀寫都建立一筆 Error Information entry。遇到初始化問題時，先保存 CAP、CC、CSTS、CRTO 及各次觀察的時間。若之後 controller 允許讀取 Log，再用錯誤與事件紀錄補足資訊。

Register 存取 · 是否記錄於 Persistent Event Log？

一般 Register 存取不是獨立的 Persistent Event。若另外發生重設、電源變化或硬體錯誤，則在支援 PEL 且符合對應事件條件時，依規則記錄。因此，不能將每次 CC 寫入都當成一次 Power-on or Reset 事件。
