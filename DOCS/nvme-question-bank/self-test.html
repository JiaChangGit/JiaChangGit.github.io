Q149–Q156

Device Self-test

Self-test 將裝置內部診斷結果回報給 Host。先確認能啟動哪種測試，再分清進度、最終結果與失敗欄位有效性。

先練習，再展開每題的 17 項解答。所有數字案例均為教學假設；Status 以 SCT/SC 表示，代碼後的 h 代表十六進位。

先認識本文使用的字詞

Controller / namespace
controller 接收命令並管理存取；namespace 是命令可指定的一份邏輯儲存空間。NVM subsystem 則包含 controller 與非揮發儲存資源，同一 subsystem 可以有多個 controller。
SQ / CQ / SQE / CQE
Submission Queue（SQ）是提交佇列，Completion Queue（CQ）是完成佇列；SQE 與 CQE 分別是其中的一筆命令及完成項目。QID 識別 queue，CID 區分同一 SQ 中尚未完成的命令，NSID 則識別 namespace。
Register / Identify / Feature / Log
Register 提供可存取的控制或狀態資訊；Identify 查詢物件的能力與屬性；Feature 用來讀取或變更工作設定；Log Page 回報特定種類的狀態或紀錄。FID、LID、CNS、CSI 則分別用來選擇 Feature、Log Page、Identify 資料結構及命令集。
index / offset / zero-based
index 指出清單中的第幾筆，通常從 0 起算；offset 表示與起點相隔多遠，解讀時必須確認單位。若數量欄位採 zero-based 編碼，實際數量等於欄位值加 1；但不是所有欄位看到 0 都要加 1。Dword 是 4 bytes，1 byte 是 8 bits。
Scope / reset / retention
scope 表示操作影響哪些物件；retention 表示狀態是否保留。清除 CC.EN 所觸發的 Controller Reset，是 Controller Level Reset（CLR）的一種。同屬 CLR 的不同觸發方式，仍可能採用不同的 Register 保留規則。

啟動、執行、結果是三種資訊

啟動 CQE 成功，不表示測試通過。

觀察欄位／介面用途
可否執行OACS、DSTO確認支援與並行條件
目前執行Current Operation、Completion Percentage了解還在做什麼
本次結果最新 Result 的 DSTC、DSTR辨識通過、失敗或中止
失敗細節VDINFO、SEGN、FLBA只有有效欄位才可推論

舉例看懂：Short 在 CLR 下需要中止；Extended 有跨 CLR 持續與失電恢復的規則。不能只看測試名稱都有 Self-test，就要求相同 reset 結果。

先把觀念接起來

教學 1 · 測試範圍先於結果解釋

NSID=0、指定 namespace 與廣播選擇有不同範圍。先保存啟動參數，才知道失敗結果對應哪個對象。若測試只涵蓋某個 namespace，不能將成功結果擴大成所有 namespace 都已測過。

教學 2 · 有效位元是資料可否使用的前提

Result 結構中有很多欄位，但不代表每次都有效。FLBA 只有有效條件成立時，才是可用的失敗位置；它也不是全部壞 LBA 清單。先讀 DSTR 與 VDINFO，再看細節，才不會將保留或無效 bytes 當成真實故障位置。

教學 3 · 比較新舊結果比只看目前 idle 更可靠

測試開始前先保存最新結果；結束後再比較最前面的新紀錄。Current Operation 回到 idle 只表示現在沒有測試進行，可能是通過、失敗或中止。再搭配時間、測試種類與結果代碼，才能說清楚這次發生了什麼。

Q149 如何確認 Device Self-test 支援與可測範圍？

先試著說明正常流程，並舉出一個未滿足執行條件的例子，再展開解答核對。

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    Self-test 提供裝置內部的診斷流程，可檢查 controller 與指定媒體，但它不能取代 Host 對資料內容的完整驗證。

  2. 02 它的影響範圍是什麼？

    NSID=0 只測 controller；特定 active NSID 加入該 namespace；FFFFFFFFh 包含開始時此 controller 可存取的全部 attached namespaces。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    Identify.OACS 確認支援，DSTO.SDSO 決定單一測試限制的範圍，EDSTT 提供延伸測試時間。

  4. 04 涉及哪些 Command 與重要欄位？

    Device Self-test 使用 STC 選操作；Get Log Page LID06h 查目前測試與最近 20 次結果。

  5. 05 正常流程及先後順序是什麼？

    先確認能力與 namespace 狀態，保存舊 Log，再啟動選定測試並追蹤新狀態。

  6. 06 成功時應回傳什麼結果？

    啟動成功表示背景測試已開始；真正通過要看新 Result 的 DSTR=0，而非只看啟動 CQE。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    不存在的 NSID 回 Invalid Namespace or Format；已配置但 inactive 的 NSID 回 Invalid Field in Command，這兩種情況不能混寫。

  8. 08 DNR 與 More 應如何設定？

    收到 CQE 時才有 DNR 與 More 可判讀。本題沒有另行指定固定值，請依本冊的共用規則，搭配實際完成條件判斷。 本冊完整規則

  9. 09 是否產生 Asynchronous Event？

    本規格沒有通用的 Device Self-test Completed AER。 本冊完整規則

  10. 10 是否更新 Error Information Log 或其他 Log？

    短程／延伸測試完成或被中止時，先建立最新 Self-test Result，再將目前操作設為 idle。 本冊完整規則

  11. 11 是否記錄於 Persistent Event Log？

    PEL 沒有通用的逐次 Self-test 結果事件；完整測試歷史以 LID06h 為主。 本冊完整規則

  12. 12 Controller Reset 後是否保留或繼續？

    影響執行 controller 的 Controller Level Reset 必須中止短程測試；延伸測試則必須跨 CLR 保留，並在重設完成後恢復。 本冊完整規則

  13. 13 NVM Subsystem Reset 後是否保留或繼續？

    Subsystem Reset 會對其範圍內的 controller 造成 CLR：短程測試被中止，延伸測試必須恢復。 本冊完整規則

  14. 14 Power Cycle 後是否保留或繼續？

    延伸測試必須在電源恢復後繼續；短程測試則不具有這項延續要求。 本冊完整規則

  15. 15 是否影響其他 Controller 或 Namespace？

    測試由收到命令的 controller 執行，NSID 決定包含哪些 namespace。 本冊完整規則

  16. 16 Identify、Feature、Log 與 Command 行為是否一致？

    核對 OACS、實際 STC、NSID 與 Log 的測試代碼，確認啟動的是預期測試。

  17. 17 結果不符預期時，第一個要檢查什麼？

    先確認「不存在」與「存在但未 active」的差別。

Q150 Short 與 Extended Self-test 有何差別？

先試著說明正常流程，並舉出一個未滿足執行條件的例子，再展開解答核對。

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    兩者提供不同深度與時間的診斷；實際 segments 與測試內容由廠商設計，規格中的 RAM／媒體檢查圖只是教學示例。

  2. 02 它的影響範圍是什麼？

    兩者都依 NSID 選範圍，且可能因共享資源影響其他工作的效能。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    EDSTT 是延伸測試時間資訊；短程測試建議在 2 分鐘內完成。這些 should 不應提升為所有情況的硬性 shall。

  4. 04 涉及哪些 Command 與重要欄位？

    STC=1 啟動 Short，2 啟動 Extended；Log 的 DSTOS 表示正在執行哪種操作，DSTCS 表示完成百分比。

  5. 05 正常流程及先後順序是什麼？

    依所需診斷與可接受影響選測試，保存開始時間並查進度；若命令需要暫停測試，controller 先暫停、完成該命令，再恢復測試。

  6. 06 成功時應回傳什麼結果？

    測試結束後由 Result 判定成功或哪個 segment 失敗；短程通過不保證延伸測試也必然通過。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    關鍵差異是 Reset：Short 必須被影響它的 CLR 中止；Extended 必須跨 CLR 與恢復供電後繼續。

  8. 08 DNR 與 More 應如何設定？

    收到 CQE 時才有 DNR 與 More 可判讀。本題沒有另行指定固定值，請依本冊的共用規則，搭配實際完成條件判斷。 本冊完整規則

    本規格沒有通用的 Device Self-test Completed AER。 本冊完整規則

  10. 10 是否更新 Error Information Log 或其他 Log？

    短程／延伸測試完成或被中止時，先建立最新 Self-test Result，再將目前操作設為 idle。 本冊完整規則

  11. 11 是否記錄於 Persistent Event Log？

    PEL 沒有通用的逐次 Self-test 結果事件；完整測試歷史以 LID06h 為主。 本冊完整規則

  12. 12 Controller Reset 後是否保留或繼續？

    影響執行 controller 的 Controller Level Reset 必須中止短程測試；延伸測試則必須跨 CLR 保留，並在重設完成後恢復。 本冊完整規則

  13. 13 NVM Subsystem Reset 後是否保留或繼續？

  14. 14 Power Cycle 後是否保留或繼續？

    延伸測試必須在電源恢復後繼續；短程測試則不具有這項延續要求。 本冊完整規則

  15. 15 是否影響其他 Controller 或 Namespace？

    測試由收到命令的 controller 執行，NSID 決定包含哪些 namespace。 本冊完整規則

  16. 16 Identify、Feature、Log 與 Command 行為是否一致？

    驗證時間時保留其他工作與暫停因素；驗證 Reset 時分別套用兩種測試規則。

  17. 17 結果不符預期時，第一個要檢查什麼？

    先查 STC，不要把 Extended 的持續性套到 Short，或反過來。

Q151 Self-test 進行中再次啟動或要求中止會怎樣？

先試著說明正常流程，並舉出一個未滿足執行條件的例子，再展開解答核對。

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    避免同一限制範圍同時跑多個測試，並提供明確的背景操作中止方法。中止 Self-test 操作應使用 STC=Fh。

  2. 02 它的影響範圍是什麼？

    DSTO.SDSO=0 以 controller 判斷是否已有測試；SDSO=1 則以 subsystem 判斷。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    先讀 DSTO 與 LID06h；只看目前 controller 的 Host outstanding 清單不足以知道另一端是否已開始測試。

  4. 04 涉及哪些 Command 與重要欄位？

    STC1／2／3 為新操作；Fh 中止；Eh 是廠商特定，互動規則也可能不同。

  5. 05 正常流程及先後順序是什麼？

    已有測試時送 Fh，controller 先中止、建立最新結果，再將目前操作設為 idle，最後完成命令。

  6. 06 成功時應回傳什麼結果？

    沒有測試時送 Fh 仍成功，且不修改 Self-test Log；不能為這次空中止捏造新結果。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    已有測試時再送 1／2／3，回 Device Self-test In Progress（1/1Dh）；不能要求它默默重啟原測試。

  8. 08 DNR 與 More 應如何設定？

    收到 CQE 時才有 DNR 與 More 可判讀。本題沒有另行指定固定值，請依本冊的共用規則，搭配實際完成條件判斷。 本冊完整規則

  9. 09 是否產生 Asynchronous Event？

    本規格沒有通用的 Device Self-test Completed AER。 本冊完整規則

  10. 10 是否更新 Error Information Log 或其他 Log？

    短程／延伸測試完成或被中止時，先建立最新 Self-test Result，再將目前操作設為 idle。 本冊完整規則

  11. 11 是否記錄於 Persistent Event Log？

    PEL 沒有通用的逐次 Self-test 結果事件；完整測試歷史以 LID06h 為主。 本冊完整規則

  12. 12 Controller Reset 後是否保留或繼續？

    影響執行 controller 的 Controller Level Reset 必須中止短程測試；延伸測試則必須跨 CLR 保留，並在重設完成後恢復。 本冊完整規則

  13. 13 NVM Subsystem Reset 後是否保留或繼續？

    Subsystem Reset 會對其範圍內的 controller 造成 CLR：短程測試被中止，延伸測試必須恢復。 本冊完整規則

  14. 14 Power Cycle 後是否保留或繼續？

    延伸測試必須在電源恢復後繼續；短程測試則不具有這項延續要求。 本冊完整規則

  15. 15 是否影響其他 Controller 或 Namespace？

    測試由收到命令的 controller 執行，NSID 決定包含哪些 namespace。 本冊完整規則

  16. 16 Identify、Feature、Log 與 Command 行為是否一致？

    核對中止 CQE 前 Log 更新順序，以及新結果 DSTR=1，避免把 idle 當成唯一證據。

  17. 17 結果不符預期時，第一個要檢查什麼？

    先查使用的是 STC=Fh，還是誤用 Abort 去中止早已完成的啟動命令。

Q152 Current Operation 與 Completion Percentage 如何解讀？

先試著說明正常流程，並舉出一個未滿足執行條件的例子，再展開解答核對。

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    Log 開頭描述正在執行的工作，後面的 Result List 描述已結束的測試。兩者可能同時存在，不應用舊結果取代當前進度。

  2. 02 它的影響範圍是什麼？

    依測試的 controller／共享範圍讀正確 Log，並保存取樣時間。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    先確認支援，再使用 LID06h 的 CDSTO、CDSTC 與 RDS1。

  4. 04 涉及哪些 Command 與重要欄位？

    DSTOS=0 為無操作，1 為 Short，2 為 Extended，3 為 Host-Initiated Refresh；DSTCS 的值 25 代表 25%，不是零起算 26%。

  5. 05 正常流程及先後順序是什麼？

    先讀 DSTOS，只有有操作時才解讀 DSTCS；idle 時應忽略百分比，再查看最新 Result。

  6. 06 成功時應回傳什麼結果？

    Short／Extended 結束時，必須先建立結果才清 DSTOS。讀到 idle 並搭配新 Result，才知道操作如何結束。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    百分比不動不一定失敗，可能測試在某個 segment 或被其他命令暫停；也不能把 100%欄位當成全部結果。

  8. 08 DNR 與 More 應如何設定？

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    測試結果需要保留原因，才能區分裝置診斷失敗與 Host 主動中止。Extended 因 Reset 暫停後恢復，不應被錯記成測試已失敗。

  2. 02 它的影響範圍是什麼？

    結果屬於一次測試，包含當時測試代碼與時間；不是啟動命令的 CQE Status。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

  4. 04 涉及哪些 Command 與重要欄位？

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    PEL 沒有通用的逐次 Self-test 結果事件；完整測試歷史以 LID06h 為主。 本冊完整規則

  12. 12 Controller Reset 後是否保留或繼續？

共用規則：各題連到的完整解釋

這些規則在本冊只完整說明一次。返回剛才的題目可用瀏覽器「上一頁」；特定命令或 Feature 的明文例外優先。

命令完成、事件與紀錄 · DNR 與 More 應如何設定？

只有收到 CQE，才有 DNR 與 More 可供判讀。DNR=1 表示相同命令即使重送到此 NVM subsystem 的任一 controller，仍預期會失敗；DNR=0 則只表示可能成功。除非個別錯誤條件另有明定，不能只看 Status 名稱就要求 DNR=1。More=1 表示 Error Information Log 有這筆命令的補充資訊。SCT=SC=0 時，DNR 應為 0。

本主題的共用條件 · 是否產生 Asynchronous Event？

本規格沒有通用的 Device Self-test Completed AER。正常完成應讀 LID06h 確認；測試發現診斷失敗時，另依 Diagnostic Failure 錯誤事件及其回報條件處理。

本主題的共用條件 · 是否更新 Error Information Log 或其他 Log？

短程／延伸測試完成或被中止時，先建立最新 Self-test Result，再將目前操作設為 idle。診斷欄位要先檢查 valid bits；不是每個失敗結果都具有有效 NSID、LBA、SCT 與 SC。

本主題的共用條件 · 是否記錄於 Persistent Event Log？

PEL 沒有通用的逐次 Self-test 結果事件；完整測試歷史以 LID06h 為主。若同時發生可記錄的硬體錯誤或 Reset，則是那些事件另行記錄，不可拿來取代 Self-test Result。

本主題的共用條件 · Controller Reset 後是否保留或繼續？

影響執行 controller 的 Controller Level Reset 必須中止短程測試；延伸測試則必須跨 CLR 保留，並在重設完成後恢復。恢復的 segment 由廠商決定，規範建議只需重做被中斷的最後 segment。

本主題的共用條件 · NVM Subsystem Reset 後是否保留或繼續？

Subsystem Reset 會對其範圍內的 controller 造成 CLR：短程測試被中止，延伸測試必須恢復。不能把重新建立 Admin Queue 與重新開始整個延伸測試當成同一件事。

本主題的共用條件 · Power Cycle 後是否保留或繼續？

延伸測試必須在電源恢復後繼續；短程測試則不具有這項延續要求。恢復後先讀 DSTOS、進度與最新結果，不能只因 power cycle 就期待兩者都新增 Reset-aborted 結果。

本主題的共用條件 · 是否影響其他 Controller 或 Namespace？

測試由收到命令的 controller 執行，NSID 決定包含哪些 namespace。DSTO.SDSO 決定同時只能有一個測試的限制是在 controller 或 subsystem；即使沒有測試其他 namespace，共享資源仍可能使其他工作變慢。
