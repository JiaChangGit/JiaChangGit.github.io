Q22–Q30

Doorbell、Queue Full 與 Wrap-around

Doorbell 告訴 controller，Host 的指標已前進到哪個位置；Phase 則讓 Host 分辨 CQ 中的是新完成結果，還是上一圈留下的資料。本冊將位置與有效性一起說明，幫助你正確處理繞回及空間釋放，避免將正常繞回誤判成倒退，或把舊 CQE 處理兩次。

先練習，再展開每題的 17 項解答。所有數字案例均為教學假設；Status 以 SCT/SC 表示，代碼後的 h 代表十六進位。

先認識本文使用的字詞

Controller / namespace
controller 接收命令並管理存取；namespace 是命令可指定的一份邏輯儲存空間。NVM subsystem 則包含 controller 與非揮發儲存資源，同一 subsystem 可以有多個 controller。
SQ / CQ / SQE / CQE
Submission Queue（SQ）是提交佇列，Completion Queue（CQ）是完成佇列；SQE 與 CQE 分別是其中的一筆命令及完成項目。QID 識別 queue，CID 區分同一 SQ 中尚未完成的命令，NSID 則識別 namespace。
Register / Identify / Feature / Log
Register 提供可存取的控制或狀態資訊；Identify 查詢物件的能力與屬性；Feature 用來讀取或變更工作設定；Log Page 回報特定種類的狀態或紀錄。FID、LID、CNS、CSI 則分別用來選擇 Feature、Log Page、Identify 資料結構及命令集。
index / offset / zero-based
index 指出清單中的第幾筆，通常從 0 起算；offset 表示與起點相隔多遠，解讀時必須確認單位。若數量欄位採 zero-based 編碼，實際數量等於欄位值加 1；但不是所有欄位看到 0 都要加 1。Dword 是 4 bytes，1 byte 是 8 bits。
Scope / reset / retention
scope 表示操作影響哪些物件；retention 表示狀態是否保留。清除 CC.EN 所觸發的 Controller Reset，是 Controller Level Reset（CLR）的一種。同屬 CLR 的不同觸發方式，仍可能採用不同的 Register 保留規則。

8 格 CQ：把繞回與 Phase 放在同一張表

CQ 索引回到 0，不表示位置 0 裡的舊資料重新有效。Host 還要比對這一圈期待的 Phase，才能確認是否已有新 CQE。

時點Host 下一格／預期 Phase讀取結果與動作
初始化位置 0，預期 P=1；記憶體 P 初始化為 0目前沒有新完成
第一輪末端位置 7，預期 P=1讀到 P=1：處理 CQE，下一格回 0，預期改 0
第二輪起點位置 0，預期 P=0若仍是舊 P=1，不處理；讀到新 P=0 才處理
通知 controller 已處理的範圍CQ Head 從 7 更新成 2表示位置 7、0、1 的 3 筆 CQE 已處理完畢，不是指標倒退 5 格

舉例看懂：這次前進距離為 (2−7+8) mod 8=3，所以 Host 將 Doorbell 寫成位置 2，通知 controller 有 3 格已可重用；不是因為寫了 2，就表示釋放 2 格。Phase 用來確認 Host 讀到的是新 CQE，CQ Head Doorbell 則通知 controller 哪些 CQE 已處理完畢，兩者負責不同工作。

先把觀念接起來

教學 1 · 指標是位置，差值才是數量

Doorbell 中的 2 表示索引位置 2，不表示這次提交了 2 筆。對 8 個位置的環狀 queue，從 7 前進到 2，經過的是 7、0、1，共 3 個位置。如果只用一般數字大小比較，看到 2<7 就判定倒退，便會把正常繞回誤認為非法操作。

教學 2 · Phase 不是成功位元

Phase 只用來判斷這個 CQ 位置是否包含目前這一圈的新完成結果。即使 Phase 有效，CQE 內仍可能是失敗 Status；反過來，舊 CQE 即使留有 Success，只要 Phase 不符合期待值，就不能再處理一次。因此，先確認有效性，再解讀 SCT 與 SC，才能避免誤讀殘留資料。

教學 3 · 為何 Host 處理完還要寫 CQ Head

Host 在自己的程式中將 CQE 標記為已處理，並不會自動通知 controller。必須更新 CQ Head Doorbell，controller 才能得知哪些位置已可重用。如果漏掉這一步，即使 Host 已處理完所有結果，controller 仍可能因 CQ Full 而停住。這時應檢查空間釋放流程，而不是先把停滯歸因於媒體延遲。

Q22 Host 應在什麼時候更新 SQ Tail Doorbell 與 CQ Head Doorbell？

先試著說明正常流程，並舉出一個未滿足執行條件的例子，再展開解答核對。

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    Host 需要通知 controller，哪些 SQE 已經準備好，以及哪些 CQE 已經處理完畢。更新 SQ Tail 是提交新命令；更新 CQ Head 則是釋放已處理的完成位置，讓 controller 可以再次使用。

  2. 02 它的影響範圍是什麼？

    每條 SQ／CQ 各有自己的 Doorbell；更新其中一條不會自動更新另一條。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    更新前，先確認 queue 仍然有效，而且 controller 已就緒。提交命令時也要確認 SQ 有足夠的可用位置，再依 CAP.DSTRD 找到正確的 Doorbell Register。

  4. 04 涉及哪些 Command 與重要欄位？

    SQ Tail 指向下一個可放入 SQE 的位置；CQ Head 指向下一個等待 Host 處理的 CQE。Doorbell 要寫入更新後的索引值，而不是這次新增或處理了幾筆。

  5. 05 正常流程及先後順序是什麼？

    提交時，Host 先寫好完整的 SQE，並依平台要求確保 controller 能看見這些記憶體內容，之後才更新 SQ Tail。接收完成結果時，則先讀取並處理有效的 CQE，再更新 CQ Head。Host 可以一次提交多筆命令，也可以一次釋放多個已處理的完成位置。

  6. 06 成功時應回傳什麼結果？

    更新 SQ Tail 後，controller 才能得知哪些新命令可以讀取；更新 CQ Head 後，controller 才能得知哪些完成位置可以重用。因此，CQ Head 前進並不表示 Host 提交了新的 I/O 命令。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    如果 Host 尚未處理 CQE 就提前釋放位置，該 CQE 可能被後續的完成結果覆寫。如果 SQE 尚未準備好就更新 Tail，controller 也可能讀到不完整的命令。這些都是使用順序錯誤，不能預期 controller 一定會回傳某個固定的錯誤 CQE。

  8. 08 DNR 與 More 應如何設定？

    本次 MMIO 存取沒有 NVMe CQE，因此 DNR／More 不適用。 本冊完整規則

  9. 09 是否產生 Asynchronous Event？

    Register 存取本身不產生成功事件。若另外發生硬體錯誤等事件，則依該事件自己的條件判斷。 本冊完整規則

  10. 10 是否更新 Error Information Log 或其他 Log？

    不要求每次 Register 讀寫都新增錯誤紀錄。先保留 Register 值及時間，再補充 controller 當時允許讀取的診斷資料。 本冊完整規則

  11. 11 是否記錄於 Persistent Event Log？

    一般 Register 存取不是 PEL 事件。若操作同時引發 Reset 或硬體錯誤，再依支援能力與對應事件條件判斷。 本冊完整規則

  12. 12 Controller Reset 後是否保留或繼續？

    清除 CC.EN 後，I/O queue 失效，Admin Queue 指標重設。即使基底位址保留，舊 completion 也不能繼續當成有效結果。 本冊完整規則

  13. 13 NVM Subsystem Reset 後是否保留或繼續？

    受影響 controller 的 queue 必須重建。這次重設的來源不同，不能直接套用清除 CC.EN 時的 Register 保留例外。 本冊完整規則

  14. 14 Power Cycle 後是否保留或繼續？

    重新初始化 queue，並重建 Host 的命令追蹤資料。記憶體中殘留的舊內容，不是新 queue 的有效命令或完成結果。 本冊完整規則

  15. 15 是否影響其他 Controller 或 Namespace？

    Queue 隸屬於各自的 controller。多條 SQ 共用同一 CQ 時，才會共同受到這條 CQ 的可用空間及使用期間影響。 本冊完整規則

  16. 16 Identify、Feature、Log 與 Command 行為是否一致？

    驗證時，依時間先後比對 Host 寫入 SQE、更新 Tail、controller 寫入帶有新 Phase 的 CQE，以及 Host 更新 Head 這四個動作。它們分別代表準備命令、提交命令、回報完成及釋放完成位置，不能互相替代。

  17. 17 結果不符預期時，第一個要檢查什麼？

    先檢查 Doorbell 是否誤寫成「這次處理的筆數」。正確值應是更新後的索引；索引到達 queue 尾端後，要依 queue 大小回到起點。

Q23 Doorbell 值重複、倒退、超過 Queue 範圍或寫到錯誤 QID 時，可能造成什麼問題？

先試著說明正常流程，並舉出一個未滿足執行條件的例子，再展開解答核對。

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    判斷指標移動是否合法，避免把環狀索引當成只會遞增的計數器。

  2. 02 它的影響範圍是什麼？

    錯誤會影響被寫入 Doorbell 的 queue。如果是多條 SQ 共用的 CQ，影響還可能延伸到這些 SQ。另外，向不存在的 queue 寫 Doorbell，與向有效 queue 寫入非法值，是兩種不同情況。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    判斷指標是否合法，需要知道 queue 大小、原來的指標、可用或已處理的位置數量，以及 Doorbell 對應的 QID。只看新寫入的數字，無法判斷這次移動是否正確。

  4. 04 涉及哪些 Command 與重要欄位？

    合法索引介於 0 與 size−1。再次寫入相同的值，不表示新增了一批位置；寫入較小的值也不一定是倒退，因為指標可能剛好跨過 queue 尾端，回到起點。

  5. 05 正常流程及先後順序是什麼？

    例如，queue 大小為 8，Tail 從 6 變成 1，代表前進 3 個位置。這次提交是否合法，還要確認原本有 3 個可用位置，而且對應的 SQE 都已準備好。相反地，從 6 再寫回 6，不能用來表示提交了整整一圈的命令。

  6. 06 成功時應回傳什麼結果？

    合法的指標更新，能讓 controller 算出新提交或新釋放的位置數量。不過，Host 不應靠讀回 Doorbell 來驗證寫入結果，因為 Doorbell 的讀回值由廠商定義。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    向有效 queue 寫入非法值時，適用 Invalid Doorbell Write Value 的非同步錯誤處理；向不存在的 queue 寫 Doorbell 時，結果則未定義。前者的事件資訊碼不是這次 MMIO 寫入的 CQE Status，兩者不能混為一談。

  8. 08 DNR 與 More 應如何設定？

    本次 MMIO 存取沒有 NVMe CQE，因此 DNR／More 不適用。 本冊完整規則

  9. 09 是否產生 Asynchronous Event？

    依 Base §3.3.1.2，若 Doorbell 值非法，而且有尚未完成的 Asynchronous Event Request，controller 會透過它回報對應錯誤事件。受影響的 SQ 可以完成已取得的命令，但不再取得新命令；Host 則需刪除並重建 queue。

  10. 10 是否更新 Error Information Log 或其他 Log？

    這是 Error 類型的非同步事件，應讀取事件指定的 Log，取得補充資料。MMIO 寫入本身沒有 More 位元。另外，若是寫到不存在 QID 的 Doorbell，規範已將結果列為未定義，不能再要求它一定產生 Log。

  11. 11 是否記錄於 Persistent Event Log？

    一般 Register 存取不是 PEL 事件。若操作同時引發 Reset 或硬體錯誤，再依支援能力與對應事件條件判斷。 本冊完整規則

  12. 12 Controller Reset 後是否保留或繼續？

    清除 CC.EN 後，I/O queue 失效，Admin Queue 指標重設。即使基底位址保留，舊 completion 也不能繼續當成有效結果。 本冊完整規則

  13. 13 NVM Subsystem Reset 後是否保留或繼續？

    受影響 controller 的 queue 必須重建。這次重設的來源不同，不能直接套用清除 CC.EN 時的 Register 保留例外。 本冊完整規則

  14. 14 Power Cycle 後是否保留或繼續？

    重新初始化 queue，並重建 Host 的命令追蹤資料。記憶體中殘留的舊內容，不是新 queue 的有效命令或完成結果。 本冊完整規則

  15. 15 是否影響其他 Controller 或 Namespace？

    Queue 隸屬於各自的 controller。多條 SQ 共用同一 CQ 時，才會共同受到這條 CQ 的可用空間及使用期間影響。 本冊完整規則

  16. 16 Identify、Feature、Log 與 Command 行為是否一致？

    先依原指標、queue 大小及剩餘空間判斷移動是否合法，不要只比較新舊數字的大小。若發生 Doorbell 錯誤，還應一起檢查對應的非同步事件，以及受影響 queue 是否停止取得新命令。

  17. 17 結果不符預期時，第一個要檢查什麼？

    先用 (new−old+size) modulo size 算出前進量，再確認這些位置是否確實可以提交或釋放。

Q24 Host 如何根據 CAP.DSTRD 計算每個 SQ 與 CQ Doorbell 的位置？

先試著說明正常流程，並舉出一個未滿足執行條件的例子，再展開解答核對。

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    Host 必須根據 NVMe Register 的起始位址及 QID，找出要更新的 Doorbell 位址，才能把通知送到正確的 queue。

  2. 02 它的影響範圍是什麼？

    Doorbell 位址以該 controller 的 MMIO 起始位址為基準，不是以 SQ 或 CQ 記憶體的起始位址為基準。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    PCI BAR0／BAR1 用來找出 NVMe Register 空間的位置；CAP.DSTRD 則用來計算相鄰 Doorbell 的位址間距。

  4. 04 涉及哪些 Command 與重要欄位？

    stride=4×2^DSTRD；SQy offset=1000h+2y×stride；CQy offset=1000h+(2y+1)×stride。每個 Doorbell 本身仍是 32 bits。

  5. 05 正常流程及先後順序是什麼？

    先取得映射後的 Register 起始位址，再由 DSTRD 算出 stride。接著依 QID 選用 SQ 或 CQ 的公式，算出 Doorbell 位址，最後使用規定的存取寬度執行 MMIO 寫入。

  6. 06 成功時應回傳什麼結果？

    例：DSTRD=2、QID=3，SQ offset=1060h、CQ offset=1070h。把各 offset 加到 controller base，才是完整位址。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    計算位址本身不會產生 Command Status。如果算錯位址，可能寫到另一條有效 queue，也可能形成結果未定義的存取。controller 無法因此得知 Host 原本想更新哪一條 queue。

  8. 08 DNR 與 More 應如何設定？

    本次 MMIO 存取沒有 NVMe CQE，因此 DNR／More 不適用。 本冊完整規則

  9. 09 是否產生 Asynchronous Event？

    Register 存取本身不產生成功事件。若另外發生硬體錯誤等事件，則依該事件自己的條件判斷。 本冊完整規則

  10. 10 是否更新 Error Information Log 或其他 Log？

    不要求每次 Register 讀寫都新增錯誤紀錄。先保留 Register 值及時間，再補充 controller 當時允許讀取的診斷資料。 本冊完整規則

  12. 12 Controller Reset 後是否保留或繼續？

    清除 CC.EN 後，I/O queue 失效，Admin Queue 指標重設。即使基底位址保留，舊 completion 也不能繼續當成有效結果。 本冊完整規則

  15. 15 是否影響其他 Controller 或 Namespace？

Q29 Host 釋放 CQ 空間後，Controller 應如何恢復 Command 處理？

先試著說明正常流程，並舉出一個未滿足執行條件的例子，再展開解答核對。

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    CQ 空間釋放後，原本受容量限制的工作便能繼續。CQ Full 本身不表示 queue 已失效，因此不需要只因空間曾經用完就重新建立 queue。

  2. 02 它的影響範圍是什麼？

    Host 釋放的是這條 CQ 中的完成位置，讓關聯 SQ 的命令可以回報結果。這不會改變可建立的 queue 數量，也不會改變 namespace 的能力。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    先確認 queue 仍然存在，而且沒有其他停止處理的原因，例如正在重設、CSTS.CFS 已設定，或 queue 處於 Processing Paused 狀態。

  4. 04 涉及哪些 Command 與重要欄位？

    Host 將新的 Head 索引寫入 CQ Head Doorbell。controller 根據 Head 的前進量得知哪些位置可以重用，後續寫入 CQE 時仍須使用正確的 Phase。

  5. 05 正常流程及先後順序是什麼？

    Host 處理 CQE 並更新 Head 後，controller 才得知有新的可用空間，接著可以寫入等待回報的完成結果，並繼續處理受影響的工作。實際執行次序仍受仲裁設定及其他正常條件限制。

  6. 06 成功時應回傳什麼結果？

    已釋放的位置可以再次使用，不必重建 queue。不過，規範沒有為所有裝置訂出同一個固定時間，要求從 Head 更新到下一筆 CQE 出現必須相隔多久。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    正確更新 CQ Head 不會另外產生一筆成功 CQE。如果 Head 值非法，應依 Doorbell 的錯誤處理規則判斷，不能套用 Create Queue 的錯誤 Status。

  8. 08 DNR 與 More 應如何設定？

    收到 CQE 時才有 DNR 與 More 可判讀。本題沒有另行指定固定值，請依本冊的共用規則，搭配實際完成條件判斷。 本冊完整規則

  9. 09 是否產生 Asynchronous Event？

    正常完成不保證會回報非同步事件。若另有事件發生，還須確認支援能力、通知設定，以及是否有等待中的 AER。 本冊完整規則

  10. 10 是否更新 Error Information Log 或其他 Log？

    依完成結果與記錄條件核對 Error Information，不能直接用失敗命令的數量推算新增 entry 數。完整條件見本冊共用規則。 本冊完整規則

  11. 11 是否記錄於 Persistent Event Log？

    PEL 記錄符合條件的事件，不是每條命令的執行歷史。只有事件受支援且符合記錄條件時，才依規則要求新增紀錄。 本冊完整規則

  12. 12 Controller Reset 後是否保留或繼續？

    清除 CC.EN 後，I/O queue 失效，Admin Queue 指標重設。即使基底位址保留，舊 completion 也不能繼續當成有效結果。 本冊完整規則

  13. 13 NVM Subsystem Reset 後是否保留或繼續？

    受影響 controller 的 queue 必須重建。這次重設的來源不同，不能直接套用清除 CC.EN 時的 Register 保留例外。 本冊完整規則

  14. 14 Power Cycle 後是否保留或繼續？

    重新初始化 queue，並重建 Host 的命令追蹤資料。記憶體中殘留的舊內容，不是新 queue 的有效命令或完成結果。 本冊完整規則

  15. 15 是否影響其他 Controller 或 Namespace？

    Queue 隸屬於各自的 controller。多條 SQ 共用同一 CQ 時，才會共同受到這條 CQ 的可用空間及使用期間影響。 本冊完整規則

  16. 16 Identify、Feature、Log 與 Command 行為是否一致？

    檢查後續 CQE 是否寫入合法且已釋放的位置，並比較共用這條 CQ 的 SQ 與其他獨立 SQ 的處理進度。

  17. 17 結果不符預期時，第一個要檢查什麼？

    先確認 Head 是否寫到正確 CQ 的 Register。如果 QID 用錯，Host 雖然執行了寫入，原本已滿的 CQ 卻沒有收到空間已釋放的通知。

Q30 多個 SQ 共用一個 CQ 時，Host 如何依 SQID 與 CID 辨識 Completion 來源？

先試著說明正常流程，並舉出一個未滿足執行條件的例子，再展開解答核對。

展開完整解答 · 17 個觀察面向

  1. 01 這個功能要解決什麼問題？

    Host 必須將每筆 completion 配對到原來的命令，才能交付正確結果。CID 只要求在同一條 SQ 的未完成命令之間保持唯一；不同 SQ 可以同時使用相同 CID。

  2. 02 它的影響範圍是什麼？

    Host 追蹤命令時，必須一起考慮 controller、SQ 的這次建立與使用期間、SQID 及 CID。controller 與 queue 的使用期間是 Host 自己維護的上下文，並不是 CQE 裡額外增加的欄位。

  3. 03 支援能力從哪個 Register、Identify 欄位、Feature 或 Log Page 確認？

    Host 使用建立 queue 時記錄的 SQ 與 CQ 對應關係，以及未完成命令的追蹤表，來尋找原命令。Identify 不會回報每筆未完成命令的位置。

  4. 04 涉及哪些 Command 與重要欄位？

    CQE.SQID 指出命令來自哪條 SQ，CID 則指出該 SQ 內的哪筆命令。SQHD 回報 controller 已消費到的 SQ 位置，不代表這筆完成命令原先所在的 SQ 位置。

  5. 05 正常流程及先後順序是什麼？

    Host 先確認 CQE 的 Phase 有效，再用 SQID 與 CID 找到原命令，處理 Status 及回傳資料，並更新該 SQ 的 Head 紀錄。這些工作完成後，才釋放 CQ 中的這個位置。

  6. 06 成功時應回傳什麼結果？

    例如 SQ1 的 CID9 與 SQ2 的 CID9 可以共用同一條 CQ。即使兩筆命令以相反順序完成，Host 仍可透過 SQID 與 CID 分別找到正確的原命令。

  7. 07 不支援、非法參數或錯誤順序時的 Status？

    同一條 SQ 中，未完成命令的 CID 重複時，可能回報 Command ID Conflict（0/03h）。controller 為了偵測衝突，會搜尋多少筆既有命令，由實作決定；這不免除 Host 維持 CID 唯一性的責任。

  8. 08 DNR 與 More 應如何設定？

    收到 CQE 時才有 DNR 與 More 可判讀。本題沒有另行指定固定值，請依本冊的共用規則，搭配實際完成條件判斷。 本冊完整規則

  9. 09 是否產生 Asynchronous Event？

    正常完成不保證會回報非同步事件。若另有事件發生，還須確認支援能力、通知設定，以及是否有等待中的 AER。 本冊完整規則

  10. 10 是否更新 Error Information Log 或其他 Log？

    依完成結果與記錄條件核對 Error Information，不能直接用失敗命令的數量推算新增 entry 數。完整條件見本冊共用規則。 本冊完整規則

  11. 11 是否記錄於 Persistent Event Log？

    PEL 記錄符合條件的事件，不是每條命令的執行歷史。只有事件受支援且符合記錄條件時，才依規則要求新增紀錄。 本冊完整規則

  12. 12 Controller Reset 後是否保留或繼續？

    清除 CC.EN 後，I/O queue 失效，Admin Queue 指標重設。即使基底位址保留，舊 completion 也不能繼續當成有效結果。 本冊完整規則

  13. 13 NVM Subsystem Reset 後是否保留或繼續？

    受影響 controller 的 queue 必須重建。這次重設的來源不同，不能直接套用清除 CC.EN 時的 Register 保留例外。 本冊完整規則

  14. 14 Power Cycle 後是否保留或繼續？

    重新初始化 queue，並重建 Host 的命令追蹤資料。記憶體中殘留的舊內容，不是新 queue 的有效命令或完成結果。 本冊完整規則

  15. 15 是否影響其他 Controller 或 Namespace？

  16. 16 Identify、Feature、Log 與 Command 行為是否一致？

    先確認 CQE 指出的 SQID 確實關聯到這條 CQ，再確認 CID 屬於目前這次建立的 SQ，而不是前一次 queue 留下的追蹤資料。

  17. 17 結果不符預期時，第一個要檢查什麼？

    先檢查 Host 是否誤把「CQID+CID」當成唯一識別方式。多條 SQ 共用 CQ 時，相同 CID 仍可能代表不同命令。

共用規則：各題連到的完整解釋

這些規則在本冊只完整說明一次。返回剛才的題目可用瀏覽器「上一頁」；特定命令或 Feature 的明文例外優先。

命令完成、事件與紀錄 · DNR 與 More 應如何設定？

只有收到 CQE，才有 DNR 與 More 可供判讀。DNR=1 表示相同命令即使重送到此 NVM subsystem 的任一 controller，仍預期會失敗；DNR=0 則只表示可能成功。除非個別錯誤條件另有明定，不能只看 Status 名稱就要求 DNR=1。More=1 表示 Error Information Log 有這筆命令的補充資訊。SCT=SC=0 時，DNR 應為 0。

命令完成、事件與紀錄 · 是否產生 Asynchronous Event？

命令完成與非同步通知是不同機制，操作成功本身不保證會產生事件。若操作引發規範定義的事件，還要確認事件受支援、相關通知設定允許回報、事件未被遮蔽，而且 Host 已提交等待中的 Asynchronous Event Request。

命令完成、事件與紀錄 · 是否更新 Error Information Log 或其他 Log？

成功 CQE 不會單憑成功這件事，就要求新增 Error Information entry。若錯誤 CQE 的 More=1，則讀取 LID01h，並以 SQID、CID 及 Error Count 關聯紀錄。其他非成功 CQE 是否需要新增 entry，仍須依記錄規則判斷，不能直接以失敗次數推算。至於操作造成的狀態變化，則用本題列出的查詢介面重新確認。

命令完成、事件與紀錄 · 是否記錄於 Persistent Event Log？

Persistent Event Log 是選配的事件歷史，不是每條命令的執行清單。先確認 LPA 宣告的支援能力及 Supported Events Bitmap，再判斷這次操作是否符合某個事件的記錄條件。不能只因命令成功或失敗，就要求新增一筆 PEL 紀錄。

Queue 的重設與影響範圍 · Controller Reset 後是否保留或繼續？

Host 清除 CC.EN 會觸發 Controller Level Reset：I/O SQ 與 CQ 被刪除，Admin Queue 的指標也會重設。這種重設雖然保留 AQA、ASQ、ACQ，卻不表示舊 CQE 仍然有效。Host 必須重新初始化 Admin CQ 的 Phase，啟用 controller 後，再配置並建立 I/O queue。

Queue 的重設與影響範圍 · NVM Subsystem Reset 後是否保留或繼續？

NVM Subsystem Reset 會讓受影響的 controller 執行 Controller Level Reset，Host 不能沿用舊 queue。恢復時，先重新確認傳輸及 Register 狀態，再建立 Admin 與 I/O 的操作環境。這種重設來源不同，不能直接套用清除 CC.EN 時對 AQA 等 Register 的保留例外。

Queue 的重設與影響範圍 · Power Cycle 後是否保留或繼續？

Power Cycle 後，Host 重新執行初始化及 queue 建立流程。即使 Host 記憶體中還留有舊 SQE 或 CQE 的內容，也不能把它們當成新 queue 的有效命令或完成結果。Host 必須重建指標、期待的 Phase，以及未完成命令的追蹤資料。

Queue 的重設與影響範圍 · 是否影響其他 Controller 或 Namespace？

Queue 隸屬於建立它的 controller；兩個 controller 使用相同 QID，不表示它們共用同一條 queue。相反地，同一 controller 中共用 CQ 的 SQ，確實會受到該 CQ 的空間及刪除順序影響。另外，queue 重設不等於刪除 namespace，也不會撤銷已完成的資料寫入。

Register 存取 · DNR 與 More 應如何設定？

這次 Register 存取沒有 NVMe CQE，因此 DNR 與 More 不適用。如果之後的 Admin 或 I/O 命令失敗，則解讀那筆命令實際回傳的 CQE，而不是替先前的 Register 寫入指定 Status 位元。

Register 存取 · 是否產生 Asynchronous Event？

Register 存取本身不定義一筆成功通知。若另外發生 Internal Error 等已定義事件，則依該事件的規則處理。controller 尚不能處理 Admin Queue 時，Host 仍須直接檢查初始化狀態，不能改以等待事件判斷是否已完成初始化。

Register 存取 · 是否更新 Error Information Log 或其他 Log？

規範不要求每次 Register 讀寫都建立一筆 Error Information entry。遇到初始化問題時，先保存 CAP、CC、CSTS、CRTO 及各次觀察的時間。若之後 controller 允許讀取 Log，再用錯誤與事件紀錄補足資訊。

Register 存取 · 是否記錄於 Persistent Event Log？

一般 Register 存取不是獨立的 Persistent Event。若另外發生重設、電源變化或硬體錯誤，則在支援 PEL 且符合對應事件條件時，依規則記錄。因此，不能將每次 CC 寫入都當成一次 Power-on or Reset 事件。
