NVMe · 規格與原理

NVMe Base 2.4：Telemetry：資料收集與一致性讀取

00.01.Telemetry 把裝置收集的內部狀態整理成主機可讀取的紀錄。這篇的重點是取得一份完整且一致的資料：誰建立紀錄、各資料區有多大，以及分段讀取期間紀錄是否已經換成另一份。

這篇的主軸

01

先確認誰建立紀錄

01-01主機發起與控制器發起的紀錄有不同建立方式；先分清來源，才能正確選擇讀取與確認完成的做法。

02

從表頭找出資料範圍

02-01先讀表頭，再用資料區邊界決定要讀哪些區段；標準定義位置，廠商資料格式決定如何理解內容。

03

確保分段讀到同一份紀錄

03-01資料可能分多次取回；要檢查紀錄識別與變更資訊，避免把不同時間的內容拼成一份。

把主軸連起來

00.02.先分清主機發起與控制器發起的紀錄，再從 header 得知資料區範圍。讀取多個區段時，要保留同一份紀錄的識別資訊，並依該類紀錄的規則確認讀取完成；資料區位置可由標準解釋，廠商自訂內容則需要相應格式資料。

01 資料區如何排列與計算大小

用 Last Block 安排分段讀取

先建立共同座標

01.01.Telemetry 以 512 bytes 為一個 block，header 在 block 0。每個 Data Area 都從 block 1 開始，所以 Area 2 是較大的累積範圍；不能把它想成只放在 Area 1 後面的另一段資料。

從終點算出長度

01.02.假設 Area 1 的 Last Block=65，該 Area 的資料是 block 1 到 65，共 65×512=33,280 bytes。連同 header 讀取則是 66×512=33,792 bytes。數量差 1 來自有沒有包含 block 0，並非 Last Block 又套了一次從 0 起算的數量編碼。

選擇要讀的集合

01.03.若 Area 2 的 Last Block=1000，它包含 block 1 到 1000，已包含前面 65 個 blocks。若主機已取得 Area 1，只想補上到 Area 2 的資料，新增部分才是 block 66 到 1000。比較兩個終點，可以分清完整集合與新增區段。

確認哪些欄位與內容可解釋

01.04.Area 4 的可用性需要結合相應支援與主機宣告。Last Block、generation number 等標準欄位可用來建立讀取計畫；payload 的廠商自訂內容則需要相應格式文件，不能單靠位置把任意 bytes 當成溫度或錯誤碼。

01.05.每次換算都先標出 block 0、起點 1 及包含在內的終點，再決定是否把 header 加進總長度。

01.06.Telemetry 的 header 為 block 0，每個 block 是 512 bytes；所有 Data Areas 都從 block 1 起算。Area 2/3/4 是更大的累積集合，不是接在 Area 1 後的獨立區塊。Last Block 是包含在內的最後 block 編號；payload 格式與大小由廠商定義。

02 建立快照、分段讀取與確認完成

取回同一個時間點的紀錄

決定這次要建立還是讀取

02.01.LID 07h 的 CTHID 決定是否要求建立新的 Host-Initiated capture。需要新紀錄時提出建立要求；後面的分段讀取沿用既有紀錄。若每段都要求重新建立，取得的資料就可能分屬不同時間。

CTHID
Create Telemetry Host-Initiated Data；07h 的 capture 要求，後續分段讀同一快照要清為 0。

先取得可比對的識別資訊

02.02.讀取 header 並保留相應 generation number，再依 Last Block 計畫每段長度和位置。Get Log Page 的 NUMD 決定本次回傳量，LPO 決定從哪個位置取；兩者與整份 capture 的大小不同。

NUMD
Number of Dwords，0's-based transfer dword count；實際 bytes = (NUMD + 1) × 4。

讀完後確認紀錄沒有被換掉

02.03.假設第一次 header 的 generation 是 7，資料取完後再讀 header 卻得到 8。這時不能把剛才各段當成一份完整的一致紀錄；應依該類 log 的規則重新取得相符的資料。兩次值相同也必須搭配正確的建立、保留及確認流程，而非任意跨時間拼接。

Controller-Initiated 另看可用狀態與確認時機

02.04.LID 08h 的資料由控制器建立。先看 TCDA 與相應通知，再依保留事件的設定讀取；需要解除保留或確認處理時，放在適當的完成步驟。過早確認可能改變後續可取得的資料或通知狀態。

TCDA
Telemetry Controller-Initiated Data Available；2.4 中表示自上次 RAE=0 acknowledgement 後是否有更新。

02.05.完整擷取需要同時維持資料範圍正確與紀錄身分一致；只檢查收到的 byte 數仍不足以證明兩者成立。

把流程對回規格條件

02.06.LID 07h 的 CTHID 是 CDW10 bit 8；設為 1 要求新 capture，0 不更新該 snapshot。MCDA 是 bits 11:9，只有 MCDAS=1 且 CTHID=1 時適用；001b 至 100b 分別要求建立至 Area 1 至 Area 4，000b 由 controller 決定。MCDAS 來自 Supported Log Pages 的 LID Specific Parameter。

controller
controller，實作 NVMe 介面、取走 command 並回報 completion 的控制實體。
MCDAS
Maximum Created Data Area Supported；07h 的 LID Specific Parameter bit 0，宣告 MCDA 支援。
MCDA
Maximum Created Data Area；支援且要求 capture 時選擇建立的最大 area。
CDW
CDW（Command Dword）；命令中的 32-bit 欄位單位，例如 CDW10 的 10 是欄位 index，不是 byte offset。
來源：Base 2.4 §5.2.13.1.8

來源：NVME-BASE-2.4, Rev. 2.4, §5.2.13.1.8, 文件頁 232-235, PDF 頁 258-261

02.07.Host 讀 header 記住 generation，以 RAE=1 分段收集，再重讀 header 比對 generation；不同就重新讀取。讀 08h 還需確認 TCDA 未被其他讀取者清除；完成後用 RAE=0 讀任一部分來 acknowledgement。Generation 是 8-bit，FFh 後回到 0h。

RAE
Retain Asynchronous Event；Telemetry 收集中用 1 保留通知狀態，完成後用 0 acknowledgement。
來源：Base 2.4 §8.1.30

來源：NVME-BASE-2.4, Rev. 2.4, §8.1.30, 文件頁 734-735, PDF 頁 760-761

02.08.Base 2.4 的 TCDA=0 表示自上次成功 RAE=0 讀取後沒有更新。第一次 capture 前 header 可讀；capture 過後，即使 TCDA=0，仍回傳 header 與目前保存的 internal state。不能把舊版『0 表示只有 header』的解讀沿用至 2.4。

來源：Base 2.4 §5.2.13.1.9

來源：NVME-BASE-2.4, Rev. 2.4, §5.2.13.1.9, 文件頁 237, PDF 頁 263

02.09.07h 的 snapshot 不變，直到新的 CTHID=1、Firmware Commit 或 power-on reset。08h Areas 1–3 跨所有 resets 保留，Area 4 可跨 Controller Level Resets 保留；08h 的 TCDA、TCDGN 跨 power cycles 與 resets 保留。

TCDGN
Telemetry Controller-Initiated Data Generation Number；8-bit generation，完成更新最後才遞增。
來源：Base 2.4 §5.2.13.1.8-5.2.13.1.9

來源：NVME-BASE-2.4, Rev. 2.4, §5.2.13.1.8-5.2.13.1.9, 文件頁 233,235,237, PDF 頁 259,261,263

02.10.Host 以 FID 0Bh 的 TLN bit 10 啟用 Telemetry Log Notices；controller 以 Notice 類型的 Telemetry Log Changed AER 通知，也可由 07h/08h 的 TCDA 得知資料更新。

AER
Advanced Error Reporting，PCIe 用來分類、遮罩與記錄 link／transaction error 的 capability。
來源：Base 2.4 §8.1.30; 5.2.30.1.6

讓控制器支援與主機可理解的資料區一致

03.07.讀 log 先選 LID 與命令集，再解讀該 log 的 LSP／LSI；NUMD 決定本次量，LPO 決定本次起點，DPTR 決定主機接收位置。

DPTR
Data Pointer，SQE 中指出 command data buffer 的欄位。
LSI
Log Specific Identifier，意義由所選 log page 定義的 identifier。
LSP
Log Specific Field，意義由所選 log page 定義的 command selector。
一起判讀的欄位或標示如何共同決定操作或結果帶入情境後怎麼讀
LID／CSI／LSP／LSILID 與 CSI 選紀錄種類，LSP、LSI 的含義由所選 log 定義。LSP 在 Boot 中可含 BPID，在 Telemetry 中有建立 capture 的控制位元，不能跨 log 照搬。
NUMDU／NUMDL先合成 NUMD=(NUMDU<<16)|NUMDL，再計算 (NUMD+1)×4 bytes。512 bytes 對應 NUMD=127；高低部分不能各自加 1。
LPOU／LPOL／OT高低欄位組成 64-bit offset；OT 決定按 byte 位移或項目索引解讀。byte-offset 模式下，從 512-byte 表頭後開始讀資料要保留起點差異；index 模式不能直接使用同一個 byte 數。
DPTR／RAEDPTR 給接收記憶體，RAE 控制相關事件的保留行為。分段讀取先準備每段 buffer，再在恰當時機確認事件，避免中途改變可取得的紀錄。
LSUPP／LID Specific ParameterSupported Log Pages 回報實際支援及 log 專屬能力。規格列有某個 LID，不代表此裝置一定實作；先查支援再使用進階選項。
NUMDL
Number of Dwords Lower，Get Log Page 的 NUMD 低 16 bits。
NUMDU
Number of Dwords Upper，Get Log Page 的 NUMD 高 16 bits。
index
index；用來選取清單中的項目或格式。它回答「選哪一項」，不是「離起點多遠」。
BPID
Boot Partition Identifier；選取 0 或 1，與目前 active partition 分開。
LPOL
Log Page Offset Lower，Get Log Page byte offset 的低 32 bits。
LPOU
Log Page Offset Upper，Get Log Page byte offset 的高 32 bits。
CSI
I/O Command Set Identifier；選擇 I/O 命令集，NVM Command Set 使用 00h。

1. Area 1 的 Last Block=3，Area 2 的 Last Block=7；Area 2 包含哪些 payload blocks？
