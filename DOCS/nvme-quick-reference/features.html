NVMe 圖表判讀與情境練習 05 · Features、電源、效能與資源

先分辨支援能力、目前值、預設值與保存值，再查各 Feature。電源延遲、排程權重、佇列數與回收資源各有單位，不能互相替代。

每張原圖都有用途、欄位和判讀例子。例子中的數值用於說明，不代表你的裝置設定；原文另有條件時，依該欄位與命令定義判斷。

用瀏覽器「在頁面中尋找」搜尋欄位、FID、LID、CNS 或 Figure。bit／byte 位置沿用原圖：bit 是位元，byte 是 8 bits，Dword 是 4 bytes；index 是第幾筆，offset 是相對起點的偏移，須看當處使用的單位。

FID（Feature Identifier）選擇功能；LID（Log Page Identifier）選擇紀錄頁；CNS（Controller or Namespace Structure）選擇 Identify 回傳的資料結構。

從情境練習開始直接查圖表

先做情境練習

每題資料均為教學假設，不是實際裝置回傳。先寫下查詢介面、目標、欄位與可支持的結論，再展開解答。題目只做 Spec 推導，不會執行命令。

練習方法：先不要急著解每個 bit。把需求寫成一句能驗證的話，例如「這個 namespace 的這筆 Write，在什麼條件下具有哪種保證」。作答時分開記錄「已知」「推導結果」「仍缺的證據」。解答中的三段依序帶你走過判讀；不熟的欄位可由末尾連結回本冊原圖介紹。

練習 01Get Features 成功，為什麼還不知道目前值？

程式讀到 DW0=5，便把某功能的「目前設定」顯示為 5。請檢查它解錯了哪一層。

模擬回傳與已知條件

  • 這是支援 Save／Select 的 controller；命令 SEL=3，目標 FID 合法，CQE success、DW0=00000005h。
  • 目前值、預設值與已保存值都尚未讀取。
展開解答：查詢路徑與完整推導

查詢次序：保留原 Get Features 的 FID／SEL／NSID → 按 SEL=3 解能力 → 再以同一 FID、正確對象、SEL=0 讀目前值。

推導 15 的二進位是 101b：CHANG=1、NSSPEC=0、SVBL=1。這表示有可變更屬性、不是 namespace-specific、可保存；不是功能值 5，也不是這個功能一定已啟用。

推導 2SEL=0、1、2 分別取得 Current、Default、Saved；三者可能不同。NSSPEC=0 也不能直接推定只影響這一個 controller，實際 scope 仍由該 Feature 定義決定。

推導 3報告若只保存 DW0 而丟掉 SEL，這次查詢的語意就無法可靠重建。需要資料 buffer 的 Feature 還要保存該 buffer；成功 CQE 不代表 DW0 已包含全部回傳資訊。

練習 02要求 16 組 queues，實際能建立幾組？

驅動要求 16 個 SQ、16 個 CQ，就直接建立 QID 1 到 16。回傳資訊是否允許這樣做？

模擬回傳與已知條件

  • Set Features FID=07h：NSQR=15、NCQR=15；成功回傳 DW0=00030007h。
  • CAP.MQES=1023；尚未執行 Create I/O CQ／SQ。
展開解答：查詢路徑與完整推導

查詢次序：解 FID=07h 完成回覆的 NCQA／NSQA；另讀 CAP.MQES，再規劃 Create I/O CQ／SQ 的數量與深度。

推導 1DW0 高 16 bits=3、低 16 bits=7，因此分配的是 4 個 CQ、8 個 SQ。要求 16 不等於獲配 16，不能用要求值覆蓋 controller 的回覆。

推導 2MQES=1023 表示每個 I/O queue 最多 1024 entries，與 queue 數量不同。多個 SQ 可依合法設定共用 CQ，因此 SQ 與 CQ 的分配數不必相同。

推導 3此時只是取得可用資源，還沒有建立 queue。後續需先有可關聯的 CQ，再建立 SQ，檢查各次 Create 的完成結果；也不能把 queue 數直接當 MSI-X vector 數。

練習 03APST 表有兩條轉換，空閒 700 ms 會在哪裡？

你要畫出自動省電流程，而不是只列出最低功耗 state。如何從 table entry 讀出轉換的起點與計時位置？

模擬回傳與已知條件

  • APSTE=1；PS0 entry：ITPT=100、ITPS=2；PS2 entry：ITPT=500、ITPS=3。
  • PS2、PS3 均為支援的 non-operational state；其餘相關 entries 停用；起始 PS0，連續 idle 700 ms。
展開解答：查詢路徑與完整推導

查詢次序：Identify CNS=01h 的 APST 能力與 Power State Descriptors → Get Features FID=0Ch、SEL=0，同時取得 APSTE 與完整 APST buffer。

推導 1表格的 entry index 是來源，ITPS 是目的地。因此流程是 PS0 ─ idle 門檻 100 ms → PS2 ─ 在 PS2 的 idle 門檻 500 ms → PS3。第二個 500 ms 不是從一開始在 PS0 就一併倒數。

推導 2若先忽略轉換耗時，700 ms 足以讓兩個門檻依序到達；但這只是教學時間線，不是讀取即時 state 的證據。實際轉換時間與控制器行為須一併考慮，APST 表本身是設定。

推導 3要討論下一筆 I/O 的代價，再查目的 state 的 EXLAT。若 EXLAT=0，意思是未回報，不能補成零延遲；若中途有工作打斷 idle，也不能照這條無工作時間線推論。

練習 04溫度升高時變慢，就能說是 HCTM 嗎？

效能測試變慢，同時讀到溫度高於 TMT1。哪些回報能補強熱管理的判斷，哪些仍無法證明因果？

模擬回傳與已知條件

  • Get Features FID=10h：TMT1=340 K、TMT2=350 K；Identify 允許這組設定。
  • SMART Composite Temperature=345 K；測試區間內 Thermal Management Temperature 1 Transition Count 增加 1，Total Time 增加 20 seconds。
展開解答：查詢路徑與完整推導

查詢次序：Identify CNS=01h 查 HCTM 能力與允許溫度範圍 → Get Features FID=10h、SEL=0 → 兩次 Get Log Page LID=02h 比較計數。

推導 1345 K 約 71.85°C，介於兩個設定門檻之間。門檻與量測值都要先確認單位，不能把 K 直接當攝氏，也不能把 Feature 的設定值當成當下溫度。

推導 2transition count 與 time 的增加，支持這段期間發生過第一階段 host-controlled thermal management。這比單張高溫快照多了行為證據，但它仍是區間累計，未交代每筆 I/O 的時間點。

推導 3因此可報告熱管理曾介入，卻不能把整段效能下降都歸因給它。還需對齊量測時段、工作負載、power state 與 PCIe link 等資訊，才能分析各因素的影響。

需要重看欄位時，接著查：Base 2.4 Figure 482 · HCTM：兩個熱管理門檻Base 2.4 Figure 213 · SMART：警告、累計量、溫度與時間Base 2.4 Figure 338 · Identify Controller：能力與限制的主要入口

練習 05HMB 位址一樣，就能聲稱原記憶體已返還嗎？

重設後 host 把原位址的 HMB 清零，再宣稱 MR=1。只比對實體位址，是否足以驗證這個設定？

模擬回傳與已知條件

  • 停用前後 descriptor 位址與總大小相同，但 buffer 內容已被清零。
  • 擬用 Host Memory Buffer Feature：EHM=1、MR=1；本題只判讀紀錄，不送出設定。
展開解答：查詢路徑與完整推導

查詢次序：Identify CNS=01h 查 HMB 能力；查 Feature FID=0Dh 與保存的停用前 descriptor／buffer 紀錄。

推導 1MR=1 表示返還先前同一份 HMB，要求的不只是相同位址與大小，也包含 descriptor 與 buffer 內容的一致。清零已破壞這項條件，所以這個宣稱不成立。

推導 2EHM=1 只要求啟用，不能補足 MR 的真實性。讀到目前 Feature 已啟用，也不足以倒推 host 過去是否保持了每個 byte；必須有生命週期與記憶體管理紀錄。

推導 3若是重新配置的記憶體，應按新的 HMB 配置流程處理，而不是把位址偶然相同當成原內容仍在。這是能力查詢與 host 履約證據不同的一個例子。

需要重看欄位時，接著查：Base 2.4 Figure 545 · HMB：啟用、新配置或返還原記憶體Base 2.4 Figure 338 · Identify Controller：能力與限制的主要入口

練習 06權重 7：3，能保證 IOPS 是 2：1 嗎？

高、低優先級 workload 的實測 IOPS 沒有依設定成比例。該直接判 controller 排程錯誤嗎？

模擬回傳與已知條件

  • CC.AMS 已選擇有權重的仲裁模式，且 CAP 表示支援；FID=01h：HPW=7、MPW=3、LPW=3、AB=2。
  • 高、低優先級分別使用不同 I/O 大小與讀寫比例。
展開解答：查詢路徑與完整推導

查詢次序：讀 CAP 與 CC.AMS → Get Features FID=01h、SEL=0 → 對照 SQ priority 與實際 workload。

推導 1HPW=7 與 LPW=3 分別解成每輪 8 與 4 個命令的權重；AB=2 則用 2^2=4 計算單次 burst。相同大小的數字不代表相同編碼方式。

推導 2權重描述命令服務機會，沒有把不同大小、不同執行成本的 I/O 變成相同工作量。因此不能從 8：4 直接推出穩定的 2：1 IOPS，更不能推出 2：1 bandwidth。

推導 3若要驗證仲裁，應記錄模式、各 SQ 的 priority、命令是否持續待處理與觀測時段，再用規格對應的服務規則判斷。單張應用 throughput 圖不足以證明排程違規。

需要重看欄位時，接著查：Base 2.4 Figure 467 · Arbitration：權重不是效能保證Base 2.4 Figure 41 · CC：主機實際選了什麼Base 2.4 Figure 36 · CAP：設定前先查硬體能力
