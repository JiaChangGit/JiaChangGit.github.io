NVMe 圖表判讀與情境練習 03 · Identify、Namespace 與資料格式

CNS 決定回傳哪一種 Identify 結構；controller 能力、namespace 格式和選定格式的大小要分開查，再組合成可用設定。

每張原圖都有用途、欄位和判讀例子。例子中的數值用於說明，不代表你的裝置設定；原文另有條件時，依該欄位與命令定義判斷。

用瀏覽器「在頁面中尋找」搜尋欄位、FID、LID、CNS 或 Figure。bit／byte 位置沿用原圖：bit 是位元，byte 是 8 bits，Dword 是 4 bytes；index 是第幾筆，offset 是相對起點的偏移，須看當處使用的單位。

FID（Feature Identifier）選擇功能；LID（Log Page Identifier）選擇紀錄頁；CNS（Controller or Namespace Structure）選擇 Identify 回傳的資料結構。

先做情境練習

每題資料均為教學假設，不是實際裝置回傳。先寫下查詢介面、目標、欄位與可支持的結論，再展開解答。題目只做 Spec 推導，不會執行命令。

練習方法：先不要急著解每個 bit。把需求寫成一句能驗證的話，例如「這個 namespace 的這筆 Write，在什麼條件下具有哪種保證」。作答時分開記錄「已知」「推導結果」「仍缺的證據」。解答中的三段依序帶你走過判讀；不熟的欄位可由末尾連結回本冊原圖介紹。

練習 01最多還能建立幾個 namespace？

管理程式把 NN 當成可建立的 namespace 數量。你要怎麼修正它，並回答「現在還能建立幾個」？

模擬回傳與已知條件

  • OACS.NMS=1；NN=1000；MNAN=16；MAXCNA=8。
  • 完整 Allocated Namespace ID list 有 10 筆；此 controller 的 Active list 有 6 筆。剩餘容量與建立參數尚未查詢。
展開解答：查詢路徑與完整推導

查詢次序：Identify CNS=01h → CNS=10h 完整已配置清單 → CNS=02h 此 controller 的活動清單；必要時再查容量與 Namespace Management 參數。

推導 1NN 是有效 NSID 的最大值；MNAN 才是此例的 subsystem namespace 數量上限。NSID 可以不連續，所以最大編號 1000 不代表存在 1000 個 namespace。MAXCNA=8 則限制此 I/O controller 可附接的數量，不能拿來取代 MNAN。

推導 2只看數量，上限還有 16−10=6 個名額；此 controller 的附接名額還有 8−6=2 個。建立與附接是不同步驟，建立第 3 個新 namespace 不等於也能把它附接到這個 controller。

推導 3這不是保證能成功建立 6 個：每個 namespace 所需容量、格式、資源及同時發生的管理操作仍會影響結果。若 MNAN=0，NN 仍是可配置 namespace 數量的上限依據；例如 NN=1000 不能解成可建立無限個 namespace。

練習 02namespace 存在，為什麼這個 controller 看不到？

盤點程式在 subsystem 找到 NSID=27，卻沒有對應的可存取 namespace。這足以判定資料遺失嗎？

模擬回傳與已知條件

  • NN=100；CNS=10h 回傳 [2, 9, 27]；CNS=02h 回傳 [2, 9]；兩張清單均已讀完。
  • 裝置支援 Namespace Management；查詢期間沒有變更 namespace 配置。
展開解答：查詢路徑與完整推導

查詢次序：Identify CNS=01h 確認範圍與能力；分別讀 CNS=10h、02h；若需確認附接對象，使用 CNS=12h、NSID=27。

推導 127 在有效範圍，而且出現在 Allocated list，表示該 namespace 已存在。它不在此 controller 的 Active list，只能得出它未附接到此 controller；不能說它不存在，更不能說媒體上的資料已遺失。

推導 2CNS=12h 回答該 namespace 附接到哪些 controller。這可區分「附接在別處」與「已建立但尚未附接」；是否應改配置是後續決策，不是盤點查詢本身的結論。

推導 3大量 namespace 時，每次清單最多容納 1024 個 NSID。下一次以最後一個非零 NSID 作為起點，取得大於該值的項目；不能只讀第一頁就把後面的 namespace 判成不存在。

練習 03重開機後 NSID 改了，還是同一份資料嗎？

開機前的 NSID=3，開機後變成 NSID=9。你會比容量、NSID，還是另一種識別資訊？

模擬回傳與已知條件

  • 前後 CNS=03h 的非零 Namespace UUID 相同；兩次都來自同一個已確認的 subsystem。
  • 容量相同，但尚未讀取使用者資料。
展開解答：查詢路徑與完整推導

查詢次序：Identify CNS=03h，分別指定當時 NSID；依 NIDT、NIDL 解析識別描述子，保留識別值。

推導 1NSID 是命令選擇 namespace 的編號，可能跨斷電改變。Namespace UUID 是用來辨識 namespace 的資訊；本例相同的 UUID 支持它是同一個 namespace，不能只因 NSID 改變就視為新建物件。

推導 2解析時先看 NIDT 指定識別種類，再依 NIDL 取出該種類的 bytes；不要把整個描述子連同表頭直接當作 UUID 比較。若改用 NGUID 或 EUI64，也要考慮 UIDREUSE 所描述的重用特性。

推導 3識別相同不代表內容從未變動，也不能證明每個 LBA 都完整。若問題改成「資料有沒有改過」，需要另訂資料校驗方法；如果沒有可用的唯一識別資訊，僅靠相同容量不足以下定論。

需要重看欄位時，接著查：Base 2.4 Figure 342 · Namespace 識別描述子：不要把 NSID 當永久身分Base 2.4 Figure 346 · Namespace 共通狀態：可用、受保護與儲存歸屬

練習 04容量是位址範圍、可配置量，還是已使用量？

容量報告把 NSZE、NCAP、NUSE 三個數字相加。請用這份回傳值解釋為什麼不對。

模擬回傳與已知條件

  • 目前 LBAF 的 LBADS=12、MS=0；NSZE=8192、NCAP=4096、NUSE=1024。
  • 這是支援 thin provisioning 的 NVM namespace，數值有效，沒有不可存取狀態造成的清零。
展開解答：查詢路徑與完整推導

查詢次序：Identify CNS=00h、目標 NSID → 由 FLBAS 選取 LBAF → 同時讀 NSZE、NCAP、NUSE。

推導 1LBADS=12 表示每個 LBA 的資料大小是 2^12=4096 bytes。NSZE=8192 給出 32 MiB 的可定址資料範圍，合法 LBA 是 0 到 8191，不是到 8192。

推導 2NCAP=4096 是最多可配置的 logical blocks，換算為 16 MiB；NUSE=1024 是目前已配置的 logical blocks，換算為 4 MiB。它們從不同角度描述同一 namespace，並不是三塊可相加的獨立空間。

推導 3NUSE 也不是檔案系統的已用容量。檔案刪除、deallocation、控制器的配置粒度與更新時機可能使兩者不同；要回答檔案還能存多少，需要檔案系統資訊，而不是改寫 NSZE 的意義。

需要重看欄位時，接著查：NVM Command Set 1.3 Figure 123 · NVM Namespace：容量、格式、原子性與建議粒度NVM Command Set 1.3 Figure 125 · LBAF：資料大小、metadata 大小與相對效能

練習 05128 KiB 資料為什麼可能超過 MDTS？

主機準備一次傳輸 32 個 4 KiB logical blocks。請判斷 interleaved metadata 會不會讓這筆命令超限。

模擬回傳與已知條件

  • CAP.MPSMIN=0；CC.MPS=1；Identify Controller 的 MDTS=5、CTRATT.MEM=0。
  • 使用中 LBAF：LBADS=12、MS=16；metadata 與資料交錯，這筆傳輸包含全部 16 metadata bytes／LBA。
展開解答：查詢路徑與完整推導

查詢次序：讀取 CAP.MPSMIN → Identify CNS=01h 的 MDTS／CTRATT.MEM → CNS=00h 的使用中格式；再檢查命令本身的限制。

推導 1MDTS 以最小記憶體頁大小為基準，並非目前 CC.MPS。此例上限是 2^5 × 2^(12+0)=131072 bytes，即 128 KiB；不能因主機選了 8 KiB 頁，就把上限放大為 256 KiB。

推導 2MEM=0 時，MDTS 計算包括交錯的 metadata。32 × (4096+16)=131584 bytes，已超出 131072；在本例條件下，31 個完整 blocks 才能放進此上限。

推導 3若 MEM=1，這個 MDTS 比較只算資料，32 blocks 可通過這項檢查，但仍要滿足其他命令與 buffer 條件。MDTS=0 也只表示這個欄位未設最大值，不能推成每種命令都能接受任意長度。

練習 06Dataset Management 的限制是 0，代表不支援嗎？

兩個 controller 的 DMRL 都是 0。請判斷能否只靠這個值關閉 Dataset Management 功能。

模擬回傳與已知條件

  • A：ONCS.NVMDSMSV=1；DMRL=0、DMRSL=0、DMSL=0。
  • B：ONCS.NVMDSMSV=0；DMRL=0、DMRSL=0、DMSL=0。
展開解答：查詢路徑與完整推導

查詢次序：Identify CNS=01h 讀 ONCS；CNS=06h、CSI=00h 讀 NVM 專屬 controller 資料，再一起解 DMRL／DMRSL／DMSL。

推導 1A 的 NVMDSMSV=1 已表示支援此命令；三個 0 表示這些欄位沒有報出相應的處理限制。不能把 DMRL=0 解成「允許 0 個 range」。

推導 2B 使用另一種支援判斷：在 NVMDSMSV=0 的情況，必須連同這些 limit 的非零條件判讀。此組全 0 不提供 Dataset Management 支援，不能照搬 A 的結論。

推導 3即使 A 支援，仍須遵守命令格式、namespace 範圍與每個 range 的定義。這題要練的是先讀能力版本，再解數值；0 沒有跨所有欄位通用的意思。

練習 07有 LID 編號，就一定能讀那張 log 嗎？

軟體認得某個 LID，但裝置可能不支援。應查哪一種資料，才不會把「軟體有名稱」當成「controller 有功能」？

模擬回傳與已知條件

  • Supported Log Pages 的目標項目 LSUPP=0；另一个項目 LSUPP=1。
  • 本題先假設可成功讀取 Supported Log Pages；各目標 log 的 namespace、CSI 與 LSP 要求仍須另外確認。
展開解答：查詢路徑與完整推導

查詢次序：Get Log Page，LID=00h；找到以目標 LID 編排的 supported-and-effects 項目，再讀該 log 的定義。

推導 1LSUPP 是這個 controller 對該 log 的支援回報。0 的項目不能因軟體已有解碼器就視為受支援；1 的項目則通過支援檢查。

推導 2支援並不表示 log 裡一定已有事件或量測結果。空紀錄、尚未產生的 Telemetry、以及不支援的 log 是不同狀態，報告應分開顯示。

推導 3後續要依各 log 的 NSID、CSI、LSP、LSI、長度及 offset 規則送命令。LSUPP=1 不能讓錯誤的讀取參數自動變合法，也不能替代內容格式或版本檢查。

03Identify Controller：能力與限制的主要入口

Base 2.4 · Figure 338 · Identify – Identify Controller Data Structure, I/O Command Set Independent
