NVMe 圖表判讀與情境練習 04 · I/O 命令與資料完整性

由命令的位址與數量走到 metadata、保護資訊和原子性。相同欄位寬度不代表相同計數方式，命令成功也不等於所有持久性與原子性保證都成立。

每張原圖都有用途、欄位和判讀例子。例子中的數值用於說明，不代表你的裝置設定；原文另有條件時，依該欄位與命令定義判斷。

用瀏覽器「在頁面中尋找」搜尋欄位、FID、LID、CNS 或 Figure。bit／byte 位置沿用原圖：bit 是位元，byte 是 8 bits，Dword 是 4 bytes；index 是第幾筆，offset 是相對起點的偏移，須看當處使用的單位。

FID（Feature Identifier）選擇功能；LID（Log Page Identifier）選擇紀錄頁；CNS（Controller or Namespace Structure）選擇 Identify 回傳的資料結構。

練習 018 個 blocks 的寫入，斷電也一定不會寫一半嗎？

同事看到 AWUN=7，便宣稱一次寫 8 個 blocks 能抵抗斷電造成的部分更新。這個結論缺了什麼？

模擬回傳與已知條件

  • AWUN=7、AWUPF=1；NSFEAT.NSABP=0、MAM=0；目前 Write Atomicity Normal 的 DN=0。
  • 目標 LBA 資料大小 4096 bytes；這是單筆一般 Write，NLB=7。
展開解答：查詢路徑與完整推導

查詢次序：Identify CNS=01h 讀 NVM 定義的 AWUN／AWUPF；CNS=00h 讀目標 namespace 的 NSFEAT；Get Features FID=0Ah、SEL=0 確認正常原子性未被停用。

推導 1AWUN 與 AWUPF 都以 blocks 數減 1 編碼。7 表示正常情況下的 8 blocks 保證；1 表示斷電或錯誤情況下的 2 blocks 保證。命令 NLB=7 也是 8 blocks，即 32768 bytes。

推導 2這筆 Write 在所給條件下符合正常原子性的大小限制，卻超過斷電原子性的大小。超出保證不代表必定發生部分更新，而是不能用 AWUPF 保證整筆 8 blocks 不被撕裂。

推導 3如果應用要求整筆 32 KiB 在斷電下也不可分割，需要其他符合規格的配置或上層資料保護方法。改成 FUA=1 會增加完成前持久化要求，但不會把 AWUPF 的 2 blocks 改成 8 blocks。

練習 02namespace 的 NAWUPF=0，為什麼不是 1 block？

一個解碼器對所有 atomic unit 欄位直接加 1。請用此例找出它會算錯哪裡。

模擬回傳與已知條件

  • Controller：AWUN=7、AWUPF=3。Namespace：NSABP=1、NAWUN=15、NAWUPF=0、NABSN=0、NABSPF=0、MAM=0。
  • 正常原子性未停用；LBA data size=4096 bytes。
展開解答：查詢路徑與完整推導

查詢次序：Identify CNS=01h 與 CNS=00h 配對取得 controller 基準及 namespace 覆寫值。

推導 1先看 NSABP，才知道 namespace atomic 欄位是否有效。本例 NAWUN=15 是非零，採用它後得到正常情況 16 blocks，也就是 64 KiB；不是只看 controller 的 8 blocks。

推導 2NAWUPF=0 在這裡有特別意思：沿用 controller 的 AWUPF，不是把 0 加 1。AWUPF=3 所以斷電保證為 4 blocks，即 16 KiB。

推導 3NABSN=NABSPF=0 表示未設此類 atomic boundary。這些 0、NAWUPF 的 0，以及 controller AWUPF=0 所表示的 1 block，語意各不同。解碼器必須按欄位定義分支，不能做全表統一加 1。

練習 03大小符合，跨過 boundary 還算整筆 atomic 嗎？

兩筆 Write 都只有 4 blocks，為什麼起始 LBA 不同，namespace 的原子性保證也可能不同？

模擬回傳與已知條件

  • AWUN=0、AWUPF=0；NSABP=1、NAWUN=7、NAWUPF=7；NABSN=7、NABSPF=7、NABO=0；DN=0。
  • 先考慮 MAM=0。Write A：SLBA=8、NLB=3；Write B：SLBA=6、NLB=3。
展開解答：查詢路徑與完整推導

查詢次序：Identify CNS=00h 讀 unit、boundary、offset 及 NSFEAT.MAM；把命令轉成實際 LBA 區間後比較。

推導 1非零 boundary size=7 代表 8 blocks，NABO=0，所以分界在 0、8、16……。A 觸及 LBA 8–11，全在同一區間；B 觸及 6–9，跨過 8。兩者雖然都少於 8 blocks，位置並不等價。

推導 2MAM=0 是 Single Atomicity Mode。A 符合本例 namespace 的整筆原子性條件；B 跨界，不能套用同一個整筆 4-block 保證。這個限制要與 unit 大小一起檢查。

推導 3若改成規格允許的 MAM=1 配置，B 可分為 6–7 與 8–9 兩個 atomic LBA subranges，保證分別適用於各段，仍不是兩段合起來的一個不可分割更新。

命令實際 LBA 範圍以 LBA 8 分界
A8–118 9 10 11：同一區間
B6–96 7 │ 8 9：跨界

練習 04Write 已成功，資料現在一定不怕斷電嗎？

你只能看到能力資料、Feature 值與命令紀錄。如何判斷成功的 Write 是否已滿足持久化要求？

模擬回傳與已知條件

  • 已確認此 namespace 有啟用中的 volatile write cache；Get Features FID=06h 的 WCE=1。
  • A：一般 Write，FUA=0，成功，之後沒有 Flush。B：Write，FUA=1，成功。
展開解答：查詢路徑與完整推導

查詢次序：Identify CNS=01h 的 VWC、CNS=08h 的 VWCNP 與適用的 FDP 配置 → Get Features FID=06h、SEL=0 → 命令 FUA 與後續 Flush 紀錄。

推導 1A 可能已經落到非揮發媒體，也可能仍依賴 volatile cache；從成功 CQE 無法區分這兩種情況。因此不能宣稱它一定已持久化，也不能反過來說它一定只在 cache。

推導 2B 的 FUA=1 要求這筆命令的資料與 metadata 在回報完成前寫入非揮發媒體。持久性關注完成後能否保留，原子性則關注更新會不會部分發生；這兩個問題要分開回答。

推導 3另一條路是先等 A 完成，再提交涵蓋它的 Flush，並確認 Flush 成功。Flush 保證涵蓋其提交前已完成的指定 namespace 寫入；若與 Write 同時送出，就少了這個先後條件。

練習 05資料與索引都用 FUA，為什麼還要排順序？

應用先把資料 Write 放進 SQ，再把指向該資料的索引 Write 放進同一 SQ。兩筆都 FUA=1，是否已保證索引不會先持久化？

模擬回傳與已知條件

  • 資料與索引使用不同 LBA 範圍；不是 fused operation。
  • 兩筆命令一起提交，尚未等待第一筆完成；目標是斷電後不出現「新索引指向尚未保存的資料」。
展開解答：查詢路徑與完整推導

查詢次序：檢查原始 SQE 的 FUA 與提交／完成時序；用 NVM 的 command ordering 與 Write FUA 規則判讀。

推導 1同一 SQ 的位置先後，不能替代這裡所需的資料依賴。FUA=1 對各筆命令提出完成前持久化要求，並沒有額外規定不同命令之間誰先完成。

推導 2符合目標的示範時序是：提交 data Write（FUA=1）→確認成功完成→才提交 index Write（FUA=1）→確認成功完成。第二步使資料的持久化先於索引寫入的提交。

推導 3這只解決題目中的依賴順序，並不把資料與索引兩筆寫入合成一筆跨範圍交易。若要求兩者一起回到舊值或一起變新值，還需要更完整的交易或復原設計。

順序主機觀察／動作
1提交 data Write，FUA=1
2等待並確認 data Write 成功
3才提交 index Write，FUA=1
4等待並確認 index Write 成功

練習 06Metadata 比 PI 大，PRACT=1 要扣掉多少 bytes？

移植程式把 PRACT=1 的 metadata buffer 一律減掉 8 bytes／LBA。這在本例是否正確？

模擬回傳與已知條件

  • 16-bit Guard 格式，PI 已啟用；LBA data=4096 bytes、MS=16，metadata 使用 separate buffer。
  • Write 的 PRACT=1、NLB=3；其他保護設定均合法。
展開解答：查詢路徑與完整推導

查詢次序：Identify CNS=00h 的 LBAF／DPS／metadata 設定，必要時 CNS=05h、CSI=00h 的 ELBAF → 對照 Write 的 16-bit Guard processing 規則。

推導 1NLB=3 是 4 blocks。資料 buffer 為 4×4096=16384 bytes；在這個 metadata 大於 8 bytes 的分支，host 仍傳輸 4×16=64 metadata bytes，不能只配置 32 bytes。

推導 2PRACT 決定 PI 的產生與處理行為，不是通用的「buffer 長度減 8」開關。當 metadata 剛好只有 8 bytes 時，圖表中的另一個分支才有不同的傳輸規則，不能把它搬到 MS=16。

推導 3除長度之外，還要對齊 separate／extended 的放置方式、PI 類型及 Guard 格式。只有這些條件都相同，才適合拿前後兩次傳輸的 bytes 作比較。

練習 07Deallocate 後讀到 FFh，是不是失敗？

驗證程式要求所有 deallocated LBA 都回傳 0。請判斷它是否把允許的行為誤當成錯誤。

模擬回傳與已知條件

  • 該範圍已確認 deallocated；DLFEAT.DRB=010b；Get Features FID=05h 的 DULBE=0。
  • 本例不啟用 PI；Read 成功且全部 data bytes 為 FFh。
展開解答：查詢路徑與完整推導

查詢次序：Identify CNS=00h 查 DLFEAT 與相關能力；Get Features FID=05h、SEL=0、目標 NSID 查 DULBE；再看 Read 結果。

推導 1DRB=010b 所描述的 deallocated 讀取內容就是 FFh，所以此例與規格回報一致。Read 成功不要求一定回 0；驗證器應由 DRB 選擇預期內容。

推導 2若 namespace 支援 DULBE 且目前設為 1，對 deallocated／unwritten block 的讀取又可能走錯誤回覆的路徑。比較兩個裝置前，要把 Feature 狀態一起保存，不能只比較讀回 bytes。

推導 3這個讀取結果只驗證邏輯介面的 deallocation 行為，不能證明所有實體媒體副本已被安全清除。需要 Sanitize 保證時，應使用該操作的能力、目標及完成狀態證據。

02Atomic Boundary：同樣大小，不同起點會有不同結果

NVM Command Set 1.3 · Figure 8 · Atomic Boundaries Example

§2.1.4.4 · 文件頁 19 · PDF 19
