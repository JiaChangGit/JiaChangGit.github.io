<section id="no-snoop"><h2>How does No Snoop relate to ordering?</h2>
<p>No Snoop is a cache-coherency attribute. Base 6.0 §2.2.6.5 Table 2-13 distinguishes the default value 0, where hardware-enforced cache coherency is expected, from value 1, where it is not expected. No Snoop itself does not change Transaction ordering. To evaluate passing, use the Ordering Rules Table with the applicable Traffic Class, transaction types, and other attributes.</p>
<p>Device Control.Enable No Snoop permits a Function to set this attribute on its own Requests when the conditions are satisfied; it does not force every Request to use it. Even when enabled, the Function may set No Snoop only when it can guarantee that the transaction address is not stored in any system cache. The control may be hardwired to 0 and has a default value of 1. Check the control and the attribute on the actual packet separately.</p>
<p><strong>Teaching example:</strong> Enable No Snoop=1 and a Memory Write with No Snoop=0 can coexist: permission to use the attribute does not require its use on this packet. If a packet instead has No Snoop=1, platform and software memory-management information is needed to assess the address condition; the bit alone does not establish that an application sees the latest data.</p>
<p>Configuration Requests, I/O Requests, Memory Requests used as Message Signaled Interrupts, and Message Requests except where specifically permitted must have No Snoop clear. Check these type-specific restrictions as well as the control.</p>
<p class="source-note">PCI Express Base 6.0 §2.2.6.5 and Table 2-13, printed/PDF p.161; §7.5.3.4, Figure 7-25 and Table 7-21, pp.959–961. Platform caching and software synchronization require the applicable platform documentation.</p></section>
<section id="ido"><h2>Start with the communication model</h2><p>Use Figure E-1 and Appendix E to distinguish one-entity communication from mixed host-memory/P2P interaction. E.4.1 shows how relaxed passing can change the final memory result in a multi-entity dependency. Appendix D examines receive-to-transmit resource dependencies; it does not define every platform’s cross-TC dependency rules. System mapping must respect the actual model.</p></section>
<section id="ido-path"><h2>Does permitted passing make a multi-device workload safe?</h2><p><strong>Teaching scenario based on Appendix E.4.1:</strong> Device Y writes host memory, then sends a peer-to-peer (P2P) write to notify Device Z. Once Z sees the notification, it writes the same memory location.</p><p>Use Figure E-1 to locate Y, Z, the Switch, and the Root Complex, then order the three transactions at the observation point. Assume Y and Z use the same TC for their writes and compare them at a common Root Complex processing point. The first two originate at Y; Z's later write has a different Requester ID. If Z's Posted Write has IDO set and the other conditions of Table 2-42 A2b hold, the Root Complex may allow it to pass Y's waiting write, changing the final memory value.</p><p>Requester IDs alone cannot express this cross-device data dependency. Evaluate the entities, TLPs, path, and synchronization before enabling IDO. The appendix mentions possible synchronization; the exact protocol is platform and device specific.</p><p>Appendix D covers a different issue: cross-TC packets can form circular dependencies on finite buffer resources, creating deadlock. An absence of general ordering across TCs does not eliminate system-level dependencies.</p></section>
<section id="stop"><h2>Quiesce all relevant traffic before renumbering</h2><p>Section 6.4 requires blocking new device requests and driver accesses, completing work serviced by the device, completing issued non-posted requests, and ensuring posted requests reached their destinations. Transactions Pending covers only part of that work. Coordinate with the driver and track outstanding traffic before changing IDs; a cleared control bit is not proof of full quiescence.</p></section>
<section id="stop-path"><h2>What must stop before changing a Bus Number?</h2><p><strong>Teaching scenario:</strong> A driver prepares to reconfigure an Endpoint. Under §6.4, coordinate with the driver to stop new device-generated Requests and new software Requests to the device, then establish that Requests being serviced by the device have completed.</p><p>Device Status.Transactions Pending addresses completion of Non-Posted Requests issued by that function. It does not by itself establish delivery of earlier Posted Writes. Check their destination using the relevant TC, ordering attributes, and device synchronization mechanism.</p><p>Section 6.4 describes host reads of the device flushing device writes to system memory using TC0; other TCs need suitable synchronization. This specific path still requires the RO, IDO, and platform memory conditions to be respected. P2P traffic needs an explicit synchronization protocol between devices even with TC0.</p></section>

<section id="message-lookup"><h2>How does a code lead to its full format?</h2><p><strong>Teaching scenario:</strong> Appendix F Table F-1 lists Invalidate Request as Message Code <code>0000 0001b</code>, Routing <code>010b</code>, type <code>MsgD</code>. <section id="vdm"><h2>Which fields identify a Vendor_Defined Message?</h2><p>Start with Table 2-28: Message Code <code>7Eh</code> identifies Vendor_Defined Type 0 and <code>7Fh</code> identifies Type 1. This message classification is separate from whether the TLP carries data: either type can use <code>Msg</code> without payload or <code>MsgD</code> with payload.</p><dl class="st-terms" aria-label="Terms in this passage"><div><dt>TLP</dt><dd>Transaction Layer Packet</dd></div></dl><p>Choose Figure 2-47 for Non-Flit Mode or Figure 2-48 for Flit Mode, then inspect Vendor ID and Routing. In the generic format, bytes 8–9 contain Destination ID for Route by ID and are otherwise Reserved. A specific message can define the same location differently: the Hierarchy ID Message places Hierarchy ID there even though its routing is broadcast. Vendor ID occupies bytes 10–11; bytes 12–15 are available to the message definition. For Vendor ID <code>0001h</code> and Message Code <code>7Fh</code>, continue to §2.2.8.6.1 and the mode-specific Figures 2-49/2-50. Find the PCI-SIG Defined VDM by Subtype: <code>09h</code>, for example, is FRS; see <a href="/DOCS/pcie-course/chapter-34.html#frs-reason">Chapter 34</a> for its events and scope.</p><dl class="st-terms" aria-label="Terms in this passage"><div><dt>FRS</dt><dd>Function Readiness Status</dd></div></dl><p>At a Completer that does not support the message, Type 0 triggers Unsupported Request detection and reporting; Type 1 is silently discarded. This is Completer handling: absence at an intermediate capture point does not establish arrival. Switches must forward received messages with Routing <code>000b</code>, <code>010b</code> or <code>011b</code>; <code>100b</code> terminates locally.</p><p>Attr is not Reserved in the generic format, but an individual message can impose more specific rules: FRS reserves Attr. Generic VDM Requester ID is implementation-specific in Non-Flit Mode and must identify the Requester in Flit Mode; PCI-SIG Defined VDMs separately require the associated Requester value. PCIe-to-PCI/PCI-X Bridge messages interoperating with PCI-X Device ID Messages also require the bridge specification's additional constraints.</p></section>
