<p class="lead">PCIe Hot-Plug turns changes at a physical slot into consistent software state. Capability, notification, power, Link readiness, and resource assignment require different evidence. This report follows one insertion, then compares orderly and asynchronous removal.</p>
<aside class="note"><strong>Sources and assumptions</strong><p>PCIe Base 6.0 and PCI Firmware 3.3 retain separate version boundaries. All values, times, and capacities are author-created examples. A separate hot-plug slot is attached to Switch Downstream Port 02:01.0, with 03:00.0 below it. The OS already owns native Hot-Plug control; SFI does not intervene, and no early-readiness mechanism is used.</p></aside>
<section id="capability"><h2>Start capability discovery at the Port that manages the slot</h2><p>After locating the PCI Express Capability at 0x70 on 02:01.0, use Figure 7-23 for Port Type and Slot Implemented, then Figure 7-30 for Slot Capabilities. Do not search the Endpoint for its parent slot controller. Physical elements depend on the form factor; Base does not require identical buttons, latches, and indicators everywhere.</p>
<div class="table-wrap"><table><caption>Initial slot snapshot</caption><thead><tr><th scope="col">Register</th><th scope="col">Offset / width</th><th scope="col">Value</th></tr></thead><tbody><tr><td>PCI Express Capabilities</td><td>0x72 / 16 bits</td><td>0x0162</td></tr><tr><td>Slot Capabilities</td><td>0x84 / 32 bits</td><td>0x002825DF</td></tr><tr><td>Slot Control</td><td>0x88 / 16 bits</td><td>0x17F8</td></tr><tr><td>Slot Status</td><td>0x8A / 16 bits</td><td>0x0048</td></tr></tbody></table></div>
<p>0x0162 means Version=2, Type=6, and Slot Implemented=1. Slot Capabilities bits 0–4 indicate an Attention Button, Power Controller, MRL sensor, and both indicators. MRL means Manually-operated Retention Latch. Bit 6 declares Hot-Plug capability; bit 18=0 indicates Command Completed support. Bits 31:19 identify physical slot 5, not Device Number. Power Limit Value=75 and Scale=0 specify a 75 W limit, not measured consumption.</p><p>HPS bit 5=0, so this example demonstrates orderly operation. This bit alone does not classify every asynchronous-removal architecture: Base 6.0 deprecates the old HPS mechanism for async hot-plug and recommends DPC. SFI can also suppress the HPS read value.</p><dl class="st-terms" aria-label="Terms in this passage"><div><dt>DPC</dt><dd>Downstream Port Containment</dd></div></dl><details class="source-note"><summary>Lookup route</summary><p>§6.7/Table 6-7 (pp.727–728); Figure 7-23/Table 7-19 (pp.953–954) → Figures 7-30–7-32/Tables 7-27–7-29 (pp.980–986). HPS versus DPC: §6.7.6 (pp.741–742).</p></details></section>
<section id="events"><h2>Separate current state, pending events, and notification</h2><p>Slot Status=0x0048 has Presence Detect State bit 6 and Presence Detect Changed bit 3 set. One reports current presence; the other records a pending event. Further slot events of the same type are ignored until that pending event is cleared. A bit is therefore neither a counter nor a complete history.</p><p>Out-of-band detection detects insertion while main power is off in this example. Generally, with In-Band PD Disable=0, Presence is the OR of in-band and applicable out-of-band detection; in-band detection requires power. Presence=1 does not establish Link Active.</p><p>0x17F8 enables Presence Changed, Command Completed, DLL State Changed, and the Hot-Plug master interrupt enable. Recording an event is distinct from receiving an interrupt, which additionally depends on the selected INTx or MSI/MSI-X enable, vector, and routing conditions.</p><dl class="st-terms" aria-label="Terms in this passage"><div><dt>MSI</dt><dd>Message Signaled Interrupt</dd></div><div><dt>MSI-X</dt><dd>Message Signaled Interrupts Extension</dd></div></dl>
<div class="table-wrap"><table><caption>Acknowledging events at separate times</caption><thead><tr><th scope="col">Slot Status snapshot</th><th scope="col">RW1C value written to 0x8A</th><th scope="col">Readback without new events</th></tr></thead><tbody><tr><td>0x0048: Presence Changed</td><td>0x0008</td><td>0x0040</td></tr><tr><td>0x0050: Command Completed</td><td>0x0010</td><td>0x0040</td></tr><tr><td>0x0140: DLL State Changed</td><td>0x0100</td><td>0x0040</td></tr></tbody></table></div><p>Preserve and process the evidence before writing 1 to selected RW1C bits. Presence is read-only. Recheck concurrent changes; do not indiscriminately perform a 32-bit read-modify-write across adjacent Control and Status.</p><details class="source-note"><summary>Events and interrupts</summary><p>§6.7.3.1, §6.7.3.4 (pp.735–737); Tables 7-28/7-29 (pp.983–986). Interrupt transport: <a href="/pcie/chapter-7-en/">Chapter 7</a>.</p></details></section>
<section id="timing"><h2>Command completion does not authorize immediate enumeration</h2><p>With the latch closed, sufficient power budget, and no previous command pending, the example writes Slot Control=0x12F8: Power On, Power Indicator Blink, Attention Indicator Off, with notification settings preserved. Any Slot Control write is a hot-plug command. Since Command Completed is supported, wait for the preceding command before another write. After one second without completion, the specification permits retrying or issuing the next command; this does not prove power succeeded.</p>
<div class="table-wrap"><table><caption>Author-created insertion timeline</caption><thead><tr><th scope="col">Time</th><th scope="col">Evidence or action</th><th scope="col">Meaning</th></tr></thead><tbody><tr><td>0 ms</td><td>Write Power On</td><td>Start the insertion power sequence.</td></tr><tr><td>20 ms</td><td>Command Completed</td><td>The controller can accept another command; the physical action need not be complete.</td></tr><tr><td>40 ms</td><td>Link Status=0x2043</td><td>Data Link Layer Link Active reads 1.</td></tr><tr><td>140 ms</td><td>Begin Configuration Requests</td><td>100 ms after observing Active; no early-readiness mechanism applies.</td></tr></tbody></table></div>
<p>Power Controller Control readback is not a power measurement; faults can prevent power-up. After DLL State Changed, read Link Active before configuration access. The one-second DLL-change deadline starts at the Power On write here. Declaring an already-active device broken for not returning Successful Configuration Completions requires allowing at least one second from Active. These deadlines answer different questions.</p><details class="source-note"><summary>Completion and wait conditions</summary><p>§6.7.3.2–§6.7.3.3 (pp.735–736); Tables 7-28/7-29 (pp.984–986). Reset/readiness exceptions: §6.6.1 (pp.721–723) and <a href="/pcie/chapter-9-en/">Chapter 9</a>.</p></details></section>
<section id="resources"><h2>Configuration access still requires usable resources afterward</h2><p>Suppose only 0x80080000–0x800FFFFF remains available along the path: 0x80000 bytes, or 512 KiB. A new size-aligned BAR requiring 0x100000 bytes, or 1 MiB, cannot fit even if Configuration Requests succeed. Writing a BAR outside a Bridge Window does not automatically extend forwarding.</p><dl class="st-terms" aria-label="Terms in this passage"><div><dt>BAR</dt><dd>Base Address Register</dd></div></dl><p>Reserving Bus Numbers and address ranges can help. Reallocation depends on Host Bridge resources, every intervening window, and software coordination. This is an author-created system deduction, not a guarantee that every hot-added card fits. Chapters 3–4 cover enumeration and BAR calculation.</p><details class="source-note"><summary>Allocation boundaries</summary><p>PCI Firmware 3.3 §3.5 (pp.34–37), §4.3.2 (p.47); <a href="/pcie/chapter-4-en/">Chapter 4</a>.</p></details></section>
<section id="removal"><h2>The removal model determines whether coordination is possible</h2><p>Orderly removal allows software to stop new work, handle outstanding work under the device protocol, and then perform the appropriate power, indicator, and removal sequence. Clearing BME does not complete earlier transactions or application work. Async removal may eliminate access before coordination, requiring invalidation and recovery of outstanding work rather than requests for evidence from an absent device.</p><p>This system sequence is an author synthesis; PCIe does not standardize every device's stop, cancel, or save operation. DPC limits error propagation without deciding application success. See <a href="/pcie/chapter-12-en/">Chapter 12</a> for its status and recovery conditions, and <a href="/pcie/chapter-13-en/">Chapter 13</a> for ownership. Sources: Base §6.7, §6.7.6 (pp.727, 741–742), §6.2.11 (pp.694–697); Firmware §4.5.</p><dl class="st-terms" aria-label="Terms in this passage"><div><dt>DPC</dt><dd>Downstream Port Containment</dd></div></dl></section>
<section id="questions"><h2>Check the interpretation</h2><details class="question"><summary>Does Presence Changed=1 with Presence=0 mean no device was ever inserted?</summary><p>No. A pending event and the current state do not reconstruct a complete history. Sources: §6.7.3.1, Table 7-29.</p></details><details class="question"><summary>Do Command Completed and Power Fault contradict each other?</summary><p>No. The command interface can accept another command without proving power succeeded. The fault still needs handling. Sources: Tables 7-28/7-29.</p></details></section>
