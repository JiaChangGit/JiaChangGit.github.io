<section id="topic-overview" class="topic-overview">
<p class="reader-paragraph opening"><span class="paragraph-number" aria-label="00.01">00.01.</span><span class="paragraph-text">After a device resets, how can we tell what happened before it? Persistent Event Log retains significant events in a common format, including health snapshots, firmware updates, power events, namespace changes and configuration. This report first explains consistent retrieval, then connects time, target, parameters and outcomes while respecting what the evidence can establish.</span></p><dl class="term-note" aria-label="Terms in this passage"><div><dt>Persistent Event Log</dt><dd>The LID 0Dh history of significant subsystem events.</dd></div><div><dt>namespace</dt><dd>Namespace, a formatted quantity of non-volatile memory accessed by a host through a controller.</dd></div></dl>
<h2 id="main-ideas">The main ideas</h2>
<div class="topic-map">
<article><span class="axis-number">01</span><h3>What the history preserves</h3><p class="axis-paragraph"><span class="axis-paragraph-number" aria-label="01-01">01-01</span><span class="paragraph-text">Support, storage limits and actual contents are distinct. Understand subsystem scope, persistence and possible omissions before treating the log as a complete trace.</span></p></article>
<article><span class="axis-number">02</span><h3>The retrieval lifecycle</h3><p class="axis-paragraph"><span class="axis-paragraph-number" aria-label="02-01">02-01</span><span class="paragraph-text">Establish context → read header → retrieve chunks → compare generation → release. Separate newly logged events from the fixed set being retrieved.</span></p><dl class="term-note" aria-label="Terms in this passage"><div><dt>context</dt><dd>The report selection and tracking state used by this retrieval; later events are excluded.</dd></div><div><dt>header</dt><dd>The leading descriptive structure containing the type, size, revision and related interpretation data.</dd></div></dl></article>
<article><span class="axis-number">03</span><h3>Three layers of data</h3><p class="axis-paragraph"><span class="axis-paragraph-number" aria-label="03-01">03-01</span><span class="paragraph-text">The log header describes the report, the common event header describes one record, and ED contains type-specific data. Lengths and revisions belong to different layers.</span></p><dl class="term-note" aria-label="Terms in this passage"><div><dt>ED</dt><dd>Event Data, the type-specific content after the common header and optional vendor information.</dd></div></dl></article>
<article><span class="axis-number">04</span><h3>Build justified relationships</h3><p class="axis-paragraph"><span class="axis-paragraph-number" aria-label="04-01">04-01</span><span class="paragraph-text">Group health, time/reset, storage changes, sanitization, hardware and configuration. Combine target, action and result rather than inferring success from one name, percentage or timestamp.</span></p></article>
<article><span class="axis-number">05</span><h3>Connecting Base and NVM</h3><p class="axis-paragraph"><span class="axis-paragraph-number" aria-label="05-01">05-01</span><span class="paragraph-text">Base provides the Namespace Change envelope; NVM specifies FLBAS/DPS. Vendor extensions complete the picture while unknown content remains bounded and preserved.</span></p><dl class="term-note" aria-label="Terms in this passage"><div><dt>FLBAS</dt><dd>Formatted LBA Size, encoding a format index and metadata transfer mode, not a literal byte size.</dd></div><div><dt>DPS</dt><dd>End-to-end Data Protection Type Settings, selecting protection-information type and position.</dd></div><div><dt>NVM</dt><dd>Non-Volatile Memory, memory that retains data without power.</dd></div></dl></article>
</div>
<p class="reader-paragraph"><span class="paragraph-number" aria-label="00.02">00.02.</span><span class="paragraph-text">Assumes operating systems, computer organization and basic SSD concepts. Controllers A/B, namespace7 and numeric examples are illustrative, not assumed hardware configurations.</span></p>
<p class="reader-paragraph"><span class="paragraph-number" aria-label="00.03">00.03.</span><span class="paragraph-text">The Chinese tutorial develops the reasoning and field examples; the equivalent posts establish a global view and then provide a forward Spec route. Other references supply only fields needed to interpret these events.</span></p>
<div class="overview-connections"><h3>Connecting the main ideas</h3>
<p class="reader-paragraph"><span class="paragraph-number" aria-label="00.04">00.04.</span><span class="paragraph-text">Follow five questions: what can this device log, which report am I reading, where does each record begin, what does its payload mean, and what conclusion does the evidence support?</span></p>
<p class="reader-paragraph"><span class="paragraph-number" aria-label="00.05">00.05.</span><span class="paragraph-text">Use a lifecycle diagram for contexts, a byte-layout diagram for lengths, and time/target comparisons for events. Group related fields and explain shared structures once, with a distinct example for each source figure.</span></p>

<section class="lesson" id="module-pel-purpose"><h2 id="heading-pel-purpose"><span class="section-number">01</span> Distinguish history, current state and completeness</h2>
<!-- claim:PEL-PURPOSE -->
<p class="reader-paragraph"><span class="paragraph-number" aria-label="01.01">01.01.</span><span class="paragraph-text">Persistent Event Log (PEL, LID 0Dh) retains significant NVM subsystem events across power cycles and resets. It is not a trace of every I/O or a guaranteed complete history: vendors define capacity, per-type limits, frequency suppression and eviction, and Sanitize may remove or modify records.</span></p><dl class="term-note" aria-label="Terms in this passage"><div><dt>NVM subsystem</dt><dd>NVM subsystem, the NVMe system boundary containing controllers, ports, namespaces, and non-volatile storage resources.</dd></div><div><dt>I/O</dt><dd>Input/Output, the class of data operations performed on a namespace.</dd></div><div><dt>LID</dt><dd>Log Page Identifier: selects the type of log page to read.</dd></div><div><dt>PEL</dt><dd>Persistent Event Log, the history examined in this report.</dd></div></dl><details class="source-note"><summary>Sources: Base 2.4 §5.2.13.1.14</summary><p>Source: NVME-BASE-2.4, Rev. 2.4, §5.2.13.1.14, printed pages 244-245, PDF pages 270-271</p></details>
<aside class="worked-example"><h3>Illustrative example</h3><p class="reader-paragraph"><span class="paragraph-number" aria-label="01.02">01.02.</span><span class="paragraph-text">Illustration: PELS=4 means a maximum of 256 KiB. TLL=4096 and TNEV=9 describe a 4 KiB report containing nine records, not nine event types.</span></p><dl class="term-note" aria-label="Terms in this passage"><div><dt>PELS</dt><dd>Persistent Event Log Size, the maximum capacity in 64KiB units.</dd></div><div><dt>TNEV</dt><dd>Total Number of Events in this report.</dd></div><div><dt>TLL</dt><dd>Total Log Length, the report size in bytes including its header.</dd></div></dl></aside>

<p class="reader-paragraph"><span class="paragraph-number" aria-label="02.01">02.01.</span><span class="paragraph-text">A reporting context fixes the event set for this report; later events are still logged but excluded from that context. <aside class="worked-example"><h3>Illustrative example</h3><p class="reader-paragraph"><span class="paragraph-number" aria-label="02.02">02.02.</span><span class="paragraph-text">For a 512-byte establish/read, ACT=1, LID=0Dh, NUMDL=127 and RAE=0 produce CDW10=007F010Dh; ACT=3 gives 007F030Dh. If the initial GNUM is 41 and the context survives, a later event does not alter that report’s GNUM. The next establishment increments to 42 only if its reported contents changed.</span></p><dl class="term-note" aria-label="Terms in this passage"><div><dt>NUMDL</dt><dd>Number of Dwords Lower, the low 16 bits of Get Log Page NUMD.</dd></div><div><dt>CDW</dt><dd>CDW (Command Dword): a 32-bit command field. In CDW10, 10 is the field index, not a byte offset.</dd></div><div><dt>RAE</dt><dd>Retain Asynchronous Event, the Get Log Page selector controlling retention of a related asynchronous event.</dd></div></dl></aside>

<p class="reader-paragraph"><span class="paragraph-number" aria-label="04.01">04.01.</span><span class="paragraph-text">ET=01h stores a 512-byte SMART snapshot at intervals no greater than 24 power-on hours. <aside class="worked-example"><h3>Illustrative example</h3><p class="reader-paragraph"><span class="paragraph-number" aria-label="04.02">04.02.</span><span class="paragraph-text">An ET01 snapshot has CTEMP=300 K; a later ET0D record has THRESH=1 and OTMP=5 with known WCTEMP=343 K. <section class="lesson" id="module-pel-sanitize"><h2 id="heading-pel-sanitize"><span class="section-number">07</span> Separate sanitize start, completion and media verification</h2>
<figure><figcaption><strong>Sanitize event names and what they establish</strong></figcaption><div class="table-wrap"><table><thead><tr><th scope="col">Record</th><th scope="col">Established fact</th><th scope="col">Not yet established</th></tr></thead><tbody><tr><td>09h Start</td><td>Entered processing; parameters and NSID saved</td><td>Operation completed</td></tr><tr><td>0Eh Media Verification</td><td>Entered verification; no ED</td><td>Successful completion or NSID in ED</td></tr><tr><td>0Ah Completion + SOS3</td><td>Entered failure state</td><td>FFFFh proves success</td></tr><tr><td>0Ah Completion + SOS1</td><td>This operation succeeded</td><td>No data can ever be written afterward</td></tr></tbody></table></div><figcaption>This compares justified conclusions; it does not guarantee complete event pairs. <dl class="term-note" aria-label="Terms in this passage"><div><dt>NSID</dt><dd>Namespace Identifier, a controller-visible numeric handle for a namespace; the identifier is not the namespace object itself.</dd></div></dl>
<!-- claim:PEL-SANITIZE -->
<p class="reader-paragraph"><span class="paragraph-number" aria-label="07.01">07.01.</span><span class="paragraph-text">ET09 records entry into sanitize processing; ET0A records entry into Idle or a failure state. Successful command completion is not completion of the long-running operation. ET0E marks entry into Media Verification with ETR=1 and EL=0, carrying no ED. Start/completion NSID identifies the target; FFFFFFFFh means the subsystem.</span></p><details class="source-note"><summary>Sources: Base 2.4 §5.2.13.1.14.2.9; 5.2.13.1.14.2.10; 5.2.13.1.14.2.14</summary><p>Source: NVME-BASE-2.4, Rev. 2.4, §5.2.13.1.14.2.9; 5.2.13.1.14.2.10; 5.2.13.1.14.2.14, printed pages 261-262,266, PDF pages 287-288,292</p></details>
<aside class="worked-example"><h3>Illustrative example</h3><p class="reader-paragraph"><span class="paragraph-number" aria-label="07.02">07.02.</span><span class="paragraph-text">An ET0A with SPROG=FFFFh and SSTAT.SOS=3 reports failure, not 100% success. ET0E alone establishes entry into verification, not sanitize completion or an NSID from its nonexistent ED.</span></p><dl class="term-note" aria-label="Terms in this passage"><div><dt>SOS</dt><dd>Status of Sanitize Operation, the state code within SSTAT.</dd></div></dl></aside>

<section class="lesson" id="module-pel-hardware"><h2 id="heading-pel-hardware"><span class="section-number">08</span> Select the hardware-error code before its additional format</h2>
<!-- claim:PEL-HARDWARE -->
<p class="reader-paragraph"><span class="paragraph-number" aria-label="08.01">08.01.</span><span class="paragraph-text">In ET05, NSHEEC selects the hardware-error kind and thereby the AHEI layout and length. Codes01h–03h carry PCIe error information, 08h unexpected-power-loss information, and 0Bh controller-ready timeout information; some kinds have no AHEI. Vendors select supported subtypes, so one fixed layout cannot decode every ET05.</span></p><dl class="term-note" aria-label="Terms in this passage"><div><dt>NSHEEC</dt><dd>NVM Subsystem Hardware Error Event Code, selecting an ET05 subtype.</dd></div><div><dt>AHEI</dt><dd>Additional Hardware Error Information, whose format depends on the error subtype.</dd></div><div><dt>PCIe</dt><dd>PCI Express, the transport and device interconnect used by an NVMe memory-based controller.</dd></div></dl><details class="source-note"><summary>Sources: Base 2.4 §5.2.13.1.14.2.5</summary><p>Source: NVME-BASE-2.4, Rev. 2.4, §5.2.13.1.14.2.5, printed pages 254-258, PDF pages 280-284</p></details>
<aside class="worked-example"><h3>Illustrative example</h3><p class="reader-paragraph"><span class="paragraph-number" aria-label="08.02">08.02.</span><span class="paragraph-text">Within ET05, NSHEEC=08h begins AHEI with a 16-byte UPL counter, whereas 0Bh begins with status bits. Skipping NSHEEC could misread a counter byte as CRIME/CNR.</span></p></aside>
</section>

<!-- qa:pel-existing -->
<details class="review-question" id="qa-pel-existing"><summary>1. After successful ACT3 returns RCE=0, is ACT1 still needed?</summary>
<div data-qa-answer="pel-existing"><p class="reader-paragraph review-answer"><span class="paragraph-number" aria-label="12.01">12.01.</span><span class="paragraph-text">No. RCE=0 describes absence before processing; ACT3 has established the context and returned the header. Continue with ACT0. ACT1 would now fail because a context exists.</span></p></div>
<details class="source-note"><summary>Sources</summary>
<p>Source: NVME-BASE-2.4, Rev. 2.4, §5.2.13.1.14, printed pages 245-246,251, PDF pages 271-272,277</p>
</details></details>
<!-- qa:pel-length -->
<details class="review-question" id="qa-pel-length"><summary>2. With EHL21, VSIL4 and EL20, is the record 44 or 48 bytes?</summary>
<div data-qa-answer="pel-length"><p class="reader-paragraph review-answer"><span class="paragraph-number" aria-label="12.02">12.02.</span><span class="paragraph-text">44. EHL+3 is the 24-byte header; EL20 already includes four VSI bytes, leaving sixteen ED bytes. 48 double-counts VSI and misses the next record’s start.</span></p></div>
<details class="source-note"><summary>Sources</summary>

<!-- qa:pel-snapshot -->
<details class="review-question" id="qa-pel-snapshot"><summary>3. Does a PEL telemetry header naming nine data blocks include those blocks?</summary>
<div data-qa-answer="pel-snapshot"><p class="reader-paragraph review-answer"><span class="paragraph-number" aria-label="12.03">12.03.</span><span class="paragraph-text">No. ET0C copies only the first512 header bytes, preserving historical boundaries, reason and generation. It neither contains the full data nor guarantees the same capture remains available.</span></p></div>
