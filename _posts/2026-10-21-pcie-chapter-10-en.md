<p class="lead">PCIe power management spans Functions, Links, and the platform. D-states, ASPM, L1 Substates, and wake each have distinct controls and evidence; an Enable bit alone does not establish current state. PMCSR and L1.2 examples connect discovery, configuration, and recovery.</p>

<aside class="note"><strong>Versions and assumptions</strong><p>PCIe follows Base 6.0; platform background uses ACPI 6.6. All numeric examples are authored. PMCSR concerns ordinary Endpoint 03:00.0. The separate L1.2 Link has the necessary capabilities at both ends, LTR, CLKREQ#, and suitable timing design. Neither example includes SR-IOV or adds undeclared features to earlier examples.</p><dl class="st-terms" aria-label="Terms in this passage"><div><dt>LTR</dt><dd>Latency Tolerance Reporting</dd></div><div><dt>SR-IOV</dt><dd>Single Root I/O Virtualization</dd></div></dl></aside>
<section id="states"><h2>Function D-states and Link L-states are separate</h2><p>D0 is the normal Function state, but ASPM can save Link power during idle periods in D0. D1/D2 are optional. D3hot retains main power; D3cold lacks main power but may retain auxiliary power for wake. D0uninitialized after reset does not establish readiness of the work interface.</p><p>L0 supports transmission. L0s can operate independently by direction, but is unsupported in Flit Mode, with Retimers, or under specified independent-SSC clock conditions. L0p is Flit-only and idles some Lanes while retaining at least one active Lane in each direction. L1 can have L1.0/L1.1/L1.2 substates. L2/L3 follow main-power removal and differ by the presence of Vaux.</p><details class="source-note"><summary>State sources</summary><p>§5.2–§5.3.1, Tables 5-1/5-2 (pp.600–609); L0s/L0p: §4.2.6.6–§4.2.6.7 (p.445).</p></details></section>
<section id="pmcsr"><h2>Read PM capabilities, then construct the D0 write correctly</h2><p>Conventional Capability ID=0x01 identifies PM. An authored full-DWORD read at 0x40 returns 0xC8035001: ID=0x01, Next=0x50, Version=3, no D1/D2 support. PME_Support=<code>(value &gt;&gt; 27) &amp; 0x1F = 0x19</code> allows PME from D0, D3hot, and D3cold. Assume no optional Data Register, Aux_Current=0 using self-power, and necessary power availability. This is capability evidence, not proof of a complete wake path.</p><dl class="st-terms" aria-label="Terms in this passage"><div><dt>PME</dt><dd>Power Management Event</dd></div></dl><div class="table-wrap"><table><caption>16-bit operations on PMCSR at 0x44</caption><thead><tr><th scope="col">Action</th><th scope="col">Value</th><th scope="col">Meaning</th></tr></thead><tbody><tr><td>Read</td><td>0x810B</td><td>D3hot, No_Soft_Reset=1, PME_En=1, PME_Status=1.</td></tr><tr><td>Write D0</td><td>0x0108</td><td>Clear PowerState; write zero to RW1CS PME_Status to preserve the event.</td></tr><tr><td>Read after waiting</td><td>0x8108</td><td>D0 with the event retained.</td></tr><tr><td>Explicitly clear after servicing</td><td>0x8108</td><td>Intentionally write 1 to PME_Status; absent a new event, readback is 0x0108.</td></tr></tbody></table></div><p>Assume no concurrent changes or new events. No_Soft_Reset=1 preserves internal state for the specified software D3hot-to-D0 transition, returning to D0active; it does not remove recovery delays. Immediate Readiness=0 and no other timing exception require at least 10 ms before further access, including Configuration. No_Soft_Reset=0 requires full reinitialization and does not guarantee old state was cleared. D3cold, Fundamental Reset, and DL_Down from L2/L3 Ready do not inherit this preservation guarantee.</p><p>PowerState has no D3cold encoding. Unsupported D1/D2 writes complete normally without changing state. PME_Status can record a qualifying event even with PME_En=0. Entering D3hot still requires handling outstanding transactions and state preservation.</p><details class="source-note"><summary>Capabilities, write semantics, and delays</summary><p>Figures 7-17–7-19, Tables 7-14/7-15 (pp.944–949); §5.3.1.4 (pp.606–608); Figure 5-18/Table 5-14 (pp.654–655). Figure 7-18 numbers bits across the full DWORD including the Header; do not apply those bit numbers to a 16-bit read at +0x02.</p></details></section>
<section id="aspm"><h2>ASPM enablement needs capabilities and a latency policy</h2><p>ASPM manages an idle Link in D0; PCI-PM uses software-directed D-state changes. An ordinary non-ARI multifunction device must have all Functions outside D0 before initiating L1 on behalf of PCI-PM.</p><p>Inspect both Link Capabilities ASPM Support fields, then Link Control ASPM Control. Enablement does not report current L1 residency. Compare Link Capabilities L1 Exit Latency with Endpoint Device Capabilities L1 Acceptable Latency across the path. Exits can overlap across Links, so adding every Port's latency is incorrect; Figure 5-8's example finishes at T+34 μs.</p><details class="source-note"><summary>ASPM sources</summary><p>§5.3.2 (pp.609–610), §5.4.1/Figure 5-8 (pp.621–640); Tables 7-20, 7-23, 7-24 (pp.956–957, 967–972).</p></details></section>
<section id="substates"><h2>Configure L1.2 using both ends and the required order</h2><div class="table-wrap"><table><caption>Separate L1.2 configuration snapshot</caption><thead><tr><th scope="col">Location</th><th scope="col">Downstream Port</th><th scope="col">Upstream Port</th></tr></thead><tbody><tr><td>Header, 0x200</td><td>0x0001001E</td><td>0x0001001E</td></tr><tr><td>Capabilities, 0x204</td><td>0x00280A1F</td><td>0x0051141F</td></tr><tr><td>Control 1, 0x208</td><td>0x40801404</td><td>0x40800004</td></tr><tr><td>Control 2, 0x20C</td><td>0x00000051</td><td>0x00000051</td></tr></tbody></table></div><p>Separate list traversal happens to locate ID=0x001E, Version=1, Next=0 at 0x200 on both ends. Version 1 lacks the +0x10 Status Register. Both low-five capability fields are 0x1F, indicating all four Substate capabilities and overall support. Advertised T_POWER_ON is 10/100 μs, and common-mode restoration is 10/20 μs. Configured Control 2 Value=10, Scale=1 gives 100 μs. Control 1 enables only ASPM L1.2 at bit 2. Common_Mode_Restore_Time is set to 20 μs on the Downstream Port and is RsvdP on the Upstream Port.</p><p>The platform has validated these settings for the connection; taking the larger advertised values is not asserted as a universal algorithm. Both ends must support the selected Substate. Configure ASPM Substates while ASPM L1 is disabled, and PCI-PM Substates while in D0. Program applicable timing and identical LTR thresholds first, then enable corresponding bits on the Downstream Port before the Upstream Port. Disable in the reverse order. Clear applicable L1.2 Enables before changing timing fields; restore ASPM L1 under policy afterward.</p><dl class="st-terms" aria-label="Terms in this passage"><div><dt>LTR</dt><dd>Latency Tolerance Reporting</dd></div></dl><details class="source-note"><summary>L1 Substates lookup and configuration</summary><p>Figures 7-146–7-150/Tables 7-129–7-132 (pp.1103–1108); §5.5, §5.5.4–§5.5.5/Table 5-11 (pp.640, 650–651). L1.1 retains common mode; L1.2 need not. Both use CLKREQ#, and ASPM L1.2 requires LTR.</p></details></section>
<section id="ltr"><h2>The same Enable can produce different entry decisions</h2><p>Control 1 threshold Value=128, Scale=2 gives 128 × 1024 ns=131072 ns (131.072 μs). Assume ASPM L1.0, deasserted CLKREQ#, and all other entry conditions satisfied. Latest valid snoop/no-snoop LTR requirements of 204800/102400 ns fail because no-snoop is below threshold. Changing them to 204800/153600 ns satisfies both, requiring entry under these assumptions.</p><p>No requirement for a traffic class is a separate branch, not Requirement=1 with Value=0; the latter requests the best possible service. These are latest valid reports, not Max Latency Register limits. LTR is also not a hard Root Complex latency guarantee. L1.1 is not enabled here, so it is not an assumed fallback. Before enabling Endpoint LTR, the Root Complex and intervening Switches must support it, with devices closest to the Root Port enabled first.</p><details class="source-note"><summary>LTR and entry conditions</summary><p>§5.5.1 (p.644); Figure 6-15, §6.18 (pp.781–782); Table 7-131 (pp.1107–1108).</p></details></section>
<section id="wake"><h2>Wake restores communication before identifying the source</h2><p>L2 cannot carry ordinary TLPs. The device uses form-factor-appropriate WAKE# or Beacon to request power, clock, and Link restoration, then sends PM_PME with its Requester ID. PME_En, auxiliary power, and platform routing must cooperate. (§5.3.3.1–§5.3.3.2, pp.615–616.)</p><p>Platform background: <a href="https://uefi.org/sites/default/files/resources/ACPI_Spec_6.6.pdf#page=568">ACPI 6.6 §7.3.8–§7.3.11</a> describes D0/D3hot power dependencies through _PR0/_PR3, not PCIe Registers. Document pp.497–498 correspond to PDF pp.568–569.</p></section>
<section id="questions"><h2>Check whether the conditions are sufficient</h2><details class="question"><summary>Does No_Soft_Reset=1 preserve all state through D3cold?</summary><p>No. It applies to the specified software D3hot-to-D0 transition.</p></details><details class="question"><summary>Can only the Endpoint enable L1.2 when its partner lacks support?</summary><p>No. Both capabilities, configuration order, LTR, and timing conditions must hold.</p></details></section>
