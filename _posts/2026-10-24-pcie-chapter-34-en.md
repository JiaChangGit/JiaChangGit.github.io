Exchanges unrelated to this lesson are omitted.</figcaption></figure><section id="ready"><h2>Interpret a device readiness notification</h2><p>Section 6.22.1 defines the Configuration-Ready scope of DRS. After notification, indicated non-VF functions must not return RRS to configuration requests until another applicable event. Switch scope has explicit limits. In the author scenario, an applicable DRS lets configuration proceed; if it has not arrived, choose the applicable waiting procedure based on support. <section id="queue"><h2>Handle queued function readiness</h2><p>Root Ports/RCECs supporting FRS must implement FRS Queueing. Messages are queued in arrival order, with the oldest visible and removed by the defined write. On a full queue, discard the new message, set overflow, and preserve existing entries. Overflow is not replacement with a fresh snapshot.</p><dl class="st-terms" aria-label="Terms in this passage"><div><dt>FRS</dt><dd>Function Readiness Status</dd></div></dl></section>
<section id="hotplug"><h2>Connect hot-plug ownership and enclosure control</h2><p>Reconnect Chapters 11–13 hot-plug, DPC, and ownership before reading Appendix I. Its recommended model checks owner/mechanism, presence, readiness, and interrupts; it recommends DPC without making the full model mandatory. NPEM (Native PCIe Enclosure Management) supplies enclosure controls such as LEDs at a downstream port or endpoint, as Figures 6-35/6-36 show. SFI (System Firmware Intermediary) is a separate firmware event-intermediary mechanism.</p><dl class="st-terms" aria-label="Terms in this passage"><div><dt>DPC</dt><dd>Downstream Port Containment</dd></div></dl></section>
<section id="readiness-path"><h2>Where does the wait begin after reset?</h2><p>Identify the device-level or function-level event first. DRS reports device readiness; FRS reports readiness of specific functions. Check the scope of the message and whether a later applicable event occurred.</p><p>On a phone, scroll the table sideways to see all columns.</p><div class="table-wrap"><table><thead><tr><th>Teaching scenario</th><th>First evidence</th><th>Next decision</th></tr></thead><tbody><tr><td>Downstream device transitions from DL_Down to DL_Up</td><td>DRS Supported and DRS Message Received in the Downstream Port; §6.22.1</td><td>Check which non-VF functions the DRS covers. These examples are illustrative.</p><dl class="st-terms" aria-label="Terms in this passage"><div><dt>BAR</dt><dd>Base Address Register</dd></div></dl></section>
<section id="frs-reason"><h2>Who does the Requester ID identify in an FRS message?</h2><p>In §2.2.8.6.3, choose Figure 2-53 for Non-Flit Mode or Figure 2-54 for Flit Mode and locate Requester ID and FRS Reason. Then read the reason definitions and §6.22.2 to determine the affected scope. FRS is a PCI-SIG Defined Vendor_Defined Type 1 Message without payload, with Subtype <code>09h</code>; Table 2-30 gives Message Code <code>7Fh</code> and Routing <code>000b</code> to the Root Complex.</p><p>Reason <code>0011b</code> reports that the identified Function completed FLR and is Configuration-Ready. For <code>1000b</code>, Requester ID identifies a Physical Function (PF), and all its associated Virtual Functions (VFs) are Configuration-Ready. Reason <code>1001b</code> means those VFs are disabled and the PF's SR-IOV structures may be accessed. Reason <code>0010b</code> identifies a Function completing D3Hot to D0; <code>0001b</code> reports DRS receipt by a qualifying Downstream Port, whose readiness scope is defined in §6.22.1. Other reason values are Reserved.</p><dl class="st-terms" aria-label="Terms in this passage"><div><dt>FLR</dt><dd>Function Level Reset</dd></div><div><dt>SR-IOV</dt><dd>Single Root I/O Virtualization</dd></div></dl><p><strong>Teaching assumption:</strong> an FRS identifies PF A and has Reason <code>1000b</code>. It reports readiness for PF A's associated VFs, not those of another PF. Receiver checks of the message formation rules are independently optional; if an implemented check finds a violation, §2.2.8.6.3 specifies Malformed TLP handling, and reserved bits must not be checked.</p><dl class="st-terms" aria-label="Terms in this passage"><div><dt>TLP</dt><dd>Transaction Layer Packet</dd></div></dl></section>

Figures 7-317 and 7-318 and Tables 7-279 and 7-280 explain the fields and their applicability.</p><p>On a phone, scroll the table sideways to see all columns.</p><div class="table-wrap"><table><thead><tr><th>Field</th><th>Start of wait</th><th>Check first</th></tr></thead><tbody><tr><td>Reset Time</td><td>Completion of Conventional Reset</td><td>Non-VF; not applicable when Immediate Readiness is set.</td></tr><tr><td>DL_Up Time</td><td>Downstream Port above reports Data Link Layer Link Active</td><td>Function associated with an Upstream Port; not applicable to VFs.</td></tr><tr><td>FLR Time</td><td>FLR is issued to the function</td><td>FLR support.</td></tr><tr><td>D3Hot to D0 Time</td><td>Function is directed from D3Hot to D0</td><td>Immediate_Readiness_on_Return_to_D0 and special VF conditions.</td></tr></tbody></table><dl class="st-terms" aria-label="Terms in this passage"><div><dt>VF</dt><dd>Virtual Function</dd></div></dl></div><p><strong>Check Valid before using the values.</strong> When it is clear, time fields are undefined. <section id="queue-example"><h2>What remains known after FRS Queue overflow?</h2><p><strong>Teaching scenario:</strong> A Root Port queue is full with A and B in order when message C arrives. Section 6.22.3 preserves A and B, discards C, and sets FRS Message Overflow. Reading the Queue Register shows A; writing it removes the oldest entry, allowing B to be read next.</p><p>A 0-to-1 transition of FRS Message Received or Overflow generates an interrupt if enabled. Overflow indicates a message was not queued, so the retained entries cannot reconstruct C. Reset empties the queue; a Root Port also empties its queue when the Link goes DL_Down. An RCEC queue contains messages generated by the RCEC or associated RCiEPs.</p></section>
<section id="management-boundary"><h2>How do readiness, enclosure indicators, and hot-plug management connect?</h2><p>Appendix I is a non-normative reference model. First identify OS and system firmware ownership, then select Hot-Plug Surprise or Downstream Port Containment (DPC); the model recommends DPC where available but is not a universal required platform sequence.</p><p>NPEM handles enclosure indicators separately. Figures 6-35 and 6-36 show the capability in a Downstream Port or at the SSD, and Figure 6-37 connects an NPEM Control write with command completion. The Base specification leaves enclosure wiring, LED count, and blink patterns outside its scope. An indicator alone does not establish Configuration-Ready.</p><dl class="st-terms" aria-label="Terms in this passage"><div><dt>NPEM</dt><dd>Native PCIe Enclosure Management</dd></div></dl></section>
<section id="af"><h2>Keep AF within its applicability</h2><p>AF (Conventional PCI Advanced Features) applies to qualifying conventional PCI devices integrated into a Root Complex. Section 6.29 limits its FLR/Transactions Pending applicability. Ordinary PCIe functions use their own capability and Chapter 9 reset rules; similar names do not imply identical registers or scope.</p></section>
